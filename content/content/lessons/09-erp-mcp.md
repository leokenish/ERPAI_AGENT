# ERP 조회와 Telegram 연결 설계

## 소스 분석에 실데이터 조회를 더하기

추출 소스는 프로그램의 구조를 설명하지만 현재 구매오더나 처리 상태를 대신하지는 않습니다. 기존 ECC의 REST JSON·RFC 업무 기능을 재사용해 필요한 조회를 MCP 도구로 제공하려는 설계입니다.

모델이 필요한 도구와 인자를 제안하고, 에이전트 실행기가 실제 호출합니다. MCP 프로그램은 입력과 권한을 확인하고 기존 API에 맞게 요청·응답을 변환합니다. 업무 계산과 조회는 ERP 기능이 수행합니다.

## 두 통신 구간 구분하기

| 구간 | 통신 목적 |
|---|---|
| 에이전트 실행기 ↔ MCP | 도구 목록·호출·결과 |
| MCP ↔ 기존 ERP REST API | 업무 조회 요청·응답 |

MCP의 수신 방식과 ERP에 보내는 REST 요청은 별도입니다. Python 예제는 설명용으로 제시됐으며, 중앙 자문 MCP의 Node.js 예제가 이를 대체했다고 단정하지 않습니다. 실제 ERP API 명세·인증·언어 선택은 미확정입니다.

## Telegram long polling의 흐름

사내 봇 프로그램이 Telegram에 getUpdates 요청을 보냅니다. Telegram은 그 요청의 응답으로 메시지를 전달하고, 봇은 질문을 에이전트 실행기에 넘긴 뒤 sendMessage로 답변을 보냅니다.

외부에서 사내 맥으로 새 연결을 개시하는 구조는 아닙니다. 사내 장비에서 Telegram으로 나가는 HTTPS 통신은 가능해야 합니다. 사용자는 사내 Telegram 접속이 가능하다고 설명했으나 실제 봇 왕복 시험은 자료에 없습니다.

## 한 장비에서 나눌 역할

- **봇 연결 프로그램:** 수신, 사용자·대화 식별, 응답 전송
- **에이전트 실행기:** 맥락 유지, 도구 호출, 답변 생성
- **ERP MCP:** 입력·권한·REST 계약 처리
- **교육 웹서버:** 포털의 정적 파일 제공

같은 장비에 둘 수 있지만 서로 다른 프로세스와 기능입니다. 교육 웹서버가 켜졌다고 봇이나 에이전트가 함께 완성되는 것은 아닙니다. 모바일 대화와 기존 Desktop 대화의 자동 공유도 아직 구현되지 않았습니다.

## 단계별 검증 계획

1. AI 없이 실제 대상이 아닌 시험 도구의 호출을 확인합니다.
2. 가상 응답으로 필드·단위·오류 계약을 확인합니다.
3. 담당자가 선정한 개발계 조회 API와 같은 입력으로 결과를 대조합니다.
4. 에이전트가 올바른 도구와 인자를 선택하는지 기록합니다.
5. Telegram 허용 사용자에게만 왕복 응답하는지 확인합니다.
6. 사용자별 대화 연결, 중복 수신, 지연·중단·복구를 시험합니다.

현재 교육은 **설계와 검증 계획** 단계입니다. ERP 접속 URL·토큰을 넣은 실행본이나 운영 성공 화면은 제공 자료에 없습니다.

## 먼저 정할 질문

첫 조회 업무는 무엇인지, 기존 API의 요청·응답 명세는 무엇인지, 결과를 대조할 담당자는 누구인지부터 정합니다. 구매오더 상태 조회 등 원천의 이름은 예시이며 실제 운영 API 이름으로 사용하지 않습니다.
