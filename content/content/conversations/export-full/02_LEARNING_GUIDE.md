# 전체 학습 가이드 — 공유 대화 전문 반영

각 에피소드는 실제 발화와 별도의 교육 해설·실습으로 구성됩니다.

## 01. 프로젝트 목적과 SAP 환경을 먼저 확인하다

처음 AI에 전달한 목표·제약과 환경 확인 질문을 읽고, 자기 업무의 시작 요청을 구성합니다.

**교육 해설 — 실제 AI 발화 아님.**

첫 요청은 단순 소스 다운로드가 아니라, 패키지 추출부터 로컬 분석·수정·Git·SAP 반영까지 이어지는 목표였다. 단일 REPORT 구성과 BASIS 700 제약도 함께 명시했다.

AI는 바로 전체 구현을 완료했다고 하지 않고 SP·Unicode, 최초 대상 패키지, PC 실행 환경을 질문했다. 사용자는 화면 정보와 Windows 11, PowerShell·Python 미설치 조건을 제공했다. 이어 진단 출력으로 실제 객체 유형과 API를 확인했다.

초기 목표와 최종 결정을 구분해야 한다. 이때의 자동 반영 구상을 현재 기능으로 읽지 말고 E16의 방향 변경까지 따라간다.

### 확인한 결과

최초 요청과 초기 AI 답변을 확보했다. 대화 4의 진단 출력 및 AI 해석에는 ZHR5 18종·618건이 나온다. 이 수치는 당시 대상이며 현재 시스템 전체 현황이 아니다.

### 따라 하기

**교육용 재작성 프롬프트 / 실습**

“현재 시스템의 버전·작업 단위·사용 가능한 PC 도구는 다음과 같습니다. 최종 목표와 먼저 검증할 최소 단계를 분리하고, 확인이 필요한 질문을 세 가지 이내로 정리해 주십시오.”

**완료 기준:** 자신의 환경표, 범위표, AI가 직접 확인할 수 없는 항목을 한 장으로 작성한다. 모르는 SP·API 정보를 추측하여 채우지 않는다.

## 02. 첫 추출기의 오류를 실행 결과로 줄이다

파일 무결성 통과와 SAP 객체 읽기 성공을 구분하고, 실행 자료를 근거로 반복 수정하는 방법을 익힙니다.

**교육 해설 — 실제 AI 발화 아님.**

언어 조건, 긴 함수 소스, SOURCE/NEW_SOURCE 선택 문제로 오류가 이어졌다. AI는 각 응답에서 원인과 수정 버전을 설명했고, 사용자는 결과물과 화면을 다시 제공했다. 대화 11에서는 함수 127개 읽기 완료를 보고하고, 이후 남은 구조체의 활성 정의와 내부 INCLUDE 범위를 별도로 다뤘다.

교육에서 중요한 점은 ZIP 파일 점검이 통과했다고 SAP 객체가 전부 추출된 것으로 보지 않는 것이다. 실패 유형과 검증 방법을 나눈다. 대화 13의 응답 본문은 공유 화면에 표시되지 않아 안내로만 남긴다.

### 확인한 결과

대화 14의 AI는 0.2.4 내부 INCLUDE 추출을 사용자 실행 결과로 검증했다고 설명한다. 이번 포털 작업에서 SAP를 다시 실행하거나 당시 모든 ZIP을 새로 감사한 것은 아니다.

### 따라 하기

**교육용 재작성 프롬프트 / 실습**

“첨부 결과에서 파일 해시·파일 개수 검증과 SAP 조회 실패를 구분해 주십시오. 원인별 수정 범위, 다시 실행할 항목, 다음 결과에서 확인할 수치를 표로 정리해 주십시오.”

**완료 기준:** 오류 → 수정 → 재실행 근거를 세 열로 기록한다. 실패 0건과 미지원·생략 0건을 같은 뜻으로 쓰지 않는다.

## 03. 다른 패키지에서 BSP·MIME 누락을 발견하다

한 패키지의 성공을 다른 패키지까지 확대하지 않고, 웹 자산과 패키지 경계 요구를 구체화합니다.

**교육 해설 — 실제 AI 발화 아님.**

ZFI1에서는 용량 상한과 개별 객체 문제를 확인한 뒤, 사용자가 BSP 라이브러리 누락을 지적했다. AI는 해당 기능이 아직 구현되지 않았음을 인정하고 0.3.0 확장본을 제공했다. 이후 XSTRLEN 사용과 SORTED TABLE의 SORT 문에서 BASIS 700 호환 오류가 반복됐다.

사용자는 특정 행만 고치는 데 그치지 않고 비슷한 SORT 사용을 함께 확인하도록 요청했다. 마지막에는 ZWEB_FI_BIZCARD가 ZBIZCARD 소속임을 알려 선택 범위 밖 자산의 추출을 제외시켰다.

### 확인한 결과

BSP·MIME 확장, XSTRLEN 계산 분리, 불필요한 SORT 제거, 외부 개발클래스 제외에 대한 당시 AI 답변을 읽을 수 있다. 각 답변의 로컬 검사와 실제 SAP 실행 보고는 별도 근거다.

### 따라 하기

**교육용 재작성 프롬프트 / 실습**

“대표 패키지와 성격이 다른 패키지 하나의 결과를 비교해 주십시오. 빠진 객체 유형, 파일 용량 제한, 범위 밖 참조를 구분하고, 보고된 문법 오류와 같은 패턴을 전체 소스에서 점검해 주십시오.”

**완료 기준:** 패키지별 객체 유형 비교표와 범위 밖 자산 처리 원칙을 작성한다.

## 04. 변경 요구를 맥락 문서와 파일 규칙으로 남기다

대화 중 바뀐 요구를 문서로 고정하고 다음 버전의 확인 기준으로 사용합니다.

**교육 해설 — 실제 AI 발화 아님.**

사용자는 장기 대화의 맥락을 정리하면서 접두어 제거, KO만 사용, BASIS 700 준수, 타 개발클래스 제외를 명시했다. AI는 맥락 문서와 0.3.5를 제공했고, 다음 결과에서는 한글 파일명이 #로 바뀌는 ZIP 이름 인코딩 문제가 드러났다. ZBUDGET 사례에서는 숫자 폴더를 페이지 이름으로 바꾸도록 요구했다.

맥락 정리는 단순 요약으로 끝나지 않는다. 새 요구를 실제 파일 경로와 검증 사례에 연결한다. 이때의 KO 전용 결정은 이후 E03에서 KO 우선·EN 보완으로 바뀐다.

### 확인한 결과

대화 26에서 AI가 ZIP 유니코드 파일명 설정 누락을 원인으로 설명했다. 대화 27에서는 ZBUDGET 점검 결과와 BSP 폴더 이름 변경을 안내했다. 최종 정책은 후속 에피소드의 변경까지 확인한다.

### 따라 하기

**교육용 재작성 프롬프트 / 실습**

“지금까지 확정된 요구, 변경된 요구, 미해결 문제를 분리해 맥락 문서로 정리해 주십시오. 파일명·언어·범위 정책마다 확인할 실제 결과 예시를 붙여 주십시오.”

**완료 기준:** 변경 이유와 적용 버전을 함께 기록한다. 한글 이름·동명 파일·페이지 경로를 다음 추출의 점검 항목으로 남긴다.

## 05. SAP 화면을 기준으로 추출 구조를 다시 정의하다

개발자가 쓰는 화면 용어를 파일 경로 계약으로 바꾼다.

**교육 해설 — 실제 AI 발화 아님.**

대화 28에서 AI는 BSP 폴더 경로 중복을 설명했고, 29~31에서는 SAP의 다섯 탭에 맞춘 폴더와 XML 출력을 안내했다. 사용자의 첫 삭제 요청에 이어 Properties·Page Attributes 정보를 보존하라는 보완이 들어왔다. 이름 정리와 정보 삭제를 구분하는 사례다. 사용자 원문의 OnDestory 오타는 보존하고 해설에서는 OnDestroy로 구분한다.

### 확인한 결과

0.3.9·0.3.10 수정 안내 전문을 확보했다. 이 응답 자체는 당시 작성 보고이며 현재 SAP에서 다시 실행했다는 뜻은 아니다.

### 따라 하기

**교육용 재작성 프롬프트 / 실습**

본인 패키지의 BSP 한 페이지를 골라 SAP의 다섯 탭과 추출 파일을 표로 대조한다. 프롬프트: “실제 페이지의 Properties, Layout, Event Handler, Page Attributes, Type Definitions와 파일 경로를 대응시켜줘. 원본에 없는 이벤트 코드를 만들지 말고 이름을 확인하지 못하면 미확인으로 남겨줘.”

**확인 방법·흔한 실패**

페이지 경로·확장자·이벤트명·UTF-8 한글이 보존되는지 확인한다. 파일 이름만 예쁘게 바꾸고 본문이 빠진 경우를 통과시키지 않는다. 현재 완전한 ZMM6 ZIP이 없으므로 첨부 화면과 코드 검토부터 수행한다.

## 06. 20개 변경 요청을 출력 계약으로 구체화하다

폴더 이름, 정보 단위, 예외를 명시하여 AI의 경로 해석 오해를 줄인다.

**교육 해설 — 실제 AI 발화 아님.**

20개 요청을 한꺼번에 받은 AI는 대화 32에서 작업 환경 연결 실패로 수정본을 제공하지 못했다고 밝혔다. 다음 응답에서 0.3.11을 제공한 뒤, NORMAL 인자 오류와 함수별 Source code 폴더 위치를 다시 수정했다. 대화 34의 실제 수정 설명은 set_normalizing 호출 두 곳의 인자를 고친 것이다. 요청 경로는 완전한 예시로 전달해야 오해를 줄일 수 있다.

### 확인한 결과

0.3.11~0.3.13의 안내와 오류 수정 응답을 확인했다. 메시지 클래스 추가와 함수 폴더 계약을 학습하며 정적 검사와 SAP 활성화 확인을 나눈다.

### 따라 하기

**교육용 재작성 프롬프트 / 실습**

프롬프트: “packages/패키지/function-groups/FUGR/그룹/Function Module/함수명/Source code/함수명.abap 구조를 계약으로 삼아줘. Import.xml 등 함수 탭 XML의 목적을 표로 설명하고, 메시지 000과 &1 자리표시자도 보존해줘.” 자신의 패키지 한 함수로 경로 명세를 작성한다.

**확인 방법·흔한 실패**

동명 함수·하위 그룹·빈 인터페이스·000 메시지 번호를 확인한다. KO 경로 삭제를 한국어 값 삭제로 해석하면 실패다. NORMAL 3067줄은 과거 버전 위치이므로 현재 같은 줄을 기계적으로 바꾸지 않는다.

## 07. 언어 fallback과 XML 값 보존 오류를 분리하다

오류 메시지를 근거로 가설을 수정하고 동일성 검사를 유지한다.

**교육 해설 — 실제 AI 발화 아님.**

KO 전용 추출 이후 사용자는 언어 문제를 의심했지만, AI는 대화 38에서 자체 XML 왕복 검사의 전제가 잘못됐다고 설명했다. 언어 fallback, 원시 직렬화, 들여쓰기를 별도 단계로 검토해야 원인 가설을 검증할 수 있다. 대화 39의 첨부 전용 요청 뒤에는 AI가 결과를 분석한 전문이 연결된다.

### 확인한 결과

AI 응답에는 콘텐츠 4,285개 일치와 SAP 프로그램 3개의 읽기 실패가 함께 보고된다. 파일 검증 통과를 전체 객체 추출 성공으로 확대하지 않는다.

### 따라 하기

**교육용 재작성 프롬프트 / 실습**

프롬프트: “언어 선택, 원시 XML 직렬화, 들여쓰기를 별도 단계로 검사해줘. 한국어·영어 혼합, 공백, 줄바꿈, &, <, 000을 가진 fixture로 값이 바뀌는 첫 단계를 찾아줘. 보호 검사를 삭제해서 성공시키지 말아줘.”

**확인 방법·흔한 실패**

XML 파싱 성공뿐 아니라 원래 값의 보존을 확인한다. SAP 재현에는 해당 BASIS 환경이 필요하다. 로컬 예시를 통과한 것을 SAP 직렬화 통과로 쓰지 않는다.

## 08. 대용량·미지원·생략을 추출 정책으로 다루다

추출 성공률과 실제 정보 손실을 구분하고 로그 정책을 정한다.

**교육 해설 — 실제 AI 발화 아님.**

대화 40~46은 대용량 예산, 숨김 파라미터 선언 오류, MIME 실패 집계, DDIC 예외와 의도적 제외 정책을 다룬다. AI가 오류 0으로 보였던 집계 문제를 인정한 응답도 포함한다. 사용자는 기술 공통 참조를 무조건 확장하지 않도록 범위를 정했다. baseline은 후속 비교 기준이므로 AI 검색 중복과 파일 보존 필요를 구분한다.

### 확인한 결과

0.3.18 안내에서 17,142개 파일 일치와 생략 19개 등의 당시 결과를 확인할 수 있다. 실패를 처리한 것과 의도적으로 생략한 것은 서로 다른 결과다.

### 따라 하기

**교육용 재작성 프롬프트 / 실습**

프롬프트: “추출 대상·지원·의도적 제외·실패를 분리해 목록을 만들어줘. baseline은 진단 기준으로 보존하고 AI 색인에서는 중복 제외해줘. ZIP은 패키지명_export.zip으로 만들고 예산 초과 원인을 파일별/누적별로 설명해줘.”

**확인 방법·흔한 실패**

한 번의 추출에서 대상 수, 생성 수, 생략 수를 함께 검토한다. 읽기 실패를 비활성 확정으로 단정하지 않는다. 예산을 무제한 늘리는 방식은 실습 해법으로 쓰지 않는다.

## 09. GitHub publish와 Mac clone으로 업무 에이전트를 시작하다

저장소 공유, PR, 로컬 작업공간의 역할을 구분한다.

**교육 해설 — 실제 AI 발화 아님.**

사용자의 목적이 패키지별 업무 AI 에이전트로 확장되는 구간이다. AI는 저장소 정리 → Publish → Mac Clone 순서를 제시하고 Clone·Pull·Pull Request를 구분했다. 대화 50의 사용자는 ZHR5 에이전트 구성을 성공했다고 보고한다. 여러 에이전트의 역할 제안과 실제 자동 협업 운영은 구분해서 읽는다.

### 확인한 결과

GitHub Publish와 Mac Clone은 사용자의 당시 성공 보고다. 현재 브랜치·설치 버전·ZFI/ZMM 자동 협업 운영을 이 포털에서 검증한 것은 아니다.

### 따라 하기

**교육용 재작성 프롬프트 / 실습**

교육용 재작성 프롬프트: “이 로컬 프로젝트의 실제 파일부터 확인하고 ZHR5 업무 에이전트의 읽기 범위와 근거 경로를 정리해줘. 현재 브랜치·변경 파일을 보여주되 push는 하지 말아줘.” 준비된 저장소가 있을 때 로컬에서 `git status --short`와 `git log -5 --oneline`으로 상태를 기록한다.

**확인 방법·흔한 실패**

보고서의 파일 경로가 실제 존재하는지 확인한다. 예시 명령은 조회용이며 현재 저장소를 우리가 검증했다는 뜻은 아니다. PR 만들기를 clone 절차로 대체하지 않는다.

## 10. 코드만으로 부족한 업무 지식을 문서·스킬로 보완하다

규정, 대화, 매뉴얼의 권위와 시점을 보존하여 업무 답변 근거를 만든다.

**교육 해설 — 실제 AI 발화 아님.**

코드와 구조만으로는 정책의 이유나 담당자의 판단 맥락을 알기 어렵다는 문제에서 시작한다. AI는 스킬의 절차, 업무 지식 MD의 근거, 원문 보존, 추출 소스의 역할을 구분했다. 대화 56에서는 11개 원문을 반영한 MD 40개·스킬 3개 키트를 제공했다고 안내하고, 57에서는 다른 패키지에도 적용할 공통 구축 가이드를 제시한다. 이전 추출본의 중복 요청 U030/U031은 공유 화면에서 하나의 요청에 대응하므로 한 번만 표시한다.

### 확인한 결과

자료 구성과 생성 안내를 실제 AI 답변으로 읽을 수 있다. 키트가 존재한다는 사실과 Mac에서 현재 스킬이 로드되어 올바른 업무 답변을 하는지는 별도 확인한다.

### 따라 하기

**교육용 재작성 프롬프트 / 실습**

프롬프트: “먼저 자료 목록과 확인 여부를 작성해줘. 규정의 시행일, 회의 합의일, 카톡 발언일을 분리하고 출처가 다른 주장 사이의 충돌을 남겨줘. AGENTS에는 작업 원칙, INDEX에는 탐색 링크, 스킬에는 절차, 업무 MD에는 근거를 배치해줘.” 원문 하나로 작은 범위를 실습한다.

**확인 방법·흔한 실패**

각 주장에 원문 위치·적용 시점·확인 상태가 있는지, 인용을 열 수 있는지 점검한다. 이번 ZIP의 스킬 사본은 자동 설치되지 않는다. 사용자 이름·연락처·인사정보는 업무에 꼭 필요한지 판단해 교육판에서 마스킹한다.

## 11. 업무 답변 하네스를 코드 하네스와 분리하다

실행 오류가 없는 답변도 평가할 수 있도록 실패 조건을 만든다.

**교육 해설 — 실제 AI 발화 아님.**

사용자는 자연어 업무 답변에는 실행 오류가 나지 않는데 어떻게 실패를 인지하는지 질문했다. AI는 앞선 설명에서 정답 판정 기준이 빠졌음을 인정했다. 이후 업무 피드백과 코드 검증을 분리하고, 담당자의 수정 지시를 근거 문서·지침·회귀 사례로 반영하는 방식으로 범위를 좁혔다. 업무 답변의 실패만으로 ABAP까지 자동 변경하지 않는다는 경계도 확인한다.

### 확인한 결과

BUSINESS_FEEDBACK_POLICY.md 제공 응답과 사용자 적용 예정 보고가 연결된다. 하네스 폴더나 정책 문서가 모든 사례의 자동 평가·무인 운영을 입증하지는 않는다.

### 따라 하기

**교육용 재작성 프롬프트 / 실습**

프롬프트: “이 답변은 적용 시점을 잘못 해석했어. 근거 문서의 해당 절을 확인하고 원인·수정 MD·추가 회귀 사례를 제시해줘. 근거가 부족하면 REVIEW_REQUIRED로 남겨줘. ABAP, Export 원본, baseline은 수정하지 말아줘.” 담당자 승인 근거가 있는 한 사례만 처리한다.

**확인 방법·흔한 실패**

질문/적용일/필수 근거/기대 판단/금지 단정/검토 상태를 기록한다. PASS·FAIL·REVIEW_REQUIRED·NOT_RUN을 구분한다. 평가 코드를 고칠 때 기존 실패 사례를 지워 성공 수치만 높이지 않는다.

## 12. SAP에서 GitHub에 직접 접속하려다 통신 제약을 확인하다

통신 오류 코드·로그·보류 결정을 연결해 재현한다.

**교육 해설 — 실제 AI 발화 아님.**

수동 ZIP 업로드를 줄이려 SAP에서 GitHub 목록을 직접 조회했으나 SSL/TLS 단계에서 막혔다. AI는 초기 화면, 실제 ICM 로그, 존재하지 않는 프로파일 파라미터 문의를 차례로 분석했다. SAP error code 407을 HTTP 프록시 인증 코드로 단정하지 않고 로그의 protocol version alert를 함께 읽는다. 토큰 수정으로 해결할 문제인지 먼저 구분하는 사례다.

### 확인한 결과

대화 70에서 사용자가 직접 통신을 보류하고 Actions 논의로 이동했다. 현재 시스템의 TLS 설정 변경·연결 성공은 확인하지 않았다.

### 따라 하기

**교육용 재작성 프롬프트 / 실습**

프롬프트: “오류 화면의 코드가 HTTP 응답인지 SAP transport 오류인지 구분해줘. 마스킹된 ICM 로그에서 직접 확인되는 문구만 근거로 후보 원인을 정리하고, 확인하지 않은 설정값을 존재한다고 단정하지 말아줘.” 실제 네트워크 연결 실습은 하지 않고 첨부 로그를 읽는다.

**확인 방법·흔한 실패**

로그의 protocol alert와 일반 traffic timeout을 구분한다. 계정·토큰을 Git이나 프롬프트에 저장하지 않는다. 재시도에는 BASIS 담당자의 지원 범위 확인이 필요하며 이 ZIP은 시스템 보안 설정을 변경하지 않는다.

## 13. GitHub Actions를 AI와 구분해 이해하다

자동 실행 규칙, 검증 범위, 로컬 피드백의 경계를 이해한다.

**교육 해설 — 실제 AI 발화 아님.**

AI는 YAML이 검사 순서를 지정하고, 실제 검사는 지정된 도구가 러너에서 수행한다고 설명한다. Actions 자체가 AI인지, 로컬 Codex에 결과가 자동 전달되는지 묻는 후속 질문으로 실행 주체와 전달 경로가 구체화된다. Ubuntu가 필수라는 오해도 해소한다. 반복 실행되는 저장소 검증과 실제 SAP 배포를 구분한다.

### 확인한 결과

사용자는 Actions를 사용해 보겠다는 의향을 밝힌 뒤 비교 프로그램으로 넘어간다. 실제 workflow 설치와 성공 로그는 이 대화의 설명만으로 확정할 수 없다.

### 따라 하기

**교육용 재작성 프롬프트 / 실습**

프롬프트: “저장소에 workflow가 실제 있는지 먼저 확인해줘. 없다면 미구현이라고 표시해줘. 현재 파일로 로컬 검증 가능한 JSON 파싱, 링크, 합성 비교 실습을 실행하고 그 결과를 SAP 검증과 구분해줘.” 새 workflow 제작이나 push는 별도 작업으로 둔다.

**확인 방법·흔한 실패**

검증 명령·대상·실패 조건이 없는 YAML은 교육상 구현 완료로 분류하지 않는다. 실패 로그를 Codex에 직접 제공하는 수동 피드백부터 재현한다.

## 14. 첫 Import는 비교 리포트부터 시작하다

원래 목표와 실제 제공 프로그램의 실행 권한을 구분한다.

**교육 해설 — 실제 AI 발화 아님.**

처음 Import는 실제 저장·활성화보다 ZIP 비교와 검증 리포트부터 구현하는 방향으로 시작했다. ABAP뿐 아니라 HTML·JS·CSS의 줄 차이도 요구했다. 대화 83에서 AI는 MOD가 포함된 조건식 네 곳을 수정하고 정적 검사와 108개 줄 비교 사례를 보고했다. 서버에 저장하지 않은 사전 검사와 실제 활성화를 구분해서 읽는다.

### 확인한 결과

첫 비교 프로그램 안내와 사용자 실행 결과 해석을 확보했다. 프로그램 이름이 Import였다는 이유로 자동 저장·활성화가 구현됐다고 해석하지 않는다.

### 따라 하기

**교육용 재작성 프롬프트 / 실습**

초기 ZIP의 README를 읽고 입력·읽기·쓰기·활성화 항목을 표로 만든다. 프롬프트: “이 소스에서 실제 SAP 저장 호출과 읽기 호출을 구분하고, 이름만으로 Import 실행이라고 추측하지 말아줘. BASIS700에서 검증되지 않은 구문을 표시해줘.”

**확인 방법·흔한 실패**

과거 0.1.0은 시행착오 참고용이다. 실습 대상 소스는 현재 DIAG 0.4.5로 하고 SAP 적용에는 개발 환경 문법 확인이 선행한다. 코드 파일 존재를 운영 검증 완료로 쓰지 않는다.

## 15. ABC 모드에서 원본 중심 세 비교로 정리하다

대비 방향과 값 존재 여부를 명확히 하여 상태를 해석한다.

**교육 해설 — 실제 AI 발화 아님.**

사용자는 ABC 모드 대신 ZIP 하나와 원본 중심 세 비교를 요구했다. 대화 86에서 AI는 DIFFERENT 78건의 내용과 파일 크기가 아닌 바이트 비교라는 점을 설명한다. 같은 길이의 다른 내용, XML 표현 차이와 의미 차이, 원본 대비 변경과 현재 두 값의 일치 여부는 각각 다른 질문이다.

### 확인한 결과

0.2.0과 0.3.0의 수정 안내를 읽을 수 있다. SAP 읽기 미확인은 파일 부재가 아니며 비교 불가를 변경없음으로 채우지 않는다.

### 따라 하기

**교육용 재작성 프롬프트 / 실습**

첨부 합성 실습을 `python3 assets/examples/compare_cases.py`로 실행한다. 프롬프트: “기준→대상의 방향으로 네 상태를 판정해줘. SAP 읽기 실패는 known absent로 바꾸지 말고 비교 불가로 분리해줘.” 같은 길이의 서로 다른 텍스트도 한 사례로 추가 검토한다.

**확인 방법·흔한 실패**

세 결과를 방향별로 손으로 설명할 수 있어야 한다. 누락은 비교 대상에서 없다는 관찰이며 SAP 삭제 명령이 아니다. 이 실습의 통과는 Python 합성 사례 검증이다.

## 16. ZIP·버전·화면 이동의 실제 장애를 나누다

서로 다른 실패를 한 오류로 뭉뚱그리지 않고 증거별로 수정 요청한다.

**교육 해설 — 실제 AI 발화 아님.**

이 구간에는 ZIP 항목·크기 제한, .git 데이터 혼입, Export 버전 제한, ALV 헤더 높이, F3 복귀 경로가 차례로 등장한다. 대화 89·90의 AI 본문은 공유 화면에 없어 안내로 표시한다. 사용자는 exports 아래만 압축하겠다고 했고, 대화 91~94의 실제 AI 응답에서 헤더 축소·버전 허용·화면 복귀·좌우 비교 수정 이유를 확인할 수 있다.

### 확인한 결과

“ALV 결과까지는 나왔다”는 사용자의 부분 성공과 이어진 F3 오류를 함께 보존한다. 한 장애가 해결됐다는 보고를 전체 완료로 확대하지 않는다.

### 따라 하기

**교육용 재작성 프롬프트 / 실습**

프롬프트: “ZIP 내부 목록에서 .git/objects, 원본 manifest, baseline, packages를 구분해줘. 제한 오류와 manifest 호환 오류를 각각 보고해줘.” 파일 검사 후 목록→상세→F3→같은 목록 복귀를 테스트 케이스로 작성한다.

**확인 방법·흔한 실패**

실제 데이터 ZIP 없이 실행 성공을 꾸미지 않는다. 헤더의 self-test PASS 아래 STOP이 있으면 전체 실행은 중단된 것이다. 과거 특정 버전 제한을 무조건 모든 파일 허용으로 바꾸는 방식은 사용하지 않는다.

## 17. 조회·활성 버전·문법 검사를 별도 사실로 표시하다

모호한 영문 상태를 증거가 분리된 한글 리포트로 바꾼다.

### 확인한 결과

0.3.8의 조회·활성 확인 분리 안내 전문을 확보했다. 화면 이름뿐 아니라 API·반환값·검사 수행 여부도 구분해 읽는다.

### 따라 하기

**확인 방법·흔한 실패**

세 비교가 변경없음인데 활성 확인 실패인 행도 설명할 수 있어야 한다. UI 라벨만 바꾸고 내부 상태의 의미를 합치면 실패다. 사용자 질문에 포함된 가설을 정답 표에 복사하지 않는다.

## 18. XML의 가짜 대량 변경을 필드 단위로 좁히다

직렬화 차이와 의미 있는 필드 변경을 구분한다.

**교육 해설 — 실제 AI 발화 아님.**

XML 비교를 추가한 뒤 유사한 값이 여러 번 변경된 것처럼 표시됐다. 대화 101에서 AI는 하위 텍스트를 합쳐 읽은 상위 요소까지 변경으로 집계한 비교 로직 문제를 설명했다. 부모·자식 경로, 직접 텍스트·속성, 공백 표현 차이를 분리해 검증해야 한다.

### 확인한 결과

당시 오류 인정과 수정 설명을 확보했다. 현재 SAP에서 모든 false positive가 사라졌다는 검증을 새로 수행한 것은 아니다.

### 따라 하기

**교육용 재작성 프롬프트 / 실습**

프롬프트: “부모 경로에 자식 텍스트가 중복 집계되는지 확인해줘. 직접 텍스트·속성·자식 경로를 분리하고, 하나의 leaf만 바꾼 합성 XML에서 해당 의미 값만 변경으로 표시해줘. 공백을 임의로 없애지 말아줘.”

**확인 방법·흔한 실패**

동일 내용의 들여쓰기 차이, leaf 변경, 속성 변경, 추가/누락을 각각 검토한다. 실제 함수 Attributes와 공통 TRDIR 값 변경은 원본 세 자료가 있어야 최종 원인을 확정할 수 있다.

## 19. 리포트 화면 자체를 업무 판단 도구로 다듬다

필드 순서·고정 열·집계 모수를 요구사항으로 명시한다.

**교육 해설 — 실제 AI 발화 아님.**

사용자가 원한 것은 단순 표 모양의 헤더가 아니라 실제 ALV 헤더였다. AI는 WIDTH 인자 오류의 동일 호출 열 곳을 수정했고, 이후 상단을 별도 ALV로 구성했다. 대화 106에서는 A=세 비교, B=활성·문법 검증으로 나눠 상태·건수 집계를 정리했다. 가독성 요구를 필드·집계 모수·화면 동작으로 구체화하는 사례다.

### 확인한 결과

0.3.11~0.3.15의 수정 응답과 “표로 바뀌었지만 ALV가 필요하다”는 사용자 피드백을 함께 읽는다. 개인 정보로 제외된 과거 화면의 공개 범위는 유지한다.

### 따라 하기

**교육용 재작성 프롬프트 / 실습**

프롬프트: “메인은 예외·유형·구성요소·파일명을 왼쪽 고정하고 상세는 순서와 세 대비를 고정해줘. 헤더 A의 각 행 합계를 표시하되 B와 집계 대상이 같다고 가정하지 말아줘.” 요구사항-화면-코드 대응표를 만든다.

**확인 방법·흔한 실패**

32인치 화면 확대·가로 스크롤·긴 경로·F3 복귀를 개발 SAP GUI에서 확인한다. 고정 필드 수와 기본 width, 사용자 저장 레이아웃의 영향을 함께 기록한다.

## 20. 자동 Import를 제외하고 DIAG로 방향을 확정하다

목표 축소를 실패가 아니라 책임 경계의 명확화로 이해한다.

**교육 해설 — 실제 AI 발화 아님.**

대화 107에서 사용자는 자동 Import·활성화가 아직 충분히 검증되지 않았다고 판단해 이를 제외하고 DIAG로 이름과 방향을 바꿨다. AI는 읽기 전용 0.4.0으로 전환한 뒤 이름 중복, 화면 높이, 입력 범위, 필터를 수정했다. 문법 사전검사 기본 선택과 모든 파일에서 검사가 실제 수행되는 것은 다르다는 후속 설명도 함께 읽는다.

### 확인한 결과

현재 교육 기준은 읽기 전용 진단이다. 초기 목표에 등장한 저장·활성화·CTS를 현재 제공 기능으로 다시 포함하지 않는다. 0.4.5 실제 SAP 실행 확인은 별도다.

### 따라 하기

**교육용 재작성 프롬프트 / 실습**

프롬프트: “DIAG는 저장·활성화 없이 비교 리포트만 생성해줘. 소스코드 기본 선택과 변경분만 표시를 적용하되 검사 실패 행을 단순 변경없음으로 숨기지 않는지 설명해줘.” 현재 소스의 조건 분기부터 확인한다.

**확인 방법·흔한 실패**

결과 필터가 실제 조회 시간 절약인지 표시만 제한하는지 확인한다. 현재 코드의 필터/헤더/JSON 모수를 검토하고 사용자 테스트에서 네 결과 유형을 각각 비교한다. 운영 ERP 변경 단계는 이 교육 범위에 없다.

## 21. 실제 ZHR5 결과로 검증 의미와 마지막 호환 오류를 좁히다

사용자 결과 데이터로 개선 항목을 만들고 최신 수정의 검증 한계를 남긴다.

**교육 해설 — 실제 AI 발화 아님.**

사용자는 일반적인 가능성 설명 대신 실제 ZHR5 엑셀의 행을 근거로 설명해 달라고 요청했다. AI는 함수/Include 연결, 공통 속성과 함수 자체 속성, 확인 실패와 검사 미수행, 잘린 설명 보존을 구체화했다. 대화 114~115에서는 선택한 개선과 날짜·시간 인자 형식 수정이 이어진다. 이전부터 확보한 RawData에서는 확인 실패 71건을 함수 70건과 DDIC 1건으로 나눠 읽는다.

### 확인한 결과

0.4.4 개선 안내와 9128행 형식 오류 수정 응답을 확보했다. 당시 AI의 정적 점검 보고와 최신 0.4.5 SAP 활성화·ALV·JSON 실행 성공은 구분한다.

### 따라 하기

**교육용 재작성 프롬프트 / 실습**

RawData JSON의 828·1440·2532–2542행을 읽고 비교 상태·SAP 검증·활성 근거·문법 검사를 각각 설명한다. 프롬프트: “71건을 구성요소별로 다시 집계하고, 공통 함수그룹 변경인지 함수 자체 변경인지 근거 필드를 찾아줘. 원본에 없는 잘린 설명은 복원하지 말아줘.”

**확인 방법·흔한 실패**

행 수 2,541, 확인 실패 70+1, 동일 byte 3,210 사례를 재대조한다. 함수 API 소스와 실제 활성 Include 내용의 정규화·추출 경계 차이는 후보 원인이며 해당 SAP와 세 원본 없이 모든 건의 원인 확정은 불가하다.

## 22. 요약 산출물에서 실제 대화 기반 교육 자료로 확장하다

증거 수준을 표시하며 실패·수정 과정을 재사용 가능한 콘텐츠로 만든다.

**교육 해설 — 실제 AI 발화 아님.**

요약 산출물에서 실제 대화 기반 교육 자료로 요구가 발전한 과정이다. 과거 AI 답변에 “전문 미확보”라고 쓰여 있는 것은 당시 추출 상태이며 이번 화면의 현재 확보 상태가 아니다. 2026-10-13에는 공유 화면의 사용자 119개·AI 본문 116개를 확보했다. 이전 자료의 진행 안내와 중복 요청은 보존 폴더에 남기되 이번 공유 경로에 임의로 끼워 넣지 않았다.

### 확인한 결과

화면의 기술 학습과 원문 추출 작업을 구분했다. 공유 화면에 없는 응답 3곳과 첨부 원본의 미확보는 별도로 표시한다.

### 따라 하기

**교육용 재작성 프롬프트 / 실습**

프롬프트: “이 JSON의 role/content_type/coverage를 이용해 실제 발화와 교육 해설을 분리해줘. 없는 AI 답변은 빈 말풍선을 생성하지 말고 원문 미확보로 표시해줘. asset path가 null이면 다운로드 버튼을 만들지 말아줘.” UI를 실제 구현하지 않고 화면 요구사항만 검토한다.

**확인 방법·흔한 실패**

첨부 검증 스크립트로 ID·참조·파일·순서·체크섬을 확인한다. 이 ZIP의 자체 검증 결과를 SAP 검증 결과와 혼동하지 않는다.
