## eac-m024 · AI 응답

출처: https://chatgpt.com/share/6acf6d07-d340-83ee-b865-0f1aa5ae8ecb / 화면 turn 18 / 2026-10-14 직접 확인

**실행 가능한 Node.js 중앙 MCP 서버 예제를 만들었습니다.** HR의 질문을 저장하고, FI 맥의 워커에 배정한 뒤 답변을 돌려주는 구조입니다.

[ERP_MCP_NodeJS_Example.zip](ERP_MCP_NodeJS_Example.zip)

**중앙 MCP 통신은 구현되어 있고, FI의 실제 AI 분석 부분은 연결 지점으로 남겨두었습니다.** 포함된 모의 워커는 통신 확인용 답변만 반환합니다.

파일 구성은 다음과 같습니다.

| 파일 | 역할 |
| --- | --- |
| `server.mjs` | 중앙 MCP 서버·질문 배정·SQLite 저장 |
| `mock-worker.mjs` | FI 맥에서 중앙 질문을 받아 답하는 통신 시험용 워커 |
| `test.mjs` | 실제 MCP 클라이언트를 사용하는 통합 테스트 |
| `README.md` | 설치·실행·Codex 연결 방법 |
| `package.json`, `package-lock.json` | 필요한 라이브러리와 설치 버전 |

중앙 서버의 핵심은 다음 코드입니다. 전체 코드에서 핵심 흐름만 줄인 예입니다.

```javascript
server.registerTool(
  "ask_expert",
  {
    description: "다른 업무 담당에게 자문 요청",
    inputSchema: {
      expert: z.string(),    // 예: ZFI
      question: z.string(),  // 질문
      context: z.string()    // ZHR에서 확인한 근거
    }
  },
  async ({ expert, question, context }) => {
    // 1. 요청자가 해당 업무에 질문할 권한이 있는지 확인
    // 2. SQLite에 질문 저장
    // 3. FI 워커가 가져갈 수 있도록 대기 상태로 등록

    return {
      content: [{
        type: "text",
        text: JSON.stringify({
          job_id: id,
          status: "queued"
        })
      }]
    };
  }
);
```

여기서 **`registerTool()`은 HR 담당자의 Codex에 “다른 담당에게 질문하기” 기능을 제공하는 부분**입니다. 원격 연결에는 MCP SDK의 Streamable HTTP를 사용했습니다. [MCP TypeScript SDK (v1)](https://ts.sdk.modelcontextprotocol.io/server?utm_source=chatgpt.com)

FI 맥의 워커는 중앙에 다음 요청을 보냅니다.

```javascript
// 자기 업무에 들어온 질문을 가져오기
POST /worker/claim

// 분석이 오래 걸리면 처리 중임을 알리기
POST /worker/작업ID/heartbeat

// 답변 반환
POST /worker/작업ID/complete
{
  "lease": "작업을 배정받을 때 받은 값",
  "answer": "ZFI 소스를 확인한 결과..."
}
```

**HR Codex는 `get_answer` 도구로 답변을 조회**합니다. 오래 걸리는 AI 분석 동안 하나의 MCP 호출을 계속 붙잡지 않도록, 요청과 결과 조회를 나눴습니다. 추가 질문은 이전 작업 ID를 지정해 앞선 질문·답변을 전달하도록 했습니다.

중앙 서버는 Node.js 24 이상에서 다음 순서로 실행합니다.

```bash
npm ci

export HR_CLIENT_TOKEN='HR전용_24자이상_임의토큰'
export FI_WORKER_TOKEN='FI워커전용_다른_임의토큰'

npm start
```

처음에는 같은 컴퓨터에서 모의 워커로 확인하고, 이후 FI 맥의 워커를 연결하면 됩니다. 상세 명령은 README에 넣었습니다.

**검증한 내용:** MCP 질문 → FI 워커 배정 → 답변 조회, 후속 질문 문맥 전달, 다른 사용자의 답변 접근 차단, 다른 업무 워커의 처리 차단, 작업 임대 만료 처리까지 통합 테스트를 통과했습니다.

다음 구현 대상은 **FI 맥의 모의 답변 부분을 “ZFI 폴더를 읽는 Codex 자문 실행”으로 교체하는 것**입니다. 중앙 서버에는 ZFI 소스나 Codex Desktop이 없어도 됩니다.

## eac-m025 · 사용자 요청

출처: https://chatgpt.com/share/6acf6d07-d340-83ee-b865-0f1aa5ae8ecb / 화면 turn 19 / 2026-10-14 직접 확인

이 프로젝트의 대화와 자료를 추출해 ‘ERP AI 에이전트 교육 포털’ 제작에 활용하려고 한다. 아래 목적과 기준에 맞춰 실제 다운로드 가능한 MD 파일과 ZIP을 만들어줘.

1. 전체 목적과 활용 방식

여러 ERP AI 프로젝트에서 진행한 내용을 통합하여, KBS ERP 담당 팀원들이 전체 구조를 이해하고 직접 실습하며 운영 중에도 참고할 수 있는 교육 포털을 만들 예정이다.

통합 대상에는 ERP 소스 추출·배포, Codex Desktop 활용, GitHub 연동, ERP MCP 구성, 담당 업무별 에이전트와 서브에이전트, 업무 지식·스킬·하네스 구성, Obsidian 활용 등이 있다. 이 중 현재 프로젝트에서 실제 다룬 범위만 정리해줘.

자료는 다음과 같이 활용한다.

1. 각 프로젝트·대화방에서 MD와 관련 자료를 추출한다.
2. 별도 통합 대화방에서 자료들을 대조하여 교육 순서로 재구성한다.
3. 원본 자료, 교육용 콘텐츠, 이미지, 실습 자료, 웹 소스를 구분하여 GitHub에서 관리한다.
4. HTML·CSS·JavaScript 기반 포털을 만들고 MD를 콘텐츠 원본으로 사용한다.
5. 맥에서 GitHub 저장소를 클론하고, Codex Desktop으로 구성·유지보수한다.
6. Node.js 기반 웹서버가 완성된 배포 폴더를 제공하고, 팀원이 사내망과 KBS 도메인으로 접속한다.
7. 이후 팀원이 추가한 업무 경험과 변경 사항도 GitHub를 통해 교육 내용에 반영한다.

지금 요청하는 작업은 현재 프로젝트의 자료 추출이다. 웹사이트 구현, 서버 설치, GitHub push는 수행하지 마.

2. 확인 범위와 작성 원칙

* 현재 접근 가능한 대화·프로젝트 자료·첨부파일·기존 MD·산출물을 확인해서 작성해줘.
* 다른 대화방까지 모두 읽을 수 있다고 가정하지 말고, 실제 확인한 범위와 접근하지 못한 범위를 명시해줘.
* 파일명만 알고 있는 것과 실제 내용을 읽은 것을 구분해줘.
* 접근 가능한 최신 원본을 확인하고, 기억이나 요약만으로 현재 상태를 단정하지 마.
* 일반적인 기술 설명보다 이 프로젝트의 목적, 실제 작업, 결정 이유, 변경 과정을 우선해줘.
* 중요한 사용자 요구·수정 요청·실패 경험·제약사항은 과도하게 축약하지 마.
* ‘제안·결정·구현·검증·운영’ 상태를 구분해줘. 코드 생성이나 사용자 무응답을 검증 완료로 판단하지 마.
* 과거 방안과 현재 방안을 구분하고, 상충하는 내용은 근거와 시점을 비교해줘. 결론을 내릴 수 없으면 미확인으로 남겨줘.
* 주요 결정과 기술 사실에는 확인 가능한 파일명·문서 절·대화 날짜 등 출처를 붙여줘. 출처를 만들지 마.
* 다른 프로젝트의 내용은 추정하지 말고, 연결되는 부분과 통합 시 확인할 사항만 기록해줘.

### conversation-data.json — 채팅 UI와 구성도 연결 데이터

UTF-8의 유효한 JSON으로 만들어줘. 주석이나 trailing comma는 넣지 않는다.

최상위 구조는 다음과 같이 맞춰줘.

```text
{
  "schema_version": "1.0",
  "project_id": "영문-프로젝트-id",
  "project_title": "프로젝트명",
  "coverage": {
    "status": "partial",
    "description": "실제로 확인한 대화와 자료 범위",
    "missing": []
  },
  "threads": [],
  "episodes": [],
  "assets": []
}
```

각 배열의 항목은 다음 기준을 따른다.

**threads — 실제 대화**

각 대화방 항목:

- id

- title

- source_description

- messages

각 messages 항목:

- id: 프로젝트 안에서 중복되지 않는 발화 ID

- sequence: 대화방 안의 실제 발화 순서

- role: user 또는 assistant

- timestamp: 확인 가능한 시각, 없으면 null

- content_type: verbatim / excerpt / summary

- content_markdown: 발화 내용

- source_locator: 원래 대화·메시지·문서 위치에 대한 확인 가능한 설명

- redacted: 마스킹 여부

- asset_ids: 연결되는 첨부 ID 배열

실제 플랫폼 메시지 ID가 없으면 자체 ID를 부여해도 된다. 자체 ID를 실제 플랫폼 ID처럼 표현하지 않는다.

**episodes — 교육 화면에 표시할 학습 단계**

각 항목:

- id

- order

- title

- goal

- map_nodes

- prerequisites

- message_refs: 해당 단계의 발화 ID를 읽을 순서대로 나열

- commentary_markdown: 실제 대화와 구분되는 교육 해설

- outcome_markdown: 결과와 확인 상태

- exercise_markdown: 따라 하기와 확인 방법

- asset_ids

map_nodes는 관련된 구성도 요소를 아래 값에서 선택한다. 여러 요소를 연결해도 되며, 이 프로젝트와 무관한 요소를 억지로 넣지 않는다.

- sap: SAP ERP

- export: 소스 추출

- git: GitHub·버전 관리

- knowledge: 업무 지식·MD

- codex: Codex·지침·스킬·업무 에이전트

- diag: DIAG·비교·검증

- maps: Obsidian·관계 문서

- feedback: 담당자 검토·피드백·회귀 사례

- agent: 원격 협업의 주 에이전트

- lookup: ERP 조회 MCP

- hub: 중앙 자문 MCP

- worker: 담당 워커

- expert: 전문 자문 에이전트

- telegram: Telegram 연결

- erp-api: REST·RFC 연계

- portal: 교육 포털 운영

**assets — 첨부와 산출물**

각 항목:

- id

- original_filename

- path: ZIP 내부 상대 경로, 미확보이면 null

- kind: image / code / document / archive / other

- description

- availability: included / unavailable

- version: 확인 가능한 버전, 없으면 null

- related_message_ids

같은 파일의 서로 다른 버전은 별개 항목으로 구분한다. 오류가 발생한 버전과 수정 완료 버전을 섞지 않는다.
