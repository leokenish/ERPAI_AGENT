# 에이전트간 협업

## 1. 왜 협업이 필요한가

인사의 시간외 정산은 재무의 회계 전표로 이어집니다. 따라서 “정산을 취소하면 회계에서는 무엇을 처리하나요?”라는 질문에 답하려면 HR과 FI 양쪽의 근거를 읽어야 합니다. 이 프로젝트도 ZHR5 정산과 ZFI 전표가 만나는 업무를 살펴보는 데서 시작했습니다.

각 담당자는 자기 업무의 자료와 변경 책임을 갖고 있습니다. 그러므로 모든 자료를 한 사람이 모으기보다 **필요한 질문을 담당 업무로 전달하고 근거가 있는 답변을 받는 방식**으로 협업 구조를 정합니다.

## 2. 어떤 방향이 맞지 않았는가

처음에는 ERP 상위 폴더에 여러 패키지를 모으고 보조 에이전트들이 나누어 조사하는 방식을 검토했습니다. 그러나 FI 담당자는 FI를, MM 담당자는 MM을 관리하며 다른 업무의 코드를 수정하지 않는다는 조건이 있었습니다. HR 담당자의 Mac에 ZFI를 복제하지 않는다는 조건도 함께 적용했습니다.

따라서 자료를 한곳에 모으는 대신 질문을 전달하는 방향으로 바꿨습니다. 공통 폴더의 요청서를 사람이 전달하는 방식도 검토했지만, 질문과 답변을 자동으로 주고받으려면 별도의 접수·배정 프로그램이 필요했습니다.

그 결과 **질문은 중앙에서 접수하고, 조사는 해당 자료를 관리하는 담당자의 환경에서 수행하는 구조**로 역할을 나눴습니다.

## 3. 어떻게 역할을 나눴는가

MCP는 AI가 사용하는 도구의 이름·입력·결과를 일정한 방식으로 주고받는 규약입니다. 여기서는 중앙 자문 프로그램이 질문을 접수하고 담당 업무로 배정하는 도구를 제공합니다.

| 역할 | 하는 일 | 자료 위치 |
|---|---|---|
| 질문하는 HR 에이전트 | 자기 소스에서 읽은 내용과 FI에 물을 질문 정리 | HR 담당자의 업무 폴더 |
| 중앙 자문 프로그램 | 요청 권한 확인, 질문 접수·배정, 상태와 답변 보관 | 중앙 서버의 작업 기록 |
| FI 자문 워커 | FI 질문을 가져와 담당 자료를 조사하고 답변 제출 | FI 담당자의 자문용 작업 사본 |

워커는 배정된 질문을 가져와 처리하는 실행 프로그램입니다. 자문용 작업 사본과 실행 환경을 별도로 두면 담당자의 편집 작업과 자문 처리를 분리할 수 있습니다.

09의 자문 MCP는 **다른 담당자의 지식과 코드**에 질문하는 구조입니다. 다음 10의 ERP 조회 MCP는 **ERP의 업무 데이터**를 읽는 연결입니다. 질문의 대상이 다르므로 도구의 역할도 나누어 구성합니다.

## 4. 무엇을 구현했는가

`erp-team-mcp-example 0.1.0`은 질문 전달을 연습하는 예제입니다. Node.js 중앙 서버, SQLite 작업 기록, MCP 도구와 모의 FI 워커로 구성합니다. Node.js는 실행 환경이고, SQLite는 질문과 답변을 파일에 저장하는 데이터베이스입니다.

| 예제 기능 | 역할 |
|---|---|
| `list_experts` | 질문할 담당 목록 조회 |
| `ask_expert` | 질문 접수와 접수번호 `job_id` 발급 |
| `get_answer` | 접수번호별 처리 상태와 답변 조회 |
| `parent_id` | 앞선 질문과 후속 질문 연결 |
| 워커의 `claim` | 담당 업무에 배정된 질문 수신 |
| `lease` · `heartbeat` | 작업 배정과 처리 중 상태 관리 |
| `complete` | 답변 또는 처리 결과 제출 |

질문과 답변은 다음 순서로 전달됩니다.

1. HR 에이전트가 FI 담당과 질문·맥락을 지정합니다.
2. 중앙 서버가 권한을 확인하고 `queued` 대기 상태로 저장합니다.
3. FI 워커가 질문을 가져가면 `running` 처리 상태로 바뀝니다.
4. 모의 워커가 `[MOCK]` 시험 답변을 반환합니다.
5. HR 에이전트는 `job_id`로 답변을 조회합니다. 결과가 등록되면 `done` 상태로 표시합니다.

후속 질문은 `ask_expert`의 `parent_id`에 앞선 접수번호를 넣어 연결합니다. 이렇게 하면 새 질문과 이전 자문의 관계를 중앙 작업 기록에서 함께 읽을 수 있습니다.

## 5. 직접 해보기

[중앙 MCP 예제 ZIP](downloads/ERP_MCP_NodeJS_Example.zip)을 별도 폴더에 풉니다. Node.js 24 이상을 준비하고 예제 폴더의 터미널에서 다음 명령을 실행합니다.

```bash
npm ci
npm test
```

예제의 통합 테스트는 요청·배정·답변·접근 차단·후속 맥락·배정 만료를 다룹니다. 먼저 이 시험으로 각 구성 요소가 질문을 주고받는 순서를 살펴봅니다.

수동 실습은 ZIP의 README를 따라 진행합니다.

1. 질문자와 워커에 서로 다른 시험용 토큰을 준비합니다. 토큰은 질문자의 권한과 워커의 담당 업무를 구분하는 값입니다.
2. 첫 터미널에서 토큰을 설정하고 `npm start`로 중앙 서버를 시작합니다. 기본 주소는 `127.0.0.1:3000`입니다.
3. 두 번째 터미널에서 같은 폴더를 열고 `HUB_URL`과 워커 토큰을 설정한 뒤 `npm run worker:mock`을 실행합니다.
4. 사용하는 앱의 MCP 설정에 중앙 주소와 질문자 인증값을 등록합니다. 앱이 읽는 설정 위치에 인증값을 넣습니다.
5. 허용된 담당에게 질문을 접수하고 같은 `job_id`로 답변을 조회합니다.

모의 워커는 다음 시험 답변을 반환합니다.

```text
[MOCK] FI 워커까지 질문 전달 성공.
```

`127.0.0.1`은 프로그램을 실행하는 컴퓨터 자신을 가리킵니다. 따라서 다른 Mac에서 접속하는 실습은 사내에서 접근할 수 있는 중앙 서버의 HTTPS 주소와 인증값을 사용합니다.

## 6. 협업 운영의 구성 기준

담당자별 자문은 읽을 자료와 버전을 명확히 지정하는 방식으로 설계합니다. 자문용 작업 사본을 정하고 답변에 근거 파일과 커밋을 연결하면, 질문자도 답변이 어떤 자료에서 나왔는지 따라갈 수 있습니다.

또한 담당 컴퓨터의 전원과 네트워크 상태가 질문 처리에 영향을 줍니다. 따라서 시간 제한, 중단 후 재시작, 중복 요청과 재시도 규칙을 작업 상태와 함께 관리합니다.

구성 순서는 **질문 전달 예제 → 담당 자료의 읽기 전용 조사 → 근거 검토 → 다른 컴퓨터와의 통신 → 중단·복구 시험**으로 잡습니다. 실제 직원·전표의 값을 읽는 기능은 [10. ERP 데이터 연동](#/learn/erp-mcp)에서 별도로 다룹니다.
