# 에이전트간 협업(계획 중)

## 1. 왜 협업이 필요한가: 내 업무의 끝이 다른 업무의 시작입니다

인사의 시간외 정산은 재무의 회계 전표와 연결됩니다. “정산을 취소하면 회계 쪽에서는 무엇을 해야 하나요?”라는 질문에 답하려면 HR 소스만으로는 부족할 수 있습니다. 실제 프로젝트도 ZHR5 정산과 ZFI 전표의 접점을 이해하려는 문제에서 시작했습니다.

각 담당자의 에이전트가 자기 업무를 잘 알더라도 다른 업무의 내부 처리를 저절로 알지는 못합니다. 이 과정의 목표는 **자료와 수정 책임은 담당자에게 두고, 필요한 질문과 근거 답변을 주고받는 것**입니다. 현재는 이를 위한 모의 통신 예제까지 만들었으며 실제 AI 자문 연결은 계획 중입니다.

## 2. 어떤 방향이 맞지 않았는가: 모두의 소스를 한곳에 모으는 방식

처음에는 ERP 상위 폴더에 여러 패키지를 놓고 작은 보조 에이전트들이 나누어 조사하는 방식이 제안됐습니다. 그러나 사용자는 FI 담당자는 FI, MM 담당자는 MM을 다루며 다른 업무 코드를 수정하면 안 된다고 설명했습니다. HR 담당자의 Mac에는 ZFI를 Clone하지 않는다는 조건도 있었습니다.

보조 에이전트를 하나 더 만든다고 접근할 수 없는 FI 자료가 생기지는 않습니다. 공통 폴더에 요청서를 놓고 사람이 전달하는 방법도, 에이전트끼리 질문과 답변을 자동으로 주고받고 싶다는 목적과 달랐습니다.

이 제약을 확인한 뒤 **질문은 중앙에서 접수하고, 답은 해당 자료가 있는 담당자의 컴퓨터에서 조사하는 방향**으로 바뀌었습니다.

## 3. 어떻게 역할을 나눴는가: 질문·전달·조사

MCP는 AI가 사용할 도구의 이름·입력·결과를 일정한 방식으로 연결하는 규약입니다. 이 프로젝트의 중앙 MCP는 질문을 접수하고 배정하는 프로그램입니다. 중앙 컴퓨터에 Codex 앱을 설치하는 것만으로 그 전달 기능이 만들어지지는 않습니다.

| 역할 | 하는 일 | 자료를 두는 곳 |
|---|---|---|
| 질문하는 HR 에이전트 | 자기 소스에서 확인한 내용과 FI에 물을 질문 정리 | HR 담당자의 업무 폴더 |
| 중앙 자문 프로그램 | 허용된 상대인지 확인, 질문 접수·배정, 상태와 답변 보관 | 중앙 서버의 작업 기록 |
| FI 자문 워커 | FI 질문을 가져와 자기 자료를 조사하고 근거 답변 제출 | FI 담당자의 별도 자문용 작업 사본 |

워커는 질문을 가져와 처리하는 실행 프로그램을 뜻합니다. 사람이 편집 중인 Desktop 대화창을 원격으로 조종하는 방식으로 잡지 않았습니다. 별도 자문 실행과 읽기 범위를 정해야 작업 중인 파일과 섞이지 않습니다.

09의 자문 MCP가 묻는 대상은 **다른 담당자의 지식과 코드**입니다. 다음 10의 ERP 조회 MCP는 **ERP에 저장된 실제 업무 데이터**를 읽는 연결이므로 목적이 다릅니다.

## 4. 무엇을 구현했는가: 질문이 왕복하는 모의 예제

`erp-team-mcp-example 0.1.0`에는 Node.js 중앙 서버, SQLite 작업 기록, MCP 도구, 모의 FI 워커가 들어 있습니다. Node.js는 이 프로그램을 실행하는 환경이고, SQLite는 접수한 질문과 답변을 저장하는 파일 기반 데이터베이스입니다. 정적 교육 포털과는 별도 프로젝트입니다.

| 실제 기능 | 쉬운 설명 |
|---|---|
| `list_experts` | 질문할 수 있는 담당 목록 확인 |
| `ask_expert` | 질문을 접수하고 접수번호 `job_id` 받기 |
| `get_answer` | 접수번호로 상태와 답변 확인 |
| `parent_id` | 앞선 접수번호를 지정해 이어서 질문 |
| 워커의 `claim` | 자신에게 허용된 담당 업무의 질문 가져오기 |
| `lease` · `heartbeat` | 배정된 작업임을 확인하고 아직 처리 중임을 알리기 |
| `complete` | 답변 또는 실패 사유를 중앙에 제출 |

처리 흐름은 다음과 같습니다.

1. HR 에이전트가 FI 담당과 질문·맥락을 지정합니다.
2. 중앙이 요청자와 허용 담당을 확인해 `queued`, 즉 대기 상태로 저장합니다.
3. FI 워커가 가져가면 `running`, 즉 처리 중이 됩니다.
4. 현재 모의 워커는 실제 소스를 읽지 않고 정해진 `[MOCK]` 답변을 반환합니다.
5. HR은 접수번호로 답변을 받습니다. `done`은 결과 등록 완료이며 회계 판단의 정답 판정은 아닙니다.

후속 질문에는 별도의 `follow_up` 도구 대신 `ask_expert`의 `parent_id`를 씁니다. 예제는 선행 자문의 일부를 전달하며, 담당자의 Desktop 전체 대화 이력을 공유하거나 기존 AI 대화를 그대로 재개하는 기능은 구현하지 않았습니다.

## 5. 직접 해보기: 실제 AI 연결 전에 질문 전달부터 확인하기

[중앙 MCP 예제 ZIP](downloads/ERP_MCP_NodeJS_Example.zip)을 별도 폴더에 풉니다. Node.js 24 이상과 패키지 설치가 필요합니다. 아래 명령은 예제 폴더의 터미널에서 실행하며, 교육 포털 폴더에서 실행하지 않습니다.

```bash
npm ci
npm test
```

원천에는 한 개의 통합 테스트 안에서 요청·배정·답변·접근 차단·후속 문맥·배정 만료를 확인한 기록이 있습니다. 이는 실제 AI가 FI 업무를 분석했다는 시험 결과가 아닙니다.

수동으로 흐름을 확인하려면 ZIP 안 README 순서대로 진행합니다.

1. 질문자와 워커에 서로 다른 시험용 토큰을 준비합니다. 토큰은 누가 질문하고 어느 담당으로 일하는지 확인하는 값입니다.
2. 첫 터미널에서 토큰을 설정하고 `npm start`로 중앙 서버를 시작합니다. 기본 주소는 같은 PC에서만 쓰는 `127.0.0.1:3000`입니다.
3. 두 번째 터미널에서 같은 폴더를 열고 `HUB_URL`과 워커 토큰을 설정한 뒤 `npm run worker:mock`을 실행합니다.
4. 사용 중인 앱의 MCP 설정에 README의 중앙 주소와 질문자 인증값을 연결합니다. 터미널의 환경 변수가 이미 열린 앱에 자동 전달되지는 않으므로 앱이 실제로 읽는지 확인합니다.
5. 허용된 담당에게 질문을 접수하고 같은 `job_id`로 답변을 조회합니다.

받아야 할 답변은 다음과 같은 모의 문장입니다.

```text
[MOCK] FI 워커까지 질문 전달 성공. 실제 ERP 소스 분석 결과가 아닙니다.
```

다른 Mac에서 시험할 때 `127.0.0.1`은 중앙 서버 주소가 아닙니다. 사내에서 접근할 실제 HTTPS 주소와 인증 구성을 먼저 준비해야 합니다. 위 결과를 얻었다면 질문 전달 경로를 확인한 것이며, 다음 단계가 실제 AI 조사 연결입니다.

## 6. 한계와 다음 방향: 전달 성공 다음에는 답변의 근거가 필요합니다

현재 실제 FI AI 워커는 미구현입니다. 모의 응답 부분을 별도의 읽기 전용 조사 실행으로 바꾸고, 답변에 근거 파일·확인한 커밋·미확인 사항을 포함해야 합니다. 자문용 작업 사본의 버전을 정하지 않으면 사람의 편집 중간 상태를 읽을 수 있습니다.

담당 Mac이 꺼지거나 잠들면 답변이 늦거나 실패할 수 있습니다. 시간 제한, 중단, 재시작, 중복 요청과 재시도 정책을 정해야 합니다. 예제의 최근 연결 표시도 앞으로 답을 끝까지 줄 수 있다는 보장은 아닙니다.

다음 검증은 **한 질문의 모의 왕복 → 한 담당자의 실제 읽기 전용 분석 → 근거 검토 → 다른 Mac에서 통신 → 중단·복구 시험** 순서로 진행합니다. 실제 직원·전표의 현재 값을 확인해야 한다면 [10. ERP 데이터 연동](#/learn/erp-mcp)을 별도로 연결합니다.
