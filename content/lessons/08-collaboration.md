# 에이전트간 협업(계획 중)

## 1. 왜 협업이 필요한가: 내 업무의 끝이 다른 업무의 시작이다

인사의 시간외 정산은 재무의 회계 전표로 이어진다. “정산을 취소하면 회계 쪽에서는 무엇을 해야 하나요?”라는 질문에는 HR 소스만으로 답하기 어려울 수 있다. 실제 프로젝트도 ZHR5 정산과 ZFI 전표가 만나는 지점을 이해하려는 데서 시작했다.

자기 업무를 잘 아는 에이전트라도 다른 업무의 내부 처리까지 저절로 알 수는 없다. 이 과정의 목표는 **자료와 수정 책임은 담당자에게 두고, 필요한 질문과 근거 답변을 주고받는 것**이다. 현재는 질문을 주고받는 모의 통신 예제까지 만들었다. 실제 AI 자문 연결은 계획 중이다.

## 2. 어떤 방향이 맞지 않았는가: 모두의 소스를 한곳에 모으는 방식

처음 제안은 ERP 상위 폴더에 여러 패키지를 모으고, 작은 보조 에이전트들이 나눠 조사하는 방식이었다. 하지만 사용자는 FI 담당자는 FI, MM 담당자는 MM을 맡으며 다른 업무의 코드를 수정하면 안 된다고 설명했다. HR 담당자의 Mac에는 ZFI를 Clone하지 않는다는 조건도 있었다.

보조 에이전트를 늘려도 접근할 수 없던 FI 자료가 새로 생기지는 않는다. 공통 폴더에 요청서를 두고 사람이 전달하는 방법도 검토했지만, 에이전트끼리 질문과 답변을 자동으로 주고받으려는 목적에는 맞지 않았다.

이 조건을 확인한 뒤 방향을 바꿨다. **질문은 중앙에서 접수하고, 답은 해당 자료가 있는 담당자의 컴퓨터에서 조사하는 방식**이다.

## 3. 어떻게 역할을 나눴는가: 질문·전달·조사

MCP는 AI가 쓰는 도구의 이름·입력·결과를 일정한 방식으로 주고받게 하는 규약이다. 이 프로젝트의 중앙 MCP는 질문을 접수하고 담당자에게 배정하는 프로그램이다. 중앙 컴퓨터에 Codex 앱을 설치하는 것만으로는 이런 전달 기능이 생기지 않는다.

| 역할 | 하는 일 | 자료를 두는 곳 |
|---|---|---|
| 질문하는 HR 에이전트 | 자기 소스에서 확인한 내용과 FI에 물을 질문 정리 | HR 담당자의 업무 폴더 |
| 중앙 자문 프로그램 | 허용된 상대인지 확인, 질문 접수·배정, 상태와 답변 보관 | 중앙 서버의 작업 기록 |
| FI 자문 워커 | FI 질문을 가져와 자기 자료를 조사하고 근거 답변 제출 | FI 담당자의 별도 자문용 작업 사본 |

워커는 질문을 가져와 처리하는 실행 프로그램이다. 사람이 편집 중인 Desktop 대화창을 원격 조종하는 방식으로 설계하지 않았다. 자문 실행을 별도로 두고 읽을 범위를 정해야 담당자가 작업 중인 파일과 섞이지 않는다.

09의 자문 MCP가 묻는 대상은 **다른 담당자의 지식과 코드**이다. 다음 10의 ERP 조회 MCP는 **ERP에 저장된 실제 업무 데이터**를 읽는 연결이므로 목적이 다르다.

## 4. 무엇을 구현했는가: 질문이 왕복하는 모의 예제

`erp-team-mcp-example 0.1.0`은 Node.js 중앙 서버, SQLite 작업 기록, MCP 도구, 모의 FI 워커로 구성돼 있다. Node.js는 프로그램 실행 환경이고, SQLite는 접수한 질문과 답변을 파일에 저장하는 데이터베이스다. 이 예제는 정적 교육 포털과 별도의 프로젝트다.

| 실제 기능 | 쉬운 설명 |
|---|---|
| `list_experts` | 질문할 수 있는 담당 목록 확인 |
| `ask_expert` | 질문을 접수하고 접수번호 `job_id` 받기 |
| `get_answer` | 접수번호로 상태와 답변 확인 |
| `parent_id` | 앞선 접수번호를 지정해 이어서 질문 |
| 워커의 `claim` | 자신에게 허용된 담당 업무의 질문 가져오기 |
| `lease` · `heartbeat` | 배정된 작업임을 확인하고 아직 처리 중임을 알리기 |
| `complete` | 답변 또는 실패 사유를 중앙에 제출 |

질문은 다음 순서로 전달되고 답변으로 돌아온다.

1. HR 에이전트가 FI 담당과 질문·맥락을 지정한다.
2. 중앙이 요청자와 허용 담당을 확인해 `queued`, 즉 대기 상태로 저장한다.
3. FI 워커가 가져가면 `running`, 즉 처리 중이 된다.
4. 현재 모의 워커는 실제 소스를 읽지 않고 정해진 `[MOCK]` 답변을 반환한다.
5. HR은 접수번호로 답변을 받는다. `done`은 결과 등록 완료이며 회계 판단의 정답 판정은 아니다.

후속 질문에는 별도의 `follow_up` 도구를 쓰지 않고, `ask_expert`의 `parent_id`로 앞선 질문을 연결한다. 예제에서는 앞선 자문의 일부만 전달한다. 담당자의 Desktop 전체 대화 이력을 공유하거나 기존 AI 대화를 그대로 이어가는 기능은 구현하지 않았다.

## 5. 직접 해보기: 실제 AI 연결 전에 질문 전달부터 확인하기

[중앙 MCP 예제 ZIP](downloads/ERP_MCP_NodeJS_Example.zip)을 별도 폴더에 푼다. Node.js 24 이상과 패키지 설치가 필요하다. 아래 명령은 예제 폴더의 터미널에서 실행하며, 교육 포털 폴더에서 실행하지 않는다.

```bash
npm ci
npm test
```

원천에는 통합 테스트 한 개로 요청·배정·답변·접근 차단·후속 문맥·배정 만료를 확인한 기록이 있다. 확인한 것은 통신과 처리 흐름이며, 실제 AI가 FI 업무를 분석한 시험 결과는 아니다.

수동으로 흐름을 확인하려면 ZIP 안 README 순서대로 진행한다.

1. 질문자와 워커에 서로 다른 시험용 토큰을 준비한다. 토큰은 누가 질문하고 어느 담당으로 일하는지 확인하는 값이다.
2. 첫 터미널에서 토큰을 설정하고 `npm start`로 중앙 서버를 시작한다. 기본 주소는 같은 PC에서만 쓰는 `127.0.0.1:3000`이다.
3. 두 번째 터미널에서 같은 폴더를 열고 `HUB_URL`과 워커 토큰을 설정한 뒤 `npm run worker:mock`을 실행한다.
4. 사용 중인 앱의 MCP 설정에 README의 중앙 주소와 질문자 인증값을 연결한다. 터미널의 환경 변수가 이미 열린 앱에 자동 전달되지는 않으므로 앱이 실제로 읽는지 확인한다.
5. 허용된 담당에게 질문을 접수하고 같은 `job_id`로 답변을 조회한다.

받아야 할 답변은 다음과 같은 모의 문장이다.

```text
[MOCK] FI 워커까지 질문 전달 성공. 실제 ERP 소스 분석 결과가 아닙니다.
```

다른 Mac에서 시험한다면 `127.0.0.1`로 중앙 서버에 접속할 수 없다. 사내에서 접근할 수 있는 실제 HTTPS 주소와 인증 구성을 먼저 준비해야 한다. 위 모의 답변을 받았다면 질문 전달 경로를 확인한 것이다. 실제 AI 조사를 연결하는 일은 그다음 단계다.

## 6. 한계와 다음 방향: 전달 성공 다음에는 답변의 근거가 필요한다

실제 FI AI 워커는 아직 구현하지 않았다. 모의 응답 부분을 별도의 읽기 전용 조사 실행으로 바꾸고, 답변에는 근거 파일·확인한 커밋·미확인 사항을 담아야 한다. 자문용 작업 사본의 버전도 정해야 한다. 그렇지 않으면 담당자가 편집 중인 내용을 읽을 수 있다.

담당 Mac이 꺼지거나 잠들면 답변이 늦어지거나 실패할 수 있다. 시간 제한과 중단·재시작 처리, 중복 요청과 재시도 정책이 필요하다. 최근에 연결됐다는 예제의 표시만으로 요청을 끝까지 처리할 수 있다고 보장할 수는 없다.

다음 검증은 **한 질문의 모의 왕복 → 한 담당자의 실제 읽기 전용 분석 → 근거 검토 → 다른 Mac에서 통신 → 중단·복구 시험** 순서로 진행한다. 실제 직원·전표의 현재 값을 확인해야 한다면 [10. ERP 데이터 연동](#/learn/erp-mcp)을 별도로 연결한다.
