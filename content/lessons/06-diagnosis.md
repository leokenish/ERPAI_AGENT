# 코드 검증 및 적용

## 1. 왜 검증 도구가 필요했는가: 내가 고친 동안 서버도 바뀔 수 있다

AI가 수정 파일을 만들었다면 다음에는 “이 파일을 ERP에 적용해도 되는가”를 판단해야 한다. 로컬에서 보기 좋게 바뀌었다는 것만으로는 충분하지 않다. 그동안 다른 담당자가 같은 SAP 객체를 수정했을 수 있고, 현재 시스템에서 지원하지 않는 문법이 들어갔을 수도 있다.

처음에는 Export와 Import 두 프로그램으로 추출부터 반영까지 처리하려 했다. 하지만 SAP에 반영하려면 파일 복사뿐 아니라 객체 잠금, 비활성본, 활성화, 변경 이관까지 고려해야 한다. 그래서 먼저 **어떤 변경이 생겼는지 읽고 비교하는 DIAG**를 만들기로 했다. DIAG는 진단 결과를 표와 상세 화면으로 보여 주는 SAP 프로그램이다.

## 2. 무엇을 겪었는가: “다르다”와 “적용해도 된다” 사이의 간격

비교 기능에도 해결할 문제가 많았다. XML의 하위 값 하나를 바꿨는데 상위 구조 전체가 수정된 것처럼 보였다. 함수 API로 읽은 내용과 활성 Include의 내용이 다르거나, 검사하지 않은 항목이 통과한 것처럼 읽히기도 했다. 이런 경험을 바탕으로 결과표를 개선했다. 성공·실패만 표시하지 않고 **비교, 현재 SAP 조회, 활성본 근거, 문법 검사**를 나눠 보여 주도록 했다.

후속 ERP 웹 개편에서는 반영 기능이 필요해졌다. 기존 MIME을 선택해 저장·재조회하고, BSP Layout을 저장한 뒤 선택한 페이지를 활성화하려는 요구였다. 사용자 승인에 따라 이 범위를 추가했다. ABAP·DDIC까지 모두 가져오는 범용 Import로 확장한 것은 아니다.

BSP 처리에서는 `.htm` 파일의 첫 줄만 보고 XML 선언행 문제라고 판단했다. 그러나 그에 맞춘 수정으로는 문제가 해결되지 않았다. 원본과 수정본을 확보한 뒤에야 내용이 SO2 XML임을 확인했고, 서버 구문을 보존하면서 편집용 Layout으로 변환하도록 고쳤다. **확장자나 오류 한 줄에 기대기보다 실제 파일 형식을 먼저 확인해야 했다.**

## 3. 어떤 기준을 정했는가: 세 자료와 네 확인 단계를 나누기

여기서 원본은 추출 당시 보존한 baseline을 뜻한다. 추출본은 현재 ZIP 안의 작업 파일이고, SAP는 진단 시점에 읽은 서버 내용이다. 이 세 자료를 두 개씩 비교하면 내가 바꾼 부분과 서버에서 바뀐 부분을 구분할 수 있다.

| 화면의 비교 열 | 기준과 대상 | 답할 수 있는 질문 |
|---|---|---|
| 추출본 / 원본 | 원본을 기준으로 작업 파일 비교 | 내가 무엇을 바꿨는가 |
| SAP / 원본 | 원본을 기준으로 현재 SAP 비교 | 추출 이후 서버가 바뀌었는가 |
| 추출본 / SAP | 현재 SAP를 기준으로 작업 파일 비교 | 지금 적용 후보와 서버의 차이는 무엇인가 |

원본과 추출본이 같은데 SAP만 다르다면 로컬 파일이 오래된 상태다. 원본과 SAP가 같고 추출본만 다르다면 내가 만든 변경 후보로 볼 수 있다. 셋이 모두 다르면 양쪽 변경을 읽고 병합해야 한다. 하나라도 읽지 못했다면 비교 근거가 부족하다. 내용이 빈 파일도 존재하는 파일이다. 읽기에 실패한 경우와 파일이 실제로 없는 경우는 구분한다.

확인은 **내용 비교 → 문법·형식 등 지원 검사 → 저장·활성화 결과 → 실제 업무 동작** 순서로 나눈다. 앞 단계를 통과해도 뒤 단계가 성공했다고 볼 수는 없다.

## 4. 어떻게 처리하는가: 진단부터 선택 반영까지

### 4-1. 도구가 읽고 보여 주는 것

1. 대상 패키지 또는 BSP 앱과 검토 ZIP을 지정한다.
2. ZIP의 경로·중복·크기와 manifest·원본의 대응을 확인한다.
3. 같은 범위의 현재 SAP 자료를 읽어 추출본과 같은 기준으로 비교한다.
4. 세 방향 차이와 SAP 조회·활성 버전 근거·문법형식 검증 결과를 나눠 계산한다.
5. ALV라는 SAP 표 화면에서 목록을 보고, 행을 열어 세 자료의 줄 차이를 확인한다. JSON 결과는 표시 길이 제한을 넘어 상세 내용을 검토할 때 사용한다.

파일 전체 바이트를 비교하므로 크기가 같아도 내용은 다를 수 있다. 화면에 ‘누락’으로 표시되면 어느 쪽을 기준으로 한 결과인지 확인해야 한다. 추출본에 없다는 표시가 SAP에서도 삭제하라는 뜻은 아니다.

### 4-2. 무엇을 반영할 수 있는가

최신 확보 소스는 **DIAG 0.7.1 / Export 0.4.1**이다. 반영 기능의 대상은 조건을 만족하는 기존 MIME·BSP Layout이다. MIME은 저장한 뒤 다시 조회하고, BSP Layout은 저장과 선택 페이지 활성화를 나눠 처리한다. ABAP·DDIC와 BSP의 다른 탭은 진단 자료로 다룬다.

반영 후보는 객체 대응, 원본, 현재 서버 변경, 선택 범위를 확인해야 한다. baseline이나 manifest를 수정해 판정을 통과시키지 않는다. 지원되지 않거나 현재 내용을 확인하지 못한 대상은 먼저 근거를 보완한다.

| 단계 | 실제로 확인할 것 |
|---|---|
| 저장 전 | 이 객체가 지원 대상인가, 서버 변경과 충돌하지 않는가 |
| 저장 | 이번에 새로 저장했는가, 기존 미활성본을 재사용했는가 |
| 활성화 | 선택 페이지가 활성화됐는가, 공통 정의나 다른 페이지 영향은 없는가 |
| 사후 조회 | 활성본을 다시 읽었을 때 기대한 내용과 같은가 |
| 업무 확인 | 브라우저에서 화면·입력·권한·데이터가 의도대로 동작하는가 |

미활성본은 저장은 됐지만 실행에 쓰이는 활성 버전으로 전환되기 전의 내용이다. CTS는 SAP의 변경을 다른 시스템으로 옮길 때 사용하는 관리 체계다. 로컬에서 Commit하거나 파일을 저장했다고 이 단계들까지 자동으로 끝나는 것은 아니다.

> **읽고 판단하기** · 이 사례의 결론은 “현재 추출본과 SAP가 다르다”입니다. 어떤 버전이 업무적으로 맞는지, SAP의 추가 줄을 반영할지는 변경 이유와 담당자 검토를 통해 판단합니다.

### 5-2. 같은 크기·검사 미수행·활성 확인 실패 읽기

2026-10-07 업로드된 `RawData` 2,541행의 재집계이다. 실제 실행 버전과 날짜는 미확인이다.

[실제 DIAG 결과 엑셀 다운로드](downloads/ZHR5_result_uploaded_20261007.xlsx)에서 각 행의 비교·검사 결과를 직접 확인해 본다.

- **1440행:** 크기는 모두 3,210 bytes, 내용은 SAP 대비 수정이다. 변경 필드 확인에는 원문 XML이 필요하다.
- **828행:** 세 비교는 변경없음, API 소스와 활성 Include 대조는 불일치이다. 실제 활성 상태는 추가 확인한다.
- **활성 확인 실패 71건:** 함수 API 70건 + DDIC 진단 1건.
- **검사 미수행 10파일:** SAP에 새로 있고 추출본에는 없는 파일이다.

### 5-3. 확인된 반영 사례: DIAG 0.6.11의 BSP 페이지

![DIAG 0.6.11 · 기존 I 버전 재사용, 페이지 활성화와 사후 검증 화면. 최신 0.7.1 시험 화면이 아니다.](assets/conversations/kbs-erp-export-diag-agents/export-diag-progress-asset-016.png)

사용자는 기존 미활성 I 버전을 재사용해 해당 페이지를 활성화했다. 이후 사후 검증과 SE80에서도 제대로 반영됐다고 확인했다. `REUSED_VERIFIED`는 이미 있던 내용을 확인한 뒤 재사용했다는 뜻이다. 이번 실행에서 새로 저장했다는 의미는 아니다.

이 사례에서 확인한 범위는 해당 페이지의 재사용·활성화·사후 조회다. 새 내용을 처음 저장하는 모든 경로, 전체 MIME, 원복, 실제 브라우저 업무 결과까지 검증한 것은 아니다. 최신 0.7.1의 성공 여부도 이 사례만으로 확인할 수 없다.

### 5-4. 먼저 읽기 전용으로 한 번 비교한다

처음에는 새로 추출한 파일을 수정하지 않은 채 비교한다. 원본과 작업본이 어떻게 대응하는지, 현재 SAP와 어떤 차이가 있는지 먼저 읽는다. 그다음 승인된 작은 변경 한 건을 넣어 결과가 어떻게 달라지는지 살펴본다. 저장·활성화는 개발 환경의 담당자가 지원 범위와 검증 계획을 정한 뒤 진행한다.

SAP 없이 비교 개념을 연습하려면 [비교 실습 스크립트](downloads/compare_cases.py)와 [입력 JSON](downloads/three_way_cases.json)을 같은 폴더에 저장해 실행한다. 이 예시는 파일 비교용이며 SAP를 실행하지 않는다.

```bash
python3 compare_cases.py
```

## 6. 한계와 다음 방향: 성공 표시의 범위를 끝까지 확인하기

BASIS 700에서 최신 문법·API를 쓸 수 있다고 가정한 것이 여러 차례 문제를 일으켰다. 0.4.4에는 날짜·시각 인수를 넘길 때 타입 오류가 있었고, 0.4.5에서 STRING 변환을 추가했다. 소스를 수정했다는 답변과 해당 시스템에서 다시 실행한 결과는 별도로 기록해야 한다.

![DIAG 0.4.4 날짜 인수 타입 오류. 당시 수정 이유를 보여 주는 과거 화면이다.](assets/images/diag-044-type-error.png)

다음에는 최신 0.7.1로 새 BSP 한 앱 ZIP을 비교한다. 작은 변경 하나를 대상으로 최초 저장·활성화·사후 조회·원복을 각각 확인하고, 실제 업무 화면의 입력과 결과도 살펴봐야 한다. 자동 반영 범위를 넓히려면 대상 객체별로 이런 확인 근거가 필요하다.

검증 결과가 업무적으로 틀렸다면 [07. 업무 스킬 및 회귀](#/learn/feedback)에 이유를 남겨 같은 판단을 반복하지 않게 한다. 다른 담당 업무의 근거가 필요한 경우는 [09. 에이전트간 협업(계획 중)](#/learn/collaboration)으로 이어진다.
