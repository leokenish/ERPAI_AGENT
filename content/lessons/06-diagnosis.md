# 코드 검증 및 적용

## 1. 왜 검증 도구가 필요했는가: 내가 고친 동안 서버도 바뀔 수 있습니다

AI가 수정 파일을 만들면 다음 질문은 “이 파일을 ERP에 적용해도 되는가”입니다. 로컬 파일이 보기 좋아졌다는 사실만으로 답할 수는 없습니다. 다른 담당자가 같은 SAP 객체를 고쳤을 수 있고, 현재 시스템에서는 사용하지 못하는 문법이 들어갔을 수도 있습니다.

초기에는 Export와 Import 두 프로그램으로 추출부터 반영까지 하려 했습니다. 그러나 SAP 반영은 파일 복사를 넘어 객체 잠금, 비활성본, 활성화, 변경 이관까지 관계됩니다. 그래서 먼저 **어떤 변경이 생겼는지 읽고 비교하는 DIAG**로 방향을 좁혔습니다. DIAG는 진단 결과를 표와 상세 화면으로 보여 주는 SAP 프로그램입니다.

## 2. 무엇을 겪었는가: “다르다”와 “적용해도 된다” 사이의 간격

비교만 해도 해결할 문제가 많았습니다. XML의 하위 값 하나가 바뀌었는데 상위 구조 전체가 수정된 것처럼 보이거나, 함수 API로 읽은 내용과 활성 Include의 내용이 다르거나, 검사하지 않은 항목이 통과처럼 읽히는 문제가 있었습니다. 결과표는 단순 성공·실패 대신 **비교, 현재 SAP 조회, 활성본 근거, 문법 검사**를 나누도록 발전했습니다.

후속 ERP 웹 개편에서는 기존 MIME을 선택해 저장·재조회하고, BSP Layout을 저장한 뒤 선택 페이지를 활성화하고 싶다는 요구가 생겼습니다. 사용자의 승인에 따라 그 범위를 추가했지만 ABAP·DDIC까지 모두 가져오는 범용 Import로 넓히지는 않았습니다.

BSP 처리에서는 `.htm` 파일의 첫 줄만 보고 XML 선언행 문제로 판단한 수정이 실제 문제를 해결하지 못했습니다. 원본과 수정본을 확보한 뒤에야 내용이 SO2 XML이라는 것을 확인했고, 서버 구문을 보존하며 편집용 Layout으로 변환하도록 고쳤습니다. **확장자나 오류 한 줄보다 실제 파일 형식이 근거가 되어야 했습니다.**

## 3. 어떤 기준을 정했는가: 세 자료와 네 확인 단계를 나누기

원본은 추출 당시 보존한 baseline, 추출본은 지금 ZIP의 작업 파일, SAP는 진단할 때 읽은 현재 서버 내용입니다. 세 자료를 두 개씩 비교하면 내 변경과 서버 변경을 나눌 수 있습니다.

| 화면의 비교 열 | 기준과 대상 | 답할 수 있는 질문 |
|---|---|---|
| 추출본 / 원본 | 원본을 기준으로 작업 파일 비교 | 내가 무엇을 바꿨는가 |
| SAP / 원본 | 원본을 기준으로 현재 SAP 비교 | 추출 이후 서버가 바뀌었는가 |
| 추출본 / SAP | 현재 SAP를 기준으로 작업 파일 비교 | 지금 적용 후보와 서버의 차이는 무엇인가 |

원본과 추출본이 같고 SAP만 다르다면, 로컬 파일이 오래된 것입니다. 원본과 SAP가 같고 추출본만 다르면 내 변경 후보입니다. 모두 다르면 양쪽 변경을 읽고 병합해야 합니다. 하나라도 읽지 못했다면 비교할 근거가 부족합니다. 빈 파일은 존재하는 파일이며, 읽기 실패와 실제 부재는 별개입니다.

그다음 확인도 나눕니다. **내용 비교 → 문법·형식 등 지원 검사 → 저장·활성화 결과 → 실제 업무 동작**입니다. 앞 단계를 통과했다고 뒤 단계까지 성공한 것은 아닙니다.

## 4. 어떻게 처리하는가: 진단부터 선택 반영까지

### 4-1. 도구가 읽고 보여 주는 것

1. 대상 패키지 또는 BSP 앱과 검토 ZIP을 지정합니다.
2. ZIP의 경로·중복·크기와 manifest·원본의 대응을 확인합니다.
3. 같은 범위의 현재 SAP 자료를 읽어 추출본과 같은 기준으로 비교합니다.
4. 세 방향 차이와 SAP 조회·활성 버전 근거·문법형식 검증 결과를 나눠 계산합니다.
5. ALV라는 SAP 표 화면에서 목록을 보고, 행을 열어 세 자료의 줄 차이를 확인합니다. JSON 결과는 표시 길이 제한을 넘어 상세 내용을 검토할 때 사용합니다.

전체 바이트 비교이므로 파일 크기가 같아도 내용은 다를 수 있습니다. 화면의 ‘누락’도 어느 쪽을 기준으로 읽는지 확인합니다. 추출본에 없다는 이유만으로 SAP에서 삭제하라는 지시는 아닙니다.

### 4-2. 무엇을 반영할 수 있는가

최신 확보 소스는 **DIAG 0.7.1 / Export 0.4.1**입니다. 현재 반영 기능은 조건을 만족하는 기존 MIME·BSP Layout을 대상으로 합니다. MIME은 저장 후 재조회하고, BSP Layout은 저장과 선택 페이지 활성화를 구분해 처리합니다. ABAP·DDIC와 BSP의 다른 탭은 진단 자료입니다.

반영 후보는 객체 대응, 원본, 현재 서버 변경, 선택 범위를 확인해야 합니다. baseline이나 manifest를 수정해 판정을 통과시키지 않습니다. 지원되지 않거나 현재 내용을 확인하지 못한 대상은 먼저 근거를 보완합니다.

| 단계 | 실제로 확인할 것 |
|---|---|
| 저장 전 | 이 객체가 지원 대상인가, 서버 변경과 충돌하지 않는가 |
| 저장 | 이번에 새로 저장했는가, 기존 미활성본을 재사용했는가 |
| 활성화 | 선택 페이지가 활성화됐는가, 공통 정의나 다른 페이지 영향은 없는가 |
| 사후 조회 | 활성본을 다시 읽었을 때 기대한 내용과 같은가 |
| 업무 확인 | 브라우저에서 화면·입력·권한·데이터가 의도대로 동작하는가 |

미활성본은 저장됐지만 아직 실행에 쓰이는 활성 버전으로 전환되지 않은 내용입니다. CTS는 SAP 변경을 다른 시스템으로 이관할 때 쓰는 관리 체계입니다. 로컬 Commit이나 파일 저장만으로 이 단계들이 자동 완료되지는 않습니다.

### 5-2. 같은 크기·검사 미수행·활성 확인 실패 읽기

2026-10-07 업로드된 `RawData` 2,541행의 재집계입니다. 실제 실행 버전과 날짜는 미확인입니다.

[실제 DIAG 결과 엑셀 다운로드](downloads/ZHR5_result_uploaded_20261007.xlsx)에서 각 행의 비교·검사 결과를 직접 확인해 보세요.

- **1440행:** 크기는 모두 3,210 bytes, 내용은 SAP 대비 수정입니다. 변경 필드 확인에는 원문 XML이 필요합니다.
- **828행:** 세 비교는 변경없음, API 소스와 활성 Include 대조는 불일치입니다. 실제 활성 상태는 추가 확인합니다.
- **활성 확인 실패 71건:** 함수 API 70건 + DDIC 진단 1건.
- **검사 미수행 10파일:** SAP에 새로 있고 추출본에는 없는 파일입니다.

### 5-3. 확인된 반영 사례: DIAG 0.6.11의 BSP 페이지

![DIAG 0.6.11 · 기존 I 버전 재사용, 페이지 활성화와 사후 검증 화면. 최신 0.7.1 시험 화면이 아닙니다.](assets/conversations/kbs-erp-export-diag-agents/export-diag-progress-asset-016.png)

사용자는 기존 미활성 I 버전을 재사용하고 해당 페이지를 활성화한 뒤, 사후 검증과 SE80에서도 제대로 반영됐다고 확인했습니다. `REUSED_VERIFIED`는 기존 내용을 확인해 재사용했다는 뜻으로, 이번 실행에서 새로 저장했다는 뜻은 아닙니다.

이 사례로 확인한 범위는 해당 페이지의 재사용·활성화·사후 조회입니다. 처음부터 새 내용을 저장하는 모든 경로, 전체 MIME, 원복, 실제 브라우저 업무 결과, 최신 0.7.1의 성공까지 확인한 것은 아닙니다.

### 5-4. 먼저 읽기 전용으로 한 번 비교합니다

처음에는 수정하지 않은 새 추출본으로 비교해 원본·작업본의 대응과 현재 SAP 차이를 읽습니다. 이어 승인된 작은 변경 한 건으로 결과가 어떻게 달라지는지 봅니다. 저장·활성화는 개발 환경의 담당자가 지원 범위와 검증 계획을 정한 뒤 진행합니다.

SAP 없이 비교 개념을 연습하려면 [비교 실습 스크립트](downloads/compare_cases.py)와 [입력 JSON](downloads/three_way_cases.json)을 같은 폴더에 저장해 실행합니다. 이 예시는 파일 비교용이며 SAP를 실행하지 않습니다.

```bash
python3 compare_cases.py
```

## 6. 한계와 다음 방향: 성공 표시의 범위를 끝까지 확인하기

BASIS 700에서는 최신 문법·API가 있다는 가정이 반복해서 문제를 만들었습니다. 0.4.4에서는 날짜·시각 인수를 넘기는 타입 오류가 있었고, 0.4.5에서 STRING 변환을 추가했습니다. 소스가 수정됐다는 답변과 해당 시스템에서 재실행한 결과는 나눠 기록해야 합니다.

![DIAG 0.4.4 날짜 인수 타입 오류. 당시 수정 이유를 보여 주는 과거 화면입니다.](assets/images/diag-044-type-error.png)

다음 검증은 최신 0.7.1에서 새 BSP 한 앱 ZIP을 비교하고, 작은 변경의 최초 저장·활성화·사후 조회·원복을 각각 확인하는 것입니다. 그 후 실제 업무 화면의 입력과 결과를 확인합니다. 자동 반영 범위를 넓히려면 대상 객체마다 이런 근거가 쌓여야 합니다.

검증 결과가 업무적으로 틀렸다면 [07. 업무 스킬 및 회귀](#/learn/feedback)에 이유를 남겨 같은 판단을 반복하지 않게 합니다. 다른 담당 업무의 근거가 필요한 경우는 [09. 에이전트간 협업(계획 중)](#/learn/collaboration)으로 이어집니다.
