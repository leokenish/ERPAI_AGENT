# 코드 검증 및 적용

## 1. 왜 검증 도구가 필요했는가

AI가 만든 수정 파일을 ERP에 적용하려면 현재 서버와의 차이부터 살펴봐야 합니다. 로컬에서 작업하는 동안 다른 담당자가 같은 SAP 객체를 수정했을 수 있기 때문입니다. 또한 파일에 포함된 문법과 형식을 현재 SAP 환경에서 사용할 수 있는지도 검토합니다.

처음에는 Export와 Import 두 프로그램으로 추출부터 반영까지 처리하려 했습니다. 그러나 SAP 반영에는 파일 복사 외에도 객체 잠금, 비활성본, 활성화, 변경 이관이 연결됩니다. 따라서 먼저 **변경 내용을 읽고 비교하는 DIAG**를 만들었습니다. DIAG는 진단 결과를 SAP 표 화면과 상세 비교 화면으로 보여 주는 프로그램입니다.

## 2. 무엇을 겪었는가

XML의 하위 값 하나만 바꿨는데 상위 구조 전체가 수정된 것처럼 표시되는 문제가 있었습니다. 또한 함수 API로 읽은 내용과 활성 Include가 서로 달라, 파일 차이와 활성 상태를 한 결과로 판단하기 어려웠습니다.

따라서 결과표에서 **파일 비교, 현재 SAP 조회, 활성본 근거, 문법 검사**를 나누었습니다. 각 열을 따로 읽으면 무엇이 달라졌는지와 어느 검사를 수행했는지 구분할 수 있습니다.

ERP 웹 개편에서는 비교한 변경을 화면에 반영할 기능도 필요해졌습니다. 이에 따라 기존 MIME의 선택 저장·재조회와 BSP Layout의 저장·선택 페이지 활성화를 추가했습니다. 반영 대상을 웹자산으로 좁혀 해당 객체의 저장 방식을 다뤘습니다.

BSP 처리 과정에서는 `.htm`이라는 확장자만으로 파일 형식을 판단해 수정 방향을 잘못 잡은 적도 있습니다. 실제 내용은 SO2 XML이었으므로, 서버 구문을 유지하면서 편집용 Layout으로 변환하도록 처리 방식을 고쳤습니다. 이 경험은 **실제 파일 형식을 먼저 읽고 수정 범위를 정하는 기준**으로 이어졌습니다.

## 3. 어떤 기준을 정했는가

원본은 추출 당시 보존한 baseline입니다. 추출본은 ZIP 안의 작업 파일이고, SAP는 진단 시점의 서버 내용입니다. 세 자료를 두 개씩 비교하면 로컬에서 바뀐 내용과 서버에서 바뀐 내용을 나누어 볼 수 있습니다.

| 화면의 비교 열 | 기준과 대상 | 알 수 있는 내용 |
|---|---|---|
| 추출본 / 원본 | 원본을 기준으로 작업 파일 비교 | 로컬에서 수정한 내용 |
| SAP / 원본 | 원본을 기준으로 현재 SAP 비교 | 추출 이후 서버에서 바뀐 내용 |
| 추출본 / SAP | 현재 SAP를 기준으로 작업 파일 비교 | 적용 후보와 현재 서버의 차이 |

원본과 추출본이 같은데 SAP만 다르면 로컬 파일이 서버보다 오래된 상태입니다. 반대로 원본과 SAP가 같고 추출본만 다르면 로컬의 변경 후보로 볼 수 있습니다. 셋이 모두 다르면 양쪽 변경을 읽고 병합합니다.

빈 파일, 읽기 실패, 실제 파일 부재도 서로 다른 상태로 다룹니다. 내용이 비어 있어도 존재하는 파일이기 때문입니다.

검토 절차는 **내용 비교 → 문법·형식 검사 → 저장·활성화 → 실제 업무 동작** 순서로 구성합니다. 단계별 결과를 나누면 문제가 발생한 위치를 찾아 다시 검토하기 쉽습니다.

## 4. 어떻게 처리하는가

### 4-1. 진단과 결과 조회

1. 대상 패키지 또는 BSP 앱과 검토 ZIP을 지정합니다.
2. ZIP의 경로·중복·크기와 manifest·원본의 대응을 확인합니다.
3. 같은 범위의 현재 SAP 자료를 읽어 추출본과 동일한 기준으로 비교합니다.
4. 세 방향 차이와 SAP 조회·활성 버전·문법형식 검사 결과를 나눠 계산합니다.
5. ALV 표에서 결과를 읽고 행을 열어 세 자료의 줄 차이를 살펴봅니다. 상세 JSON은 화면 표시 길이를 넘는 내용을 검토할 때 활용합니다.

비교는 파일 전체 바이트를 기준으로 합니다. 따라서 크기가 같아도 내용은 다를 수 있습니다. ‘누락’ 표시는 비교 방향과 함께 읽습니다. 예를 들어 추출본/SAP의 누락은 SAP에 있는 파일이 추출본에는 없다는 뜻입니다.

### 4-2. 웹자산 선택 반영

자료실의 **DIAG 0.7.1 / Export 0.4.1** 소스는 기존 MIME·BSP Layout을 대상으로 선택 반영을 다룹니다. MIME은 저장 후 재조회하고, BSP Layout은 저장과 선택 페이지 활성화를 나누어 처리합니다. ABAP·DDIC와 BSP의 다른 탭은 진단 자료로 사용합니다.

반영할 객체를 고를 때는 객체 대응, baseline, 현재 서버 변경, 선택 범위를 함께 대조합니다. baseline과 manifest는 비교 기준이므로 원래 내용대로 보존합니다.

| 단계 | 검토 항목 |
|---|---|
| 저장 전 | 지원 객체와 선택 범위, 현재 서버 변경과의 충돌 |
| 저장 | 새 저장 또는 기존 미활성본 재사용 여부 |
| 활성화 | 선택 페이지의 활성화와 공통 정의·다른 페이지의 영향 |
| 사후 조회 | 활성본 재조회 결과와 기대 내용의 일치 |
| 업무 동작 | 브라우저의 화면·입력·권한·데이터 처리 |

미활성본은 저장한 내용을 실행용 활성 버전으로 전환하기 전의 상태입니다. CTS는 SAP 변경을 다른 시스템으로 옮기는 관리 체계입니다. 따라서 로컬 파일 수정 이후에는 SAP의 저장·활성화·이관 절차를 차례대로 진행합니다.

## 5. 실제 사례와 따라 해보기

### 5-1. 서버 변경의 화면 비교

다음 두 화면은 **DEVHUB DIAG 0.4.5의 읽기 전용 진단 결과**입니다. 요약에서 차이를 찾고 상세 화면에서 실제 변경 줄을 읽는 순서로 살펴봅니다.

#### 요약 결과와 검사 범위

![DIAG 0.4.5 요약과 파일 목록. A는 파일 비교 합계이고 B는 변경 필터 적용 전 전체 SAP 검증 결과입니다.](assets/images/diag-045-summary.png)

| 화면 영역 | 표시 값 | 해석 |
|---|---|---|
| A · 추출본/원본 | 변경없음 8, 합계 8 | 추출본 8개가 기준 원본과 같습니다. |
| A · SAP/원본 | 신규 3, 수정 8, 합계 11 | 현재 SAP에 원본과 다른 내용이 있습니다. |
| A · 추출본/SAP | 누락 3, 수정 8, 합계 11 | SAP 기준으로 추출본에 없는 3개와 다른 8개가 표시됩니다. |
| B · SAP 검증 | 전체 2,541건, 변경 필터 적용 전 | A는 선택 범위이고 B는 전체 결과입니다. |
| 하단 목록 | SAP 조회·활성 버전·문법형식 검증 열 | 각 검사 결과를 별도로 읽습니다. |

#### 원본·추출본·SAP의 줄 차이

![ZHR_52TM_AWART_LIST의 세 자료 비교. 원본과 추출본은 같고 SAP에 추가된 줄은 초록 영역으로 표시됩니다.](assets/images/diag-045-three-way.png)

| 순서 | 화면에서 읽는 내용 |
|---|---|
| 1 · 비교 방향 | 추출본/원본은 변경없음, SAP/원본과 추출본/SAP는 수정입니다. |
| 2 · 바이트 | 원본과 추출본은 각각 16,719 bytes, SAP는 16,939 bytes입니다. |
| 3 · 초록 행 | SAP의 228–233행에만 내용이 있고 원본·추출본에는 `(없음)`으로 표시됩니다. |
| 4 · 생략 행 | 세 자료가 같은 221줄·273줄은 접어서 표시합니다. |
| 5 · 검사 결과 | 조회 성공·활성 버전 확인·문법 사전검사 통과를 각각 표시합니다. |

이 사례에서는 SAP 쪽에만 추가된 내용이 있습니다. 따라서 로컬 변경을 적용하기 전에 서버에서 해당 줄을 추가한 이유를 살펴보고 병합 여부를 판단합니다.

### 5-2. 파일 크기와 검사 결과의 차이

[DIAG 결과 엑셀](downloads/ZHR5_result_uploaded_20261007.xlsx)의 `RawData` 2,541행에서 비교 결과를 읽어볼 수 있습니다.

- **1440행:** 세 자료의 크기가 모두 3,210 bytes이지만 내용 비교에서는 SAP 대비 수정으로 표시됩니다.
- **828행:** 세 파일 비교는 변경없음이며, API 소스와 활성 Include의 대조 결과는 불일치입니다.
- **활성 확인 실패 71건:** 함수 API 70건과 DDIC 진단 1건으로 나뉩니다.
- **검사 미수행 10파일:** SAP에는 새로 존재하고 추출본에는 없는 파일입니다.

이 결과는 파일 크기, 내용 차이, 활성본 대조가 서로 다른 기준임을 보여 줍니다. 따라서 한 열의 표시만으로 전체 상태를 판단하지 않고 관련 열을 함께 읽습니다.

### 5-3. BSP 페이지 활성화 사례

![DIAG 0.6.11에서 기존 I 버전을 재사용하고 페이지를 활성화한 뒤 사후 검증한 화면입니다.](assets/conversations/kbs-erp-export-diag-agents/export-diag-progress-asset-016.png)

DIAG 0.6.11 사례에서는 기존 미활성 I 버전을 재사용해 해당 페이지를 활성화했습니다. 이후 사후 조회와 SE80에서 반영 결과를 확인했습니다. `REUSED_VERIFIED`는 기존 내용을 대조한 뒤 재사용했다는 처리 결과입니다.

따라서 저장 결과를 읽을 때는 새로 저장한 경우와 기존 미활성본을 재사용한 경우를 구분합니다. 이어서 선택 페이지의 활성화와 사후 조회 결과를 차례로 살펴봅니다.

### 5-4. 읽기 전용 비교 실습

먼저 새로 추출한 파일을 수정하지 않은 상태로 비교합니다. 원본과 추출본의 대응, 현재 SAP와의 차이를 읽은 다음 작은 변경 한 건을 넣어 결과가 어떻게 달라지는지 살펴봅니다. 저장·활성화 실습은 개발 환경에서 담당자가 정한 대상과 범위로 진행합니다.

파일 비교 개념은 [비교 실습 스크립트](downloads/compare_cases.py)와 [입력 JSON](downloads/three_way_cases.json)으로 연습할 수 있습니다. 두 파일을 같은 폴더에 저장한 뒤 다음 명령을 실행합니다.

```bash
python3 compare_cases.py
```

## 6. 호환성 오류와 검증 기록

SAP_BASIS 700에서는 사용하는 API와 인수 타입을 해당 환경에 맞춰야 합니다. DIAG 0.4.4의 날짜·시각 인수에서 타입 오류가 발생한 사례가 있었고, 0.4.5에서는 STRING 변환을 추가해 처리 방식을 수정했습니다.

![DIAG 0.4.4의 날짜 인수 타입 오류 화면입니다.](assets/images/diag-044-type-error.png)

이런 오류는 수정 위치와 실행 조건을 함께 남겨야 다음 변경에서도 참고할 수 있습니다. 따라서 비교 결과와 수정 내용, 저장·활성화·사후 조회 결과를 한 작업 기록으로 연결합니다.

업무 판단을 바로잡은 내용은 [07. 업무 스킬 및 회귀](#/learn/feedback)에 기록합니다. 다른 담당 업무의 지식과 코드가 필요한 질문은 [09. 에이전트간 협업](#/learn/collaboration)으로 연결합니다.
