# ERP 데이터 연동

## 1. 왜 실데이터가 필요한가: 계산 방법과 오늘의 결과는 다릅니다

추출 소스를 읽으면 “어떤 조건이면 처리 대상에서 제외되는가”를 설명할 수 있습니다. 그러나 “이번 직원이 실제로 왜 제외됐는가”에 답하려면 기준일의 인사 정보와 처리 결과를 조회해야 합니다. 원 대화에서도 이 차이를 직원 누락의 가상 사례로 설명했습니다. 특정 직원의 실제 원인을 확인했다는 기록은 아닙니다.

이 과정의 목표는 앞에서 만든 에이전트에 **ERP의 현재 상태를 확인하는 조회 기능**을 더하는 것입니다. 사람이 화면에서 값을 확인하고 다시 AI에게 입력하는 반복을 줄이되, 어떤 조건으로 언제 조회한 결과인지 함께 남기려는 방향입니다.

## 2. 무엇에서 출발했는가: 기존 REST·RFC를 재사용하기

사용자는 ECC 6.0의 RFC 함수를 JSON REST API로 외부 시스템과 연결하고 있다고 설명했습니다. API는 다른 프로그램이 정해진 입력을 주고 결과를 받는 접점입니다. RFC는 SAP 기능을 호출하는 방식이며, 여기서는 기존에 마련된 REST 접점을 재사용하는 구상입니다.

처음 설명에서는 중계 서버 이야기만 있어 “여기에 AI는 어디에 있나?”라는 질문이 나왔습니다. MCP 자체가 생각하거나 답을 만드는 AI는 아니기 때문입니다. **질문을 해석하는 AI, 호출을 실행하는 프로그램, ERP 조회를 연결하는 MCP**의 역할을 나눠 설명할 필요가 있었습니다.

모바일 사용에서도 처음 제시된 VPN·원격 화면 접근은 사용자의 목적과 달랐습니다. 사용자는 Telegram에서 질문하고 답을 받고 싶다고 정정했습니다. 그래서 화면을 원격 조작하기보다 메시지를 받아 같은 조회 흐름으로 넘기는 방향을 검토했습니다.

## 3. 어떤 방향을 택했는가: 허용된 조회 하나부터 연결하기

AI가 임의의 테이블을 마음대로 읽게 하는 대신, “구매오더 상태 조회”처럼 업무 목적이 분명한 도구를 정합니다. 필요한 입력과 반환 항목을 설명하고, 기존 API의 인증·권한·조회 조건과 맞춥니다.

| 역할 | 맡는 일 | 예시 |
|---|---|---|
| AI | 질문을 이해하고 필요한 조회와 조건 선택 | 기간이 빠졌으면 확인, 상태 조회 도구 선택 |
| 에이전트 실행기 | AI가 선택한 도구를 실제로 호출하고 결과를 다시 전달 | 조회 요청과 응답을 한 작업으로 이어 줌 |
| ERP 조회 MCP | 입력·권한 확인, 기존 ERP API 형식으로 변환 | 도구의 입력명을 ERP 필드에 대응 |
| 기존 ERP 기능 | 실제 자료 조회와 업무 계산 | 기존 REST/RFC가 결과 반환 |
| Telegram 봇 | 모바일 메시지 수신·답변 전송 | 허용 사용자의 질문을 실행기로 전달 |

09의 담당자 자문 MCP는 다른 업무 담당의 지식에 묻는 연결입니다. 여기서는 ERP 조회 기능에 요청합니다. 두 MCP가 같은 컴퓨터에 있어도 자동으로 같은 기능이 되는 것은 아닙니다.

## 4. 어떻게 연결하는가: 질문에서 ERP 결과까지

### 4-1. 통신 구간을 나눕니다

첫 구간은 **에이전트 실행기와 MCP** 사이입니다. 사용할 도구의 이름·입력·결과를 주고받습니다. 두 번째 구간은 **MCP와 기존 ERP REST API** 사이입니다. 기존 API가 요구하는 형식과 인증으로 실제 업무 조회를 요청합니다.

사용자가 질문하면 AI가 대상과 기간을 확인하고 도구를 고릅니다. 실행기가 호출을 수행하고, MCP는 입력과 권한을 검사한 뒤 ERP 요청으로 바꿉니다. ERP 결과를 받은 AI는 값의 의미와 조회 조건을 설명합니다. 조회가 실패했거나 비어 있으면 추정한 값으로 채우지 않습니다.

### 4-2. 가상 계약으로 입력과 출력을 맞춰 봅니다

확보한 `erp_readonly_contract.example.json`은 다음 관계를 보여 주는 **교육용 가상 예제**입니다. 실제 KBS API 주소·필드 규칙·상태 코드로 확정된 것이 아닙니다.

| 연결 단계 | 예제 값 | 먼저 확인할 질문 |
|---|---|---|
| 도구 이름 | `get_purchase_order_status` | 어떤 업무 상태를 조회하는가 |
| AI가 넣을 입력 | `purchase_order` | 번호 형식과 허용 범위는 무엇인가 |
| ERP 요청 필드 | `EBELN` | 실제 API의 어떤 필드에 넣는가 |
| 가상 응답 | `STATUS: APPROVED` | 이 상태가 어떤 의미이며 언제 조회됐는가 |
| 반환 결과 | 주문번호와 상태 | 사용자에게 보여도 되는 항목인가 |

예제 주소는 `erp.example.invalid`입니다. 실행 가능한 사내 주소가 아닙니다. 실제로 연결하려면 담당자가 요청·응답 명세, 인증 방식, 사용자 권한, 오류 응답과 상태 의미를 먼저 확인해야 합니다.

### 4-3. Telegram은 질문 창구로 연결합니다

검토한 방식은 long polling입니다. 사내 봇 프로그램이 Telegram에 먼저 `getUpdates` 요청을 보내 새 메시지를 기다렸다가 그 응답으로 메시지를 받습니다. 받은 질문을 에이전트 실행기에 넘기고, 답은 `sendMessage`로 전송합니다.

따라서 사내에서 Telegram으로 나가는 HTTPS 통신이 필요합니다. 메시지 번호를 관리하는 `offset`은 중복 수신을 줄이기 위한 수신 확인이며 ERP 업무 처리 완료 표시가 아닙니다. 실제 작업의 성공·실패 기록은 별도로 남겨야 합니다. [Telegram 공식 Bot API](https://core.telegram.org/bots/api#getupdates)

장비 한 대를 쓰더라도 봇, 에이전트 실행기, ERP MCP는 역할이 다른 프로그램으로 나눌 수 있습니다. 교육 사이트를 제공하는 웹서버도 별도 역할입니다. 전원을 켰다고 모든 연결과 재시작 처리가 자동으로 갖춰지지는 않습니다.

## 5. 어떤 순서로 검증하는가: 작은 조회 하나의 왕복

이 프로젝트는 설계와 예제 계약을 확보한 단계입니다. 다음은 구축·검증 순서이며 실제 ERP와 Telegram의 왕복 성공 기록이 아닙니다.

1. **업무 선택:** 첫 질문 하나와 담당자를 정합니다. 예를 들어 상태 조회라면 무엇을 ‘상태’라고 부르는지 합의합니다.
2. **계약 작성:** 입력, 응답, 단위, 기준일, 오류, 권한을 표로 적습니다. 가상 구매오더 예제로 형식을 연습할 수 있습니다.
3. **모의 응답:** ERP에 연결하지 않고 정상·빈 결과·권한 거부·시간 초과를 구분해 반환합니다.
4. **개발계 대조:** 승인된 API에 같은 입력을 보내 ERP 담당자가 확인한 값과 맞는지 봅니다.
5. **AI 연결:** AI가 맞는 도구와 인자를 고르고, 부족한 조건을 되묻는지 확인합니다.
6. **모바일 연결:** 먼저 허용 사용자의 Telegram 질문에 고정 문장을 돌려주고, 그다음 AI·ERP 조회를 붙입니다.
7. **운영 조건 시험:** 사용자별 대화 분리, 중복 수신, 처리 지연, 중단 후 복구를 확인합니다.

```text
우리 업무의 첫 조회 도구를 설계해 주세요.
질문은 <담당 업무의 질문>, 사용할 자료는 <확보한 API 명세>입니다.
사용자 입력, ERP 요청 필드, 결과의 단위·기준시점·오류를 대응시켜 주세요.
명세에 없는 인증·필드·업무 규칙은 만들지 말고 확인 목록에 남겨 주세요.
정상·빈 결과·권한 거부·시간 초과의 가상 응답부터 작성해 주세요.
이번에는 실제 ERP 호출과 변경 기능을 넣지 마세요.
```

꺾쇠 부분을 실제 업무와 문서로 바꿉니다. API 명세가 없다면 먼저 그 문서를 준비하는 것이 다음 행동입니다.

## 6. 한계와 향후 방향: 연결보다 결과를 믿을 조건이 먼저입니다

현재 실제 조회 API 선정, 서버 설치, AI 실행기와 Telegram의 종단 간 연결은 확인되지 않았습니다. 과거 Python 설명 예제와 09의 Node.js 자문 예제는 서로 다른 역할이며, 하나가 있다는 이유로 다른 쪽 구현이 끝난 것은 아닙니다.

앞으로는 누가 어떤 업무 자료를 조회할 수 있는지, 조회 시점과 단위를 어떻게 보여 줄지, 실패를 어떻게 구분할지 정해야 합니다. 실제 데이터가 있어도 오래된 값이나 잘못된 대상이면 답이 틀릴 수 있습니다. 조회 권한을 지급·승인·변경 권한으로 확대하지 않습니다.

모바일과 Desktop 대화가 자동으로 공유되는 기능도 미구현입니다. 대화 연결 방식을 따로 정하고, 모델 서비스와 Telegram의 외부 통신 조건도 확인해야 합니다.

첫 완료 목표는 **담당자가 확인한 조회 한 건을, 허용된 사용자가 같은 조건으로 요청해 같은 값과 기준시점을 받는 것**입니다. 여기까지 검증한 뒤 업무와 도구 수를 늘립니다. 이어지는 [11. 근로시간 AI 에이전트 구축](#/learn/worktime-agent)부터는 앞 과정의 자료·지식·검토 흐름을 실제 프로젝트에 적용한 사례를 읽습니다.
