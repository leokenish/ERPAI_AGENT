# ERP 데이터 연동

## 1. 왜 실데이터가 필요한가: 계산 방법과 오늘의 결과는 다르다

추출 소스를 읽으면 “어떤 조건이면 처리 대상에서 제외되는가”를 설명할 수 있다. 하지만 “이번 직원이 실제로 왜 제외됐는가”를 알려면 기준일의 인사 정보와 처리 결과가 필요하다. 원 대화에서도 직원이 누락된 가상 사례로 이 차이를 설명했다. 특정 직원의 실제 누락 원인을 확인한 기록은 아니다.

앞에서 만든 에이전트에 **ERP의 현재 상태를 확인하는 조회 기능**을 더하는 것이 이 과정의 목표다. 사람이 화면에서 값을 확인한 뒤 AI에게 다시 입력하는 반복을 줄이려는 것이다. 조회 결과에는 언제, 어떤 조건으로 읽은 값인지도 함께 남긴다.

## 2. 무엇에서 출발했는가: 기존 REST·RFC를 재사용하기

사용자는 ECC 6.0의 RFC 함수를 JSON REST API로 외부 시스템과 연결해 쓰고 있다고 설명했다. API는 다른 프로그램이 정해진 입력을 보내고 결과를 받는 접점이고, RFC는 SAP 기능을 호출하는 방식이다. 이번 구상은 이미 마련된 REST 접점을 재사용하는 데서 출발했다.

처음 설명이 중계 서버에 집중되자 “여기에 AI는 어디에 있나?”라는 질문이 나왔다. MCP 자체는 생각하거나 답을 만드는 AI가 아니다. 그래서 **질문을 해석하는 AI, 호출을 실행하는 프로그램, ERP 조회를 연결하는 MCP**가 각각 무엇을 하는지 나눠 설명해야 했다.

모바일 사용에서도 처음 제시한 VPN·원격 화면 접근은 사용자 목적에 맞지 않았다. 사용자는 Telegram에서 질문하고 답을 받고 싶다고 정정했다. 이에 따라 원격으로 화면을 조작하는 대신, 메시지를 받아 같은 조회 흐름으로 넘기는 방향을 검토했다.

## 3. 어떤 방향을 택했는가: 허용된 조회 하나부터 연결하기

첫 도구는 “구매오더 상태 조회”처럼 업무 목적이 분명한 조회로 정한다. AI가 임의의 테이블을 읽도록 열어 두지 않는다. 필요한 입력과 반환 항목을 설명하고, 기존 API의 인증·권한·조회 조건에 맞춘다.

| 역할 | 맡는 일 | 예시 |
|---|---|---|
| AI | 질문을 이해하고 필요한 조회와 조건 선택 | 기간이 빠졌으면 확인, 상태 조회 도구 선택 |
| 에이전트 실행기 | AI가 선택한 도구를 실제로 호출하고 결과를 다시 전달 | 조회 요청과 응답을 한 작업으로 이어 줌 |
| ERP 조회 MCP | 입력·권한 확인, 기존 ERP API 형식으로 변환 | 도구의 입력명을 ERP 필드에 대응 |
| 기존 ERP 기능 | 실제 자료 조회와 업무 계산 | 기존 REST/RFC가 결과 반환 |
| Telegram 봇 | 모바일 메시지 수신·답변 전송 | 허용 사용자의 질문을 실행기로 전달 |

09의 담당자 자문 MCP는 다른 업무 담당의 지식에 질문한다. 이 과정의 MCP는 ERP 조회 기능에 요청한다. 같은 컴퓨터에 두더라도 두 MCP의 역할이 자동으로 합쳐지는 것은 아니다.

## 4. 어떻게 연결하는가: 질문에서 ERP 결과까지

### 4-1. 통신 구간을 나눈다

첫 구간은 **에이전트 실행기와 MCP** 사이다. 여기서는 사용할 도구의 이름·입력·결과를 주고받는다. 두 번째는 **MCP와 기존 ERP REST API** 사이다. 기존 API에 맞는 형식과 인증으로 실제 업무 조회를 요청한다.

사용자의 질문을 받은 AI는 대상과 기간을 확인해 도구를 고른다. 실행기가 도구를 호출하면 MCP가 입력·권한을 검사하고 ERP 요청 형식으로 바꾼다. AI는 돌아온 ERP 결과를 바탕으로 값의 의미와 조회 조건을 설명한다. 조회에 실패했거나 결과가 비어 있다면 추정값으로 채우지 않는다.

### 4-2. 가상 계약으로 입력과 출력을 맞춰 본다

확보한 `erp_readonly_contract.example.json`은 입력과 출력의 관계를 보여 주는 **교육용 가상 예제**다. 실제 KBS API 주소·필드 규칙·상태 코드로 확정된 내용은 아니다.

| 연결 단계 | 예제 값 | 먼저 확인할 질문 |
|---|---|---|
| 도구 이름 | `get_purchase_order_status` | 어떤 업무 상태를 조회하는가 |
| AI가 넣을 입력 | `purchase_order` | 번호 형식과 허용 범위는 무엇인가 |
| ERP 요청 필드 | `EBELN` | 실제 API의 어떤 필드에 넣는가 |
| 가상 응답 | `STATUS: APPROVED` | 이 상태가 어떤 의미이며 언제 조회됐는가 |
| 반환 결과 | 주문번호와 상태 | 사용자에게 보여도 되는 항목인가 |

예제 주소는 `erp.example.invalid`이다. 실행 가능한 사내 주소가 아니다. 실제로 연결하려면 담당자가 요청·응답 명세, 인증 방식, 사용자 권한, 오류 응답과 상태 의미를 먼저 확인해야 한다.

### 4-3. Telegram은 질문 창구로 연결한다

검토한 방식은 long polling이다. 사내 봇 프로그램이 Telegram에 `getUpdates`를 요청한 뒤 새 메시지를 기다린다. 메시지가 도착하면 응답으로 받아 에이전트 실행기에 질문을 넘기고, 답변은 `sendMessage`로 전송한다.

이 방식에는 사내에서 Telegram으로 나가는 HTTPS 통신이 필요하다. 메시지 번호를 관리하는 `offset`은 중복 수신을 줄이기 위한 수신 확인 값이다. ERP 업무 처리가 끝났다는 표시는 아니므로 실제 작업의 성공·실패는 따로 기록해야 한다. [Telegram 공식 Bot API](https://core.telegram.org/bots/api#getupdates)

한 장비에서 실행하더라도 봇, 에이전트 실행기, ERP MCP는 역할이 다른 프로그램으로 나눌 수 있다. 교육 사이트를 제공하는 웹서버도 별도의 역할을 맡는다. 장비 전원을 켜는 것만으로 연결과 재시작 처리가 자동으로 준비되지는 않는다.

## 5. 어떤 순서로 검증하는가: 작은 조회 하나의 왕복

현재 확보한 것은 설계와 예제 계약이다. 아래는 앞으로 구축하고 검증할 순서이며, 실제 ERP와 Telegram의 왕복이 성공했다는 기록은 아니다.

1. **업무 선택:** 첫 질문 하나와 담당자를 정한다. 예를 들어 상태 조회라면 무엇을 ‘상태’라고 부르는지 합의한다.
2. **계약 작성:** 입력, 응답, 단위, 기준일, 오류, 권한을 표로 적는다. 가상 구매오더 예제로 형식을 연습할 수 있다.
3. **모의 응답:** ERP에 연결하지 않고 정상·빈 결과·권한 거부·시간 초과를 구분해 반환한다.
4. **개발계 대조:** 승인된 API에 같은 입력을 보내 ERP 담당자가 확인한 값과 맞는지 본다.
5. **AI 연결:** AI가 맞는 도구와 인자를 고르고, 부족한 조건을 되묻는지 확인한다.
6. **모바일 연결:** 먼저 허용 사용자의 Telegram 질문에 고정 문장을 돌려주고, 그다음 AI·ERP 조회를 붙이다.
7. **운영 조건 시험:** 사용자별 대화 분리, 중복 수신, 처리 지연, 중단 후 복구를 확인한다.

```text
우리 업무의 첫 조회 도구를 설계해 주세요.
질문은 <담당 업무의 질문>, 사용할 자료는 <확보한 API 명세>입니다.
사용자 입력, ERP 요청 필드, 결과의 단위·기준시점·오류를 대응시켜 주세요.
명세에 없는 인증·필드·업무 규칙은 만들지 말고 확인 목록에 남겨 주세요.
정상·빈 결과·권한 거부·시간 초과의 가상 응답부터 작성해 주세요.
이번에는 실제 ERP 호출과 변경 기능을 넣지 마세요.
```

꺾쇠 부분을 실제 업무와 문서로 바꾼다. API 명세가 없다면 먼저 그 문서를 준비하는 것이 다음 행동이다.

## 6. 한계와 향후 방향: 연결보다 결과를 믿을 조건이 먼저다

실제 조회 API 선정과 서버 설치, AI 실행기부터 Telegram까지의 전체 연결은 아직 확인되지 않았다. 과거 Python 설명 예제와 09의 Node.js 자문 예제도 역할이 다르다. 한쪽 예제가 있다고 다른 쪽 구현까지 끝난 것으로 볼 수는 없다.

다음에는 누가 어떤 자료를 조회할 수 있는지, 조회 시점과 단위를 어떻게 표시할지, 실패를 어떻게 구분할지 정해야 한다. 실제 데이터라도 오래된 값이거나 다른 대상의 값이면 답이 틀릴 수 있다. 조회 권한의 범위는 지급·승인·변경까지 넓히지 않는다.

모바일과 Desktop의 대화를 자동 공유하는 기능도 아직 구현하지 않았다. 대화를 어떤 방식으로 연결할지 따로 정하고, 모델 서비스와 Telegram의 외부 통신 조건도 확인해야 한다.

첫 완료 목표는 **담당자가 확인한 조회 한 건을, 허용된 사용자가 같은 조건으로 요청해 같은 값과 기준시점을 받는 것**이다. 여기까지 검증한 뒤 업무와 도구 수를 늘린다. 이어지는 [11. 근로시간 AI 에이전트 구축](#/learn/worktime-agent)부터는 앞 과정의 자료·지식·검토 흐름을 실제 프로젝트에 적용한 사례를 읽는다.
