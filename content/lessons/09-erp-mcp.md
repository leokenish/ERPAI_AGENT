# ERP 데이터 연동

## 1. 왜 실데이터가 필요한가

추출 소스를 읽으면 어떤 조건에서 처리 대상이 제외되는지 설명할 수 있습니다. 하지만 특정 직원이 제외된 이유를 알려면 기준일의 인사 정보와 처리 결과도 필요합니다. 계산 방법과 실제 입력값이 함께 있어야 해당 결과를 설명할 수 있기 때문입니다.

따라서 업무 에이전트에 **ERP의 값을 읽는 조회 도구**를 연결하는 방향을 다룹니다. 사람이 화면에서 값을 찾아 AI에게 다시 입력하는 단계를 줄이고, 조회 결과에 대상·조건·기준시점을 함께 담는 것이 목표입니다.

## 2. 무엇에서 출발했는가

KBS에서는 ECC 6.0의 RFC 함수를 JSON REST API로 외부 시스템과 연결해 사용했습니다. API는 정해진 입력을 보내고 결과를 받는 접점이며, RFC는 SAP 기능을 호출하는 방식입니다. 따라서 ERP 조회 연결도 기존 REST 접점을 활용하는 방향으로 검토했습니다.

초기 설명이 중계 서버에 집중되면서 AI가 어디에서 질문을 이해하는지 구분하기 어려웠습니다. 이를 풀기 위해 **질문을 해석하는 AI, 호출을 실행하는 프로그램, ERP 조회를 연결하는 MCP**의 역할을 나눴습니다.

모바일의 목적도 원격 화면 조작이 아니라 Telegram에서 질문하고 답을 받는 것이었습니다. 따라서 모바일 메시지를 같은 에이전트 실행 흐름으로 전달하는 구조를 검토했습니다.

## 3. 어떤 방향을 택했는가

첫 조회 도구는 ‘구매오더 상태 조회’처럼 목적이 분명한 업무로 정합니다. 대상과 입력 조건을 좁히면 어떤 결과를 반환할지 설명하기 쉽고, 기존 API의 권한과 조회 조건도 대응할 수 있습니다.

| 역할 | 맡는 일 | 예시 |
|---|---|---|
| AI | 질문 이해와 조회 도구·조건 선택 | 기간 질문, 상태 조회 도구 선택 |
| 에이전트 실행기 | 도구 호출과 결과 전달 | 조회 요청과 응답을 한 작업으로 연결 |
| ERP 조회 MCP | 입력·권한 검사와 ERP 요청 변환 | 도구의 입력명을 ERP 필드에 대응 |
| 기존 ERP 기능 | 자료 조회와 업무 계산 | REST/RFC 결과 반환 |
| Telegram 봇 | 모바일 메시지 수신과 답변 전송 | 허용된 질문을 실행기로 전달 |

09의 자문 MCP는 담당자의 지식과 코드에 질문하고, 여기서 다루는 MCP는 ERP 조회 기능에 요청합니다. 같은 컴퓨터에서 운영하더라도 질문의 대상에 맞춰 도구와 권한을 따로 구성합니다.

## 4. 어떻게 연결하는가

### 4-1. 에이전트·MCP·ERP의 통신 구간

첫 구간은 **에이전트 실행기와 MCP** 사이입니다. 도구의 이름·입력·결과를 주고받습니다. 두 번째는 **MCP와 ERP REST API** 사이입니다. 기존 API의 형식과 인증 방식을 사용해 업무 데이터를 조회합니다.

사용자의 질문을 받은 AI가 대상과 기간에 맞는 도구를 고르면 실행기가 호출합니다. MCP는 입력과 권한을 검사하고 ERP 요청 형식으로 변환합니다. 이어서 ERP 결과가 돌아오면 AI가 값의 의미와 조회 조건을 설명합니다.

정상 결과, 빈 결과, 오류 응답도 서로 구분합니다. 그래야 값이 없는 경우와 조회에 실패한 경우를 다른 상황으로 안내할 수 있습니다.

### 4-2. 입력·출력 대응표

`erp_readonly_contract.example.json`은 구매오더 조회의 입력과 출력을 연결하는 **교육용 예제**입니다. 이 형식을 참고해 자신의 업무 API에 맞는 대응표를 작성합니다.

| 연결 단계 | 예제 값 | 대응할 내용 |
|---|---|---|
| 도구 이름 | `get_purchase_order_status` | 조회할 업무와 상태 |
| AI 입력 | `purchase_order` | 번호 형식과 허용 범위 |
| ERP 요청 필드 | `EBELN` | 실제 API의 입력 필드 |
| 예제 응답 | `STATUS: APPROVED` | 상태의 업무적 의미와 조회 시점 |
| 반환 결과 | 주문번호와 상태 | 사용자에게 제공할 항목 |

연결 설정에는 담당 API의 주소, 인증 방식, 사용자 권한, 오류 응답을 사용합니다. 같은 필드명이라도 업무에 따라 의미가 달라질 수 있으므로, 응답 단위와 상태의 의미도 대응표에 함께 적습니다.

### 4-3. Telegram 질문과 답변 연결

검토한 수신 방식은 long polling입니다. 사내 봇 프로그램이 Telegram에 `getUpdates`를 요청하고 새 메시지를 기다립니다. 메시지가 도착하면 에이전트 실행기로 전달하고, 답변은 `sendMessage`로 전송합니다.

이 흐름에는 사내에서 Telegram으로 나가는 HTTPS 통신이 필요합니다. `offset`은 이미 받은 메시지를 다시 가져오지 않도록 관리하는 값이며, 업무 처리 결과는 별도의 작업 기록으로 남깁니다. [Telegram 공식 Bot API](https://core.telegram.org/bots/api#getupdates)

한 장비를 사용하더라도 봇, 에이전트 실행기, ERP MCP의 실행과 재시작을 각각 관리할 수 있습니다. 역할을 나누면 메시지 수신, AI 처리, ERP 조회 중 어느 구간에서 문제가 생겼는지도 찾기 쉽습니다.

## 5. 어떤 순서로 검증하는가

업무 하나의 입력과 결과를 먼저 맞춘 뒤 AI와 모바일을 연결하는 순서로 구성합니다. 연결할 요소를 한 번에 늘리지 않으면 오류가 난 구간을 구분하기 쉽습니다.

1. **업무 선택:** 첫 질문과 담당자를 정하고 조회할 상태의 의미를 합의합니다.
2. **계약 작성:** 입력, 응답, 단위, 기준일, 오류, 권한을 표로 정리합니다.
3. **모의 응답:** 정상·빈 결과·권한 거부·시간 초과의 반환 형식을 작성합니다.
4. **개발계 대조:** 승인된 API에 같은 입력을 보내 담당자의 조회 결과와 비교합니다.
5. **AI 연결:** 도구와 인자를 선택하고 필요한 조건을 되묻는 흐름을 살펴봅니다.
6. **모바일 연결:** Telegram의 질문·답변 전달을 시험한 뒤 AI·ERP 조회를 연결합니다.
7. **운영 조건 시험:** 사용자별 대화 분리, 중복 수신, 처리 지연, 중단 후 복구를 살펴봅니다.

```text
우리 업무의 첫 조회 도구를 설계해 주세요.
질문은 <담당 업무의 질문>, 사용할 자료는 <확보한 API 명세>입니다.
사용자 입력, ERP 요청 필드, 결과의 단위·기준시점·오류를 대응시켜 주세요.
명세에 없는 인증·필드·업무 규칙은 만들지 말고 확인 목록에 남겨 주세요.
정상·빈 결과·권한 거부·시간 초과의 가상 응답부터 작성해 주세요.
이번에는 실제 ERP 호출과 변경 기능을 넣지 마세요.
```

위 요청문의 꺾쇠 부분을 실제 업무 질문과 API 명세 이름으로 바꾸어 사용합니다.

## 6. 조회 결과와 운영 기준

조회한 값은 대상·시점·단위와 함께 전달합니다. 값이 실제 ERP에서 나왔더라도 다른 직원이나 다른 기간의 값이면 질문에 맞는 답이 될 수 없기 때문입니다. 따라서 도구의 입력 조건과 결과의 기준시점을 답변에 함께 연결합니다.

권한도 업무별로 정합니다. 조회 도구는 허용된 읽기 범위를 사용하고, 지급·승인·변경은 각각 별도의 업무 권한과 처리 절차로 관리합니다.

모바일과 Desktop을 함께 사용할 때는 사용자별 대화를 구분하고 연결할 맥락을 정합니다. 또한 모델 서비스와 Telegram의 통신 경로, 작업 기록과 재시작 절차를 운영 구성에 포함합니다.

첫 구성 목표는 **같은 조건으로 요청한 조회에서 같은 값과 기준시점을 받는 것**입니다. 이 흐름을 바탕으로 업무와 도구 수를 늘립니다. 이어지는 [11. 근로시간 AI 에이전트 구축](#/learn/worktime-agent)부터는 자료·지식·검토 절차를 프로젝트에 적용한 사례를 살펴봅니다.
