# 17. 근로시간 시스템 고도화

## 1. 추진 이유

근로시간 업무에서는 같은 근무시간이라도 근무형태, 휴가, 단가 적용일, 정산 시점에 따라 금액이 달라집니다. 따라서 계산식 하나를 알아내는 것만으로는 직원의 문의나 인사 담당자의 검증 요청을 해결하기 어렵습니다.

이 사례에서는 11과정에서 구성한 **근로시간 AI 에이전트에게 실제 업무를 질문하고, 담당자의 판단으로 범위를 정한 뒤 ABAP 코드까지 연결**했습니다. AI는 업무 지식과 추출 소스를 읽고 수정안을 작성했으며, 담당자는 실제 업무 기준과 실행 결과를 전달하면서 잘못 잡힌 전제를 바로잡았습니다.

대화 담당자는 학습을 위한 가상 인물입니다. 각 세부 사례 안에서는 같은 인물이 AI와 대화하고, 요청의 조건·숫자·코드는 실제 자료를 따릅니다. 일곱 대화는 이 페이지 하단에서 이어 읽을 수 있습니다.

## 3. 업무 기준에서 코드까지

먼저 **어떤 직원의 어떤 시점에 발생한 문제인지** 업무 언어로 설명합니다. 이후 관련 지식 문서와 소스를 찾아 입력·계산·저장·정산 중 어느 단계에서 차이가 생기는지 확인합니다.

담당자가 적용 기준과 제외 범위를 정하면 AI는 그 범위에 맞춰 코드를 작성합니다. 실제 실행에서 나온 오류나 숫자를 다시 전달하면, AI는 이전 가정과 코드의 차이를 비교해 수정합니다. 이때 최종 요구와 중간 검토안을 구분해야 다음 작업에서도 같은 기준을 유지할 수 있습니다.

| 업무 표현 | 코드에서 확인한 대상 | 확인 목적 |
|---|---|---|
| 대휴 금액 | ZTHRBS01의 ZD_MONEY·JORGEH | 최초 실비와 별도 정산 금액의 관계 |
| 직원 구분 | 근무일에 유효한 PA0001-PERSK | 직군마다 다른 단가 적용 |
| 선택기간·실적 | ZTHR0132·ZTHR0112 | 정확히 어느 기간의 자료인지 확인 |
| 정산 결과·마감 | ZTHR0113·ZTHR0160 | 정산 전후 처리 가능 시점 구분 |
| 수기보정 | ZTHREDITCOST | 담당자가 반영한 조정 금액 확인 |
| 급여 지급 항목 | PA2010의 8050 | 정산 내역과 실제 지급 항목 분리 |

## 4. 휴일을 넘긴 대휴 금액 추적

### 업무 상황

인사 담당자가 반기마다 보정 금액을 보내면 ERP 담당자가 대휴 정산 금액을 수동 반영하고 있었습니다. 하지만 왜 차이가 생겼는지 설명하지 못하면 같은 작업이 반복됩니다. 따라서 최팀장은 **이미 틀어진 최초 저장값의 원인**부터 확인하도록 요청했습니다.

### 근거와 방향 설정

휴일 두 날짜에 걸친 근무는 대휴 발생일과 다른 날의 실비를 구분해야 합니다. AI가 처음 제시한 정산 확정·취소 문제는 더 나중 단계였으므로, 이번 수정에서는 입력·저장 경로에 집중했습니다.

또한 같은 날의 시간이 여러 행으로 나뉘는 예시가 실제 선택근무 경로에도 적용되는지 다시 확인했습니다. 선택 실적의 CW 경로와 일반 A 유형 휴일에서는 해당 분할 예시를 그대로 적용할 수 없었습니다. **다른 경로에서 발견한 가능성을 이번 오류의 원인으로 단정하지 않은 것**이 중요한 전환점입니다.

```worktime-lab
huhu
```

### 기술적 구현

`LZHR008_2F03`와 `ZHR_52TM_GET_OVERTIME_SAVE` 두 소스의 8개 변경 구간을 제안 사본으로 정리했습니다. 검토 내용은 현재 호출의 계산 결과를 기존 반환 통로로 직접 전달하고 날짜별로 합산하는 방식, 이전 임시 DB값에 대한 조회 의존성 제거, 오류 처리와 금액 복사 과정입니다.

원래의 단가 계산식과 시간 구간 분할은 유지했습니다. 대신 계산 결과가 저장값으로 전달되는 과정에 집중했습니다. 전체 코드 비교 보고서에서 변경 전후의 줄과 각 구간의 이유를 함께 볼 수 있습니다.

## 5. 단가 인상 전후 금액 점검

### 업무 상황

9월 단가 인상 뒤 인사 담당자는 일부 대휴 금액에 이전 단가가 남아 있는지 확인하고 싶었습니다. 인정시간 산식을 처음부터 재현하려면 시간이 많이 들기 때문에, 우대리는 **금액이 특정 단가의 배수인지 확인하는 1차 선별 도구**를 요청했습니다.

### 근거와 시행착오

0.5시간 단위의 대휴 실비를 검사하므로 일반 직원의 검사 단위는 8월 2,100원, 9월 2,310원입니다. 처음에는 다른 화면의 표시식을 가져와 23,100원을 100으로 나눴고, 그 결과 231원으로 잘못 검사했습니다. 사용자 실행 화면을 근거로 조회·판정·차액·화면 표시의 단위를 모두 원으로 맞췄습니다.

또한 SAP_BASIS 700에서 조건문 내부의 곱셈 비교가 오류를 냈습니다. 따라서 곱셈 결과를 변수에 먼저 담고 변수끼리 비교하도록 수정했습니다.

```worktime-lab
rate
```

### 기술적 구현

`ZHR_DAEH_RATE_CHECK`는 승인된 대휴를 근무 시작일 기준으로 조회합니다. 근무일에 유효한 직원 구분을 확인해 일반 직원, E1·E4·E5·E6·E7, 단가가 유지되는 E8을 구분합니다. `JORGEH`가 있는 건은 별도 검토 대상으로 분류합니다.

23,100원은 두 검사 단위의 공배수이므로 금액만으로 어느 단가를 적용했는지 정할 수 없습니다. 따라서 결과를 일치·구단가 의심·판별 불가 등으로 나눠 보여줍니다. 이 도구의 목적은 정산액을 자동 변경하는 것이 아니라 **담당자가 확인할 대상을 줄이는 것**입니다.

## 6. 정산 전후 차이와 단가 기준

### 업무 상황

정산 후 과거 실적이 달라지면 금액과 대휴가 어떻게 바뀌는지 비교해야 합니다. 이과장은 실제 지급 자료를 수정하기 전에, 확정 당시 값과 현재 실적을 재계산한 값을 나란히 확인하는 프로그램을 활용했습니다.

### 실제 결과와 판단

업로드한 비교 결과는 143명 중 122명에서 금액 차이를 보였습니다. 반면 대휴 개수·시간·저장금액·발생일별 비교는 모두 같았습니다. 인사 담당자가 9월 단가 인상분을 `ZTHREDITCOST`에 수기보정했다는 설명을 연결하자, 차이를 실적 오류로만 볼 수 없다는 점이 드러났습니다.

```worktime-lab
compare
```

### 기술적 구현과 후속 설계

`ZRPTH411_COMPARE`는 실적을 내부 복사본으로 만들고 대휴와 금액을 재계산해 확정 당시 자료와 비교합니다. 업무 DB에 쓰지 않는 조회 리포트이며, 금액·개수·일자 비교를 구분해 원인을 추적합니다.

후속 대화에서는 4주 전체 시간 계산을 유지하면서 입력별 시작일의 단가를 적용하는 방향을 정했습니다. 8월 31일 시작 후 9월 1일에 끝난 한 입력은 시작일 기준으로 계산합니다. 시차실비와 재량·간주근무 금액도 기존 기준을 보존합니다. **현재 비교 도구와 이후 논의한 단가 개선 설계**를 구분해 읽으면 변경 범위를 이해하기 쉽습니다.

## 7. 소급 차액의 월별 분리

### 업무 상황

과거 여러 달의 근무실적을 고쳐 다시 계산하면 당월 지급액에 소급 차액이 반영됩니다. 하지만 금액이 한 행에 섞이면 어느 달에서 얼마가 늘거나 줄었는지 알기 어렵습니다. 채주임은 계산 결과를 **월별 상세와 당월 지급액으로 나눠 표시**하도록 요청했습니다.

### 범위와 계산 기준

10월 정산에서 소급 시작월을 5월로 입력하면 5월 한 달만이 아니라 5~9월이 대상입니다. 2월 변경도 포함하려면 시작월을 2월로 지정해야 합니다. 월별 증가액과 감소액은 서로 상계합니다.

```worktime-lab
retro
```

### 시행착오와 기술적 구현

최초 전달안에는 표시 데이터를 만드는 부분이 빈 골격으로 남아 있었습니다. 담당자가 “내부 결과에는 값이 있는데 화면이 비어 있다”는 실행 결과를 전달하자, AI는 실제 표시 행을 구성하도록 보완했습니다. 이후에는 전체 코드를 다시 적용하는 부담을 줄이기 위해 이미 반영한 버전을 기준으로 추가 변경 구간을 제공했습니다.

표시용 `GT_DISPLAY`에는 당월 행과 과거 상세 행을 넣고, 기존 `GT_DISP2`와 확정 저장 처리는 유지했습니다. 계산 함수에서 확보한 과거 확정·재계산 상세를 반환하고, ALV와 엑셀 표시를 함께 변경했습니다. 따라서 **상세 행이 늘어나도 지급을 여러 번 하는 구조로 바꾸지 않습니다.**

수기보정 `ZTHREDITCOST`가 있는 대상 정산월·직원은 기존 표시 방식을 유지합니다. 그 밖의 대상은 월별·정산기간별 상세를 펼쳐 보여 줍니다. 따라서 수기로 확정한 보정 내역과 자동 재계산 내역을 같은 방식으로 섞지 않습니다.

사용자는 보완안 실행에서 소급 상세 54건과 총 130,200원이 표시된 것을 확인했습니다. 이후 최종 표시안에서는 당월을 먼저 두고 과거 월을 최신순으로 정렬하며, 소급 합계와 최종 지급액을 당월 행에 배치했습니다. 기지급 소급액 차감 방식의 변경은 이번 화면 개선과 구분합니다.

## 8. 정산 후 지급 항목 제외

### 업무 상황과 범위 변경

월정산 이후 인사 담당자가 특정 직원의 선택근로실비 지급 항목을 제외해야 하는 경우가 있었습니다. 이 대화는 기존 `ZRPTH411_RET_DEL` 코드를 다시 확인하는 데서 시작했으며, 이후 퇴직자뿐 아니라 다른 직원도 처리할 수 있도록 요구가 확장됐습니다.

최팀장은 퇴직자 제한을 해제하도록 요청했습니다. AI는 퇴직 여부 검사와 관련 안내를 수정하면서도 **대상 사번·정산월·지급 항목의 범위는 유지**했습니다.

```worktime-lab
retired
```

### 기술적 구현

정산 대상연월에 연결된 정산일을 찾은 뒤 `PA2010`의 선택근로실비 `8050`만 대상으로 삼습니다. 전표 참조가 있거나 같은 지급일에 다른 정산월이 섞이면 처리 범위를 다시 확인하도록 중단합니다.

삭제 건수 확인 후 사번을 잠그고 자료를 재조회합니다. 정확한 레코드를 HR 정보형 함수로 삭제한 뒤 한 번에 저장합니다. 선택기간·실적·정산결과·마감 자료는 보존하므로, 직원 구분을 넓히는 요구가 다른 업무 자료의 삭제로 이어지지 않습니다.

## 9. 선택근무 등록 직후 취소

### 업무 상황과 범위 확정

선택근무 대상자로 지정하고 기간을 만든 직후, 업무 사정으로 취소해야 하는 경우가 있었습니다. 이과장은 인사 담당자가 사번·시작일·종료일을 입력해 처리하는 전용 프로그램을 요청했습니다.

AI는 처음에 인사 등록원장, 선택기간, 실적, 대휴까지 넓게 검토했습니다. 하지만 담당자는 “대휴 생성 전의 급한 취소”, “정산이 끝난 자료는 제외”, “기간 보정 없이 삭제”로 범위를 좁혔습니다. 마지막에는 **인사 등록원장을 보존하고 선택기간과 실적만 삭제**하도록 결정했습니다.

```worktime-lab
cancel
```

### 기술적 구현

`ZHR_CW_MEMBER_DEL`의 최종본은 `ZTHR0132`와 `ZTHR0112`만 처리하며 `PA9021`은 유지합니다. 예를 들어 9월 28일~10월 25일 선택기간은 종료월인 10월의 마감 여부를 기준으로 판단합니다. 사번·기간·근로유형이 정확히 일치하는 자료만 선택합니다.

마감 또는 정산 이력이 있으면 중단합니다. 실행 전 건수 확인, 잠금, 재조회 후 기간과 실적 삭제가 모두 성공해야 한 번 저장합니다. 이 사례는 앞의 지급 제외와 달리 **정산이 끝나기 전**을 대상으로 합니다.

| 구분 | 등록 직후 취소 | 정산 후 지급 제외 |
|---|---|---|
| 업무 시점 | 마감·정산 전 | 마감·정산 후 |
| 처리 자료 | 선택기간·실적 | 8050 지급 항목 |
| 유지 자료 | 인사 등록원장 | 기간·실적·정산결과 |

## 10. 반일 휴가의 시간외 입력 안내

### 업무 상황

오전 반일을 사용한 직원이 실제 출근시각부터 입력하면 기대한 실비와 다른 금액이 나올 수 있습니다. 오사원은 이런 결과를 계산식 오류로 단정하기 전에 정상 근무시간·휴가·휴게시간과 입력 방식부터 확인했습니다.

### 판단과 안내 기준

해당 입력 방식은 정상 근무 시작부터 전체 시간을 입력하고 승인된 반일을 별도로 반영합니다. 따라서 직원에게 “실제 출근시각”과 “시간외 입력의 시작시각”을 구분해 안내해야 합니다.

```worktime-lab
halfday
```

### 기술적 구현

최종안은 기존 `CHECK_ABSENCE_DATA` 처리에서 반일 상황을 찾아 기존 정보 안내 전달 경로에 `I95`와 `TEXT-E95`를 추가하는 방식입니다. 처음 검토한 여러 위치의 중복 검사와 새 조회를 줄이고, 기존 확인 결과에 필요한 안내를 연결했습니다.

또한 통상근무와 시차근무를 같은 기준으로 처리하지 않도록 범위를 구분했습니다. 안내 문구는 직원이 다음에 무엇을 입력해야 하는지 구체적으로 알려주는 방향으로 다듬었습니다. **업무 기준을 이해한 뒤 입력 안내와 코드 위치를 정한 사례**입니다.

## 11. 사례를 통한 학습

일곱 사례에서 AI가 작성한 코드의 출발점은 담당자의 업무 설명이었습니다. 담당자가 단가 적용일, 마감 여부, 삭제 범위 같은 기준을 명확히 하자 수정할 코드와 보존할 코드도 구분할 수 있었습니다.

특히 실행 결과와 예상이 다를 때는 오류 문구만 전달하는 것보다 **입력 조건·실제 결과·기대한 결과를 함께 전달**하는 방식이 도움이 됐습니다. 이 과정을 반복하면 AI가 추정한 업무를 실제 기준으로 바꾸고, 그 기준을 다음 질문에서도 다시 활용할 수 있습니다.
