# ERP 소스 추출하기

## 1. 왜 추출했는가: ERP 안의 자료를 AI가 읽을 수 있게 만들기

SAP 화면에서 프로그램 한 개의 코드를 복사해도 업무 전체가 보이지는 않는다. 그 프로그램이 부르는 함수, 공통 코드, 필드 정의, 웹 화면, 오류 메시지가 서로 다른 곳에 있기 때문이다. AI가 이 관계를 확인하려면 관련 자료를 함께 파일로 읽을 수 있어야 한다.

최초 요청은 **팀이 SE80에서 개발·관리하던 패키지 단위로 자료를 꺼내는 것**이었다. 패키지, 또는 개발클래스는 관련 개발물을 묶는 SAP의 관리 단위다. 담당 업무 자료를 이 단위로 모아 PC의 VS Code와 AI로 읽고, Git으로 변경 이력을 관리하려 했다.

이번 추출의 대상은 도구가 지원하는 개발 소스와 정의다. 이를 **어느 SAP 객체에서 가져왔는지 알 수 있는 파일 묶음으로 만든다.** ERP를 복제하거나 업무 데이터를 전부 내려받는 작업은 아니다. 대상 기록의 환경은 ECC 6.0 / SAP_BASIS 700이다.

## 2. 실제로 무엇이 부족했는가: 파일이 있어도 업무가 보이지 않았다

### 코드를 읽는 데 코드 이외의 자료가 필요했다

웹 화면에서 버튼을 누르는 경우를 생각해 보자. JavaScript가 동작한 뒤 페이지의 서버 이벤트나 호출 경로를 거쳐 ABAP 함수가 처리할 수 있다. 함수의 입력·출력 형식과 테이블 필드의 뜻은 별도 정의에 있고, 오류가 나면 메시지 클래스의 안내가 표시될 수 있다. 관계를 이해하기 위한 일반적인 예이므로, 실제 연결은 해당 파일을 읽어 확인한다.

| 추출 대상 | 쉽게 말하면 | 함께 봐야 하는 관계 |
|---|---|---|
| ABAP 프로그램·Include | 처리 순서와 나누어 둔 공통 코드 | 어느 프로그램이 어떤 Include를 사용하는지 |
| 함수 본문·인터페이스 | 처리 코드와 입력·출력 설명서 | Import·Export·Changing·Tables·Exception 정의와 본문 |
| DDIC 정의 | 데이터의 설계도 | 테이블·구조·필드·데이터 요소·도메인. 실제 데이터 행과 구분 |
| BSP Layout | SAP 웹 페이지의 화면 구성 | 페이지 속성·이벤트·JS·CSS와의 연결 |
| BSP 속성·이벤트·타입 | 페이지 설정과 서버 처리 코드 | Layout에서 쓰는 값과 페이지 동작 |
| MIME | JS·CSS·이미지·글꼴 등 화면에서 쓰는 파일 | URL·객체 ID·소유 패키지·앱과 파일의 대응 |
| 메시지 클래스 | 오류 번호와 안내 문구 | 코드의 메시지 번호와 실제 표시 문장 |

초기 ZFI1 추출에서 8,886개 파일 비교는 통과했다. 하지만 당시 추출기는 BSP·MIME 본문을 지원하지 않았고, 사용자가 웹 화면 자료가 보이지 않는다고 지적하면서 범위를 보완했다. **만들어진 파일이 정상인지와 필요한 자료를 모두 가져왔는지는 따로 확인해야 했다.**

### 실제 오류를 통해 추출 방법을 고쳤다

- **함수 소스를 놓친 문제:** 처음에는 언어 조건 때문에 함수 읽기가 막혔다. 이후에는 API의 `NEW_SOURCE` 반환값만 확인하다가 70개를 놓쳤다. 값이 비어 있으면 `SOURCE`도 확인하도록 바꿨고, 당시 시험에서 127개 함수를 읽었다. 같은 API라도 실제 시스템이 어떤 형태로 값을 반환하는지 확인해야 했다.
- **사람이 찾기 어려운 폴더:** 숫자로 된 페이지 폴더와 원시 XML만 보면 SE80의 어느 탭에 해당하는지 알기 어려웠다. 폴더와 파일에 실제 페이지명, `Layout`, `Event Handler`, `Properties.xml` 등의 이름을 사용했다. 함수 본문도 각 함수 폴더 아래에 두어 찾아가기 쉽게 맞췄다.
- **XML을 보기 좋게 바꾸다가 값이 달라지는 위험:** 정렬 전후의 값이 보존되는지 검사하다가, 공백 문자열의 변환을 잘못 가정해 처리가 중단됐다. 0.3.15에서는 SAP 원시 XML과 정렬 XML의 태그·속성·리프 값을 비교하도록 고쳤다. 읽기 쉬운 형태로 바꾸면서 원래 값도 유지되는지 함께 확인했다.
- **압축 파일이 작은데 용량 초과:** 작업 파일과 원본 사본이 함께 들어가므로 압축 ZIP 크기보다 비압축 합계가 중요했다. 한도를 조정하면서도 큰 파일·생략·실패를 로그로 구별했다.

이 사례들은 당시 버전의 실행·수정 기록이다. 과거 패키지의 성공 건수를 최신 버전의 모든 객체 검증으로 옮기지는 않는다.

## 3. 어떤 범위를 정했는가: 패키지 전체와 BSP 한 앱을 나눈다

### 처음에는 담당 패키지가 기준이었다

선택 패키지와 하위 패키지에서 지원하는 객체를 가져오는 것으로 범위를 정했다. 참조 관계가 있다는 이유만으로 다른 업무의 소스까지 계속 따라가지는 않기로 했다. 실제로 ZFI1을 추출할 때, 다른 패키지인 ZBIZCARD 소속 BSP에 연결된 MIME까지 가져오는 것은 취지와 다르다는 사용자 지적이 있었다. 범위를 정하지 않으면 담당 업무를 이해하려던 추출이 ERP 전체 수집으로 번질 수 있다.

범위 밖 객체는 이름과 관계를 확인할 과제로 남긴다. 파일이 없으면 해당 기능이 ERP에 없다는 뜻이 아니라, 이번 추출에 포함되지 않았을 수 있다.

### 이후 웹 화면 개편 때문에 BSP 한 앱 모드를 추가했다

ERP 웹 개편을 진행하면서 `ZWEB_COMMON`, `ZWEB_WF`처럼 특정 BSP 애플리케이션만 필요한 작업이 생겼다. 매번 함수그룹과 DDIC까지 가져오는 것보다 **그 앱의 페이지와 JS·CSS·이미지를 묶어 고치고 비교하는 방식**이 작업 범위에 맞았다.

그래서 패키지 모드를 유지하면서 BSP 한 앱 모드를 추가했다. 두 모드는 목적에 따라 선택한다.

| 하고 싶은 일 | 선택할 범위 | 이유 |
|---|---|---|
| 담당 업무의 코드·데이터 구조를 폭넓게 이해 | 개발 패키지 | 프로그램·함수·DDIC 등 함께 읽을 자료가 필요 |
| 특정 웹 앱의 화면·자산을 개편 | BSP 한 앱 | 실제 변경할 페이지·웹자산에 집중 |

한 앱을 추출해도 MIME의 실제 소유 패키지는 여러 개일 수 있다. 0.4.1에서는 본문을 한 앱 폴더에 모으고 실제 소유권은 metadata에 남겼다. 다른 패키지 소유라는 이유로 그 앱의 자산을 삭제한 것이 아니다.

Export의 범위만 줄이고 DIAG가 전체 패키지를 조회하면, 애초에 범위 밖인 파일을 누락으로 잘못 표시할 수 있다. 그래서 두 도구의 **추출 모드·앱 이름·파일 목록·원본·현재 SAP 조회 범위**를 함께 맞추도록 변경했다.

## 4. 어떻게 구현했는가: 읽기·파일화·원본 보존·점검

### SAP 객체를 파일과 다시 대응시킨다

1. 대상 패키지 또는 BSP 앱을 정하고 지원 객체 목록을 만든다.
2. 실제 시스템에서 사용 가능한 읽기 기능으로 본문과 정의를 가져온다. 없는 API나 최신 ABAP 문법이 동작한다고 가정하지 않는다.
3. 사람이 찾기 쉬운 경로로 저장한다. 함수 본문과 입력·출력 정의, BSP 페이지와 이벤트·자산을 연결할 수 있게 한다.
4. `manifest.xml`에는 파일이 어느 객체인지와 추출 범위를 기록한다. catalog와 로그를 함께 읽어 성공·제외·생략·실패·미지원을 구분한다. 모든 제외가 개별 오류 로그로 남는 것은 아니다.
5. `.devhub/baseline/`에 추출 당시 원문 사본을 보존한다. 이후 수정은 작업 파일에서 하고 이 기준 사본은 바꾸지 않는다.
6. 경로 충돌·크기·XML 값·파일 무결성 등을 확인하고 ZIP으로 전달한다.

BSP 한 앱 묶음에는 `pages/`, `MIMEs/`, `catalog/mime-metadata.xml`, `catalog/web-assets.xml`, `.devhub/baseline/` 등이 들어간다. Layout 이외의 속성·이벤트·타입도 이해와 비교를 위해 보존한다. 이 모두를 다시 업로드할 수 있다는 뜻은 아니다.

### 왜 원본·추출본·ERP 서버를 세 방향으로 비교하나요?

다음은 교육용 예시다. 월요일에 SAP 코드를 내려받고 화요일에 내 PC에서 화면 문구를 고쳤다. 같은 날 다른 개발자는 SAP의 예외 처리를 고쳤다. 수요일에 PC와 서버의 두 파일만 비교하면 서로 다르다는 사실만 알 수 있다. 월요일 원본을 함께 보면 **내가 바꾼 부분과 서버에서 바뀐 부분**을 구분할 수 있다.

| 자료 | 의미 | 바꿔도 되는가 |
|---|---|---|
| 원본 | 추출할 때 보존한 baseline | 비교 기준이므로 편집하지 않음 |
| 추출본 | 지금 ZIP에 담긴 작업 파일. 로컬 수정이 있을 수 있음 | 변경 대상이며 수정 이유와 범위를 기록 |
| SAP | 진단할 때 현재 서버에서 읽은 내용 | 로컬 작업만으로 바뀌지 않으며 별도 적용 절차 필요 |

- **원본=추출본, SAP만 다름:** 나는 안 바꿨고 서버가 바뀌었다. 오래된 파일로 덮으면 서버 변경을 잃을 수 있다.
- **원본=SAP, 추출본만 다름:** 서버는 그대로이고 내 작업만 바뀌었다. 검토·검사할 변경 후보다.
- **추출본=SAP:** 이미 같은 내용이다. 반복 반영할 이유가 있는지 먼저 본다.
- **셋 다 다름:** 양쪽 변경을 읽고 병합·재검토해야 한다.
- **어느 하나를 읽지 못함:** 비교 자료가 부족하다. ‘없음’이나 ‘변경 없음’으로 바꾸어 적지 않는다.

baseline의 중복 파일은 AI 검색에서 제외하더라도 비교 기준으로 보존해야 한다. 해시로는 같은 파일인지 확인할 수 있다. 하지만 해시만 남기면 원본 본문이나 달라진 줄을 복원할 수 없다.

### 최종적으로 만들어진 도구

| 도구 · 확보 버전 | 하는 일 | 결과를 읽을 때의 경계 |
|---|---|---|
| `Z_PACKAGE_EXPORT` 0.4.1 | 패키지 또는 BSP 한 앱을 파일화 | 업무 데이터 행·모든 SAP 객체의 완전 복제가 아님 |
| `DEVHUB_CHECK` 0.3.3 | PC의 추출 파일·원본 대응·로그 점검 | 현재 SAP를 조회하지 않음. 새 BSP manifest 0.4 호환은 추가 확인 |
| `Z_PACKAGE_DIAG` 0.7.1 | 원본·추출본·SAP 비교, 지원 검사, 기존 웹자산 선택 반영 | ABAP·DDIC는 진단 범위. 최신 SAP 성공은 별도 확인 |

패키지 manifest는 0.3, BSP 모드는 0.4 형식이다. 자료실의 과거 0.3.18 Export와 최신 0.4.1을 혼동하지 말고, 도구 헤더와 묶음의 안내를 함께 확인한다.

## 5. 직접 해보기: 첫 추출물에서 함수 하나와 페이지 하나 찾기

SAP 실행은 개발 환경의 담당자가 도구 버전·권한·지원 범위를 확인한 뒤 진행한다. 처음 방문한 분은 이미 확보된 추출 ZIP을 읽는 것부터 시작해도 된다.

1. ZIP을 별도 폴더에 풀고 manifest에서 대상·모드·시점을 확인한다.
2. 로그에서 성공뿐 아니라 실패·생략·미지원이 있는지 찾는다. CHECK가 통과해도 이 목록을 생략하지 않는다.
3. 함수 하나의 본문과 입력·출력 XML을 열고 같은 함수에 대응하는지 본다.
4. BSP가 있다면 실제 페이지명, Layout, 이벤트, 참조 자산을 SE80의 해당 페이지와 대조한다.
5. 작업 파일과 baseline의 대응 경로를 확인하고 기준본을 Git으로 관리할 준비를 한다.

```text
이 추출 폴더의 manifest, catalog, 로그와 가이드를 먼저 읽어 주세요.
대상 패키지 또는 BSP 앱, 추출 시점, 실패·생략·미지원 범위를 정리해 주세요.
함수 하나는 본문과 입력·출력 정의를, BSP 페이지 하나는 Layout·이벤트·자산을
실제 파일 경로로 연결해 설명해 주세요. 추출물에서 찾지 못한 대상은 미확보로 표시해 주세요.
baseline과 원천 파일은 수정하지 말고, 현재 SAP를 확인한 것처럼 쓰지 마세요.
```

결과물은 “파일 몇 개를 가져왔다”는 숫자보다 **무엇을 읽을 수 있고 무엇을 아직 모르는지 설명한 목록**이어야 한다.

## 6. 한계와 다음 방향: 추출 범위와 적용 범위는 다르다

현재 자료는 개발 코드·정의 중심이다. 실제 직원·전표 등 업무 데이터 행은 포함하지 않는다. 외부 참조의 본문, 미지원 클래스 본문, 메시지 Long Text 등은 확인 범위 밖이다. 한국어를 우선하되 항목별로 영어를 보완하는 정책도 모든 언어의 완전 수집을 뜻하지 않는다.

파일당 16 MiB, 비압축 전체 512 MiB 한도가 있으며 baseline도 용량에 영향을 준다. 객체를 순차적으로 읽으므로 추출 도중 서버가 바뀌면 모든 파일이 정확히 같은 시점이라고 보장할 수도 없다.

최신 0.4.1 소스와 BSP 한 앱 ZIP 형식은 확보했다. DIAG 0.7.1이 실제 SAP에서 비교·저장·활성화에 성공했는지는 추가 확인이 필요하다. 현재 확인된 성공은 0.6.11에서 특정 BSP 페이지의 기존 미활성본을 재사용하고 활성화한 뒤 SE80에서 확인한 사례다. 이를 모든 객체의 일괄 반영 성공으로 해석하지 않는다.

다음 [03. GITHUB 연동](#/learn/workspace)에서는 추출한 자료를 보존하고 변경 이력을 공유한다. 서버와의 실제 비교·선택 반영은 [08. 코드 검증 및 적용](#/learn/diagnosis)에서 이어간다.
