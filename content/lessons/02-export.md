# ERP 소스 추출하기

## 1. 왜 추출했는가

SAP 프로그램 하나의 코드를 복사해도 업무 전체를 이해하기는 어렵습니다. 그 프로그램이 사용하는 함수, 공통 코드, 필드 정의, 웹 화면, 오류 메시지가 서로 다른 곳에 있기 때문입니다.

따라서 AI가 프로그램의 역할과 연결 관계를 읽을 수 있도록 관련 자료를 함께 추출했습니다. 최초 요청은 **팀이 SE80에서 개발·관리하던 패키지 단위로 자료를 꺼내는 것**이었습니다. 패키지, 또는 개발클래스는 관련 개발물을 묶는 SAP의 관리 단위입니다.

이 단위로 모은 자료를 PC의 VS Code와 AI로 분석하고, Git으로 변경 이력을 관리하려고 했습니다. 추출 대상은 ECC 6.0 / SAP_BASIS 700의 개발 소스와 객체 정의이며, 각 파일에는 **어느 SAP 객체에서 가져왔는지 찾아갈 수 있는 정보**를 함께 남깁니다.

## 2. 실제로 무엇이 부족했는가

### ABAP 코드와 연관 자료

웹 화면에서 버튼을 누르면 JavaScript와 서버 이벤트를 거쳐 ABAP 함수가 실행될 수 있습니다. 그런데 함수 본문만 읽으면 입력값의 형식이나 테이블 필드의 의미까지 알기 어렵습니다. 따라서 코드와 함께 인터페이스·데이터 정의·화면 자산을 연결해 읽어야 합니다.

| 추출 대상 | 쉽게 말하면 | 함께 읽는 관계 |
|---|---|---|
| ABAP 프로그램·Include | 처리 순서와 공통 코드 | 프로그램과 Include의 사용 관계 |
| 함수 본문·인터페이스 | 처리 코드와 입력·출력 설명서 | Import·Export·Changing·Tables·Exception 정의와 본문 |
| DDIC 정의 | 데이터의 설계도 | 테이블·구조·필드·데이터 요소·도메인 |
| BSP Layout | SAP 웹 페이지의 화면 구성 | 페이지 속성·이벤트·JS·CSS |
| BSP 속성·이벤트·타입 | 페이지 설정과 서버 처리 코드 | Layout에서 사용하는 값과 페이지 동작 |
| MIME | JS·CSS·이미지·글꼴 등 화면 자산 | URL·객체 ID·소유 패키지·앱과 파일의 대응 |
| 메시지 클래스 | 오류 번호와 안내 문구 | 코드의 메시지 번호와 실제 표시 문장 |

초기 ZFI1 추출에서는 8,886개 파일의 비교가 통과했습니다. 이후 사용자가 웹 화면 자료를 찾으면서 BSP·MIME 본문도 필요하다는 점이 드러났습니다. 그래서 파일의 정상 저장 여부와 함께 **업무를 이해하는 데 필요한 자료의 포함 여부**를 따로 점검하도록 범위를 보완했습니다.

### 추출 오류와 개선 과정

- **함수 소스 읽기:** 언어 조건을 조정한 뒤에도 API의 `NEW_SOURCE` 반환값만 읽어 함수 70개를 놓쳤습니다. 따라서 값이 비어 있으면 `SOURCE`도 읽도록 변경했고, 당시 시험에서는 함수 127개를 가져왔습니다.
- **폴더와 파일 이름:** 숫자로 된 페이지 폴더와 원시 XML은 SE80의 어느 항목인지 찾기 어려웠습니다. 그래서 실제 페이지명과 `Layout`, `Event Handler`, `Properties.xml` 등의 이름을 사용하고, 함수 본문도 해당 함수 폴더에 배치했습니다.
- **XML 값 보존:** XML을 보기 좋게 정렬하는 과정에서 공백 문자열의 처리 방식 때문에 검사가 중단됐습니다. 따라서 0.3.15에서는 SAP 원시 XML과 정렬 XML의 태그·속성·리프 값을 비교해 원래 값을 유지하도록 변경했습니다.
- **압축 용량 계산:** ZIP에는 작업 파일과 원본 사본이 함께 들어갑니다. 따라서 압축 후 파일 크기와 함께 비압축 합계를 기준으로 용량을 계산하고, 큰 파일·생략·실패를 로그로 구분했습니다.

## 3. 어떤 범위를 정했는가

### 추출 기준: 담당 패키지

담당 업무를 이해하려면 범위를 먼저 정해야 합니다. 참조 관계를 계속 따라가면 다른 업무의 자료까지 포함될 수 있기 때문입니다.

실제로 ZFI1을 추출할 때 다른 패키지인 ZBIZCARD 소속 BSP에 연결된 MIME까지 가져오는 것은 목적과 다르다는 의견이 있었습니다. 따라서 **선택한 패키지와 하위 패키지의 지원 객체**를 기본 추출 범위로 정했습니다.

### BSP 애플리케이션 별도 추출

ERP 웹 화면을 개편하면서 `ZWEB_COMMON`, `ZWEB_WF`처럼 특정 BSP 애플리케이션의 자료만 필요한 작업이 생겼습니다. 이 경우에는 함수그룹과 DDIC를 함께 가져오기보다 **해당 앱의 페이지와 JS·CSS·이미지를 묶어 수정·비교하는 방식**이 적합했습니다.

그래서 패키지 모드에 BSP 한 앱 모드를 추가했습니다. 작업 목적에 따라 다음과 같이 선택합니다.

| 하고 싶은 일 | 선택할 범위 | 이유 |
|---|---|---|
| 담당 업무의 코드·데이터 구조를 폭넓게 이해 | 개발 패키지 | 프로그램·함수·DDIC를 함께 분석 |
| 특정 웹 앱의 화면·자산을 개편 | BSP 한 앱 | 변경할 페이지와 웹자산에 집중 |

한 앱이 사용하는 MIME은 여러 패키지에 속할 수 있습니다. 따라서 0.4.1에서는 본문을 앱 폴더에 모으고, 실제 소유 패키지는 metadata에 기록했습니다. 이렇게 하면 앱 단위로 작업하면서 원래 객체의 소유 관계도 따라갈 수 있습니다.

추출 범위를 줄인 뒤에는 DIAG의 비교 범위도 맞췄습니다. 두 도구의 범위가 다르면 앱 밖의 파일을 누락으로 판단할 수 있기 때문입니다. 따라서 **추출 모드·앱 이름·파일 목록·원본·현재 SAP 조회 범위**를 같은 기준으로 연결했습니다.

## 4. 어떻게 구현했는가

### SAP 객체와 파일 경로 연결

1. 대상 패키지 또는 BSP 앱을 정하고 지원 객체 목록을 만듭니다.
2. 해당 시스템의 읽기 기능으로 소스 본문과 객체 정의를 가져옵니다.
3. 함수 본문과 입력·출력 정의, BSP 페이지와 이벤트·자산을 찾아가기 쉬운 경로에 저장합니다.
4. `manifest.xml`에 파일과 SAP 객체의 대응 관계, 추출 범위를 기록합니다. catalog와 로그에는 처리 결과를 남깁니다.
5. `.devhub/baseline/`에 추출 당시의 원문 사본을 보존합니다. 이후 수정은 작업 파일에서 진행합니다.
6. 경로 충돌·크기·XML 값·파일 무결성을 점검하고 ZIP으로 묶습니다.

BSP 한 앱 묶음에는 `pages/`, `MIMEs/`, `catalog/mime-metadata.xml`, `catalog/web-assets.xml`, `.devhub/baseline/` 등이 들어갑니다. Layout과 속성·이벤트·타입을 함께 보존하므로 화면 구성과 서버 처리의 관계를 읽을 수 있습니다.

### 원본·추출본·ERP 서버의 3자 비교

월요일에 SAP 코드를 내려받고, 화요일에 PC에서 화면 문구를 수정했다고 가정합니다. 같은 날 다른 개발자가 SAP의 예외 처리를 고쳤다면 PC와 서버의 파일이 모두 달라집니다.

이때 두 파일만 비교하면 어느 쪽에서 무엇을 바꿨는지 알기 어렵습니다. 따라서 월요일의 원본도 함께 비교합니다. 원본을 기준으로 읽으면 **내가 바꾼 부분과 서버에서 바뀐 부분**을 구분할 수 있습니다.

| 자료 | 의미 | 관리 방법 |
|---|---|---|
| 원본 | 추출 당시 보존한 baseline | 비교 기준으로 보존 |
| 추출본 | 현재 ZIP에 담긴 작업 파일 | 수정 이유와 변경 범위 기록 |
| SAP | 진단 시점에 서버에서 읽은 내용 | 서버 변경과 적용 결과 확인 |

- **원본=추출본, SAP만 다름:** 서버에서 바뀐 내용을 먼저 살펴봅니다. 오래된 작업 파일을 적용하면 서버 변경을 덮어쓸 수 있기 때문입니다.
- **원본=SAP, 추출본만 다름:** 로컬에서 변경한 부분을 검토하고 검사합니다.
- **추출본=SAP:** 같은 내용이므로 중복 반영 여부를 살펴봅니다.
- **셋 다 다름:** 양쪽 변경의 목적을 읽고 병합합니다.

원본은 AI 검색 대상에서 제외하더라도 비교 기준으로 보존합니다. 해시는 파일이 같은지 판단하는 데 사용하고, 실제 원본 본문은 달라진 줄을 비교하는 데 사용합니다.

### 추출·점검·진단 도구

| 도구 · 버전 | 역할 | 주요 결과 |
|---|---|---|
| `Z_PACKAGE_EXPORT` 0.4.1 | 패키지 또는 BSP 한 앱 추출 | 소스·객체 정의·manifest·baseline |
| `DEVHUB_CHECK` 0.3.3 | PC의 추출 묶음 점검 | 파일·원본 대응·로그 점검 결과 |
| `Z_PACKAGE_DIAG` 0.7.1 | 원본·추출본·SAP 비교와 지원 대상 검사·선택 반영 | 비교표·검사 결과·웹자산 반영 로그 |

패키지 manifest는 0.3, BSP 모드는 0.4 형식을 사용합니다. 도구와 추출 묶음을 함께 관리하면 어떤 범위와 형식으로 만든 자료인지 구분할 수 있습니다.

## 5. 직접 해보기

첫 연습에서는 추출 ZIP에서 함수 하나와 BSP 페이지 하나를 찾아봅니다. 파일 이름에서 끝내지 않고 관련 정의와 자산까지 연결하는 것이 목적입니다.

1. ZIP을 별도 폴더에 풀고 manifest에서 대상·모드·시점을 읽습니다.
2. 로그에서 객체별 처리 결과를 살펴봅니다.
3. 함수의 본문과 입력·출력 XML을 열고 같은 함수에 대응하는지 비교합니다.
4. BSP 페이지의 Layout·이벤트·참조 자산을 SE80의 해당 페이지와 대조합니다.
5. 작업 파일과 baseline의 대응 경로를 찾고 Git으로 관리할 준비를 합니다.

```text
이 추출 폴더의 manifest, catalog, 로그와 가이드를 먼저 읽어 주세요.
대상 패키지 또는 BSP 앱, 추출 시점과 객체별 처리 결과를 정리해 주세요.
함수 하나의 본문과 입력·출력 정의를 실제 파일 경로로 연결해 주세요.
BSP 페이지 하나는 Layout·이벤트·참조 자산의 관계를 설명해 주세요.
분석에 사용한 파일 경로를 함께 적고, baseline과 원천 파일은 보존해 주세요.
```

이 연습의 결과는 **함수·페이지·정의·자산이 실제 파일 경로로 연결된 목록**입니다. 이 목록을 만들면 다음 과정에서 AI에게 분석할 범위를 구체적으로 전달할 수 있습니다.

## 6. 추출 자료 관리

추출 묶음에는 개발 코드와 정의가 들어갑니다. DDIC는 데이터의 구조를 설명하며, 실제 직원이나 전표 같은 업무 데이터 행은 별도 조회 대상으로 다룹니다.

파일당 16 MiB, 비압축 전체 512 MiB 한도를 사용하므로 baseline 사본도 용량 계산에 포함합니다. 또한 객체를 순서대로 읽기 때문에 추출 시점을 함께 기록해 파일 묶음의 기준을 관리합니다.

다음 [03. GITHUB 연동](#/learn/workspace)에서는 추출한 자료와 변경 이력을 공유합니다. 서버와의 비교·선택 반영은 [08. 코드 검증 및 적용](#/learn/diagnosis)에서 이어갑니다.
