# 업무 지도 만들기

## 1. 왜 지도가 필요한가: 문서를 모았는데 무엇부터 읽을지 모르겠습니다

업무 자료를 모으면 다음 문제가 생깁니다. “시간외 단가가 바뀌면 어디를 확인해야 하지?”라는 질문에 규정 폴더, 과거 대화, 함수 설명을 각각 찾아야 합니다. 파일이 수백 개가 되면 사람도 AI도 매번 같은 탐색을 반복합니다.

업무지도는 **질문 하나에서 관련 기준·협의·코드·확인 사례로 찾아가는 길을 적은 문서**입니다. 규정의 복사본을 또 만드는 대신 “이 기준은 이 대화에서 정정됐고, 이 함수가 관련 값을 읽는다”는 연결 이유를 남깁니다.

## 2. 무엇을 오해했는가: 폴더를 열면 관계가 저절로 생길까요?

실제 대화에서는 이미 skill·knowledge·harness·exports가 있는데 Obsidian으로 열면 자동으로 관계가 만들어지는지, AI가 그 그래프를 보는지, 답변 속도가 빨라지는지 질문했습니다.

Obsidian은 MD 문서와 링크를 사람이 탐색하는 도구입니다. 폴더를 보관함으로 열었다고 업무의 의미가 자동으로 정리되지는 않습니다. **사람은 노트와 그래프를 보고, AI는 같은 MD 본문과 링크를 읽습니다.** 그래프의 선에는 연결이 있다는 사실이 보이지만, 왜 관련 있는지는 문서에 적어야 합니다.

설치만으로 모델 계산이 빨라지는 것도 아닙니다. 필요한 자료를 먼저 찾게 하면 탐색 부담을 줄일 수 있지만, 실제 시간이 얼마나 줄었는지는 같은 질문으로 비교해야 합니다.

## 3. 어떤 방향을 택했는가: 기존 폴더를 유지하고 길 안내를 추가하기

기존 자료를 새 폴더 구조로 모두 옮기면 소스 경로와 스킬의 참조가 깨질 수 있습니다. 그래서 원래 위치를 유지하고 `maps/`에 연결 문서를 추가하는 방식을 택했습니다. 업무별로 작게 시작하면 무엇을 연결했고 무엇이 오래됐는지 관리하기도 쉽습니다.

| 구성 | 쉬운 역할 | 담을 내용 |
|---|---|---|
| INDEX | 첫 안내판 | 질문·주제별로 읽을 업무지도 |
| 업무별 지도 | 한 업무의 찾아가는 길 | 기준·협의·구현·검증의 관계와 근거 |
| 소스 설명 MD | 프로그램을 읽기 전 안내문 | 객체의 역할·실제 원본 위치·확인 범위 |
| Obsidian Vault | 문서를 여는 보관함 | 관련 자료가 모인 기존 프로젝트 폴더 |
| 미확인 목록 | 길이 끊긴 지점의 기록 | 미추출 코드·없는 원문·추가 확인할 담당 |

링크가 많을수록 좋은 지도는 아닙니다. “관련 있음”이라는 선을 늘리는 대신 관계를 말로 설명할 수 있는 연결을 만듭니다.

## 4. 어떻게 만드는가: 질문 하나에서 원문까지 연결하기

1. 기존 INDEX·스킬·소스의 실제 위치를 확인합니다. 자료를 이동하지 않습니다.
2. “시간외 단가와 적용일 확인”처럼 질문 하나를 고릅니다.
3. 적용 기준, 후속 협의, 관련 코드, 과거 오류와 검증 질문을 찾습니다.
4. `maps/`의 연결 문서에 파일 경로와 관계의 의미를 적습니다. 확인된 호출과 단순 검색 후보를 구별합니다.
5. INDEX → 지도 → 실제 근거 문서의 링크를 차례로 엽니다. 다른 저장소나 미추출 코드라면 그 경계를 표시합니다.
6. Obsidian에서 기존 폴더를 Vault로 엽니다. 그래프에서 연결을 보고, 노트를 열어 관계 설명을 읽습니다.
7. 원문이 갱신되면 지도도 검토합니다. 오래된 행 번호나 적용일이 남지 않도록 합니다.

```markdown
# 시간외 단가를 확인하는 지도
- 업무 질문: 대상 직군과 근무일에 어떤 기준을 적용하는가?
- 기준 문서: 실제 정책 파일 경로와 적용일
- 후속 정정: 당시 설명을 바꾼 대화·피드백 경로
- 구현 연결: 실제로 읽은 함수·테이블 설명 경로
- 관계의 의미: 기준일과 등급을 조회할 때 이 자료를 확인함
- 확인 수준: 문서 확인 / 코드 구간 확인 / 실행 확인 중 해당 항목
- 남은 질문: 개인 마스터 반영과 과거 입력 보정 완료 여부
```

위 양식은 작성 예시입니다. 없는 경로나 실행 결과를 채워 넣지 않습니다. [업무 연결 문서 양식](downloads/relationship-map.md)도 사용할 수 있습니다.

### Obsidian에서 기존 폴더 열기

[공식 설치 안내](https://obsidian.md/help/install)에서 운영체제에 맞는 앱을 설치합니다. Windows는 설치 프로그램의 안내를 따르고, macOS는 앱을 Applications로 옮겨 엽니다.

Vault 선택 화면에서 **Open folder as vault → Open**을 누르고 업무 문서와 maps가 들어 있는 기존 프로젝트 폴더를 선택합니다. 이미 다른 Vault를 열었다면 왼쪽 아래 Vault 메뉴의 **Manage Vaults**에서 선택할 수 있습니다. 파일을 새 보관함으로 옮길 필요는 없습니다. [공식 Vault 안내](https://obsidian.md/help/manage-vaults)

먼저 `maps/INDEX.md`를 열고 문서 링크를 눌러 보세요. 그다음 그래프를 보면 선이 무엇을 연결하는지 이해하기 쉽습니다. 위 설치·열기 메뉴는 2026-10-26 공식 안내를 확인했습니다.

## 5. 실제 사례: 단가 질문에서 정책·코드·검증으로

### 5-1. 실제 확보된 rates.md 읽기

근로시간 프로젝트의 `maps/topics/rates.md`는 단가와 직군·효력일을 연결합니다. 먼저 2026-09-01 기준 문서를 읽고, 후속 직군 정정과 과거 협의를 구분합니다. 이어 근무일의 인사·등급을 읽는 함수, 실비를 계산하는 함수의 설명으로 연결합니다.

지도에는 과거 입력 보정이나 실제 지급 확인이 미완료라는 경계도 남아 있습니다. 검증 질문 Q18·Q19·Q35·Q36으로 이어지지만, 질문을 연결했다는 사실이 그 질문을 모두 통과했다는 뜻은 아닙니다. 답변을 만들 때는 기대 답안 대신 실제 정책·협의 자료를 근거로 읽습니다.

이처럼 하나의 질문에서 **기준 → 정정 → 구현 → 남은 확인**을 따라갈 수 있으면 지도가 제 역할을 합니다. [11. 근로시간 AI 에이전트 구축](#/learn/worktime-agent)의 문서 지도에서도 실제 MD를 찾아볼 수 있습니다.

### 5-2. 실제 Obsidian 화면으로 찾기

실제 적용 화면 2장입니다. 첫 지도는 업무와 근거를 따라 읽고, 전체 그래프는 문서 연결 규모를 살펴보는 데 사용합니다.

#### 업무를 중심으로 읽는 지도

![사례 1 · 실제 Obsidian 업무지도. INDEX 주변에 settlement, selective, working-time, SRC 문서와 소스 유형별 색인이 연결되어 있습니다. 클릭하면 확대할 수 있습니다.](assets/images/obsidian-business-map.png)

| 화면에서 찾을 곳 | 업무 탐색에 활용하는 방법 |
|---|---|
| `INDEX`와 `INDEX-DB테이블`, `INDEX-함수` 등 | 업무 문서에서 구현 근거를 찾을 진입점을 고릅니다. |
| `settlement`, `selective`, `working-time` | 정산·선택근무·근로시간의 관련 문서를 탐색합니다. |
| `SRC-10-early-SRC-11` 등 SRC 노드 | 정리 문장의 근거가 된 협의 이력으로 돌아갑니다. |
| `OPEN_QUESTIONS`, `open-questions` | 미확인 사항이 확정된 지식과 섞이지 않도록 확인합니다. |

정산 질문은 `settlement`에서 시작해 연결 문서의 적용 조건·구현·출처를 확인합니다. 캡처의 색상 분류 규칙은 미확인입니다.

#### 전체 규모를 살펴보는 그래프

![사례 2 · 실제 Obsidian 전체 연결망. 촘촘한 노드와 군집을 통해 연결 규모와 중심부·주변부를 살펴보는 화면입니다.](assets/images/obsidian-full-graph.png)

전체 그래프에서 연결이 집중된 곳과 떨어진 문서를 찾고, 개별 질문은 업무별 지도로 좁혀 읽습니다. 현재 자료는 적용 캡처이며 링크 유효성과 성능은 추가 확인 대상입니다.

> **직접 찾아보기** · 캡처에서 `settlement` → 업무 노드 → SRC 문서를 찾아보세요. 실제 Vault에서는 링크를 열어 관계 설명과 출처 날짜를 확인합니다.

## 6. 한계와 다음 방향: 연결의 수보다 연결의 정확성

초기 대화에서는 설계 단계였지만 후속 자료에는 실제 `maps/` 문서와 적용 캡처가 있습니다. 당시 검증 기록에는 23개 업무군·100개 단계·651개 정규 소스/데이터 설명을 정리한 범위가 남아 있습니다. 이 숫자는 모든 업무 규칙이나 모든 SAP 실행을 검증했다는 뜻이 아닙니다.

특히 포털의 MD 스냅샷에는 소스 설명 문서가 있어도 그 문서가 가리키는 ABAP 원본 전체가 포함되지는 않습니다. 실제 코드를 확인하려면 해당 추출본이 필요합니다. 파일이 열리는지 확인하는 링크 검사와 문장 내용이 업무적으로 맞는지 검토하는 작업도 나눕니다.

처음 만든 지도는 질문 하나로 시험하세요. 필요한 문서를 찾는 데 도움이 됐는지, 후속 정정을 놓치지 않았는지, 없는 근거는 구체적으로 드러나는지 봅니다. 다음 [07. 업무 스킬 및 회귀](#/learn/feedback)에서는 이 탐색 순서를 반복 절차로 만들고 틀린 답을 고치는 방법을 다룹니다.
