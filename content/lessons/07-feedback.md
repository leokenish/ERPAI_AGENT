# 피드백을 다음 검증으로 남기기

## 업무 답변도 검증 대상입니다

답변의 적용일과 예외를 확인하고, 정정 근거를 지식 문서와 회귀 사례에 반영합니다.

수정된 지식과 검증 기록은 프로젝트 파일에 저장합니다.

## 피드백의 흐름

1. 원래 질문·답변·사용자 정정을 기록합니다.
2. 원문·적용 시점·후속 협의를 확인합니다.
3. 원인이 있는 지식·색인·작업 절차를 수정합니다.
4. 같은 질문과 관련 경계 사례를 회귀 항목으로 남깁니다.
5. 실행 가능한 검증을 수행하고 결과와 한계를 기록합니다.

| 오류 유형 | 수정할 대상 |
|---|---|
| 원문 요약 오류 | 업무 지식과 관련 FAQ |
| 필요한 자료를 못 찾음 | INDEX·동의어·탐색 절차 |
| 적용일·대상 혼동 | 조건 설명과 경계 사례 |
| 정책 근거 충돌 | 양쪽 출처와 검토 요청 |
| 실제 코드 오류 의심 | 별도의 코드 변경 검토 과제 |

## 판정 상태를 구분하기

| 상태 | 뜻 |
|---|---|
| PASS | 실제 실행한 해당 검사 기준 충족 |
| FAIL | 실제 검사에서 기준 위반 확인 |
| REVIEW_REQUIRED | 근거 충돌 또는 담당자 판단 필요 |
| NOT_RUN | 자료·도구 부재 등으로 미실행 |

문서 수정 상태와 검사 결과를 따로 기록합니다. 질문 초안 34개는 검증할 항목의 목록입니다.

## 따라 하기: 피드백 한 건 작성

[피드백 기록 양식](downloads/feedback-record.md)을 복사합니다. 질문, 적용 조건, 근거 위치, 반드시 답해야 할 요소와 금지할 단정을 적습니다. 실제 검사기가 없으면 수동 대조 결과를 기록하고 자동 검사는 NOT_RUN으로 남깁니다.

```text
방금 답변에서 두 근무유형을 혼동했어.
기존 규정과 후속 대화의 대상·적용일을 확인해줘.
확인된 오류는 지식에 반영하고 피드백과 회귀 사례를 남겨줘.
근거가 충돌하면 REVIEW_REQUIRED로 기록해줘.
이번 작업에서는 SAP 추출 소스와 baseline을 수정하지 마.
```

## 반복 수정의 기준

한 건당 수정·재검증은 최대 3회를 기본으로 합니다. 근거가 부족하거나 같은 실패가 반복되면 담당자에게 확인을 요청합니다. 지식 수정과 SAP 반영은 별도 작업으로 관리합니다.
