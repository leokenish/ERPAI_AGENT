# 업무 스킬 및 회귀

## 1. 왜 절차와 재검증이 필요한가: AI는 틀려도 오류 창을 띄우지 않습니다

AI가 그럴듯하게 답했지만 적용일을 놓쳤거나, 사용자 설정을 코드 결함으로 오해할 수 있습니다. 프로그램 오류처럼 경고가 뜨지 않으므로 담당자가 근거와 조건을 확인해야 합니다. 실제 대화에서도 “업무 질문에는 에러가 표시되지 않는데 무엇으로 실패를 알 수 있나?”라는 질문이 나왔습니다.

그때그때 “그건 틀렸어요”라고만 하면 다음 대화에서 같은 실수를 반복할 수 있습니다. 이 과정에서는 **어떻게 자료를 읽을지, 무엇이 잘못됐는지, 다시 무엇을 물어볼지**를 파일로 남깁니다.

‘회귀’는 여기서 과거로 돌아간다는 일상어가 아니라, 수정 뒤에도 이전 문제가 다시 생기지 않는지 확인하는 검사를 뜻합니다. 예전에 틀린 질문을 다시 묻고 비슷한 조건의 다른 질문도 확인합니다.

## 2. 무엇을 바꾸기로 했는가: 업무 답변 정정과 코드 수정을 분리하기

프로젝트에서는 업무 피드백과 코드 피드백을 나누고, 먼저 사용자의 정정으로 업무 MD를 보완하는 흐름을 만들었습니다. 답변이 틀렸다고 SAP 코드를 바로 고치는 것이 아니라, 어떤 근거를 놓쳤는지부터 찾는 방향입니다.

원문 요약이 틀렸다면 지식 문서를, 필요한 문서를 못 찾았다면 INDEX와 스킬을, 적용 대상을 혼동했다면 조건 설명과 검증 질문을 고칩니다. 실제 코드 결함이 확인되면 별도의 변경 과제로 넘깁니다.

이 흐름을 지속 지침으로 남긴 문서가 `BUSINESS_FEEDBACK_POLICY.md`입니다. 지침을 작성하는 것과 실제 답변을 자동 채점하는 실행 프로그램을 만드는 것은 별개의 작업입니다.

## 3. 어떤 파일이 어떤 역할을 맡는가

| 구성 | 쉬운 설명 | 이 과정에서 남길 것 |
|---|---|---|
| 업무 지식 | 답변의 근거 | 규정·협의·입력 방법·용어와 출처 |
| 스킬 · SKILL.md | 반복 작업의 절차서 | 언제 쓰고 어떤 자료를 어떤 순서로 읽는지 |
| 피드백 | 틀린 답을 고친 기록 | 질문·잘못된 판단·정정 근거·수정 파일 |
| 회귀 질문 | 같은 실수를 다시 확인하는 질문 | 필요한 답변 요소·금지할 단정·경계 조건 |
| 하네스 | 검증을 실행·판정·기록하는 절차와 도구 묶음 | 자동 실행 또는 수동 대조 방법과 결과 |

확보된 ZHR5 스킬 자료에는 업무 질문에 답하기, 변경 영향을 분석하기, 새 지식을 정리하기의 세 절차가 마련되어 있습니다. 지식을 모두 스킬 안에 복사하지 않고, 해당 지식으로 가는 경로와 읽는 순서를 둡니다.

예를 들어 업무 질문 스킬은 **대상·시점 확인 → INDEX → 규정과 후속 정정 → 필요한 원문·코드 → 근거와 미확인 사항을 포함한 답변** 순서로 작동하도록 구성합니다. 평가용 기대 답안을 일반 업무 답변의 근거로 사용하는 방식은 피합니다.

## 4. 어떻게 반복하는가: 피드백 한 건을 끝까지 남기기

1. 질문과 당시 AI 답변, 대상·기간·입력 조건을 기록합니다.
2. 담당자 정정의 원문과 근거를 확인합니다. 근거가 충돌하면 확정하지 않고 확인할 사람·자료를 적습니다.
3. 오류의 원인에 맞춰 지식·INDEX·스킬을 수정합니다. 기존 유효한 지침은 병합해 유지합니다.
4. 원래 질문과 조건을 바꾼 질문을 남깁니다. 무엇을 답해야 하고 어떤 단정을 하면 안 되는지 적습니다.
5. 새 답변을 생성해 원문과 대조합니다. 수동 검토인지, 독립 평가인지, 자동 검사인지 구분합니다.
6. 수정 파일과 검증 결과를 기록해 다음 작업에서 읽게 합니다.

| 기록 상태 | 의미 |
|---|---|
| PASS | 실제 실행한 그 검사 기준을 충족 |
| FAIL | 실제 검사에서 기준 위반 확인 |
| REVIEW_REQUIRED | 근거 충돌이나 담당자 판단이 필요 |
| NOT_RUN | 해당 검사는 실행하지 못함 |

문서 링크 검사가 PASS여도 SAP 실행은 NOT_RUN일 수 있습니다. 같은 AI가 기대 기준을 읽고 스스로 대조한 결과도 독립된 평가 결과와 구분합니다.

## 5. 실제 사례: 고쳐야 할 것은 코드일까요, 업무 이해일까요?

### 5-1. 0원이 나온 반차 사례에서 코드 결함 판단을 철회했습니다

실제 피드백 `FB-20261001-001`에는 원래 14–22시 시차근무, 오전반차 승인, 실제 근무 18–23시, 휴게 19:30–20:00이라는 조건이 있습니다. 18–23시로 입력하자 표시 금액이 0원이었습니다.

AI는 7시간 미달일 때 0원을 표시하는 분기를 찾아 반차 예외가 빠진 코드 결함이라고 추정했습니다. 그러나 담당자는 이 근무유형에서는 **원래 출근시각인 14시부터 전체 구간을 입력하고 반차를 별도로 반영하는 방식**이라고 정정했습니다.

문제는 코드 조건을 찾기 전에 화면의 입력 규칙을 확인하지 않은 데 있었습니다. 결함 판단을 철회하고 입력 안내·INDEX·FAQ를 보완했으며 Q37·Q38을 회귀 질문으로 남겼습니다. 이 업무 답변 정정에서 ABAP 원본은 바꾸지 않았습니다. 수정 입력 후의 최종 지급액이나 SAP 실행 결과는 아직 확보되지 않았습니다.

### 5-2. “왜 다시 되돌렸는가”도 지식입니다

`FB-20261008-001`에는 누적근로시간 표시의 변경 이유를 보완한 사례가 있습니다. 확보한 코드 주석과 협의 기록에는 2024-10-15에 대휴가 발생한 것으로 오해하지 않도록 가산시간을 표시에서 제외했다가, 10-28에는 소정시간을 채우지 못했다고 오해하는 문제가 더 크다고 판단해 포함 표시로 되돌린 이유가 남아 있습니다.

코드의 롤백 주석만으로는 이 이유를 빠르게 찾기 어려워 업무 문서·용어집·지도에 연결하고 Q39·Q40·Q41을 추가했습니다. 이는 당시 기술 답변이 가산 제외를 현행 정책이라고 잘못 설명했다는 사례가 아니라 **판단 이유와 탐색 경로를 보완한 사례**입니다. 화면 표시 이유를 대휴·수당 계산 규칙의 변경 승인으로 넓혀 해석하지 않습니다.

### 5-3. 자기 업무의 피드백 한 건으로 연습하기

[피드백 기록 양식](downloads/feedback-record.md)을 복사해 최근 답변 하나를 정리해 보세요.

```text
방금 답변은 입력 규칙을 확인하기 전에 코드 결함으로 판단했습니다.
첨부한 담당자 설명과 기존 업무 문서의 대상·적용 시점을 대조해 주세요.
확인된 정정을 지식·INDEX·필요한 스킬에 반영하고 변경 이유를 적어 주세요.
원래 질문과 조건이 달라진 질문 하나를 회귀 항목으로 남겨 주세요.
문서 검사, 새 답변 대조, SAP 실행 중 실제로 한 것과 못 한 것을 나눠 주세요.
이번 업무 지식 정정에서는 추출 소스와 baseline을 수정하지 마세요.
```

## 6. 한계와 다음 방향: 기록이 쌓여도 자동으로 정답이 되지는 않습니다

후속 근로시간 자료에는 41개 업무 질문과 기대 답변 초안이 있습니다. 이는 실무자 승인 전의 검증 기준이며, 41개 모두를 독립 실행해 통과했다는 기록은 아닙니다. 기존 과정의 초기 34개 초안에서 후속 질문이 추가된 상태입니다.

이 절차가 바꾸는 것은 다음 작업에서 읽을 지식·지침·검증 사례입니다. AI 모델 자체가 영구적으로 재학습됐다는 뜻은 아닙니다. 실제 검사기가 없다면 수동 대조부터 하고 자동 평가는 NOT_RUN으로 남깁니다. 매번 Python 검사기를 고치는 것도 아니며, 검사 방법 자체에 문제가 있을 때만 수정합니다.

프로젝트의 피드백 정책은 한 건당 최대 3회의 수정·재검증을 기본으로 합니다. 같은 문제가 계속되거나 근거가 부족하면 필요한 자료와 판단 지점을 남겨 담당자가 확인합니다. 코드 변경이 필요한 것으로 확인됐다면 다음 [08. 코드 검증 및 적용](#/learn/diagnosis)에서 변경 전후와 실제 시스템 결과를 검토합니다.
