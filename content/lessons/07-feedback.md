# 업무 스킬 및 회귀

## 1. 왜 절차와 재검증이 필요한가

AI의 답변은 문장이 자연스러워도 업무 조건을 잘못 해석할 수 있습니다. 적용일을 놓치거나 화면 입력 방법을 코드 결함으로 판단하는 경우가 여기에 해당합니다. 이런 오류는 프로그램의 에러 메시지처럼 드러나지 않으므로, 답변과 근거를 대조하는 절차가 필요합니다.

대화에서 한 번 정정하는 데 그치면 다음 질문에서도 같은 판단을 반복할 수 있습니다. 따라서 **자료를 읽는 순서, 잘못 판단한 이유, 다시 물어볼 질문**을 파일로 남깁니다.

‘회귀 검사’는 수정한 뒤에 이전 문제가 다시 생기지 않는지 살펴보는 검사입니다. 예전에 틀린 질문을 다시 묻고, 조건을 조금 바꾼 질문도 함께 확인합니다.

## 2. 무엇을 바꾸기로 했는가

ZHR5에서는 업무 답변에 대한 피드백과 코드 변경을 나누었습니다. 답변이 틀린 이유가 업무 기준을 잘못 읽은 데 있다면, 먼저 그 설명과 탐색 경로를 바로잡아야 하기 때문입니다.

잘못 요약한 기준은 지식 문서에서 고칩니다. 필요한 문서를 찾지 못했다면 INDEX와 스킬의 읽기 순서를 보완합니다. 적용 대상을 혼동했다면 조건 설명과 회귀 질문을 수정합니다. 실제 코드 결함으로 판단된 사안은 별도의 코드 변경 작업으로 이어집니다.

이 처리 순서를 `BUSINESS_FEEDBACK_POLICY.md`에 정리하고 프로젝트의 공통 지침에서 연결했습니다. 따라서 다음 정정에서도 같은 기준으로 기록·수정·재검토를 진행할 수 있습니다.

## 3. 어떤 파일이 어떤 역할을 맡는가

| 구성 | 쉬운 설명 | 남기는 내용 |
|---|---|---|
| 업무 지식 | 답변의 근거 | 규정·협의·입력 방법·용어와 출처 |
| 스킬 · SKILL.md | 반복 작업의 절차서 | 사용할 상황과 자료를 읽는 순서 |
| 피드백 | 답변을 바로잡은 기록 | 질문·잘못된 판단·정정 근거·수정 파일 |
| 회귀 질문 | 같은 실수를 살펴보는 질문 | 필수 답변 요소·피할 단정·경계 조건 |
| 하네스 | 답변의 검토 작업대 | 검사 순서·판정 기준·실행 방법·결과 |

ZHR5의 세 스킬은 업무 질의, 변경 영향 분석, 새 지식 정리로 나뉩니다. 각 스킬에는 관련 문서의 위치와 읽는 순서를 두므로, 업무 기준이 바뀌어도 그 기준을 적은 지식 문서와 함께 관리할 수 있습니다.

업무 질문 스킬은 **대상·시점 확인 → INDEX → 규정과 후속 정정 → 원문·코드 → 근거를 붙인 답변** 순서로 구성합니다. 회귀 질문은 이 절차가 제대로 적용됐는지 검토하는 데 사용합니다.

## 4. 어떻게 만드는가

ZHR5는 업무 답변을 고치는 공통 절차를 먼저 정하고, 실제 정정 사례를 MD로 남겼습니다. 이어서 같은 문제를 다시 묻는 질문과 검토 결과를 연결했습니다. 이렇게 질문·정정·수정·재검토를 이어 놓은 것이 하네스의 기본 구성입니다.

### 1단계 · 피드백 정책과 AGENTS 연결

`docs/BUSINESS_FEEDBACK_POLICY.md`에 기록 시점, 수정할 파일, 결과를 살펴보는 순서를 적습니다. `AGENTS.md`에는 업무 답변을 정정할 때 이 정책을 읽도록 연결합니다. 공통 규칙을 한 문서에서 관리하므로 절차를 바꿀 때도 수정할 곳이 분명합니다.

### 2단계 · harness/feedback 기록

`harness/feedback/FB-날짜-번호.md`를 만들고 원래 질문·당시 답변·담당자 정정·근거·수정 파일·재검토 결과를 적습니다. ZHR5에는 이런 피드백 MD 네 건이 있습니다. 다음 담당자가 같은 일을 이해할 수 있도록 무엇을 바꿨는지와 바꾼 이유를 함께 기록합니다.

폴더도 기록의 목적에 따라 나눕니다. **업무에서 오간 협의는 knowledge/feedback에, AI 답변을 바로잡은 이력은 harness/feedback에** 보관합니다. 이렇게 구분하면 업무 기준을 찾는 일과 답변 오류를 조사하는 일을 각각 시작할 수 있습니다.

### 3단계 · 관련 문서와 회귀 질문 보완

입력 방법을 잘못 이해했다면 업무 설명을 수정합니다. 자료를 찾는 순서에 문제가 있었다면 INDEX와 해당 스킬을 보완합니다. 오류의 원인에 맞는 파일을 고친 뒤 `tests/business-qa.md`에 원래 질문과 조건을 바꾼 질문을 추가합니다.

| 문서 | 작성·수정 시점 | 남기는 내용 |
|---|---|---|
| `docs/BUSINESS_FEEDBACK_POLICY.md` | 피드백 처리 방식을 정하거나 바꿀 때 | 기록·정정·재검토의 공통 순서 |
| `harness/feedback/FB-…md` | 업무 답변을 정정할 때 | 질문·오답·근거·수정 경로·결과 |
| `knowledge/…md`·`knowledge/INDEX.md` | 업무 설명이나 탐색 경로를 고칠 때 | 조건과 출처, 문서 연결 |
| `.agents/skills/…/SKILL.md` | 읽는 절차에서 반복 오류가 생길 때 | 확인 단계와 탐색 순서 |
| `tests/business-qa.md` | 같은 문제를 다시 검토할 때 | 질문·필수 답변 요소·금지 주장·관련 사례 |
| `docs/VALIDATION.md` | 문서와 답변을 검사한 뒤 | 검사 대상·방법·담당자·결과 |

```document-tree
feedback-files
```

파일 관계도는 정정 내용을 기록한 뒤 지식·스킬·회귀 질문으로 연결하는 순서를 보여 줍니다. 문서 이름을 누르면 해당 MD를 다운로드할 수 있습니다.

### 4단계 · Codex 정정·재검토 요청

다음 요청문에 자신의 질문과 담당자 설명을 넣으면, 정정 기록과 관련 문서 수정까지 한 흐름으로 진행할 수 있습니다.

```text
방금 답변은 화면 입력 방법을 확인하기 전에 코드 결함으로 판단했습니다.
담당자가 확인한 입력 기준과 기존 협의 자료를 다시 대조해 주세요.
docs/BUSINESS_FEEDBACK_POLICY.md에 따라 harness/feedback에 이번 일을 기록해 주세요.
관련 업무 MD와 INDEX를 고치고, 검색 절차에 문제가 있었다면 해당 SKILL만 보완해 주세요.
tests/business-qa.md에는 원래 질문과 조건을 바꾼 질문을 연결해 주세요.
다시 답한 결과를 근거와 대조하고, 실제로 한 검사와 못 한 검사를 따로 기록해 주세요.
추출 원본과 SAP 코드는 이번 업무 지식 정정에서 수정하지 마세요.
```

### 피드백 검토 순서

1. 질문과 당시 답변, 대상·기간·입력 조건을 기록합니다.
2. 담당자의 정정과 원문 근거를 대조하고 적용할 기준을 정리합니다.
3. 원인에 맞춰 지식·INDEX·스킬을 수정하고 기존의 유효한 설명은 유지합니다.
4. 원래 질문과 조건을 바꾼 질문에 필요한 답변 요소를 적습니다.
5. 새 답변을 원문과 대조하고 수동 검토·독립 평가·자동 검사 등 사용한 방법을 기록합니다.
6. 수정 파일과 검사 결과를 연결해 다음 작업에서 읽도록 합니다.

| 기록 상태 | 의미 |
|---|---|
| PASS | 실행한 검사의 기준 충족 |
| FAIL | 실행한 검사에서 기준 위반 |
| REVIEW_REQUIRED | 근거 충돌 또는 담당자 판단 대상 |
| NOT_RUN | 검사 실행 전 |

문서 링크, 업무 답변, SAP 실행은 서로 다른 검사 대상입니다. 따라서 각각의 결과를 따로 기록해야 어느 단계에서 문제가 생겼는지 찾기 쉽습니다.

## 5. 실제 사례

### 5-1. 반차 입력 기준과 코드 판단

다음은 `FB-20261001-001`을 바탕으로 정리한 사례 문답입니다.

**사용자 질문 ·** “오전 반차 후 18~23시를 입력했는데 실비가 0원입니다. 계산 오류인가요?”

**당시 AI 판단 ·** 7시간 미달 시 0원을 표시하는 조건을 보고 반차 예외가 빠졌다고 판단했습니다.

**담당자 정정 ·** 해당 근무유형은 원래 시작시각인 14시부터 전체 구간을 입력하고, 승인된 반차를 별도로 반영하는 방식이었습니다.

이 사례의 조건은 원래 14–22시 시차근무, 오전반차 승인, 실제 근무 18–23시, 휴게 19:30–20:00입니다. AI는 0원이 되는 코드 분기를 찾았지만 화면의 입력 기준을 함께 읽지 않아 원인을 잘못 판단했습니다.

따라서 코드 결함 판단을 철회하고 **원래 출근시각부터 입력하는 업무 기준**을 지식 문서와 INDEX·FAQ에 반영했습니다. 또한 `tests/business-qa.md`의 Q37·Q38에 원래 질문과 조건 차이를 남겨, 다음 답변에서도 입력 방법부터 살펴보도록 했습니다.

관련 파일은 `harness/feedback/FB-20261001-001.md`와 `knowledge/processes/overtime-start-time.md`입니다.

### 5-2. 누적시간 표시의 결정 이유 연결

**질문 ·** “누적시간에 가산시간을 다시 포함한 이유도 다음 답변에서 찾을 수 있나요?”

`FB-20261008-001`은 표시를 바꾼 이유를 업무 문서와 용어집에 연결한 사례입니다. 2024년 10월 15일에는 대휴가 발생한 것으로 오해하지 않도록 가산시간을 표시에서 제외했습니다. 그러나 소정시간을 채우지 못했다고 오해하는 문제가 더 크다고 판단해 10월 28일에는 표시를 되돌렸습니다.

코드 주석만으로는 이 협의 배경을 빠르게 찾기 어려웠습니다. 따라서 `knowledge/processes/selective-cumulative-display.md`, `knowledge/BUSINESS_GLOSSARY.md`, 관련 지도에 이유를 연결하고 Q39~Q41을 회귀 질문으로 추가했습니다.

이 사례에서 보완한 핵심은 **현재 표시 방식과 그 판단 이유를 함께 찾는 경로**입니다. 따라서 다음 질문에서는 누적시간 표시의 결정 배경을 읽고, 대휴·수당 계산에 관한 기준은 해당 업무 문서에서 별도로 찾습니다.

### 5-3. 업무 피드백 작성 연습

[피드백 기록 양식](downloads/feedback-record.md)을 복사해 최근 업무 답변 하나를 정리합니다. 질문의 조건, 담당자 정정, 수정할 문서가 서로 연결되도록 적습니다.

```text
방금 답변은 입력 규칙을 확인하기 전에 코드 결함으로 판단했습니다.
첨부한 담당자 설명과 기존 업무 문서의 대상·적용 시점을 대조해 주세요.
확인된 정정을 지식·INDEX·필요한 스킬에 반영하고 변경 이유를 적어 주세요.
원래 질문과 조건이 달라진 질문 하나를 회귀 항목으로 남겨 주세요.
문서 검사, 새 답변 대조, SAP 실행 중 실제로 한 것과 못 한 것을 나눠 주세요.
이번 업무 지식 정정에서는 추출 소스와 baseline을 수정하지 마세요.
```

## 6. 피드백 활용과 관리

근로시간 프로젝트의 `tests/business-qa.md`에는 업무 질문 41개와 기대 답변 초안이 정리되어 있습니다. 새 정정이 생기면 관련 질문을 연결하고, 같은 조건으로 답했을 때 필요한 근거가 포함되는지 검토합니다.

이 과정을 거치면 다음 답변에서 읽을 지식과 작업 절차가 함께 보완됩니다. 따라서 피드백은 한 번의 답변을 고치는 기록이자, 이후 같은 업무를 처리하는 기준으로 활용할 수 있습니다.

프로젝트 정책은 한 건당 최대 3회의 수정·재검토를 기본으로 합니다. 실제 코드 변경으로 이어지는 사안은 다음 [08. 코드 검증 및 적용](#/learn/diagnosis)에서 변경 전후와 시스템 결과를 살펴봅니다.
