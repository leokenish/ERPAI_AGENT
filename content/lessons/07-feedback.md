# 업무 스킬 및 회귀

## 1. 왜 절차와 재검증이 필요한가: AI는 틀려도 오류 창을 띄우지 않는다

AI의 답변이 그럴듯해도 적용일을 놓치거나 사용자 설정을 코드 결함으로 오해할 수 있다. 이런 오류에는 프로그램처럼 경고 창이 뜨지 않는다. 담당자가 근거와 조건을 확인해야 하는 이유다. 실제 대화에서도 “업무 질문에는 에러가 표시되지 않는데 무엇으로 실패를 알 수 있나?”라는 질문이 나왔다.

그때그때 “그건 틀렸어요”라고만 정정하면 다음 대화에서 같은 실수를 할 수 있다. 이를 막기 위해 **어떻게 자료를 읽을지, 무엇이 잘못됐는지, 다시 무엇을 물어볼지**를 파일로 남긴다.

여기서 ‘회귀’는 수정한 뒤에 이전 문제가 다시 생기지 않는지 확인하는 검사다. 일상에서 말하는 과거로의 회귀와는 뜻이 다르다. 예전에 틀린 질문을 다시 묻고, 비슷한 조건의 다른 질문도 함께 확인한다.

## 2. 무엇을 바꾸기로 했는가: 업무 답변 정정과 코드 수정을 분리하기

프로젝트에서는 업무 답변에 대한 피드백과 코드에 대한 피드백을 나눴다. 사용자의 정정을 받으면 먼저 업무 MD에서 보완할 내용을 찾는다. 답변이 틀렸다는 이유로 SAP 코드를 바로 수정하기보다, 어떤 근거를 놓쳤는지부터 확인하는 흐름이다.

잘못된 요약은 지식 문서에서 고친다. 필요한 문서를 못 찾았다면 INDEX와 스킬을 보완하고, 적용 대상을 혼동했다면 조건 설명과 검증 질문을 수정한다. 실제 코드 결함이 확인된 경우에는 별도의 변경 과제로 넘긴다.

이 흐름을 계속 따를 수 있도록 정리한 문서가 `BUSINESS_FEEDBACK_POLICY.md`다. 지침을 작성했다고 답변을 자동 채점할 수 있는 것은 아니다. 자동 채점을 실행하는 프로그램은 별도로 만들어야 한다.

## 3. 어떤 파일이 어떤 역할을 맡는가

| 구성 | 쉬운 설명 | 이 과정에서 남길 것 |
|---|---|---|
| 업무 지식 | 답변의 근거 | 규정·협의·입력 방법·용어와 출처 |
| 스킬 · SKILL.md | 반복 작업의 절차서 | 언제 쓰고 어떤 자료를 어떤 순서로 읽는지 |
| 피드백 | 틀린 답을 고친 기록 | 질문·잘못된 판단·정정 근거·수정 파일 |
| 회귀 질문 | 같은 실수를 다시 확인하는 질문 | 필요한 답변 요소·금지할 단정·경계 조건 |
| 하네스 | 검증을 실행·판정·기록하는 절차와 도구 묶음 | 자동 실행 또는 수동 대조 방법과 결과 |

확보된 ZHR5 스킬은 업무 질문에 답하기, 변경 영향 분석하기, 새 지식 정리하기의 세 절차로 구성돼 있다. 스킬 안에 모든 지식을 복사하지 않고, 필요한 지식으로 가는 경로와 읽는 순서를 둔다.

예를 들어 업무 질문 스킬은 **대상·시점 확인 → INDEX → 규정과 후속 정정 → 필요한 원문·코드 → 근거와 미확인 사항을 포함한 답변** 순서로 작동하도록 구성한다. 평가용 기대 답안을 일반 업무 답변의 근거로 사용하는 방식은 피한다.

## 4. 어떻게 반복하는가: 피드백 한 건을 끝까지 남기기

1. 질문과 당시 AI 답변, 대상·기간·입력 조건을 기록한다.
2. 담당자 정정의 원문과 근거를 확인한다. 근거가 충돌하면 확정하지 않고 확인할 사람·자료를 적는다.
3. 오류의 원인에 맞춰 지식·INDEX·스킬을 수정한다. 기존 유효한 지침은 병합해 유지한다.
4. 원래 질문과 조건을 바꾼 질문을 남긴다. 무엇을 답해야 하고 어떤 단정을 하면 안 되는지 적는다.
5. 새 답변을 생성해 원문과 대조한다. 수동 검토인지, 독립 평가인지, 자동 검사인지 구분한다.
6. 수정 파일과 검증 결과를 기록해 다음 작업에서 읽게 한다.

| 기록 상태 | 의미 |
|---|---|
| PASS | 실제 실행한 그 검사 기준을 충족 |
| FAIL | 실제 검사에서 기준 위반 확인 |
| REVIEW_REQUIRED | 근거 충돌이나 담당자 판단이 필요 |
| NOT_RUN | 해당 검사는 실행하지 못함 |

문서 링크 검사가 PASS라고 해서 SAP 실행까지 확인된 것은 아니다. SAP 실행은 여전히 NOT_RUN일 수 있다. 같은 AI가 기대 기준을 읽고 스스로 대조한 결과와 독립된 평가 결과도 나눠 기록한다.

## 5. 실제 사례: 고쳐야 할 것은 코드일까요, 업무 이해일까요?

### 5-1. 0원이 나온 반차 사례에서 코드 결함 판단을 철회했다

실제 피드백 `FB-20261001-001`에 남은 조건은 원래 14–22시 시차근무, 오전반차 승인, 실제 근무 18–23시, 휴게 19:30–20:00이다. 화면에 18–23시를 입력하자 금액이 0원으로 표시됐다.

AI는 7시간에 미달하면 0원을 표시하는 코드 분기를 찾았다. 이를 보고 반차 예외가 빠진 결함이라고 추정했다. 하지만 담당자는 이 근무유형이 **원래 출근시각인 14시부터 전체 구간을 입력하고 반차를 별도로 반영하는 방식**이라고 정정했다.

코드 조건을 찾기 전에 화면의 입력 규칙을 확인했어야 했다. 결함 판단을 철회한 뒤 입력 안내·INDEX·FAQ를 보완하고 Q37·Q38을 회귀 질문으로 남겼다. 이 답변 정정 과정에서 ABAP 원본은 바꾸지 않았다. 입력을 수정한 뒤의 최종 지급액과 SAP 실행 결과는 아직 확보하지 못했다.

### 5-2. “왜 다시 되돌렸는가”도 지식이다

`FB-20261008-001`은 누적근로시간 표시를 바꾼 이유를 보완한 사례다. 코드 주석과 협의 기록에 따르면 2024-10-15에는 대휴가 발생한 것으로 오해하지 않도록 가산시간을 표시에서 제외했다. 그러나 소정시간을 채우지 못했다고 오해하는 문제가 더 크다고 판단해, 10-28에는 가산시간을 포함하는 표시로 되돌렸다.

코드의 롤백 주석만으로는 이 배경을 빠르게 찾기 어려웠다. 업무 문서·용어집·지도에 이유를 연결하고 Q39·Q40·Q41을 추가했다. 당시 기술 답변이 가산 제외를 현행 정책이라고 잘못 설명한 사례는 아니다. **판단 이유와 탐색 경로를 보완한 사례**이며, 화면 표시의 변경 이유를 대휴·수당 계산 규칙까지 바꿔도 된다는 승인으로 해석하지 않는다.

### 5-3. 자기 업무의 피드백 한 건으로 연습하기

[피드백 기록 양식](downloads/feedback-record.md)을 복사해 최근 답변 하나를 정리해 본다.

```text
방금 답변은 입력 규칙을 확인하기 전에 코드 결함으로 판단했습니다.
첨부한 담당자 설명과 기존 업무 문서의 대상·적용 시점을 대조해 주세요.
확인된 정정을 지식·INDEX·필요한 스킬에 반영하고 변경 이유를 적어 주세요.
원래 질문과 조건이 달라진 질문 하나를 회귀 항목으로 남겨 주세요.
문서 검사, 새 답변 대조, SAP 실행 중 실제로 한 것과 못 한 것을 나눠 주세요.
이번 업무 지식 정정에서는 추출 소스와 baseline을 수정하지 마세요.
```

## 6. 한계와 다음 방향: 기록이 쌓여도 자동으로 정답이 되지는 않는다

후속 근로시간 자료에는 업무 질문 41개와 기대 답변 초안이 있다. 아직 실무자 승인 전의 검증 기준이며, 41개 모두를 독립적으로 실행해 통과했다는 기록은 아니다. 기존 과정의 초기 34개 초안에 후속 질문이 더해진 상태다.

이 절차를 거치면 다음 작업에서 읽을 지식·지침·검증 사례가 바뀐다. AI 모델 자체를 영구적으로 재학습시키는 것은 아니다. 실행할 검사기가 없으면 수동 대조부터 시작하고, 자동 평가는 NOT_RUN으로 남긴다. Python 검사기도 매번 고치는 것이 아니라 검사 방법에 문제가 있을 때만 수정한다.

프로젝트의 피드백 정책은 한 건당 최대 3회의 수정·재검증을 기본으로 한다. 같은 문제가 계속되거나 근거가 부족하면 필요한 자료와 판단 지점을 남겨 담당자가 확인한다. 코드 변경이 필요한 것으로 확인됐다면 다음 [08. 코드 검증 및 적용](#/learn/diagnosis)에서 변경 전후와 실제 시스템 결과를 검토한다.
