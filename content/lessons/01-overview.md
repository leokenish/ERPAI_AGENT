# ERP AI 에이전트 전체 그림

## 1. 왜 만드는가: 같은 업무를 매번 처음부터 설명하지 않기

“이 직원의 근로시간이 왜 이렇게 계산됐나요?”라는 문의를 받았다고 생각해 보세요. 화면만 봐서는 답하기 어렵습니다. 규정의 적용 조건을 읽고, 예전에 담당자끼리 협의한 내용을 찾고, 프로그램이 실제로 어떻게 계산하는지 확인해야 합니다. 이 자료들은 ERP 서버, 문서 폴더, 메신저 대화에 흩어져 있습니다.

담당자가 바뀌거나 시간이 지나면 **무엇을 바꿨는지는 남아 있어도 왜 그렇게 바꿨는지는 찾기 어렵습니다.** AI에게 질문해도 우리 회사의 규정, 오래된 예외, 실제 프로그램을 주지 않으면 일반적인 설명으로 빈칸을 채울 수 있습니다. 대화창에 자료를 다시 붙여 넣는 작업도 반복됩니다.

이 프로젝트의 출발점은 그 반복을 줄이는 것입니다. **내 업무의 코드·규정·협의 이력을 함께 읽고, 답의 근거를 찾아 주며, 수정안과 확인 방법까지 준비하는 업무 도우미**를 만듭니다. 여기서 ‘에이전트’는 정해 둔 자료와 도구를 이용해 여러 단계의 일을 수행하는 AI를 뜻합니다.

## 2. 무엇을 만드는가: 내 업무를 근거로 설명하는 작업 공간

처음부터 ERP 전체를 아는 AI를 만들 필요는 없습니다. 근로시간, 구매계약처럼 담당하는 업무 하나를 정하고, 그 업무를 설명할 수 있는 파일과 작업 방법을 한 폴더에 모읍니다. Codex에서 이 폴더를 열면 자료를 찾고 문서를 작성하고 변경 파일을 검토하는 작업을 이어갈 수 있습니다.

완성하려는 결과물은 채팅 답변 한 번이 아니라 **다음 질문과 다음 담당자도 다시 사용할 수 있는 작업 공간**입니다.

| 업무에서 필요한 도움 | 에이전트가 준비할 결과 | 담당자가 확인할 내용 |
|---|---|---|
| “왜 이 값이 나오나요?” | 규정·협의·코드의 근거를 나눈 설명 | 질문한 대상과 적용 시점이 맞는가 |
| “이 조건을 바꾸면 어디가 영향을 받나요?” | 관련 화면·함수·테이블과 시험할 사례 목록 | 빠진 업무와 다른 담당자의 확인이 필요한가 |
| “화면을 이렇게 바꿔 주세요.” | 로컬 수정 파일, 변경 이유, 검사 결과 | 원하는 동작을 유지했고 실제 ERP에서도 맞는가 |
| “지난번에 틀린 답을 또 하지 않게 해 주세요.” | 고친 지식 문서, 작업 절차, 다시 물어볼 검증 질문 | 정정의 근거가 있고 같은 오류를 피하는가 |

위 질문은 이해를 돕는 예시입니다. 실제 프로젝트에서는 근로시간 업무 지식, ERP WEBGUI 개편, ESS 근태시스템 개편 등의 자료가 축적됐습니다. 모든 사례가 같은 단계까지 운영 검증된 것은 아니므로 각 사례에서 확인된 결과를 읽습니다.

## 3. 어떤 방향을 택했는가: 담당 업무 하나부터, 파일로 남기기

최초 목표는 SAP에서 개발 패키지를 꺼내 PC의 편집기와 AI로 분석·수정하고, 바뀐 내용을 다시 검토하는 것이었습니다. 패키지는 SAP에서 관련 개발물을 묶어 관리하는 단위입니다. 실제 업무 분장과 출발 범위를 맞추기 쉬웠습니다.

진행하면서 세 가지가 분명해졌습니다. 첫째, 코드만으로는 업무의 이유를 알 수 없어 규정과 대화가 필요했습니다. 둘째, SAP와 GitHub의 직접 연결은 당시 TLS 통신 오류로 보류되어 PC를 거쳐 파일을 공유하게 됐습니다. 셋째, 파일이 바뀌었다고 곧바로 ERP에 덮어쓸 수는 없어 원본·작업본·현재 서버를 비교하는 도구가 필요했습니다.

그래서 **자료를 확보하고 → 근거를 연결하고 → AI가 작업하고 → 결과를 확인하고 → 배운 내용을 다시 남기는 흐름**을 만들었습니다. 설치할 제품 목록보다 이 흐름을 먼저 이해하면 각 도구를 왜 쓰는지 알 수 있습니다.

## 4. 어떻게 구성하는가: 필요한 역할을 하나씩 연결하기

### 자료를 가져오고 같은 기준으로 관리합니다

02과정에서는 Export라는 SAP 프로그램으로 코드와 관련 정의를 파일로 꺼냅니다. 03과정에서는 Git으로 변경 이력을 남기고 GitHub로 공유합니다. GitHub는 팀이 같은 자료를 받는 장소이며, 누가 무엇을 바꿨는지 되짚는 기준이 됩니다.

### AI가 읽을 업무 근거와 작업 방법을 준비합니다

04과정에서는 로컬 폴더를 Codex의 작업 대상으로 엽니다. 05과정에서 규정과 협의 대화를 읽을 수 있는 업무 문서로 정리하고, 06과정에서 질문과 관련 문서·코드 사이에 링크를 만듭니다. 07과정에서는 반복 작업의 순서를 스킬로 적고 틀린 답을 다시 확인할 질문을 남깁니다. MD는 이런 내용을 저장하는 읽기 쉬운 텍스트 문서 형식입니다.

### 바꾼 내용을 확인한 뒤 필요한 범위만 적용합니다

08과정의 DIAG는 내 수정과 서버의 다른 수정이 겹치는지, 지원되는 검사를 수행했는지 보여줍니다. 일부 기존 웹자산은 선택 저장·활성화 기능까지 만들어졌습니다. 업무 규칙과 실제 화면이 맞는지는 해당 업무의 담당자가 확인합니다.

| 구성 | 하는일 | 연결되는자료 |
|---|---|---|
| Export · CHECK | SAP 자료를 파일로 꺼내고 추출 묶음의 상태를 점검 | 소스·객체 정의·파일 목록·추출 원본·로그 |
| Git · GitHub | 파일의 변경 이력과 팀 공유 기준을 관리 | 저장소·커밋·검토 기록 |
| Codex | 선택한 폴더의 자료를 찾아 설명·문서·수정안을 작성 | 담당 업무 소스·AGENTS.md 지침·업무 문서 |
| 업무 지식 · 스킬 · 검증 질문 | 무엇을 근거로 어떤 순서로 일하고 어떻게 답을 확인할지 제공 | 규정·협의·SKILL.md·피드백·회귀 사례 |
| 업무지도 · Obsidian | 질문에서 관련 근거로 찾아가는 길을 연결 | INDEX·maps의 MD·실제 문서 링크 |
| DIAG | 원본·작업본·현재 SAP를 비교하고 지원 대상을 검사·선택 반영 | 비교표·줄 차이·검사 결과·반영 로그 |
| 담당자 자문 MCP · 09 | 다른 업무 담당 에이전트에 질문을 전달하는 연결 | 질문·작업 상태·근거가 있는 답변. 실제 AI 연결은 계획 중 |
| ERP 조회 MCP · 10 | 허용된 ERP 조회 기능을 AI가 호출하도록 연결 | 기존 REST/RFC의 요청·결과. 현재는 설계 단계 |

MCP는 AI가 외부 도구를 일정한 방식으로 요청하도록 연결하는 규약입니다. 09는 **다른 담당자의 지식에 묻는 일**, 10은 **ERP의 현재 데이터를 조회하는 일**입니다. 먼저 01–08로 내 업무의 자료와 검토 흐름을 만든 뒤 필요에 따라 확장합니다.

## 5. 실제 사례로 보면 무엇이 달라지는가

### “시간외 입력 시간이 이상해요”라는 문의

제공된 실제 대화에는 근무표가 00:00–09:00인데 입력 화면의 기본값은 18:00–24:00이라는 문의가 있습니다. 당시 담당자는 개인 IAM 설정이 먼저 반영된다고 설명했고, 업무 담당자는 그 설정을 지우도록 안내하기로 했습니다. 그러나 삭제 후 정상화된 화면까지는 확보되지 않았습니다.

이 사안을 “시간 오류 수정 완료”로만 요약하면 다음 AI도 잘못된 결론을 내릴 수 있습니다. 업무 맥락을 정리하면 **화면에서 관찰한 현상, 담당자의 설명, 합의한 조치, 아직 확인하지 못한 결과**가 남습니다. 다음 문의에서는 현재 설정과 해당 코드부터 확인할 수 있습니다. 이 과정을 05에서 자세히 다룹니다.

### “AI가 고친 파일을 바로 올려도 되나요?”라는 질문

로컬 수정 중 다른 담당자가 SAP의 같은 프로그램을 고쳤을 수도 있습니다. 현재 파일 두 개가 다르다는 사실만으로는 누가 무엇을 바꿨는지 알 수 없습니다. 추출할 때의 원본을 남겨 두면 내 변경과 서버 변경을 각각 찾을 수 있습니다. 02에서 이 기준을 준비하고 08에서 실제 비교 화면을 읽습니다.

이처럼 먼저 줄이려는 것은 **자료를 다시 찾는 시간, 배경을 반복 설명하는 수고, 잘못된 전제를 따라 수정하는 일**입니다. 절감 시간을 숫자로 검증한 자료는 아직 없으며, 자기 업무에서는 같은 질문을 전후로 비교해 효과를 확인하면 됩니다.

## 6. 어디까지 맡길 수 있고, 무엇부터 시작하면 되는가

AI가 규정을 찾아 설명하는 것과 실제 ERP에 적용해도 되는지는 서로 다른 질문입니다. 예를 들어 “이 규정은 누구에게 언제부터 적용되는가”는 업무 담당자가, “이 수정이 개발계에서 정상 실행되는가”는 SAP 담당자가 확인합니다. “비교 결과가 같다”는 말만으로 지급·근태 결과까지 맞다고 볼 수는 없습니다.

현재 직접 활용할 수 있는 자료에는 추출·진단 소스, 업무 문서·스킬, 업무지도, 대화와 화면 사례가 있습니다. 다른 담당 AI에게 자동으로 자문받는 부분은 모의 통신 예제까지, 실제 ERP 데이터 조회와 Telegram 연결은 설계까지 진행됐습니다. 각 기능을 연결해 운영하는 일은 다음 단계입니다.

첫 업무는 다음 순서로 정해 보세요.

1. 최근 반복해서 받은 질문 하나를 고릅니다. “근로시간 전체”보다 “시간외 입력 기본값은 무엇을 따르는가”처럼 작게 적습니다.
2. 그 질문과 관련된 프로그램·규정·협의 기록을 준비합니다. 없는 자료도 목록에 남깁니다.
3. 원하는 결과를 정합니다. 첫 목표는 근거가 있는 설명과 확인할 질문을 받는 것입니다.
4. 답변의 근거를 직접 열어 보고, 틀린 부분은 문서와 검증 질문에 반영합니다.

다음 [02. ERP 소스 추출하기](#/learn/export)에서 AI가 읽을 실제 자료를 준비합니다. 활용 모습부터 보고 싶다면 [11. 근로시간 AI 에이전트 구축](#/learn/worktime-agent)이나 [12. ERP WEBGUI 개편](#/learn/webgui)을 먼저 읽어도 좋습니다.
