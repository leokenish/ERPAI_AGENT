# 로컬 에이전트 구성

## 1. 왜 로컬에서 시작했는가

업무를 이어서 분석하려면 코드와 앞선 협의, 수정 결과를 함께 읽어야 합니다. 그런데 매번 대화창에 파일을 올리고 변경 위치를 설명하면 준비 작업이 반복됩니다.

이 프로젝트는 SAP 코드를 PC로 추출해 GitHub로 공유하는 흐름을 먼저 만들었습니다. 따라서 **PC의 소스와 업무 문서를 AI의 작업 폴더로 지정하는 방식**을 선택했습니다. 같은 폴더에서 분석과 문서 갱신을 이어가면 자료를 다시 모으는 수고를 줄일 수 있습니다.

담당 업무의 패키지를 Clone하면 시작 범위도 분명해집니다. 예를 들어 인사 담당자는 인사 자료를 중심으로 분석하고, 재무 업무와 연결되는 부분은 관련 문서와 담당 영역을 함께 정리할 수 있습니다.

## 2. 왜 Codex 데스크톱을 활용했는가

필요한 도구는 **여러 파일을 읽고, 문서를 작성하며, 수정 전후의 차이와 검사 결과를 보여주는 도구**였습니다. 따라서 실제 프로젝트에서는 Mac에 저장소를 Clone한 뒤 Codex에서 해당 폴더를 열었습니다.

업무 에이전트는 이 작업 공간에 회사 자료와 작업 지침을 연결해 구성합니다. AI가 읽을 근거와 따라갈 절차를 함께 준비하면, 코드 설명에서 업무 분석과 문서 관리로 작업을 넓힐 수 있습니다.

여기서 로컬은 작업 파일과 명령 실행 환경이 놓이는 내 컴퓨터를 뜻합니다. 사용 계정과 자료 처리 범위는 회사의 업무 기준에 맞춰 설정합니다.

## 3. 어떤 구성을 만들 것인가

처음부터 ERP 전체를 대상으로 하면 답변의 범위와 근거를 점검하기 어렵습니다. 따라서 담당 업무 하나의 질문에 답하고 실제 근거 파일을 제시하는 것부터 시작합니다. 이 흐름을 구성한 뒤 문서 정리와 작은 수정으로 넓혀 갑니다.

| 준비할 것 | 필요한 이유 | 첫 작업의 결과 |
|---|---|---|
| 실제 추출 소스 | 프로그램의 처리 방식 이해 | 객체명과 파일 경로 |
| 규정·협의·사용 방법 | 코드가 만들어진 배경 이해 | 적용 조건과 출처 |
| AGENTS.md와 INDEX | 작업 원칙과 자료 탐색 순서 연결 | 업무별 시작 문서와 읽기 경로 |
| 스킬과 검증 질문 | 반복 작업과 점검 방법 정리 | 작업 절차와 재검토 사례 |
| Git 이력 | 변경 검토와 공유 | 변경 파일·이유·결과 |

AGENTS.md에는 공통 작업 지침을, INDEX에는 자료를 찾는 안내를, SKILL.md에는 특정 작업의 절차를 담습니다. 각 문서에서 실제 규정과 코드로 찾아갈 경로를 연결하면, 같은 내용을 여러 곳에 중복해서 적는 부담도 줄일 수 있습니다.

## 4. 어떻게 구성하는가

### 4-1. 설치와 로그인

1. [공식 앱 안내](https://learn.chatgpt.com/docs/app)의 Download에서 사용하는 OS와 장비에 맞는 설치 파일을 받습니다.
2. macOS에서는 Applications에 앱을 설치합니다. Windows에서는 설치 프로그램의 안내에 따라 진행합니다.
3. 업무용 ChatGPT 계정으로 로그인하고 사용할 워크스페이스를 선택합니다.
4. Codex를 선택하고 New chat으로 작업을 시작합니다.
5. 작업 위치로 로컬 저장소 폴더를 지정합니다.

### 4-2. 프로젝트 폴더 지정

프로젝트 추가 또는 폴더 열기에서 **Clone한 저장소의 루트**를 선택합니다. 프로젝트에 폴더를 추가하는 화면에서는 Edit project → Add folder를 사용합니다. 경로의 예는 Windows `C:\work\ERPAI_AGENT`, macOS `~/work/ERPAI_AGENT`이며 실제 Clone한 위치를 지정합니다.

| 선택 대상 | 폴더를 찾는 기준 |
|---|---|
| 저장소 루트 | README·AGENTS.md와 소스·문서 폴더가 있는 위치 |
| 담당 패키지 저장소 | README·manifest에 담당 패키지와 업무 범위가 적힌 위치 |
| 기존 작업 폴더 | 현재 Git 변경과 작업 이력을 관리하는 위치 |

소스와 문서를 함께 분석하려면 빌드 결과인 `dist/`보다 저장소 루트에서 시작하는 편이 적합합니다. 따라서 첫 요청에서는 VS Code와 Codex가 같은 작업 경로를 사용하는지 살펴봅니다.

```text
현재 작업 폴더의 절대 경로와 Git 저장소 루트를 확인해 주세요.
README.md, 적용되는 AGENTS.md, git status와 현재 브랜치를 읽어 주세요.
소스·업무 지식·스킬·검증 자료의 실제 위치를 정리해 주세요.
기존 사용자 변경은 보존하고, 이번에는 폴더와 자료 구성만 설명해 주세요.
```

앱에서 별도 작업 사본이나 Worktree를 선택했다면 그 경로를 기준으로 변경 내용을 관리합니다. 작업 위치를 먼저 정하면 다른 폴더의 수정본과 혼동하는 일을 줄일 수 있습니다.

### 4-3. 지침·지식·스킬 배치

| 자료 | 역할 | 관리 기준 |
|---|---|---|
| AGENTS.md | 작업 원칙·읽기 순서·수정 범위 | 공통 지침과 폴더별 지침 연결 |
| knowledge/INDEX.md | 업무 자료 탐색의 입구 | 질문별 실제 문서 경로 |
| knowledge/ | 규정·협의·업무 설명 | 출처·효력일·예외 |
| SKILL.md | 반복 작업의 처리 절차 | 사용 조건·탐색·판단·검증 순서 |
| 추출 소스 폴더 | ABAP·웹 자산·객체 정의 | 원천·baseline 보존과 파일 위치 |
| tests/ 또는 harness/ | 평가 질문·검증 기록 | 기대 행동과 실행 결과 |
| maps/ | 업무·코드·검증 관계 | 문서 사이의 연결 경로 |

Codex는 AGENTS.md를 작업 지침으로 읽습니다. 프로젝트의 공통 지침과 하위 폴더 지침이 연결되므로, 기존 파일을 읽고 업무 범위에 맞게 보완합니다. [공식 AGENTS.md 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

폴더 구성은 실제 저장소의 경로에 맞춥니다. 이후 [업무 맥락 만들기](#/learn/knowledge)와 [업무 스킬 및 회귀](#/learn/feedback)에서 각 문서의 제작과 활용을 자세히 다룹니다.

### 4-4. 첫 분석 요청

첫 요청에는 업무 대상·기준 시점·사용할 자료·원하는 결과를 적습니다. 이 네 가지가 분명하면 AI도 어떤 문서와 코드를 연결해야 하는지 찾기 쉽습니다.

```text
이 저장소의 근로시간 누적 표시 업무를 분석해 주세요.
업무 INDEX, 관련 규정과 후속 정정을 읽고 실제 추출 소스와 연결해 주세요.
규정과 협의 배경, 코드의 처리 방식, 실행 기록을 구분해 설명해 주세요.
질문의 적용 대상과 기준 시점을 적고, 판단의 근거가 되는 파일과 관련 구간을 제시해 주세요.
이번에는 영향 분석만 작성하고 코드는 수정하지 마세요.
```

위 요청의 업무명은 자신이 맡은 업무로 바꿉니다. 결과를 읽을 때는 파일 목록과 함께 적용 조건, 관련 코드, 후속 정정이 어떻게 연결됐는지 살펴봅니다.

### 4-5. 수정 요청과 차이 검토

분석을 마친 뒤에는 변경할 동작과 유지할 기능을 정합니다. 또한 결과를 어떤 방법으로 검사할지 함께 적어야 수정 범위와 완료 기준을 맞출 수 있습니다.

```text
앞서 확인한 파일에 요청한 표시 문구를 수정해 주세요.
사용자 변경, AGENTS.md, .git, .github, 로컬 설정을 보존해 주세요.
원천과 baseline의 바이트·줄바꿈을 유지해 주세요.
변경 전후와 이유를 기록하고 관련 검사를 실행해 주세요.
검사 명령·결과와 변경 파일 목록을 정리해 주세요.
변경 비교 보고서와 변경 파일 ZIP을 제공해 주세요.
커밋·push·운영 배포는 제가 하겠습니다.
```

작업 후에는 앱의 변경 보기나 VS Code Source Control에서 파일별 차이를 읽습니다. 요청한 기능과 변경 파일을 대응시키고, 원천과 줄바꿈도 기존 기준대로 유지됐는지 살펴봅니다.

| 검토 항목 | 결과에 포함할 내용 |
|---|---|
| 실제 변경 | 파일 경로, 변경 이유, 요청한 동작과 유지 조건 |
| 검사 | 실행 명령과 결과, 화면 점검 내용 |
| 적용 | SAP 시험과 검토, 적용 기록 |

### 4-6. 포털 검증과 공유

이 포털은 Node.js 24 이상에서 빌드합니다. 저장소 루트에서 다음 명령을 실행하면 사이트 생성과 테스트, 오프라인 미리보기를 이어서 점검할 수 있습니다.

```bash
npm run build
npm test
npm run preview:file
```

변경한 화면과 다운로드를 살펴본 뒤 [GITHUB 연동](#/learn/workspace)의 Commit·Push 절차로 공유합니다. ABAP 저장소에서는 해당 프로젝트의 검사와 SAP 적용 절차를 사용합니다.

### 4-7. 프로젝트 진행 문서

다음 작업자가 같은 배경에서 시작하려면 목적과 결정, 진행 과정을 남겨야 합니다. 따라서 프로젝트별로 다음 네 문서를 관리합니다.

| 문서 | 정리할 내용 |
|---|---|
| intent.md | 프로젝트의 목적, 대상 사용자, 방향과 범위 |
| spec.md | 합의한 동작·결과물·수용 기준 |
| plan.md | 작업 순서와 진행 결과, 다음 작업 |
| insight.md | 프로젝트의 존재 이유와 가치, 관련 사람들이 얻는 이해와 관점 |

이 문서를 프로젝트별로 구분하면 같은 파일명이라도 맥락을 유지할 수 있습니다. [소스 추출·진단의 자료확인](#/library/export-diag)에서 실제 프로젝트 문서를 내려받을 수 있습니다.

## 5. 실제로 달라진 작업

초기에는 AI가 추출 소스를 읽고 설명하는 작업에 집중했습니다. 그런데 코드만으로는 회사의 규정과 협의 배경까지 알기 어려웠습니다. 따라서 ZHR5의 근로시간·시간외·대휴·정산 자료를 문서와 스킬로 연결했습니다.

그 결과 작업 절차도 업무 질의, 변경 영향 분석, 지식 정리로 나눴습니다. 질문의 목적에 맞는 절차를 선택하면 자료 탐색과 답변 구성을 일정하게 유지하기 쉽습니다.

실제 피드백에는 반차를 사용한 날 시간외 금액이 0원으로 나온 사례가 있습니다. 담당자는 해당 시차근무 사례에서 원래 출근시각부터 전체 구간을 입력하는 업무 규칙을 설명했습니다. 따라서 계산 코드의 수정안을 만들기 전에 **입력 규칙과 업무 절차부터 읽는 순서**를 정했습니다. 이 사례는 [07. 업무 스킬 및 회귀](#/learn/feedback)에서 자세히 다룹니다.

첫 분석의 결과도 같은 기준으로 살펴봅니다. 질문의 대상과 적용 시점이 분명한지, 근거 문서에서 관련 코드까지 따라갈 수 있는지 확인하면 업무에 필요한 답인지 판단하기 쉽습니다.

## 6. 자료 갱신과 다음 작업

정책과 프로그램이 바뀌면 AI가 읽는 근거도 함께 바뀌어야 합니다. 따라서 추출본과 업무 문서의 날짜를 관리하고, 새 자료가 들어오면 INDEX·지식 문서·검증 질문을 함께 갱신합니다.

수정 결과는 로컬 검사, ZIP 전달, GitHub 공유, SAP 적용 순서로 기록합니다. 이렇게 하면 다음 작업자는 마지막으로 진행한 위치에서 작업을 이어갈 수 있습니다.

작업 중 문제가 생기면 작업 경로 → 적용 지침 → 근거 자료 → 변경 차이 → 실행 결과 순서로 살펴봅니다. 다음 [05. 업무 맥락 만들기](#/learn/knowledge)에서는 실제 사용자 대화를 업무 지식으로 정리합니다.
