# 로컬 에이전트 구성

## 1. 왜 로컬에서 시작했는가: 자료를 매번 설명하는 작업에서 벗어나기

코드 일부를 대화창에 붙여 넣으면 당장의 설명은 받을 수 있다. 하지만 실제 업무를 이해하려면 여러 파일과 앞선 협의, 수정 결과를 함께 읽어야 한다. 매번 파일을 다시 올리고 변경 위치를 설명하는 방식으로는 작업을 이어가기 어렵다.

이 프로젝트는 먼저 SAP 코드를 PC로 추출해 GitHub로 공유하는 흐름을 만들었다. SAP와 GitHub의 직접 연결은 TLS 문제로 보류됐지만, **PC에 확보한 소스와 업무 문서는 바로 분석할 수 있었다.** 이제 그 폴더를 AI의 작업 대상으로 지정하면 됐다.

담당자가 자기 업무의 패키지를 Clone해 열면 어디서 시작할지 분명해진다. 인사 담당은 인사 자료에서 시작하고, 재무 자료가 필요한 질문에는 연결 지점과 확인할 내용을 남길 수 있다. 다만 폴더 선택은 작업 범위를 정하는 방법이다. 다른 자료에 대한 접근을 기술적으로 차단하는 권한 설정까지 자동으로 보장하지는 않는다.

## 2. 왜 Codex 데스크톱을 활용했는가

실제 대화에서는 Mac에서 저장소를 Clone한 뒤 Codex Desktop 프로젝트로 여는 흐름을 택했다. 질문에 답하는 것뿐 아니라 **여러 파일을 읽고, 실제 문서를 만들고, 수정 전후의 차이를 보여주고, 실행 가능한 검사를 수행하는 도구**가 필요했기 때문이다.

별도의 업무 AI 모델을 처음부터 학습시킨 것은 아니다. 이미 사용할 수 있는 AI에 우리 업무의 자료, 작업 지침, 필요한 도구를 연결했다. 효과를 내려면 앱을 설치하는 것만큼 정확한 자료와 검토 절차를 준비하는 일도 중요하다.

‘로컬’은 작업 파일을 두고 명령을 실행하는 장소가 내 컴퓨터라는 뜻이다. 모델 자체를 PC에 설치한 오프라인 AI를 말하는 것은 아니다. 사용 계정과 자료 처리 범위는 회사가 허용한 기준을 따른다.

## 3. 어떤 구성을 만들 것인가: 한 폴더, 한 업무, 확인 가능한 결과

첫 목표가 “모든 ERP 질문을 처리하는 AI”이면 무엇이 부족한지 확인하기 어렵다. 먼저 담당 업무 하나의 질문에 답하고 근거 파일을 제시하도록 구성한다. 이 흐름을 만든 뒤 문서 정리와 작은 수정으로 범위를 넓힌다.

| 준비할 것 | 필요한 이유 | 첫 작업에서 확인할 결과 |
|---|---|---|
| 실제 추출 소스 | 프로그램이 하는 일을 확인 | 객체명과 파일 경로를 찾을 수 있음 |
| 규정·협의·사용 방법 | 코드가 이렇게 된 이유를 이해 | 적용 조건과 출처를 제시함 |
| AGENTS.md와 INDEX | 작업 원칙과 자료 찾는 순서를 전달 | 잘못된 폴더·오래된 문서부터 읽지 않음 |
| 스킬과 검증 질문 | 반복 작업 방법과 정답 확인 기준을 남김 | 동일한 오류를 다시 점검함 |
| Git 이력 | AI가 바꾼 내용을 검토하고 공유 | 변경 파일과 이유를 설명할 수 있음 |

AGENTS.md에는 작업 공통 지침을, INDEX에는 자료를 찾는 안내를, SKILL.md에는 특정 작업의 절차를 담는다. 긴 규정 전문을 각 문서에 모두 복사할 필요는 없다. 실제 자료로 찾아갈 경로를 연결한다.

## 4. 어떻게 구성하는가: 설치·폴더 선택·첫 요청

이 프로젝트의 과거 명칭은 Codex Desktop이다. 2026-10-26 확인한 [공식 앱 안내](https://learn.chatgpt.com/docs/app)는 ChatGPT 데스크톱 앱에서 Codex를 선택하는 흐름을 설명한다. 설치할 제품과 지원 환경은 공식 다운로드 화면을 기준으로 확인한다.

### 4-1. 설치와 로그인

1. [공식 앱 안내](https://learn.chatgpt.com/docs/app)의 Download에서 사용하는 OS에 맞는 설치 파일을 받는다. 해당 화면의 OS·장비 조건을 확인한다.
2. macOS는 받은 파일을 열어 안내에 따라 Applications에 앱을 설치한다. Windows는 제공되는 설치 프로그램의 안내에 따라 설치한다.
3. 앱을 실행하고 업무용 ChatGPT 계정으로 로그인한다. 개인·업무 계정을 함께 쓰면 선택된 계정과 워크스페이스를 확인한다.
4. Codex를 선택하고 New chat으로 작업을 시작한다. 설치 버전에 따라 처음 표시되는 프로젝트·폴더 선택 순서는 다를 수 있다.
5. 작업 위치를 로컬 저장소로 지정한다. GitHub 로그인만으로 원하는 폴더가 자동 선택되었다고 판단하지 않는다.

설치·로그인·작업 위치 선택은 공식 앱 안내를 기준으로 한다. 아래의 폴더 구성과 보고 방식은 이 프로젝트에 적용할 작업 절차다.

### 4-2. 프로젝트 폴더 지정

앱의 프로젝트 추가 또는 폴더 열기 기능에서 **Clone한 저장소의 루트**를 선택한다. 프로젝트에 폴더를 붙이는 화면이라면 프로젝트 메뉴의 Edit project → Add folder로 추가한다. 추가 후에는 이 저장소가 기본 작업 폴더인지 확인한다. 경로의 예는 Windows `C:\work\ERPAI_AGENT`, macOS `~/work/ERPAI_AGENT`이며, 실제 Clone한 위치를 사용한다.

| 선택 대상 | 확인할 내용 |
|---|---|
| 저장소 루트 | README·AGENTS.md와 소스·문서 폴더가 보이는 위치 |
| 담당 패키지 저장소 | 패키지명과 업무 범위가 README·manifest와 일치 |
| 기존 작업 폴더 | 작업 전 Git 차이를 확인하고 사용자 변경 보존 |

`dist/`만 열면 생성 결과만 보게 된다. ZIP 사본에는 Git 이력이 없을 수 있다. VS Code와 Codex에서 같은 경로를 열었는지 첫 요청으로 확인한다.

```text
현재 작업 폴더의 절대 경로와 Git 저장소 루트를 확인해 주세요.
README.md, 적용되는 AGENTS.md, git status와 현재 브랜치를 읽어 주세요.
소스·업무 지식·스킬·검증 자료의 실제 위치를 정리해 주세요.
사용자 변경과 읽지 못한 자료를 구분하고, 아직 파일은 수정하지 마세요.
```

경로·브랜치가 예상과 다르면 먼저 작업 폴더를 바꾼다. 앱에 별도 작업 사본이나 Worktree 선택이 보이는 경우에도 현재 경로를 확인한다. 별도 작업 사본의 수정이 원래 폴더에 자동 반영된 것으로 생각하지 않는다.

### 4-3. 지침·지식·스킬 배치

| 자료 | 역할 | 관리 기준 |
|---|---|---|
| AGENTS.md | 작업 원칙·읽기 순서·수정 범위 | 기존 파일과 하위 지침을 읽고 적용 |
| knowledge/INDEX.md | 업무 자료 탐색의 입구 | 질문별 실제 문서 경로 연결 |
| knowledge/ | 규정·협의·업무 설명 | 출처·효력일·예외·확인 수준 기록 |
| SKILL.md | 반복 작업을 처리하는 절차 | 사용 조건·탐색·판단·검증 순서 |
| 기존 추출 소스 폴더 | ABAP·웹 자산·객체 정의 | 원천·baseline 보존, 실제 위치 인용 |
| tests/ 또는 harness/ | 평가 질문·검증 기록 | 기대 행동과 실제 결과 구분 |
| maps/ | 업무·코드·검증 관계 | 기존 경로를 유지하고 문서로 연결 |

Codex는 AGENTS.md를 작업 지침으로 읽는다. 상위·하위 지침이 함께 적용될 수 있고, 여러 폴더를 연결하면 기본 폴더를 중심으로 지침을 찾는다. 그래서 첫 요청에서 실제 적용되는 지침을 확인한다. 기존 내용을 새 지침으로 통째로 덮어쓰지 않는다. [공식 AGENTS.md 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

폴더명은 예시이며 실제 저장소의 구조를 우선한다. [업무 맥락 만들기](#/learn/knowledge), [업무 스킬 및 회귀](#/learn/feedback)에서 자료 정리·반복 작업의 기준을 이어간다.

### 4-4. 첫 분석 요청

업무 하나의 대상·기준 시점·근거 범위·원하는 결과를 적는다. 소스와 업무 문서의 관계를 먼저 확인해 수정 범위를 정한다.

```text
이 저장소의 근로시간 누적 표시 업무를 분석해 주세요.
업무 INDEX, 관련 규정과 후속 정정을 읽고 실제 추출 소스와 연결해 주세요.
규정 설명, 사용자 요청, 코드 구현, 실행 확인을 구분해 주세요.
근거 파일과 관련 구간을 적고, 없는 자료나 동적 호출 때문에
확정할 수 없는 부분은 확인할 질문으로 남겨 주세요.
이번에는 영향 분석만 작성하고 코드는 수정하지 마세요.
```

업무명은 실제 담당 업무로 바꾼다. 파일 이름만 나열한 답변인지, 본문·조건·후속 정정을 읽고 판단했는지 검토한다. 소스를 읽은 것과 SAP에서 실행한 것은 각각 기록한다.

### 4-5. 수정 요청과 차이 검토

분석 후 변경할 동작·유지할 기능·검증 방법을 정한다. 앱이 파일 수정이나 명령 실행 권한을 요청하면 대상 경로와 작업 범위를 확인한다.

```text
앞서 확인한 파일에 요청한 표시 문구를 수정해 주세요.
사용자 변경, AGENTS.md, .git, .github, 로컬 설정을 보존해 주세요.
원천과 baseline의 바이트·줄바꿈을 유지해 주세요.
변경 전후와 이유를 기록하고 관련 검사를 실행해 주세요.
미실행 검사와 실제 SAP 검증이 필요한 항목을 구분해 주세요.
변경 비교 보고서와 변경 파일 ZIP을 제공해 주세요.
커밋·push·운영 배포는 제가 하겠습니다.
```

작업이 끝나면 앱의 변경 보기 또는 VS Code Source Control에서 파일별 차이를 읽는다. 요청 밖 변경·원천 수정·줄바꿈 전체 변경을 확인한다.

| 검토 항목 | 확인할 결과 |
|---|---|
| 실제 변경 | 파일 경로, 이유, 요청한 동작과 유지 조건 |
| 검사 | 실행 명령·결과, 화면 확인 범위, 미실행 항목 |
| 후속 작업 | 필요한 원문, SAP 시험, 사용자 승인·운영 반영 |

### 4-6. 포털 검증과 공유

이 포털은 Node.js 24 이상을 사용한다. 루트 package.json과 지침을 확인하고 다음 명령을 실행한다. 다른 ABAP 저장소는 그 프로젝트의 검사 절차를 따른다.

```bash
npm run build
npm test
npm run preview:file
```

변경한 화면과 다운로드를 확인한 뒤 [GITHUB 연동](#/learn/workspace)의 Commit·Push 절차로 공유한다. 포털 검사 통과와 실제 SAP 호환성·운영 검증을 구분한다.

### 4-7. 다음 작업에 넘길 MD

다음 대화에서 상태를 다시 추정하지 않도록 목적·결정·진행·근거를 남긴다. 프로젝트 문서 4종은 다음 질문으로 읽는다.

| 문서 | 읽을 질문 |
|---|---|
| intent.md | 왜 이 일을 하며 어떤 방향·경계를 유지하는가? |
| spec.md | 어떤 동작·결과물·수용 기준이 합의되었는가? |
| plan.md | 무엇을 구현·검증했고 다음에 무엇이 남았는가? |
| insight.md | 프로젝트의 이유가 누구에게 왜 설득력 있고, 사람들은 어떤 이해와 관점을 얻는가? |

동명 파일도 프로젝트별로 구분한다. [소스 추출·진단의 자료확인](#/library/export-diag)에서 해당 문서를 받는다. 문서 안의 초안·미확인 표기는 작성 당시의 상태로 읽는다.

## 5. 실제로 달라진 작업: 코드 설명에서 업무 근거 확인으로

초기 작업은 AI가 추출한 소스를 이해하도록 하는 데 집중했다. 이후 “코드만으로 우리 회사의 업무를 알 수 있는가”라는 질문이 나왔고, ZHR5의 근로시간·시간외·대휴·정산 자료를 문서와 스킬로 보완했다. 업무 질의, 변경 영향 분석, 지식 정리를 세 절차로 나누는 방향도 여기서 나왔다.

반차를 사용한 날 시간외 금액이 0원이라는 질문에 곧바로 코드 수정안을 제시하면, 원래 입력 규칙을 놓칠 수 있다. 실제 피드백에서 담당자는 이 시차근무 사례의 입력이 원래 출근시각부터의 전체 구간이어야 한다고 설명했다. **업무 절차부터 확인하고 그다음 코드를 보자**는 순서가 중요한 이유다. 상세 사례는 [07. 업무 스킬 및 회귀](#/learn/feedback)에서 다룬다.

첫 분석 요청의 성공 기준도 구체적으로 정한다. “파일을 많이 읽었다”는 보고만으로는 충분하지 않다. 질문의 대상과 적용 시점을 확인했는지, 근거 파일을 직접 열어 볼 수 있는지, 남은 질문이 구체적인지를 살핀다.

## 6. 한계와 다음 방향: 파일을 읽는 AI에서 업무를 이해하는 AI로

새 정책이나 최신 SAP 변경은 앱을 설치하는 것만으로 자동 반영되지 않는다. 추출본과 업무 문서의 날짜를 관리하고, 새 자료가 생기면 관련 INDEX·지식·검증 질문도 함께 갱신해야 한다. 같은 폴더를 열었더라도 모든 파일을 매번 읽었다고 가정하지 않고, 답변에 실제 근거를 요청한다.

로컬에서 문법·파일 검사를 통과한 결과와 SAP에서 실행한 결과도 나눈다. 수정 ZIP 전달, GitHub Push, 개발계 적용 중 어디까지 했는지 보고서에 남기면 다음 작업자가 이어갈 수 있다.

막혔을 때는 작업 경로 → 적용 지침 → 근거 자료 → 변경 차이 → 실행 결과 순서로 확인한다. 다음 [05. 업무 맥락 만들기](#/learn/knowledge)에서는 AI가 업무의 이유를 읽을 수 있도록 실제 사용자 대화를 정리한다.
