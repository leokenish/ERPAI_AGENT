# 실제 사례: ESS 근태시스템 개편

## 화면 개선에서 승인 데이터 보존까지

근태 신청 BSP의 날짜·반차 화면을 개선하고 저장·상신·승인·잔여 연차까지 확인한 사례입니다.

공유 대화 4개에 사용자 요청 254개·AI 본문 245개가 있습니다. 본문 미확보 9곳과 첨부 전용 요청도 원래 순서에 표시합니다.

[첫 요청부터 학습흐름대화 읽기](#/conversations/kbs-erp-ess-attendance/ess-01)

## 이번 공유 링크 재확인

2026-10-24 네 공유 링크의 254턴·499본문을 재대조했습니다. 새 턴은 없으며 기존 26개 에피소드를 유지하고 미확보 이미지 51개를 복구했습니다. 최종 SUBMIT_PRG01 적용 후 재시험은 여전히 미확인입니다.

## 네 대화방이 이어지는 순서

| 대화 | 주요 흐름 | 확인할 전환점 |
|---|---|---|
| 근태 페이지 개선 진행 | 요구·미리보기·BSP 자료·저장·결재 경로 추적 | 연차촉진과 근태 신청의 범위를 바로잡음 |
| 근태페이지 수정 완료 | 기존 안내문·도움말 수정, R1 적용 안내와 초기 오류 | 기존 페이지 수정과 신규 개발을 구분 |
| 작업 자료 확인 | R1 분리 개발, 날짜 선택·일괄 상신·저장 상태 변경 | 원래 페이지를 보존하고 현재 소스에 맞춰 안내 |
| 근태페이지 개선 이어가기 | 기승인 변경·반차·승인 재개·중복 제출 | 업무 처리 결과와 마지막 PRG 수정안의 검증을 구분 |

## 사례 1: 기존 화면을 비교 기준으로 남기기

기존 `guntae_input.kbs`를 보존하며 `guntae_input_r1.kbs`와 R1 클래스·관리자 페이지를 분리했습니다. 기존 경로의 동작과 새 경로가 호출하는 함수·클래스를 대조합니다.

V2 일부 적용 후 R1으로 전환한 사례입니다. AI에게 현재 적용 단계와 실제 파일을 함께 제공해 기존 객체와 추가 객체를 확인합니다.

[R1 분리와 적용 단계의 대화](#/conversations/kbs-erp-ess-attendance/ess-11)

## 사례 2: 날짜 선택 UI와 서버 처리를 함께 보기

날짜 선택·기간 분할·일괄 상신은 화면과 서버 처리를 함께 확인합니다.

| 요구 | 화면에서 확인 | 저장·결재에서 확인 |
|---|---|---|
| 주말을 사이에 둔 신청 | 선택 가능 날짜와 기간 구분 | 생성된 신청 건수와 각 기간 |
| 여러 건 상신 | 선택된 행과 처리 결과 표시 | 건별 결재 번호·부분 실패 |
| 1일을 반차로 변경 | 오전·오후와 0.5일 표시 | 승인 결과·실제 차감·잔여 일수 |
| 기승인 날짜 이동 | 기존 신청과 변경 신청 구분 | 승인 전 원래 데이터 보존·승인 후 반영 |

[날짜 선택과 일괄 상신의 대화](#/conversations/kbs-erp-ess-attendance/ess-14)

## 사례 3: 결재가 보이지 않을 때 확인 순서

신청 이력에 상신 상태가 보여도 결재자의 실제 목록에는 나타나지 않을 수 있었습니다. 대화에서는 BSP 경로, 저장 함수, 결재 번호 연결, 워크아이템 상태, 실제 결재자와 이벤트를 차례로 확인했습니다.

조회 키와 `ZSERIAL`·`SAVED` 상태를 확인하고, 적용 함수의 `BEFORE_ACTION`·`BIND_SERIAL` 호출과 BSP 버튼 이벤트를 대조했습니다.

[결재 번호 연결의 대화](#/conversations/kbs-erp-ess-attendance/ess-21) · [승인 재개와 BSP 이벤트의 대화](#/conversations/kbs-erp-ess-attendance/ess-23)

## 사례 4: 원래 휴가를 보존하고 결과를 확인하기

기승인 변경은 원래 승인 데이터와 새 신청을 함께 확인합니다. 변경 메타데이터·잔여 연차·결재 상태를 대조합니다.

날짜 이동 후 승인 재개와 반차 변경 후 잔여 0.5일 표시는 **사용자 성공 보고**가 있습니다. 부분 취소·동시 신청·연도 경계 등 전체 회귀 검증은 남아 있습니다.

[원래 데이터 비교](#/conversations/kbs-erp-ess-attendance/ess-22) · [반차 변경 결과](#/conversations/kbs-erp-ess-attendance/ess-24)

## 사례 5: 업무 처리는 성공했는데 첫 상신 팝업이 남음

문제 시점은 **첫 상신**이었습니다. 토큰 진단과 F5·뒤로 가기의 POST 재제출 흐름을 대조하고, 실제 중복 실행 여부를 확인 과제로 남겼습니다.

`SUBMIT_PRG01`은 POST 처리 후 GET으로 이동하고 진단 정보를 보완하는 수정안입니다. **적용 후 사용자 재시험은 대기 상태**입니다.

[첫 상신 문제의 대화](#/conversations/kbs-erp-ess-attendance/ess-25) · [최종 PRG 수정안과 남은 시험](#/conversations/kbs-erp-ess-attendance/ess-26)

## 따라 하기: 근거가 있는 상태표 작성

대화와 첨부를 읽고 한 에피소드의 상태표를 작성합니다.

1. 사용자의 실제 요구와 AI가 처음 해석한 내용을 비교합니다.
2. 기준 소스·화면·오류 메시지와 적용 단계를 적습니다.
3. 제안한 수정, 실제 적용 보고, 결과 확인을 구분합니다.
4. 원래 승인 데이터·새 신청·잔여 일수·결재 상태에서 확인한 항목을 표시합니다.
5. 마지막 수정 뒤 다시 확인해야 할 시나리오를 적습니다.

SAP 재시험 항목은 첫 상신·연속 클릭·F5·뒤로 가기·토큰 만료·처리 실패와 재시도·IE11/Chrome 차이입니다.
