# ESS 근태시스템 개편

## 화면 개선에서 승인 데이터 보존까지

근태 신청 BSP의 날짜·반차 화면을 개선한 사례다. 화면 변경에서 시작해 저장·상신·승인·잔여 연차까지 확인했다.

공유 대화 4개에는 사용자 요청 254개와 AI 본문 245개가 있다. 본문을 확보하지 못한 9곳과 첨부 전용 요청도 원래 순서에 표시한다.


## 이번 공유 링크 재확인

2026-10-24에 네 공유 링크의 254턴·499본문을 다시 대조했다. 새 턴은 없었다. 기존 26개 에피소드를 유지하고, 확보하지 못했던 이미지 51개를 복구했다. 최종 SUBMIT_PRG01 적용 후 재시험은 여전히 미확인 상태다.

## 네 대화방이 이어지는 순서

| 대화 | 주요 흐름 | 확인할 전환점 |
|---|---|---|
| 근태 페이지 개선 진행 | 요구·미리보기·BSP 자료·저장·결재 경로 추적 | 연차촉진과 근태 신청의 범위를 바로잡음 |
| 근태페이지 수정 완료 | 기존 안내문·도움말 수정, R1 적용 안내와 초기 오류 | 기존 페이지 수정과 신규 개발을 구분 |
| 작업 자료 확인 | R1 분리 개발, 날짜 선택·일괄 상신·저장 상태 변경 | 원래 페이지를 보존하고 현재 소스에 맞춰 안내 |
| 근태페이지 개선 이어가기 | 기승인 변경·반차·승인 재개·중복 제출 | 업무 처리 결과와 마지막 PRG 수정안의 검증을 구분 |

## 사례 1: 기존 화면을 비교 기준으로 남기기

기존 `guntae_input.kbs`를 보존하고, `guntae_input_r1.kbs`와 R1 클래스·관리자 페이지를 분리했다. 기존 경로의 동작과 새 경로에서 호출하는 함수·클래스를 대조한다.

V2를 일부 적용한 뒤 R1으로 전환한 사례다. AI에게 현재 적용 단계와 실제 파일을 함께 제공하고, 기존 객체와 추가 객체를 확인한다.


## 사례 2: 날짜 선택 UI와 서버 처리를 함께 보기

날짜 선택·기간 분할·일괄 상신은 화면과 서버 처리를 함께 확인한다.

| 요구 | 화면에서 확인 | 저장·결재에서 확인 |
|---|---|---|
| 주말을 사이에 둔 신청 | 선택 가능 날짜와 기간 구분 | 생성된 신청 건수와 각 기간 |
| 여러 건 상신 | 선택된 행과 처리 결과 표시 | 건별 결재 번호·부분 실패 |
| 1일을 반차로 변경 | 오전·오후와 0.5일 표시 | 승인 결과·실제 차감·잔여 일수 |
| 기승인 날짜 이동 | 기존 신청과 변경 신청 구분 | 승인 전 원래 데이터 보존·승인 후 반영 |


## 사례 3: 결재가 보이지 않을 때 확인 순서

신청 이력에는 상신 상태가 보이지만 결재자의 실제 목록에는 나타나지 않는 경우가 있었다. 대화에서는 BSP 경로, 저장 함수, 결재 번호 연결, 워크아이템 상태, 실제 결재자와 이벤트를 차례로 확인했다.

조회 키와 `ZSERIAL`·`SAVED` 상태를 확인했다. 이어서 적용 함수의 `BEFORE_ACTION`·`BIND_SERIAL` 호출과 BSP 버튼 이벤트를 대조했다.


## 사례 4: 원래 휴가를 보존하고 결과를 확인하기

이미 승인된 휴가를 바꿀 때는 원래 승인 데이터와 새 신청을 함께 확인한다. 변경 메타데이터·잔여 연차·결재 상태도 대조한다.

날짜 이동 후 승인을 재개한 경우와 반차 변경 후 잔여 0.5일이 표시된 경우에는 **사용자 성공 보고**가 있다. 부분 취소·동시 신청·연도 경계 등을 포함한 전체 회귀 검증은 남아 있다.


## 사례 5: 업무 처리는 성공했는데 첫 상신 팝업이 남음

문제가 발생한 시점은 **첫 상신**이었다. 토큰 진단과 F5·뒤로 가기의 POST 재제출 흐름을 대조했다. 실제로 중복 실행됐는지는 확인 과제로 남겼다.

`SUBMIT_PRG01`은 POST 처리 후 GET으로 이동하고 진단 정보를 보완하는 수정안이다. **적용 후 사용자 재시험은 대기 상태**다.


## 따라 하기: 근거가 있는 상태표 작성

대화와 첨부를 읽고 한 에피소드의 상태표를 작성한다.

1. 사용자의 실제 요구와 AI가 처음 해석한 내용을 비교한다.
2. 기준 소스·화면·오류 메시지와 적용 단계를 적는다.
3. 제안한 수정, 실제 적용 보고, 결과 확인을 구분한다.
4. 원래 승인 데이터·새 신청·잔여 일수·결재 상태에서 확인한 항목을 표시한다.
5. 마지막 수정 뒤 다시 확인해야 할 시나리오를 적는다.

SAP에서 다시 시험할 항목은 첫 상신·연속 클릭·F5·뒤로 가기·토큰 만료·처리 실패와 재시도·IE11/Chrome 차이다.
