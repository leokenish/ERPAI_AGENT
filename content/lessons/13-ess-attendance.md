# 실제 사례: ESS 근태시스템 개편

## 화면 개선에서 승인 데이터 보존까지

이 프로젝트는 기존 근태 신청 BSP의 화면을 개선하는 작업에서 시작했습니다. 날짜 선택과 반차 표시를 다듬다가 저장·상신·승인·반려·취소와 잔여 연차까지 확인 범위가 넓어졌습니다. **화면에서 원하는 모양이 보이는 것과 업무 데이터가 올바르게 처리되는 것은 다른 확인입니다.**

2026-10-16에 공유 대화 4개를 확인했습니다. 사용자 요청 254개, AI 응답 본문 245개와 본문이 표시되지 않은 응답 위치 9곳을 순서대로 반영했습니다. 첨부만 보낸 요청도 원래 위치를 유지했습니다.

[첫 요청부터 학습흐름대화 읽기](#/conversations/kbs-erp-ess-attendance/ess-01)

## 네 대화방이 이어지는 순서

| 대화 | 주요 흐름 | 확인할 전환점 |
|---|---|---|
| 근태 페이지 개선 진행 | 요구·미리보기·BSP 자료·저장·결재 경로 추적 | 연차촉진과 근태 신청의 범위를 바로잡음 |
| 근태페이지 수정 완료 | 기존 안내문·도움말 수정, R1 적용 안내와 초기 오류 | 기존 페이지 수정과 신규 개발을 구분 |
| 작업 자료 확인 | R1 분리 개발, 날짜 선택·일괄 상신·저장 상태 변경 | 원래 페이지를 보존하고 현재 소스에 맞춰 안내 |
| 근태페이지 개선 이어가기 | 기승인 변경·반차·승인 재개·중복 제출 | 업무 처리 결과와 마지막 PRG 수정안의 검증을 구분 |

## 사례 1: 기존 화면을 비교 기준으로 남기기

사용자는 기존 `guntae_input.kbs`를 바로 수정하기에는 위험이 크다고 설명했습니다. 이후 `guntae_input_r1.kbs`와 R1 클래스·관리자 페이지를 분리하는 방향으로 안내가 바뀌었습니다. 여기서 중요한 것은 파일 이름을 바꾸는 행위보다 **기존 경로가 계속 동작하는지, 새 경로가 어떤 함수와 클래스를 호출하는지** 확인하는 일입니다.

V2 안내를 일부 적용한 상태에서 R1 안내가 나왔기 때문에, 이미 만든 객체와 새로 만들어야 할 객체를 다시 대조해야 했습니다. AI에게는 현재 적용 단계와 실제 파일을 함께 제공해야 합니다.

[R1 분리와 적용 단계의 대화](#/conversations/kbs-erp-ess-attendance/ess-11)

## 사례 2: 날짜 선택 UI와 서버 처리를 함께 보기

하루 선택, 시작·종료일 입력 후 자동 조회, 작은 창에서 날짜가 겹치는 문제, 주말을 사이에 둔 기간 분할, 일괄 상신은 서로 다른 요구입니다. 날짜가 두 줄로 보이는 문제를 고쳤다고 신청 기간의 저장 방식까지 검증된 것은 아닙니다.

| 요구 | 화면에서 확인 | 저장·결재에서 확인 |
|---|---|---|
| 주말을 사이에 둔 신청 | 선택 가능 날짜와 기간 구분 | 생성된 신청 건수와 각 기간 |
| 여러 건 상신 | 선택된 행과 처리 결과 표시 | 건별 결재 번호·부분 실패 |
| 1일을 반차로 변경 | 오전·오후와 0.5일 표시 | 승인 결과·실제 차감·잔여 일수 |
| 기승인 날짜 이동 | 기존 신청과 변경 신청 구분 | 승인 전 원래 데이터 보존·승인 후 반영 |

[날짜 선택과 일괄 상신의 대화](#/conversations/kbs-erp-ess-attendance/ess-14)

## 사례 3: 결재가 보이지 않을 때 확인 순서

신청 이력에 상신 상태가 보여도 결재자의 실제 목록에는 나타나지 않을 수 있었습니다. 대화에서는 BSP 경로, 저장 함수, 결재 번호 연결, 워크아이템 상태, 실제 결재자와 이벤트를 차례로 확인했습니다.

`ZSERIAL` 연결이나 `SAVED` 메타데이터만으로 실제 승인·반려를 판단하지 않습니다. 사용자가 조회에 사용한 키부터 확인하고, `BEFORE_ACTION`·`BIND_SERIAL` 호출이 현재 적용 함수에 있는지 대조했습니다. 마지막에는 버튼이 보이는지와 버튼을 눌렀을 때 BSP 이벤트가 처리되는지도 나눠 확인했습니다.

## 사례 4: 원래 휴가를 보존하고 결과를 확인하기

기승인 변경 신청 중에는 원래 승인 휴가와 새 변경 신청이 함께 존재합니다. 대화에서는 원래 데이터, 변경 메타데이터, 잔여 연차와 결재 상태를 함께 확인했습니다. 특정 로그 조회에 결과가 없다는 사실만으로 데이터가 전혀 바뀌지 않았다고 확정하지 않았습니다.

후반에는 사용자가 날짜 이동 후 승인 재개 결과와 1일을 반차로 바꾼 뒤 잔여 0.5일 표시를 확인했습니다. 이는 **대화에 제시된 특정 시나리오의 실행 보고**입니다. 모든 근태 종류·부분 취소·동시 신청·연도 경계까지 통과했다는 의미는 아닙니다.

[원래 데이터 비교](#/conversations/kbs-erp-ess-attendance/ess-22) · [반차 변경 결과](#/conversations/kbs-erp-ess-attendance/ess-24)

## 사례 5: 업무 처리는 성공했는데 첫 상신 팝업이 남음

사용자가 말한 문제는 ‘승인 후’가 아니라 **첫 상신 시점**의 팝업이었습니다. AI의 초기 해석을 수정한 뒤 토큰 진단, F5와 뒤로 가기의 POST 재제출 맥락을 대조했습니다. `TOKEN_STOP` 표시만으로 저장 함수가 실제로 두 번 실행됐다고 단정할 수는 없습니다.

마지막 `SUBMIT_PRG01`은 POST 처리 뒤 GET으로 이동하는 방식과 진단 정보 표시를 보완한 제안입니다. **이 마지막 수정안의 적용 후 사용자 재시험 결과는 공유 대화에 없습니다.** 앞선 반차 승인 성공을 PRG 수정안의 성공으로 소급하지 않습니다.

## 따라 하기: 근거가 있는 상태표 작성

SAP나 데이터베이스를 변경하지 않고 대화와 첨부를 읽는 실습입니다. 한 에피소드를 골라 다음 항목을 작성합니다.

1. 사용자의 실제 요구와 AI가 처음 해석한 내용을 비교합니다.
2. 기준 소스·화면·오류 메시지와 적용 단계를 적습니다.
3. 제안한 수정, 실제 적용 보고, 결과 확인을 구분합니다.
4. 원래 승인 데이터·새 신청·잔여 일수·결재 상태에서 확인한 항목을 표시합니다.
5. 마지막 수정 뒤 다시 확인해야 할 시나리오를 적습니다.

최종 제출 흐름은 정상 첫 상신, 연속 클릭, F5, 뒤로 가기, 토큰 만료, 업무 처리 실패와 재시도, IE11·Chrome 차이를 포함해 확인해야 합니다. 교육 포털의 빌드·테스트는 이 SAP 회귀 시험을 대신하지 않습니다.
