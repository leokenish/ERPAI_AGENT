# ESS 근태시스템 개편

## 날짜 입력과 승인 데이터 연결

근태 신청 BSP의 날짜·반차 화면을 개선한 사례입니다. 화면에서 입력한 내용이 업무 기록까지 이어져야 하므로 저장·상신·승인·잔여 연차의 처리 경로를 함께 살폈습니다.

## 대화별 진행 흐름

| 대화 | 주요 내용 | 핵심 전환점 |
|---|---|---|
| 근태 페이지 개선 진행 | 요구·미리보기·BSP·저장·결재 경로 | 일반 근태 신청의 화면과 처리 범위 정리 |
| 근태페이지 수정 완료 | 안내문·도움말·R1 적용 | 기존 페이지와 새 경로의 역할 분리 |
| 작업 자료 확인 | R1·날짜 선택·일괄 상신·저장 상태 | 현재 소스에 맞춘 화면·처리 연결 |
| 근태페이지 개선 이어가기 | 기승인 변경·반차·승인 재개·첫 상신 | 승인 데이터와 변경 신청의 연결 |

## 사례 1. 기존 화면과 R1 분리

변경 전후를 비교할 수 있도록 기존 `guntae_input.kbs`를 보존하고, 개선 기능을 `guntae_input_r1.kbs`와 R1 클래스·관리자 페이지로 나눴습니다. 이후 기존 경로와 새 경로가 호출하는 함수·클래스를 대조했습니다.

V2 일부 적용 뒤 R1으로 전환한 과정이므로, AI에게 현재 파일과 적용 단계를 함께 전달했습니다. 이를 통해 기존 객체와 추가할 객체를 같은 기준으로 정리했습니다.

## 사례 2. 날짜 선택과 서버 처리

날짜 선택·기간 분할·일괄 상신은 화면에서 고른 값과 저장·결재 결과가 함께 맞아야 합니다. 따라서 다음 항목을 짝지어 대조했습니다.

| 요구 | 화면의 입력·표시 | 저장·결재의 대응 항목 |
|---|---|---|
| 주말을 사이에 둔 신청 | 선택 가능 날짜와 기간 구분 | 생성된 신청 건수와 각 기간 |
| 여러 건 상신 | 선택한 행과 처리 결과 | 건별 결재 번호·부분 실패 |
| 1일을 반차로 변경 | 오전·오후와 0.5일 | 승인 결과·실제 차감·잔여 일수 |
| 기승인 날짜 이동 | 기존 신청과 변경 신청 | 승인 전 데이터 보존·승인 후 반영 |

## 사례 3. 결재 전달 경로 추적

신청 이력에는 상신 상태가 보이지만 결재자 목록에는 나타나지 않는 문제가 있었습니다. 따라서 BSP 경로에서 저장 함수·결재 번호·워크아이템·결재자 이벤트까지 순서대로 추적했습니다.

먼저 조회 키와 `ZSERIAL`·`SAVED` 상태를 살폈습니다. 이어서 적용 함수의 `BEFORE_ACTION`·`BIND_SERIAL` 호출과 BSP 버튼 이벤트를 대조해 신청과 결재가 연결되는 지점을 찾았습니다.

## 사례 4. 기승인 휴가 변경

이미 승인된 휴가를 바꿀 때는 원래 승인 데이터와 새 신청을 구분합니다. 그래야 변경 신청을 처리하는 동안 원래 기록을 보존하고, 최종 결재 결과에 따라 새 날짜와 사용량을 반영할 수 있습니다.

날짜 이동 후 승인을 재개한 사례와 반차 변경 후 잔여 0.5일이 표시된 사례가 있습니다. 두 사례에서 원래 휴가·변경 메타데이터·결재 상태·잔여 연차를 함께 대조했습니다.

## 사례 5. 첫 상신과 페이지 전환

첫 상신 때 팝업이 남는 문제를 조사하면서 토큰 처리와 F5·뒤로 가기의 POST 재제출 흐름을 비교했습니다. POST는 신청 내용을 서버에 보내는 요청이므로 페이지 이동 방식과 함께 살폈습니다.

`SUBMIT_PRG01` 수정안은 POST 처리 뒤 GET으로 이동하도록 구성했습니다. 이를 통해 신청 처리와 결과 화면 조회의 역할을 나누는 접근을 살펴볼 수 있습니다.

## 사례별 처리표 작성

한 에피소드의 대화와 첨부를 읽고 처리표를 작성합니다. 화면에 입력한 값부터 실제 업무 데이터까지 이어지는 경로를 정리하는 연습입니다.

1. 사용자의 업무 요구와 적용 범위를 적습니다.
2. 기준 소스·화면·오류 메시지를 기록합니다.
3. 입력·저장·상신·승인의 처리 순서를 연결합니다.
4. 원래 승인 데이터·새 신청·잔여 일수·결재 상태를 짝지어 적습니다.
5. 첫 상신·연속 클릭·F5·뒤로 가기·토큰 만료·재시도의 동작을 비교합니다.
