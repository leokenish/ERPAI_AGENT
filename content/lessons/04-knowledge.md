# 업무 맥락 만들기

## 1. 왜 코드 밖의 자료가 필요한가

코드를 읽으면 어떤 조건에서 값이 계산되는지 알 수 있다. 하지만 “왜 이 조건을 만들었는가”, “담당자들은 어떤 예외를 합의했는가”, “예전 요청은 취소됐는가”까지 코드에 담겨 있지는 않다. 이 배경을 놓치면 프로그램의 동작을 설명하고도 실제 업무 질문에는 잘못 답할 수 있다.

실제 프로젝트에서도 추출한 코드와 구조만으로는 부족하다는 요청이 나왔다. 규정·매뉴얼·사용자 의견을 함께 읽어야 한다는 것이다. 업무 맥락을 만든다는 것은 **당시의 상황, 적용 대상, 판단 이유, 바뀐 이력을 근거와 함께 남기는 것**이다.

결과물은 주제별 업무 문서다. 짧게 요약하는 데서 끝내지 않고, 다음 담당자와 AI가 원래 문서로 돌아가 근거를 확인할 수 있게 만든다.

## 2. 어떤 문제를 겪었는가: 대화를 줄이면 중요한 차이가 사라진다

메신저에 “처리했습니다”라고 적혀 있어도 모든 문제가 끝난 것은 아닐 수 있다. 개인 설정은 바꿨지만 과거 자료는 다음 주에 고치기로 했을 수도 있다. “이렇게 바꾸면 어떨까요?”라는 제안도 확정된 규정과 구분해야 한다.

첨부 자료도 놓치기 쉬웠다. 카카오톡 TXT로 업무 문서를 만든 뒤, 이미지 내용이 빠졌다는 사용자 지적이 나왔다. TXT에 ‘사진’이라고 적혀 있어도 그 안의 화면이나 수치는 알 수 없다. 파일 저장 시각만 보고 발화에 연결하면, 나중에 다운로드한 시간을 실제 전송 시각으로 잘못 해석할 수도 있다.

그래서 **발화 순서·후속 정정·이미지의 실제 내용**을 함께 확인하고, 확보하지 못한 자료는 미확인으로 남기는 방식을 택했다.

## 3. 어떻게 정리하기로 했는가: 원문·업무 지식·절차를 나누기

| 자료 | 여기서 찾는 것 | 정리할 때 놓치지 않을 것 |
|---|---|---|
| 규정·지침 | 공식 기준과 적용 조건 | 효력일·대상·예외 |
| 매뉴얼·양식 | 실제 입력과 처리 절차 | 입력값·승인 흐름·예외 처리 |
| 사용자 대화 | 문의·불편·협의·정정의 이유 | 요청·합의·완료보고·재발의 구분 |
| 회의록 | 결정과 미결 사항 | 결정 주체·기한·후속 확인 |
| 이미지·엑셀 | 화면의 관찰값과 계산 근거 | 원본 위치·단위·표시값·읽지 못한 부분 |

원본을 보존한 상태에서 업무별 설명을 MD로 작성한다. Markdown은 제목·표·링크를 담을 수 있는 텍스트 문서 형식으로, 검색과 변경 비교가 쉽다. 다만 읽기 좋은 TXT의 확장자를 MD로 바꾸는 것만으로는 충분하지 않다. **출처와 적용 조건을 함께 정리하는 작업이 핵심**이다.

업무 지식에는 “**무엇을 근거로 답하는가**”를 담고, 스킬에는 “**그 근거를 어떤 순서로 찾고 판단하는가**”를 적는다. **규정마다 스킬을 하나씩 만들기보다 규정·협의는 지식 문서에 두고, 그 자료를 읽는 절차를 스킬로 연결한다.**

## 4. 어떻게 만드는가: ZHR5의 업무를 확인하고 문서에 역할을 나누기

ZHR5 구축 안내는 추출 폴더를 AI에게 읽게 하고, 무엇을 하는 프로그램인지 설명을 받는 데서 시작했다. 담당자가 그 설명을 확인하고 정정한 뒤 문서를 구성하는 순서였다. 이후 사용자가 에이전트 구성 완료를 보고했고, 확보된 문서에는 근로시간·시간외실비·대휴·정산의 업무 범위와 추가한 규정·협의 자료가 담겨 있다.

### 먼저 알아둘 세 문서의 역할

요청에서 말한 `AGENT.md`의 실제 파일명은 **AGENTS.md**다. Codex 공식 안내에서도 S가 붙은 이름을 사용한다.

| 파일 | Codex 공식 안내와 프로젝트에서의 역할 | ZHR5에 적은 내용 |
|---|---|---|
| `README.md` | 사람이 프로젝트의 목적과 시작 방법을 읽는 안내문이다. Codex가 자동으로 적용하는 지침 파일로 지정된 것은 아니며, 필요할 때 읽거나 읽도록 요청한다. | 어떤 업무를 다루는지, 어느 문서부터 볼지, 세 스킬이 어디에 있는지 |
| `AGENTS.md` | Codex가 작업을 시작할 때 읽는 프로젝트 지침이다. 프로젝트와 작업 폴더에 적용되는 규칙을 알려 준다. | 담당 업무의 범위, 근거를 읽는 순서, 출처·시점 구분, 원본 보존과 피드백 처리 |
| `SKILL.md` | 반복하는 작업의 절차서다. 이름과 설명으로 필요한 스킬을 고르고, 선택한 스킬의 본문을 읽는다. | 업무 질문에 답하기, 새 자료 정리하기, 변경 영향 살펴보기 |

공식 역할은 [AGENTS.md 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [스킬 안내](https://learn.chatgpt.com/docs/build-skills), [프로젝트 문서 구성 예시](https://developers.openai.com/cookbook/examples/codex/iterating-development-workflows-with-codex)에서 확인했다. README를 읽는 것만으로 스킬이 자동 실행되거나, 세 스킬을 매번 전부 읽는 구조는 아니다.

### 1단계 · 추출 폴더에서 핵심 업무를 찾아보기

Codex에서 실제 추출본이 들어 있는 프로젝트 폴더를 연다. 파일 목록과 추출 기록, 주요 프로그램·함수·화면을 읽게 하고 어떤 업무인지 설명을 요청한다. ZHR5의 초기 분석에서는 탄력근로 계획·결재·월정산, 통상·교대 시간외 신청과 일부 회계 연결이 확인됐다.

다음은 당시 구축 흐름을 따라 해볼 수 있도록 정리한 요청 예시다.

```text
이 프로젝트의 실제 추출 폴더와 manifest·catalog·로그를 확인해 주세요.
주요 프로그램·함수·화면이 담당하는 업무를 묶고 근거 파일 경로를 적어 주세요.
knowledge/hr/overview.md에는 업무 범위를, flows.md에는 처리 흐름을 정리해 주세요.
파일에서 확인한 사실과 이름으로 추정한 부분, 추출되지 않은 부분을 나눠 주세요.
아직 원본 코드는 수정하지 마세요.
```

### 2단계 · 담당자가 업무 설명을 읽고 바로잡기

`overview.md`와 `flows.md`를 읽으며 실제 담당 업무와 맞는지 확인한다. 예를 들어 ‘근로시간 정산’과 ‘급여 전체’를 같은 범위로 묶지 않았는지, 입력 화면과 승인·지급 단계를 혼동하지 않았는지 살핀다. 틀린 부분은 규정·매뉴얼·협의 기록을 근거로 정정한다.

실제 대화에서도 코드와 구조만으로는 업무 배경을 알기 어렵다는 의견이 나왔다. 이후 원문 11개를 정리한 업무 지식 묶음과 세 스킬이 전달됐다. 이때 만든 지식 문서의 함수 이름은 우선 탐색 후보였고, 실제 추출 코드와 대조하는 작업은 후속으로 이어졌다.

### 3단계 · 합의한 업무 범위를 README·AGENTS·세 스킬에 나누기

`README.md`에는 프로젝트를 처음 여는 사람이 볼 목적과 시작 링크를 둔다. `AGENTS.md`에는 확인한 업무 범위와 공통 작업 규칙을 적는다. 업무 기준 자체는 `knowledge/`에 두고, 반복해서 하는 세 가지 작업만 별도의 스킬로 만든다.

| 실제 스킬 경로 | 어떤 요청에 쓰는가 | 수행 순서 |
|---|---|---|
| `.agents/skills/zhr5-business-qa/SKILL.md` | “이 경우 어떻게 처리하나요?” | 조건 확인 → 관련 지식과 후속 정정 → 필요한 코드 확인 → 근거를 붙인 답변 |
| `.agents/skills/zhr5-knowledge-curation/SKILL.md` | “새 규정과 대화를 지식에 반영해 주세요.” | 원문 확인 → 기존 설명과 비교 → 출처·적용일 정리 → 지식과 목차 갱신 |
| `.agents/skills/zhr5-change-impact/SKILL.md` | “이 기준을 바꾸면 어디에 영향이 있나요?” | 변경 전후 조건 확인 → 관련 문서와 코드 탐색 → 영향 범위와 재확인 항목 정리 |

```text
방금 확인하고 정정한 핵심 업무를 기준으로 README.md와 AGENTS.md를 구성해 주세요.
README에는 목적·시작 방법·주요 문서 링크를, AGENTS에는 범위·읽는 순서·근거 기준을 적어 주세요.
업무 질의, 새 지식 정리, 변경 영향 분석은 각각 SKILL.md로 나눠 주세요.
스킬에는 언제 사용하는지와 읽는 절차를 적고, 업무 규정은 knowledge 문서로 연결해 주세요.
기존 문서가 있으면 유효한 내용을 유지하며 필요한 부분만 병합해 주세요.
```

### 4단계 · 질문에서 실제 코드 위치까지 길을 잇기

`knowledge/INDEX.md`는 질문에 맞는 문서를 찾는 목차다. 코드 질문이면 `knowledge/code-map/working-time.md`에서 관련 함수·화면을 찾고, `docs/EXPORT_GUIDE.md`를 참고해 추출본의 실제 파일을 연다. 후속으로 만든 `maps/INDEX.md`와 소스 설명 문서는 이 길을 더 자세히 안내한다.

```document-tree
knowledge-files
```

위 트리는 파일을 읽는 관계다. `AGENTS.md` 안에 다른 파일이 저장된다는 뜻은 아니다. 이 포털에는 MD와 코드 확인 위치가 보존돼 있다. 마지막 ABAP·화면 원본은 해당 추출본이 있는 로컬 프로젝트에서 열어야 한다.

### 업무 자료 한 건을 추가할 때

1. 원본에 ID를 붙이고 파일명·대화 기간·문서일·검토 범위를 기록한다. 업로드일과 규정 효력일은 나눈다.
2. 한 질문과 관련된 앞뒤 대화를 읽는다. 최초 요청 뒤에 취소·정정·추가 조건이 있는지 확인한다.
3. 문장을 관찰 사실, 담당자 설명, 요청, 합의, 완료보고, 실제 검증으로 나눈다.
4. 이미지가 있으면 화면명·수치·오류 문구와 발화를 대조한다. 시각은 연결 후보를 찾는 단서로 사용한다.
5. 주제별 MD에 결론·조건·출처 위치·미확인 사항을 적는다. 기존 문서와 충돌하면 양쪽 근거와 시점을 남긴다.
6. INDEX와 관련 업무지도에서 새 문서로 찾아갈 링크를 연결한다.

```text
이 대화 TXT와 확보된 첨부에서 시간외 입력 기본값에 관한 사안을 정리해 주세요.
문의, 담당자 설명, 합의, 완료보고, 실제 결과 확인을 나눠 주세요.
후속 정정까지 읽고 각 문장에 원문 파일·시각·행 또는 페이지를 적어 주세요.
이미지는 전송 시각과 파일 저장 시각을 구분하고 내용으로도 대조해 주세요.
없는 첨부나 애매한 연결은 미확인으로 남겨 주세요.
원본은 유지하고 기존 업무 MD·INDEX에서 보완할 부분을 작성해 주세요.
```

위 문장은 교육용 요청 예시이다. 대상 업무와 자료 이름을 자기 업무에 맞게 바꾼다.

## 5. 실제 사례: 문서를 따라 답하고 원문으로 확인하기

### 문서 구성이 답변을 어떻게 바꾸는가

아래 문답은 실제 지식 MD와 피드백 기록을 바탕으로 읽기 쉽게 재구성한 사례다. 당시 대화의 직접 인용은 아니며, 금액이나 기준을 현재의 모든 직원에게 적용하는 안내도 아니다.

**질문 · “오전 반차 후 실제 근무한 18~23시를 입력했는데 실비가 0원이에요. 코드가 잘못된 건가요?”**

**정정 후 답변 ·** “이 사례의 원래 근무시간은 14~22시입니다. 담당자 확인에 따르면 원래 시작시각인 14시부터 전체 구간을 입력하고, 승인된 반차는 별도로 반영하는 방식입니다. 먼저 입력 기준을 확인해야 합니다. 수정 입력 후의 최종 금액은 실행 결과가 없어 확정할 수 없습니다.”

AI는 처음에 0원 처리 조건만 보고 반차 예외가 빠졌다고 판단했다. 이후 입력 시작시각 문서와 정정 기록을 연결하면서, **코드를 고치기 전에 입력 방법부터 확인하는 답변**으로 바로잡았다. 읽는 경로는 `knowledge/INDEX.md` → `processes/overtime-start-time.md` → `FB-20261001-001.md`다.

**질문 · “누적근로시간에서 가산시간을 뺐다가 왜 다시 넣었나요?”**

**근거를 연결한 답변 ·** “2024년 10월 15일에는 대휴가 생긴 것으로 오해하지 않도록 가산시간을 표시에서 제외했습니다. 하지만 소정시간을 채우지 못했다고 오해하는 문제가 더 크다고 판단해 10월 28일에 표시를 되돌렸습니다. 누적시간 표시와 대휴 발생 계산은 구분해서 봐야 합니다.”

이 답변에는 현재 코드뿐 아니라 결정 이유가 필요하다. `knowledge/processes/selective-cumulative-display.md`에는 협의 배경과 함수·화면의 확인 위치가 함께 있다. `ZHR_52TM_CW_BASE_DATA` → `LZHR008_3F02`의 시간 변환 → `DAILY_WORK_MONTHLY_CONDITION` 표시 구간으로 이어지는 기록을 따라갈 수 있다.

**질문 · “시간외실비 예시에서 계속 8,400원을 써도 되나요?”**

**후속 정정을 반영한 답변 ·** “해당 기록에서는 2026년 9월 1일 기준 변경과 직군별 후속 정정을 함께 확인해야 합니다. 담당자는 정규직, 연봉계약직·특정업무직과 방송지원직의 기준을 구분해 설명했습니다. 적용일과 직군을 먼저 확인하고, 과거 기간에 새 단가를 일괄 적용하면 안 됩니다.”

숫자 하나만 바꾸는 대신 `knowledge/policies/overtime-rate-20260901.md`와 두 건의 9월 23일 피드백을 함께 읽는다. 개인별 마스터 반영이나 실제 지급까지 확인한 답변은 아니다.




사용자가 제공한 **SRC-11.txt**를 살펴본다. 대화는 **2026-08-24~2026-09-21**에 오갔고, 파일 저장 시각은 **2026-09-22 10:20:26**이다. 저장일을 사안의 발생일이나 적용일로 읽지 않도록 구분한다. 교육본에서는 이름과 사번을 제외하고 역할 또는 사례 A로 표시했다.

### 5-1. 사례 A · 교대근무 시간과 기본 입력값이 다른 이유

**상황:** 교대근무표에는 00:00–09:00인데 시간외 입력 화면은 18:00–24:00을 기본값으로 보여 준다는 문의가 들어왔다.

| 대화 순서 | 원문에서 확인한 내용 | 업무지식에 남길 상태 |
|---|---|---|
| 8/24 15:58 · 문의 | 근무표와 입력 기본값이 다르다는 사용자 보고 | 관측 증상 · SRC-11, 8–10행 |
| 16:22–16:27 · 확인 | 담당자는 스케줄을 확인하고 개인 IAM 설정이 우선 반영된다고 설명 | 담당자 설명 · 16–26행 |
| 16:31–16:40 · 협의 | 설정 삭제 또는 우선순위 변경을 묻고, IAM을 지우도록 안내하겠다고 합의 | 안내 합의 · 27–34행 |
| 이후 확인 | 실제 IAM 삭제 후 결과 화면은 제공 TXT에서 확인되지 않음 | 결과 검증 미확인 |

대화에서 확인한 발화는 다음과 같다. 교육본에서는 발신자 이름을 역할로 바꿨다.

> **시스템 담당 · 2026-08-24 16:27**
> “IAM 설정이 되어있으면 이게 우선으로 들어가네요;”
> — SRC-11.txt, 26행

> **업무 담당 · 2026-08-24 16:40**
> “그럼 IAM을 지우라고 할게요! ㅋㅋ”
> — SRC-11.txt, 32행

**관찰한 현상·담당자 설명·안내 합의·검증 결과**를 따로 남긴다. 이렇게 구분한 기록은 다음 업무 질문에 답할 때도 활용할 수 있다.

### 5-2. MD로 바꾼 결과

```markdown
# 교대근무 시간외 입력 기본값과 IAM 설정
- 상태: 과거 담당자 설명·안내 합의 / 실무자 검토 전
- 출처: SRC-11.txt, 2026-08-24, 8–34행
- 대상: 교대근무자 사례 A의 시간외 입력 기본값
- 현상: 근무표 00:00–09:00, 입력 기본값 18:00–24:00
- 당시 설명: 개인 IAM 설정이 스케줄보다 먼저 반영된다고 설명함
- 합의: 사용자에게 IAM 설정 삭제를 안내하기로 함
- 미확인: 실제 삭제·재조회 결과, 현재 코드의 우선순위
- 이미지: 18·23행에 사진 표시만 있음. 원본 이미지 미제공
- 후속 검증: IAM 유무에 따른 입력값을 담당자가 비교
```

### 5-3. 사례 B · “처리했다”의 범위를 구분하기

같은 TXT의 9/16–9/18 대화에는 신규 입력 단가와 과거 입력 내역을 구분하는 사례가 있다.

| 시점 | 대화 근거 | 남겨야 할 판단 |
|---|---|---|
| 9/16 13:30–13:38 | 신규 입사 사례의 단가 문제와 9월 이후 내역 확인 요청 · 329–345행 | 확인·조치 요청 |
| 9/17 09:50 | 개별 등급 변경 완료 발화 · 348행 | 해당 조치의 완료보고 |
| 9/18 16:13–16:33 | 신규 입력은 9,240원, 과거 입력은 아직 수정되지 않았다는 발화와 다음 주 처리 예정 · 351–363행 | 과거 내역은 완료가 아닌 예정 |
