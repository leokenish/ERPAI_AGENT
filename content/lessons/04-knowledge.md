# 업무 맥락 만들기

## 1. 왜 코드 밖의 자료가 필요한가

코드를 읽으면 어떤 조건에서 값이 계산되는지 알 수 있습니다. 하지만 담당자가 그 조건을 선택한 이유나 예외를 합의한 배경까지는 알기 어렵습니다. 따라서 코드의 동작을 실제 업무 질문에 연결하려면 규정·매뉴얼·협의 기록도 함께 읽어야 합니다.

ZHR5 프로젝트에서도 추출한 코드와 구조를 분석한 뒤, 업무 주관부서의 설명과 사용자 의견을 더하는 작업으로 이어졌습니다. **당시의 상황, 적용 대상, 판단 이유, 바뀐 이력을 근거와 함께 남기는 것**이 업무 맥락을 만드는 핵심입니다.

이렇게 정리한 결과는 주제별 업무 문서로 만듭니다. 각 문서에 출처를 연결하면 다음 담당자와 AI도 결론이 나온 과정을 따라 읽을 수 있습니다.

## 2. 어떤 문제를 겪었는가

### 업무 정의 단계의 기술 용어 배제

**처음 업무 맥락을 만들 때는 코딩·IT·ERP 관련 기술 용어를 적지 않습니다.** 이 단계에서는 “누가, 어떤 상황에서, 어떤 기준으로, 무슨 일을 하는가”를 일상적인 업무 언어로 설명합니다. 프로그램명·함수명·테이블명·구현 방식은 업무 정의에 넣지 않고, 업무 기준을 정리한 뒤에 연결합니다.

처음부터 기술 내용을 섞으면 담당자는 업무를 설명하기 전에 시스템 구조부터 알아야 한다고 느끼게 됩니다. 실제로 팀원들이 에이전트를 구성할 때 이 지점에서 어려움을 겪고 있습니다. 또한 현재 코드의 동작을 기준으로 업무를 정의하면, 원래 적용해야 할 정책이나 예외가 설명에서 빠질 수 있습니다.

에이전트에게 처음 묻는 것은 “어느 코드를 바꿀까요?”보다 “이 직원에게 어떤 기준을 적용하나요?”, “이 예외는 왜 인정하나요?” 같은 업무 질문입니다. 따라서 **업무와 정책을 질문하고 → 답변을 담당자가 검토·정정하고 → 정리된 기준에 따라 필요한 코드를 찾아 수정하는 순서**로 구성합니다. 기술적인 연결은 업무 정의가 분명해진 다음에 진행합니다.

**업무에서 코드로 이어지는 순서**

![업무 맥락 추출 → 업무 기준 정리 → 에이전트 구조 설계 → 코드 구현 및 적용](assets/images/agent-four-steps-score-dream.png)

| 처음 정리할 내용 | 업무 언어로 작성한 예 |
|---|---|
| 적용 대상 | 어떤 근무형태의 직원에게 적용하는 기준인가요? |
| 상황과 조건 | 오전 반차를 사용한 날의 시간외근무는 어떻게 신청하나요? |
| 기준과 예외 | 어떤 시간을 인정하며, 예외는 언제 적용하나요? |
| 판단 이유와 근거 | 이렇게 처리하기로 한 이유와 근거 규정은 무엇인가요? |
| 원하는 답변 | 적용 조건과 이유를 함께 설명하고, 담당자의 정정을 반영합니다. |

**업무 정의 문서는 기술을 모르는 담당자도 읽고 맞는지 판단할 수 있어야 합니다.** 업무 이름을 어렵게 바꾸기보다 실제 직원의 질문과 담당자의 설명을 그대로 출발점으로 삼습니다.

### 업무 메신저 대화 맥락 보존

카카오톡에서는 하나의 문의에 여러 담당자가 답하고, 며칠 뒤에 추가 조건이나 정정이 이어집니다. 따라서 마지막 답변만 요약하면 **누구에게 적용한 기준인지, 무엇까지 처리했는지, 왜 그렇게 결정했는지**가 빠질 수 있습니다.

ZHR5의 출처 등록부에는 카카오톡 TXT 5개, 총 11,412행을 날짜별로 나누어 검토한 내역이 기록되어 있습니다. 대화 파일에는 `SRC-07`부터 `SRC-11`까지 출처 ID를 붙였고, 날짜별 협의 내용을 `knowledge/feedback/`에 정리했습니다. 여기서는 실제 단체 대화 `SRC-11.txt`를 발췌해 그 과정을 따라갑니다.

**전체 대화에서 업무카드까지**

1. **원문 등록:** 내보낸 TXT를 보존하고 출처 ID, 대화 기간, 저장일, 줄 수와 파일 해시를 등록합니다. 해시는 같은 원본인지 비교하는 값입니다.
2. **앞뒤 대화 읽기:** 날짜 순서로 읽으며 문의가 시작된 곳부터 설명·합의·후속 정정까지 묶습니다. 하루에 다른 업무가 섞이면 주제별로 나누고, 며칠 뒤 이어진 답변은 같은 사안에 연결합니다.
3. **업무별 구분:** ‘입력 기본시간’, ‘시간외 단가’, ‘과거 내역 정정’처럼 담당자가 이해하는 업무 이름을 붙입니다. 같은 사안의 후속 답변은 새 결론으로 덮어쓰지 않고 이력으로 덧붙입니다.
4. **식별자 부여:** 원본의 `SRC-11`과 카드의 식별자를 연결합니다. 아래 예시에서는 `KC-20260824-01`처럼 ‘처음 논의한 날짜 + 같은 날의 일련번호’로 교육용 카드 ID를 새로 붙였습니다. 제목이 바뀌어도 ID는 유지합니다.
5. **날짜와 의미 정리:** 발화일, 대상 근무일, 기준 적용일, 파일 저장일을 나눕니다. 또한 각 발화를 문의·설명·제안·합의·완료보고로 구분해 무엇을 뜻하는지 적습니다.
6. **지식 문서 연결:** 카드의 조건·이유·근거를 주제별 MD에 정리하고 `knowledge/INDEX.md`에서 찾을 수 있도록 연결합니다. 후속 정정이 생기면 해당 카드와 관련 지식 문서를 함께 보완합니다.

| 구분 | 실제 기록의 예 | 정리하는 이유 |
|---|---|---|
| 원문 출처 ID | `SRC-11` | 어느 대화 파일인지 찾습니다. |
| 업무카드 ID | `KC-20260824-01` · 교육용 부여 | 같은 업무의 질문과 후속 답변을 묶습니다. |
| 대상 근무일 | 2026-08-23 | 어떤 날의 입력 문제인지 구분합니다. |
| 대화일 | 2026-08-24 | 언제 문의하고 설명했는지 남깁니다. |
| 파일 저장일 | 2026-09-22 10:20:26 | 원문을 내보낸 시점이며 업무 발생일과 구분합니다. |
| 별도 적용일 | 단가 협의의 2026-09-01 | 8월에 논의했어도 어떤 근무일부터 새 기준을 적용하는지 적습니다. |

**원문 대화와 업무카드 비교**

아래에서는 실제 세 발언자에게 우대리·나팀장·이과장을 대역으로 배정했습니다. 말투와 날짜를 살리고 이름·사번만 바꿨습니다. ‘정리된 업무카드’를 누르면 같은 대화를 업무 기준과 근거로 정제한 결과를 볼 수 있습니다.

```work-chat
KC-20260824-01
```

**며칠 뒤 이어지는 같은 업무**

다음 사례는 9월 16일의 문의가 17일의 등급 변경 보고, 18일의 과거 내역 협의로 이어집니다. 따라서 한 카드 안에서도 신규 입력과 과거 입력을 나누어 읽습니다.

```work-chat
KC-20260916-01
```

**첨부와 연결하는 방법**

TXT의 ‘사진’ 표시는 첨부를 찾는 위치로 사용합니다. 대화 날짜·전송 시각과 앞뒤 설명을 먼저 읽고, 이미지의 화면명·입력 시간·금액을 대조해 같은 사안의 카드에 연결합니다. 파일을 저장한 시각만으로 연결을 정하면 다른 화면이 섞일 수 있기 때문입니다. 위 원문 발췌에서는 대화에 적힌 값과 담당자의 설명을 근거로 정리했습니다.

**직접 정리할 때 사용할 요청문**

```text
첨부한 카카오톡 TXT를 날짜순으로 끝까지 읽고, 업무별 사안으로 묶어 주세요.
같은 사안의 후속 정정은 기존 카드에 연결하고, 다른 사안은 분리해 주세요.
각 카드에는 고정 ID, 업무 질문, 대상, 조건, 날짜, 판단 이유, 합의와 처리 범위를 적어 주세요.
대화일·대상 근무일·적용일·파일 저장일을 구분해 주세요.
원문의 파일 ID와 행 범위를 각 설명에 연결하고, 문의·설명·제안·합의·완료보고를 구분해 주세요.
이름·사번은 사례명으로 바꾸고, 업무 기준은 기술 용어 없이 먼저 설명해 주세요.
원문은 수정하지 말고 카드 초안을 담당자가 검토할 수 있게 작성해 주세요.
```

## 3. 어떻게 정리하기로 했는가

| 자료 | 여기서 찾는 것 | 정리 기준 |
|---|---|---|
| 규정·지침 | 공식 기준과 적용 조건 | 효력일·대상·예외 |
| 매뉴얼·양식 | 실제 입력과 처리 절차 | 입력값·승인 흐름·예외 처리 |
| 사용자 대화 | 문의·불편·협의·정정의 이유 | 요청·합의·완료보고·재발의 구분 |
| 회의록 | 업무 결정과 후속 작업 | 결정 주체·기한·담당자 |
| 이미지·엑셀 | 화면의 관찰값과 계산 근거 | 원본 위치·단위·표시값 |

원본을 보존하고 업무별 설명을 Markdown 문서로 작성합니다. Markdown은 제목·표·링크를 담는 텍스트 형식이므로 검색과 변경 비교가 쉽습니다. 여기에 **출처와 적용 조건을 함께 정리하면**, 문장을 읽는 사람도 그 결론이 어떤 상황에서 나온 것인지 이해할 수 있습니다.

업무 지식에는 “**무엇을 근거로 답하는가**”를 담고, 스킬에는 “**그 근거를 어떤 순서로 찾고 판단하는가**”를 적습니다. **규정·협의는 지식 문서에 두고, 그 자료를 읽는 절차를 스킬로 연결합니다.** 이렇게 나누면 규정이 바뀌었을 때 관련 지식 문서를 고치고 기존 작업 절차를 계속 활용할 수 있습니다.

## 4. 어떻게 만드는가

새로 업무 에이전트를 만들 때는 아래 0단계에서 업무 질문과 기준부터 정리합니다. **업무 정의를 먼저 마친 뒤, 그 내용을 안내문·공통 지침·작업별 스킬과 코드에 연결합니다.**

ZHR5에서는 추출 폴더를 분석해 담당 업무의 후보를 찾았고, 담당자가 실제 업무와 대조하면서 범위와 용어를 바로잡았습니다. 여기서 코드 분석은 업무를 이해하기 위한 참고 자료로 활용했습니다. 최종적으로는 담당자와 합의한 근로시간·시간외실비·대휴·정산 업무를 기준으로 안내문, 공통 지침, 작업별 스킬을 구성했습니다.

### 0단계 · 업무 질문과 기준 정의

직원에게 자주 받는 질문과 담당자가 실제로 판단하는 기준을 먼저 적습니다. 적용 대상·시점·예외·처리 이유를 업무 언어로 설명하고, AI가 정리한 내용을 담당자가 읽고 바로잡습니다. 이 단계에서는 파일 구조나 코드를 설계하려 하지 않습니다.

```text
지금은 업무 맥락을 정의하는 단계입니다.
코딩·IT·ERP 관련 기술 용어, 프로그램명·함수명·테이블명과 구현 방식은 적지 마세요.
제가 설명하는 업무를 대상, 상황, 적용 기준, 예외, 처리 이유, 근거로 나눠 정리해 주세요.
직원이 실제로 물어볼 질문과 그 질문에 답할 때 필요한 조건도 함께 정리해 주세요.
설명이 부족하면 업무 담당자가 일상적인 말로 답할 수 있도록 질문해 주세요.
제가 검토하고 정정한 업무 정의가 정리된 뒤에 기술적인 연결을 진행해 주세요.
```

### README·AGENTS·SKILL의 역할

| 파일 | 기본 역할 | ZHR5에 적은 내용 |
|---|---|---|
| `README.md` | 사람이 프로젝트의 목적과 시작 방법을 읽는 안내문입니다. AI에게 프로젝트 개요를 설명할 때도 함께 읽도록 요청합니다. | 담당 업무, 시작할 문서, 세 스킬의 위치 |
| `AGENTS.md` | Codex가 작업을 시작할 때 읽는 프로젝트 지침입니다. 프로젝트와 작업 폴더에 적용할 규칙을 담습니다. | 업무 범위, 근거를 읽는 순서, 출처·시점 구분, 원본 보존과 피드백 처리 |
| `SKILL.md` | 반복 작업의 절차서입니다. 요청에 맞는 스킬을 선택하고 그 안에 적힌 순서로 작업합니다. | 업무 질문에 답하기, 새 자료 정리하기, 변경 영향 살펴보기 |

[AGENTS.md 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [스킬 안내](https://learn.chatgpt.com/docs/build-skills), [프로젝트 문서 구성 예시](https://developers.openai.com/cookbook/examples/codex/iterating-development-workflows-with-codex)에서 각 문서의 역할과 구성 방법을 살펴볼 수 있습니다.

### 1단계 · 추출 폴더의 핵심 업무 조사

Codex에서 실제 추출본이 들어 있는 프로젝트 폴더를 엽니다. 이어서 파일 목록과 추출 기록, 주요 프로그램·함수·화면을 읽게 하고 담당 업무를 설명하도록 요청합니다. ZHR5의 초기 분석에서는 탄력근로 계획·결재·월정산, 통상·교대 시간외 신청과 일부 회계 연결을 정리했습니다.

다음 요청문에서 폴더와 문서 이름을 자신의 프로젝트에 맞게 바꾸어 사용할 수 있습니다.

```text
이 프로젝트의 실제 추출 폴더와 manifest·catalog·로그를 확인해 주세요.

knowledge/hr/overview.md에는 업무 범위를, flows.md에는 처리 흐름을 정리해 주세요.
파일에서 확인한 사실과 이름으로 추정한 부분, 추출되지 않은 부분을 나눠 주세요.
아직 원본 코드는 수정하지 마세요.
```

### 2단계 · 담당자의 업무 설명 검토

`overview.md`와 `flows.md`를 실제 담당 업무와 대조합니다. 예를 들어 근로시간 정산과 급여 전체를 같은 범위로 묶었는지, 입력 화면과 승인·지급 단계를 구분했는지 살펴봅니다. 차이가 있으면 규정·매뉴얼·협의 기록을 근거로 설명을 바로잡습니다.

이 과정에서 코드만으로 알기 어려운 업무 배경도 드러납니다. ZHR5는 원문 11개를 업무 지식으로 정리하고 세 스킬에 연결했습니다. 또한 지식 문서에 적은 함수 이름을 추출 코드와 대조하면서 실제 구현을 찾아가는 경로를 보완했습니다.

### 3단계 · 업무 범위와 세 스킬 구성

`README.md`에는 프로젝트의 목적과 시작할 문서 링크를 둡니다. `AGENTS.md`에는 업무 범위와 공통 작업 규칙을 적습니다. 그리고 업무 기준은 `knowledge/`에 보관하고, 반복해서 하는 세 가지 작업을 각각의 스킬로 구성합니다.

| 실제 스킬 경로 | 사용하는 요청 | 수행 순서 |
|---|---|---|
| `.agents/skills/zhr5-business-qa/SKILL.md` | “이 경우 어떻게 처리하나요?” | 조건 확인 → 관련 지식과 후속 정정 → 필요한 코드 확인 → 근거를 붙인 답변 |
| `.agents/skills/zhr5-knowledge-curation/SKILL.md` | “새 규정과 대화를 지식에 반영해 주세요.” | 원문 확인 → 기존 설명과 비교 → 출처·적용일 정리 → 지식과 목차 갱신 |
| `.agents/skills/zhr5-change-impact/SKILL.md` | “이 기준을 바꾸면 어디에 영향이 있나요?” | 변경 전후 조건 확인 → 관련 문서와 코드 탐색 → 영향 범위와 검토 항목 정리 |

```text
방금 확인하고 정정한 핵심 업무를 기준으로 README.md와 AGENTS.md를 구성해 주세요.
README에는 목적·시작 방법·주요 문서 링크를, AGENTS에는 범위·읽는 순서·근거 기준을 적어 주세요.
업무 질의, 새 지식 정리, 변경 영향 분석은 각각 SKILL.md로 나눠 주세요.
스킬에는 언제 사용하는지와 읽는 절차를 적고, 업무 규정은 knowledge 문서로 연결해 주세요.
기존 문서가 있으면 유효한 내용을 유지하며 필요한 부분만 병합해 주세요.
```

### 4단계 · 질문과 코드 위치 연결

`knowledge/INDEX.md`에서 질문에 맞는 업무 문서를 찾습니다. 코드와 관련된 질문은 `knowledge/code-map/working-time.md`에서 함수·화면을 찾고, `docs/EXPORT_GUIDE.md`를 따라 추출본의 실제 파일로 이동합니다. 후속으로 만든 `maps/INDEX.md`와 소스 설명 문서는 이 경로를 더 자세히 안내합니다.

```document-tree
knowledge-files
```

파일 관계도에서 문서 이름을 누르면 해당 MD를 다운로드할 수 있습니다. 각 문서를 열어 안내문 → 공통 지침 → 작업별 스킬 → 업무 근거로 이어지는 읽기 순서를 살펴봅니다.

### 업무 자료 추가 절차

1. 원본에 ID를 붙이고 파일명·대화 기간·문서일·검토 범위를 기록합니다. 업로드일과 규정 효력일은 별도로 적습니다.
2. 한 질문의 앞뒤 대화를 함께 읽고 취소·정정·추가 조건을 찾습니다.
3. 문장을 관찰 사실, 담당자 설명, 요청, 합의, 완료보고, 실제 결과로 나눕니다.
4. 이미지의 화면명·수치·오류 문구를 대화와 대조합니다. 시각은 연결 후보를 찾는 단서로 활용합니다.
5. 주제별 MD에 결론·조건·출처 위치를 적습니다. 기존 문서와 설명이 다르면 양쪽 근거와 적용 시점을 함께 남깁니다.
6. INDEX와 업무지도에 새 문서 링크를 추가합니다.

```text
이 대화 TXT와 확보된 첨부에서 시간외 입력 기본값에 관한 사안을 정리해 주세요.
문의, 담당자 설명, 합의, 완료보고, 실제 결과 확인을 나눠 주세요.
후속 정정까지 읽고 각 문장에 원문 파일·시각·행 또는 페이지를 적어 주세요.
이미지는 전송 시각과 파일 저장 시각을 구분하고 내용으로도 대조해 주세요.
각 연결의 근거가 되는 대화와 첨부 위치를 함께 적어 주세요.
원본은 유지하고 기존 업무 MD·INDEX에서 보완할 부분을 작성해 주세요.
```

위 요청문의 대상 업무와 자료 이름을 바꾸어 같은 절차를 적용할 수 있습니다.

## 5. 실제 사례

### 문서 구성을 활용한 업무 문답

아래는 ZHR5의 지식 MD와 피드백 기록을 바탕으로 정리한 사례 문답입니다.

**질문 · “오전 반차 후 실제 근무한 18~23시를 입력했는데 실비가 0원입니다. 코드 오류인가요?”**

**답변 ·** “이 사례의 원래 근무시간은 14~22시입니다. 해당 입력 방식에서는 원래 시작시각인 14시부터 전체 구간을 입력하고 승인된 반차를 별도로 반영합니다. 따라서 계산 코드에 앞서 입력한 시간 구간을 살펴봅니다.”

AI는 처음에 0원 처리 조건을 보고 반차 예외가 빠졌다고 판단했습니다. 이후 담당자의 정정과 입력 기준을 연결하면서 **코드를 고치기 전에 입력 방법부터 살펴보는 답변**으로 바뀌었습니다. 읽는 경로는 `knowledge/INDEX.md` → `processes/overtime-start-time.md` → `FB-20261001-001.md`입니다.

**질문 · “누적근로시간에서 가산시간을 뺐다가 다시 넣은 이유는 무엇인가요?”**

**답변 ·** “2024년 10월 15일에는 대휴가 생긴 것으로 오해하지 않도록 가산시간을 표시에서 제외했습니다. 그러나 소정시간을 채우지 못했다고 오해하는 문제가 더 크다고 판단해 10월 28일에 표시를 되돌렸습니다. 이 결정은 누적시간의 표시 방식에 관한 내용입니다.”

이 질문에는 현재 계산 코드뿐 아니라 당시 협의 이유가 필요합니다. 따라서 `knowledge/processes/selective-cumulative-display.md`에서 결정 배경을 읽고, `ZHR_52TM_CW_BASE_DATA` → `LZHR008_3F02`의 시간 변환 → `DAILY_WORK_MONTHLY_CONDITION`의 표시 구간으로 연결합니다.

**질문 · “시간외실비 예시에 계속 8,400원을 사용해도 되나요?”**

**답변 ·** “해당 기록에는 2026년 9월 1일 기준 변경과 직군별 후속 정정이 있습니다. 정규직, 연봉계약직·특정업무직, 방송지원직의 기준을 나누어 설명하므로 적용일과 직군에 맞는 단가를 선택합니다.”

단가 하나만 바꾸면 다른 직군이나 과거 기간에 잘못 적용할 수 있습니다. 따라서 `knowledge/policies/overtime-rate-20260901.md`와 두 건의 9월 23일 피드백을 함께 읽어 대상과 시점을 구분합니다.

### 5-1. 교대근무 시간과 기본 입력값

사용자가 제공한 **SRC-11.txt**에는 **2026-08-24~2026-09-21**의 업무 대화가 담겨 있습니다. 파일 저장 시각은 **2026-09-22 10:20:26**이므로, 사안의 발생일은 대화에 적힌 날짜로 구분합니다. 아래 사례에서는 이름과 사번 대신 담당 역할과 사례 A를 사용합니다.

**상황:** 교대근무표는 00:00–09:00인데 시간외 입력 화면은 18:00–24:00을 기본값으로 표시했습니다.

| 대화 순서 | 확인한 내용 | 업무지식에 남길 구분 |
|---|---|---|
| 8/24 15:58 · 문의 | 근무표와 입력 기본값이 다르다는 사용자 보고 | 관찰 현상 · SRC-11, 8–10행 |
| 16:22–16:27 · 확인 | 개인 IAM 설정이 스케줄보다 먼저 반영된다는 담당자 설명 | 입력값 결정 기준 · 16–26행 |
| 16:31–16:40 · 협의 | 사용자에게 IAM 설정 삭제를 안내하기로 합의 | 안내 내용 · 27–34행 |

대화를 업무 문장으로 정리하면 다음과 같습니다.

- **시스템 담당:** 개인 IAM 설정이 있으면 해당 값이 먼저 입력됩니다.
- **업무 담당:** 사용자에게 IAM 설정 삭제 방법을 안내합니다.

이처럼 **관찰한 현상·담당자 설명·안내 합의**를 나누면, 다음에 같은 질문을 받았을 때 입력값이 결정된 이유부터 설명할 수 있습니다.

### 5-2. 업무지식 MD 작성 예시

```markdown
# 교대근무 시간외 입력 기본값과 IAM 설정
- 출처: SRC-11.txt, 2026-08-24, 8–34행
- 대상: 교대근무자 사례 A의 시간외 입력 기본값
- 현상: 근무표 00:00–09:00, 입력 기본값 18:00–24:00
- 당시 설명: 개인 IAM 설정이 스케줄보다 먼저 반영된다고 설명함
- 합의: 사용자에게 IAM 설정 삭제를 안내하기로 함
```

### 5-3. 개별 조치와 과거 내역 처리 구분

같은 TXT의 9/16–9/18 대화에서는 신규 입력 단가와 과거 입력 내역을 나누어 다뤘습니다. 하나의 조치가 두 범위에 동시에 적용되는 것은 아니었기 때문입니다.

| 시점 | 대화 내용 | 업무별 구분 |
|---|---|---|
| 9/16 13:30–13:38 | 신규 입사 사례의 단가 문제와 9월 이후 내역 확인 요청 · 329–345행 | 대상자와 기간 확인 |
| 9/17 09:50 | 개별 등급 변경 완료 보고 · 348행 | 개인 등급 변경 |
| 9/18 16:13–16:33 | 신규 입력에 9,240원이 적용되고, 과거 입력 내역은 별도 처리 대상으로 협의 · 351–363행 | 신규 입력과 과거 내역 분리 |

따라서 “처리했습니다”라는 말도 어떤 대상과 기간에 대한 조치인지 함께 기록합니다. 이렇게 남겨야 같은 사안을 다시 읽을 때 개인 설정 변경과 과거 데이터 정정을 구분할 수 있습니다.
