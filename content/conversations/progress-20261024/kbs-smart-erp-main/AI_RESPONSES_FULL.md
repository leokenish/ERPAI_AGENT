# AI 최종 답변 전문

## smart-erp-progress-t000-a1

**충분히 가능합니다. 현재 구조에서는 기존 업무 기능과 SAP 연계를 유지하면서, 메인화면의 디자인을 전면 개편하는 방식이 적합합니다.** HTML·JavaScript·CSS와 SVG만으로 요청하신 화면을 구현할 수 있습니다.

첨부 이미지 3장, 교육 포털 영상의 주요 장면, 압축파일의 메인 관련 소스를 확인했습니다. 아래는 그 결과에 근거한 검토입니다. 내부망 ERP에서의 실제 실행 검증은 아직 하지 않았습니다.

**1. 소스를 확인한 결과**

압축파일에는 폴더를 제외하고 **975개 파일**이 있습니다. JavaScript 98개, CSS 29개, HTM 69개이며 이미지와 SAP 관련 파일도 포함되어 있습니다. 파일 수 전체를 수정할 필요는 없습니다.

중요한 점은 **layout.htm 하나가 전체 화면을 그리는 구조가 아니라는 것**입니다.

| 구분 | 확인한 소스 또는 호출 경로 | 개편 시 역할 |
| --- | --- | --- |
| 전체 외곽 화면 | ZWEB_COMMON/pages/layout/Layout/layout.htm | 상단 바, 좌우 영역, 화면 크기 조정 |
| 중앙 홈 화면 | ZWEB_COMMON/pages/main/Layout/main.htm | 기존 배너·공지사항·관련서식을 새 화면으로 교체 |
| 레이아웃 스타일 | ZWEB_COMMON/MIMEs/common/layout3.css | 상단·사이드바 등 외곽 디자인 |
| 공통 리소스 로딩 | pages/server_util/Layout/server_util.ssjs | jQuery·공통 CSS 등의 로딩 |
| 왼쪽 메뉴 트리 | /sap/bc/bsp/sap/zweb_menu/menu.htm | 별도 iframe에서 메뉴 표시 |
| 왼쪽 결재현황 | /sap/bc/bsp/sap/zweb_wf/approval_common_view.htm | 별도 iframe에서 결재현황 표시 |

현재 공통 로더에서는 **jQuery 1.10.2**를 불러오며, 레이아웃은 jquery.layout-1.3.0 경로의 플러그인을 사용합니다.

또한 첨부된 .htm은 일반 정적 HTML이 아니라 **so2:page, so2:script, 서버 출력 구문이 들어 있는 SAP BSP 내보내기 형식**입니다. AI가 이를 일반 HTML로 통째로 바꾸면 로그인 사용자 정보와 서버 연계가 깨질 수 있습니다.

따라서 이번 프로젝트에서 가장 중요한 지시는 다음입니다.

> **새 디자인은 HTML·CSS·JavaScript·SVG로 구현하되, 기존 BSP 서버 구문과 프레임 간 호출 계약은 보존한다.**

**2. 요청하신 디자인의 구현 방향**

첨부 교육 포털의 **흰색·옅은 회색 배경, 코발트 포인트, 사람이 기기와 함께 일하는 일러스트**를 ERP에 맞게 가져오는 방향이 좋습니다.

| 영역 | 권장 방향 |
| --- | --- |
| 상단 | KBS Smart ERP, 사용자 정보, 홈·새창·전체화면·ERP 연결·매뉴얼 기능을 정돈된 버튼으로 구성 |
| 왼쪽 | 기존 메뉴 계층·검색·즐겨찾기를 유지하고, 행 간격·선택 상태·접기/펼치기·아이콘 개선 |
| 중앙 | 방송 제작과 경영지원 인력이 컴퓨터·모니터·방송 장비를 활용하는 큰 SVG 일러스트 |
| 문구 | “방송을 만드는 사람들, 업무를 연결하는 KBS Smart ERP” 등의 문구를 짧은 타이핑 효과로 표시 |
| 하단 | 재무회계·구매재고·예산원가·인사관리·자산관리의 5개 건수 카드 |
| 색상 | 코발트를 선택 상태·주요 버튼·일러스트 강조색에 사용하고 넓은 배경은 밝게 유지 |
| 폰트 | S-Core Dream을 내부 서버에서 제공하고 개편 대상 문서별로 적용 |

**중앙 일러스트와 타이핑 문구는 분리하는 것이 좋습니다.** 일러스트는 하나의 SVG로 만들고, 문구는 HTML 텍스트로 두면 폰트·줄바꿈·접근성·유지보수가 수월합니다.

SVG는 단순히 PNG를 SVG 파일 안에 넣는 방식이 아니라, 실제 벡터 도형으로 제작해야 확대해도 선명합니다. 교육 포털 수준의 인물 일러스트를 구현하려면 코드 작업 외에 인물 비례와 장비 표현을 다듬는 시각 검수가 필요합니다.

건수 카드는 다음처럼 구성할 수 있습니다.

| 업무 | 시안용 샘플 건수 |
| --- | --- |
| 재무회계 | 3,458,989건 |
| 구매재고 | 1,245,680건 |
| 예산원가 | 1,087,420건 |
| 인사관리 | 1,526,300건 |
| 자산관리 | 1,103,250건 |

숫자는 약 1.5~2초 동안 빠르게 증가하다가 천천히 멈추게 하고, 화면 진입 시 한 번만 실행하는 편이 업무 화면에 적합합니다. 시안에는 **예시 데이터**임을 표시해야 합니다.

실제 연계 단계에서는 “각 모듈의 데이터 건수”가 전표 수인지, 문서 수인지, 상세행 수인지 먼저 정해야 합니다. 또한 매번 홈 화면을 열 때 대용량 테이블 전체를 집계하기보다, 서버에서 미리 집계한 결과를 제공하는 방식을 권장합니다.

**3. 기능 보존을 위해 주의할 부분**

이번 작업은 디자인보다 **기존 동작을 빠짐없이 보존하는 검증**에 공수가 들어갑니다.

- **jQuery 업그레이드는 별도 작업으로 분리:** 디자인 개편과 동시에 올리면 기존 플러그인과 업무 화면의 문제 원인을 분리하기 어렵습니다. 신규 애니메이션은 순수 JavaScript로 작성할 수 있습니다.
- **iframe별 스타일 적용:** 상위 화면의 CSS와 폰트가 메뉴·결재·본문 iframe에 자동 적용되지 않습니다. 각 문서에 적용해야 합니다.
- **공통 CSS 영향 제한:** common.css를 광범위하게 바꾸면 다른 업무 화면까지 달라질 수 있으므로, 메인 전용 클래스와 스타일 파일을 권장합니다.
- **고정 높이 계산 수정:** 현재 코드에 190, 203, 206 같은 높이 보정값이 있습니다. 상단 바나 검색창 크기를 바꾸면서 그대로 두면 트리 하단이 잘리거나 스크롤이 어긋날 수 있습니다.
- **공지사항·관련서식 호출까지 정리:** 현재 main.htm은 시작 시 getList(), getList1()을 호출합니다. 화면만 숨기지 말고 이 화면에서 불필요해진 조회도 제거해야 합니다. 공유 서버 함수 자체를 삭제할 필요는 없습니다.
- **기존 버튼 동작 보존:** 홈 복귀, 메뉴 접기, 매뉴얼, 새창, 전체화면, ERP 직접연결과 업무 화면 전환을 회귀 검증해야 합니다.

**추가로 필요한 자료는 ZWEB_MENU의 메뉴 페이지·관련 JS/CSS/아이콘과 ZWEB_WF의 결재현황 페이지·관련 리소스입니다.** 현재 첨부만으로 중앙 홈과 외곽 개편은 시작할 수 있지만, 트리와 결재현황의 완전한 개편·검증에는 이 자료가 필요합니다.

**4. 예상 공수**

아래는 **SAP BSP 구조를 아는 개발자 1명이 AI를 활용하고, 추가 소스와 개발계 테스트 환경이 준비된 경우의 잠정 추정치**입니다. 1인일은 약 8시간 기준이며 확정 견적은 아닙니다.

| 작업 | 예상 공수 |
| --- | --- |
| 메인 관련 의존성 분석·기존 기능 목록 작성 | 1~2인일 |
| 디자인 시안·중앙 SVG 제작 및 보정 | 2~4인일 |

실무 일정으로는 **약 2~4주**를 잡는 것이 현실적입니다. 화면 방향을 확인할 정적 시안은 약 **1~3인일**로 먼저 만들 수 있습니다.

이 추정에는 전체 업무 화면 개편, jQuery 전면 교체, 실제 집계용 서버 프로그램 개발은 포함하지 않았습니다. IE 모드 지원이 필수이거나 iframe 간 숨은 의존성이 많으면 추가 공수가 발생합니다.

**6. 바로 사용할 작업 프롬프트**

아래 프롬프트는 첨부자료와 함께 사용하면 됩니다. 분석부터 시안, BSP 통합, 검증까지 단계적으로 진행하도록 구성했습니다.

글쓰기

너는 SAP ECC의 BSP 기반 웹 시스템과 레거시 JavaScript·jQuery를 이해하는 시니어 프런트엔드 개발자이자 ERP UI 디자이너다.

KBS 스마트 ERP 메인화면을 전면 개편하라. 목표는 기존 업무 기능과 SAP 연계를 보존하면서, 현대적이고 세련된 방송사 ERP 화면을 구현하는 것이다.

[입력 자료]

- ZWEB_COMMON.zip
- 기존 ERP 메인화면 이미지
- 기존 ERP 로그인 화면 이미지
- ERP 교육 포털 메인화면 영상
- 개발계 주소: [https://erpdev.kbs.co.kr](https://erpdev.kbs.co.kr)
- 전체 레이아웃: ZWEB_COMMON/pages/layout/Layout/layout.htm
- 중앙 홈: ZWEB_COMMON/pages/main/Layout/main.htm

내부망 접속 가능 여부를 먼저 구분하라. 접근하지 못한 시스템에서 실행·검증했다고 표현하지 마라.

[기술 원칙]

1. 신규 화면 구현은 HTML, CSS, JavaScript와 실제 벡터 SVG만 사용한다.
2. React, Vue, TypeScript, Tailwind, 신규 UI 프레임워크 및 필수 빌드 도구를 도입하지 않는다.
3. 기존 jQuery와 레이아웃·트리 플러그인은 우선 유지한다. 버전 업그레이드는 별도 개선 과제로 정리한다.
4. 외부 CDN, 외부 폰트 URL, 외부 이미지 URL에 의존하지 않는다.
5. 첨부 HTM은 SAP BSP 내보내기 형식이다. so2 태그, 서버 스크립트, 로그인 정보 출력, include 및 기존 서버 연계를 보존한다.
6. 브라우저용 정적 미리보기와 실제 SAP 반영용 소스를 구분한다. 내보내기 XML을 BSP 편집기에 그대로 붙여 넣도록 안내하지 말고 실제 반영 방식을 명시한다.
7. 기존 DOM ID, iframe name/id, 외부에서 호출하는 함수 이름과 인자, URL·파라미터·세션·권한 처리를 보존한다.
8. 전역 CSS 변경을 최소화하고 메인 전용 클래스와 파일로 적용 범위를 제한한다.
9. 원본의 인코딩과 한글을 보존한다.

[반드시 유지할 기능]
소스에서 다음 기능의 구현과 호출 관계를 확인하고 보존 목록을 작성한다.

- 사용자 이름 및 사번 표시
- 메뉴 트리 계층, 펼치기·접기, 선택, 검색, 검색 초기화, 즐겨찾기
- 메뉴 클릭에 따른 기존 업무 화면 실행
- 결재현황 조회와 이동
- 홈 복귀
- 메뉴 영역 접기·펼치기와 너비 조절
- 매뉴얼 표시 및 기존 상태 저장
- 새창, 전체화면, ERP 직접연결
- 부모·자식 iframe 간 함수 호출과 크기 변경 처리

화면에 보이는 버튼뿐 아니라 소스에서 발견한 추가 기능도 보존 목록에 포함한다.

[디자인 요구]

1. 상단 바·왼쪽 메뉴·중앙 홈의 디자인을 일관되게 개편한다.
2. 왼쪽 트리는 기존 기능과 계층을 유지한다. 폴더, 펼치기, 접기, 업무 항목, 즐겨찾기 아이콘은 고해상도 벡터로 개선한다.
3. 폰트는 S-Core Dream을 적용한다. 내부 서버에 저장한 폰트를 @font-face로 사용하고, 필요한 굵기만 로딩한다. 실제 폰트 파일이 없으면 가짜 파일을 만들지 말고 필요한 파일과 임시 대체 폰트를 명시한다.
4. 공지사항과 관련서식은 중앙 홈에서 삭제한다. 이 홈에서만 사용되는 초기 조회와 이벤트도 정리하되, 공유 서버 기능은 삭제하지 않는다.
5. 그 외 기존 바로가기와 기능은 임의로 삭제하지 말고 새 디자인에 배치한다.
6. 중앙에는 하나의 큰 SVG 일러스트를 배치한다. 방송사에서 사람들이 컴퓨터·모니터·태블릿·방송 장비를 활용하며 협업하는 장면으로 구성한다.

글쓰기

[최종 산출물 — ERP 서버 반영용 웹자산 ZIP 패키지]

이번 작업은 화면 시안이나 코드 제안으로 끝내지 않는다. 최종적으로 수정·추가한 웹자산을 ERP 서버에 반영할 수 있도록 ZIP 패키지로 제공해야 한다.

현재 별도 프로젝트에서 다음 기능을 수행하는 프로그램을 개발 중이다.

- 웹자산 ZIP 업로드
- ZIP에 포함된 소스와 ERP 서버의 기존 자산 비교
- 코드 및 반영 대상 검증
- 검증 결과 확인 후 ERP 서버에 저장·활성화

이 프로젝트에서는 해당 프로그램 자체를 새로 개발하지 않는다. 해당 프로그램이 처리할 수 있는 정확한 웹자산 패키지를 제작하는 것을 최종 납품 범위에 포함한다.

1. 반영 프로그램과의 형식 일치

- 반영 프로그램의 ZIP 입력 규격, 지원 객체 유형, 경로 매핑, 문자 인코딩, 메타데이터 형식, 신규 자산 생성 지원 여부를 확인한다.
- 규격이 제공되면 이를 최우선으로 준수한다.
- 규격을 확인하지 못한 상태에서 임의로 만든 패키지를 ‘업로드 즉시 반영 가능’하다고 표현하지 않는다.
- 규격이 없어도 소스 수정과 변경 목록 정리는 진행하고, 최종 패키징에 필요한 확인 사항을 구체적으로 제시한다.
- SAP BSP 내보내기 XML, BSP 편집기에 들어갈 소스 본문, MIME 바이너리를 구분하고 반영 프로그램이 요구하는 형식으로 제공한다.

2. 패키지 범위

- 이번 개편으로 수정하거나 추가한 HTML/HTM, JavaScript, CSS, SVG, 이미지, 아이콘, 폰트 등 웹자산을 포함한다.
- 신규 파일뿐 아니라 이를 참조하도록 변경한 페이지와 스타일 파일도 빠짐없이 포함한다.
- 기존 파일은 원래 BSP 애플리케이션과 상대 경로를 유지한다.
- ZWEB_COMMON, ZWEB_MENU, ZWEB_WF 등 서로 다른 애플리케이션의 자산을 구분하고 동일 파일명 간 충돌을 방지한다.
- 로컬 파일 경로와 실제 SAP 서버의 대상 경로가 다르면 명확한 대응표를 제공한다.
- 서버 스크립트가 포함된 BSP 페이지나 SSJS의 변경이 필요하면 별도로 식별하고, 반영 프로그램이 지원하는지 확인한다.
- ABAP 프로그램, DDIC 객체 등 별도 프로젝트에서 아직 지원하지 않는 객체를 웹자산으로 위장하거나 패키지에 섞어 넣지 않는다.

3. 변경 목록
   반영 프로그램에서 요구하는 메타데이터가 있으면 그 규격을 사용한다. 별도로 사람이 검토할 수 있는 변경 목록에 다음 정보를 제공한다.

- 대상 BSP 애플리케이션
- 객체 또는 자산 유형
- ZIP 내 경로와 서버 대상 경로
- 신규·수정 구분
- 변경 목적
- 텍스트 인코딩 또는 바이너리 여부
- MIME Content-Type
- 파일 크기와 SHA-256
- 기준 원본이 있는 경우 원본 SHA-256
- 함께 반영해야 하는 의존 자산

해시는 실제 파일 바이트를 기준으로 계산한다. 원본 해시는 제공받은 소스의 기준값이며 현재 운영 서버와 동일하다고 단정하지 않는다. 서버 비교에서 차이가 발견되면 덮어쓰기 전에 차이를 검토할 수 있도록 한다.

4. 삭제 처리

- ZIP에 파일이 없다는 이유로 서버 파일을 삭제하도록 설계하지 않는다.
- 공지사항·관련서식 제거는 우선 중앙 홈의 표시와 해당 화면 전용 호출을 제거하는 방식으로 수행한다.
- 기존 서버 자산의 물리적 삭제가 필요하면 삭제 후보와 참조 관계를 별도로 제시한다.
- 반영 프로그램의 삭제 지원과 삭제 대상이 확인되지 않으면 자동 삭제 지시를 포함하지 않는다.

5. 패키지 검증

- 수정된 페이지에서 참조하는 CSS, JS, 이미지, SVG, 폰트의 경로와 대소문자를 점검한다.
- 신규 의존 파일의 누락, 중복 경로, 파일명 충돌을 확인한다.
- 내부망에서 외부 CDN이나 외부 폰트 다운로드 없이 동작하도록 구성한다.
- 폰트와 이미지 바이너리는 손상 없이 보존하고 필요한 라이선스 자료를 별도로 제공한다.
- 텍스트 인코딩, 한글, BSP 서버 구문, JavaScript 및 CSS 구문을 점검한다.
- 로컬 구문 검증, 브라우저 화면 검증, SAP 서버 저장·활성화 검증을 구분한다.
- 로컬 검증만으로 SAP 저장·활성화 또는 실제 업무 기능 검증이 완료됐다고 표현하지 않는다.
- 최종 ZIP을 다시 열어 파일 목록과 해시를 확인한다.

6. 적용 및 원복

- 신규 리소스와 이를 참조하는 페이지의 적용 순서 또는 일괄 반영 필요성을 명시한다.
- CSS·JS·이미지·폰트 캐시 때문에 구버전이 남지 않도록 기존 운영 방식에 맞는 캐시 갱신 방안을 제시한다.
- 원복 자료는 업로드용 변경 패키지와 분리한다.
- 제공받은 원본으로 만든 원복 자료와 서버 반영 직전에 확보해야 하는 실제 서버 백업을 구분한다.
- 신규 자산은 원복 시 처리 방법을 명시한다.
- 이 프로젝트에서 ERP 서버에 직접 업로드하거나 저장·활성화하지 않는다. 서버 반영은 별도 프로그램과 사용자가 정한 절차를 따른다.

7. 최종 전달물

- 별도 검증·반영 프로그램의 규격에 맞춘 웹자산 ZIP
- 변경 파일 목록 및 서버 경로 대응표
- 검증 결과와 미검증 항목
- 적용 순서와 개발계 확인 절차
- 별도 원복 패키지 또는 원복 안내
- 패키지 버전, 작성일, 기준 원본 식별 정보

서버 반영용 ZIP에는 반영 대상 웹자산과 프로그램이 요구하는 메타데이터만 포함한다. 정적 시안, 스크린샷, 임시 파일, 개발 도구, 설명 문서 및 백업은 반영 프로그램의 규격에서 요구하지 않는 한 별도로 제공한다.

최종 완료 기준은 ‘화면이 보기 좋게 완성됨’과 ‘변경 웹자산이 검증·반영 가능한 패키지로 정리됨’을 모두 충족하는 것이다. 반영 규격이 확인되지 않았다면 패키지를 잠정본으로 표시하고, 확정에 필요한 항목을 명시한다.

서버 반영용 ZIP과 함께 ‘웹자산 변경 전후 비교 보고서’를 작성한다. 단순한 작업 요약이 아니라 제공받은 원본과 최종 수정본을 실제 비교한 명세서여야 한다.

1. 비교 기준

- 수정 전에 원본을 별도로 보존하고, 원본과 최종 반영 패키지를 비교한다.

- 제공받은 원본과 비교한 결과임을 명시한다. ERP 서버의 현재 파일과 직접 비교하지 않았다면 서버 현행본과 일치한다고 표현하지 않는다.
- 원본 파일 전체를 기준으로 신규·수정·삭제·이동·이름 변경·미변경을 구분한다.
- 이동이나 이름 변경을 확인할 근거가 부족하면 임의로 단정하지 않는다.
- 파일이 ZIP에서 제외된 것과 서버에서 삭제해야 하는 것을 구분한다.

2. 전체 요약
   다음 항목을 표로 제공한다.

- 원본 및 최종 비교 대상 파일 수
- 신규·수정·삭제·이동·이름 변경·미변경 파일 수
- BSP 애플리케이션별 변경 건수
- HTML/HTM·JS·CSS·SVG·이미지·폰트 등 유형별 변경 건수
- 주요 디자인 변경과 기능에 영향을 주는 변경
- 서버 반영 대상 및 별도 확인 대상

중복 집계되지 않도록 상태 분류 기준을 명시한다.

3. 파일별 변경 명세
   변경 파일마다 다음 정보를 기록한다.

- 변경 식별번호
- 변경 상태
- 대상 BSP 애플리케이션 및 객체 유형
- 변경 전 파일명과 전체 상대 경로
- 변경 후 파일명과 전체 상대 경로
- 서버 반영용 ZIP 내부 경로
- 실제 ERP 서버 대상 경로 또는 객체 식별자
- 기존 파일의 역할
- 변경 후 파일의 역할
- 구체적인 변경 내용과 변경 이유
- 유지한 기능과 제거·추가한 기능
- 참조하는 파일 및 이 파일을 참조하는 페이지·스크립트
- 영향 범위와 함께 반영해야 하는 파일
- 검증 결과 및 미검증 사항
- 원복 방법

경로는 파일명만 쓰거나 중간을 생략하지 말고, 기준 루트부터 전체 상대 경로를 표시한다. 로컬 임시 경로와 ERP 서버 경로를 혼동하지 않는다. 서버 경로를 확정할 수 없으면 확인 필요로 표시한다.

4. 텍스트 파일의 상세 비교
   HTML/HTM, JavaScript, CSS, SVG 등은 다음 내용을 제공한다.

- 주요 변경 구간의 전후 코드
- 원본 및 수정본 각각의 줄 번호
- 변경된 함수명, DOM ID, CSS 선택자 등 관련 식별자
- 변경 전 동작과 변경 후 동작
- 사용자 화면에서 달라지는 점
- 기존 업무 기능 보존 여부와 판단 근거

내용이 긴 경우 보고서에는 핵심 변경을 설명하고, 전체 변경 내용은 별도 unified diff 파일로 제공한다. 공백·개행·인코딩 변경과 실제 로직 변경을 구분한다.

BSP 내보내기 XML과 실제 페이지 본문 사이에 형식 변환이 있으면 변환 자체와 업무 코드 변경을 구분한다. 서로 다른 표현 형식을 그대로 비교하여 전체 코드가 바뀐 것처럼 보고하지 않는다.

5. 이미지·아이콘·폰트 등 바이너리 비교

- 이미지와 아이콘: 원본·변경본 파일명, 경로, 형식, 용량, 가로·세로 크기 및 사용 위치를 기록한다.
- 시각 자산은 가능한 경우 변경 전후 이미지를 나란히 배치한다.
- SVG는 실제 벡터 여부와 viewBox 등 크기 관련 정보를 기록한다.
- 폰트는 글꼴명, 굵기, 파일 형식, 용량, 적용 페이지와 라이선스 자료 위치를 기록한다.
- 신규 파일은 ‘변경 전 없음’으로 표시한다.
- 비교할 수 없는 바이너리는 바이트 변경 여부와 해시를 기록하고 내용을 추측하지 않는다.

6. 화면·기능과 파일의 대응표
   사용자가 요구한 개편 항목별로 실제 변경 파일을 연결한다.
   예:

- 상단 바 개선 → 관련 HTM·CSS·아이콘
- 메뉴 트리 개선 → 메뉴 페이지·JS·CSS·SVG
- 공지사항 및 관련서식 제거 → 중앙 홈·초기 조회 코드
- 중앙 일러스트 → SVG·배치 스타일
- 타이핑 효과 → HTML 문구·JS·CSS
- 모듈별 건수 카드 → 데이터 정의·렌더링 JS·CSS
- S-Core 폰트 → 폰트 파일·@font-face·적용 문서

요구사항 → 변경 파일 → 변경 내용 → 검증 결과를 따라갈 수 있도록 작성한다.

7. 보고서 형식 및 패키지 정합성

- 사람이 검토하기 쉬운 비교 보고서는 HTML로 제공한다.
- 파일별 명세와 전체 파일 목록은 정렬·필터가 가능한 XLSX로 함께 제공한다.
- 텍스트 변경의 전체 diff를 별도로 제공한다.
- 비교 보고서와 명세서는 서버 반영용 ZIP과 분리하여 제공한다.
- 보고서의 반영 대상 목록과 실제 ZIP 내부 파일 목록을 대조한다.
- 보고서에만 있거나 ZIP에만 있는 파일이 있으면 사유를 명시한다.
- 마지막 수정 이후 비교 보고서와 해시를 다시 생성하여 최종 패키지와 일치시킨다.

최종 완료 기준에 ‘원본 대비 변경 사항을 파일명·경로·역할·코드·화면·검증 결과 수준에서 추적할 수 있는 비교 보고서 제공’을 추가한다.

13. 제공되지 않은 소스·서버 함수·API·설정 테이블을 실제로 존재하는 것처럼 가정하지 않는다.

- 폰트가 없으면 가짜 파일을 만들지 말고 필요한 파일과 임시 대체 폰트를 명시한다.
- 관련 라이선스 자료와 배포 조건을 확인하여 함께 정리한다.
- 상위 문서의 폰트가 iframe에 자동 적용된다고 가정하지 말고 개편 대상 문서별로 적용한다.
- 폰트 변경에 따른 버튼 높이, 메뉴 줄바꿈, 숫자 폭과 화면 잘림을 확인한다.

[6. 중앙 SVG 일러스트와 타이핑 효과]

일러스트:

- 교육 포털 영상과 ERP 로그인 화면의 인물·기기 중심 표현을 참고한다.
- 여러 사람이 컴퓨터, 모니터, 태블릿, 방송 장비 등을 사용하며 협업하는 장면으로 구성한다.
- 방송 제작과 재무·구매·예산·인사·자산 업무의 연결이 자연스럽게 느껴지게 한다.
- 하나의 SVG 안에 인물·장비·배경을 그룹으로 구성한다.
- 실제 path·shape·group 기반의 벡터로 제작한다.
- PNG/JPEG를 SVG 내부에 넣은 결과물을 실제 벡터라고 제출하지 않는다.
- 확대 시 선명도를 유지하고 화면 크기에 맞게 비율을 조정한다.
- 인물과 장비의 형태를 시각적으로 검수한다.

타이핑 문구:

- 일러스트와 분리된 HTML 텍스트로 구현한다.
- 기본 문구: “방송을 만드는 사람들, 업무를 연결하는 KBS Smart ERP”
- 필요하면 의미를 유지하는 범위에서 문구와 줄바꿈을 다듬는다.
- 교육 포털처럼 글자가 타이핑되듯 나타나게 한다.
- 타이핑 중 레이아웃이 흔들리지 않도록 공간을 확보한다.
- 반복 재생하지 않고, 애니메이션이 없어도 완성된 문구를 읽을 수 있어야 한다.
- 모션 감소 설정을 지원하는 브라우저에서는 이를 존중한다.

[7. 모듈별 데이터 건수 카드]

SVG 일러스트 하단에 다음 5개 업무 카드를 배치한다.

- 재무회계: 3,458,989건
- 구매재고: 1,245,680건
- 예산원가: 1,087,420건
- 인사관리: 1,526,300건
- 자산관리: 1,103,250건

위 숫자는 시안용 샘플이다. 실제 운영 데이터처럼 표시하지 말고 ‘예시 데이터’임을 알 수 있게 한다.

동작:

- 숫자는 0에서 목표값까지 약 1.5~2초 동안 증가한다.
- 초반에는 빠르게 증가하고 마지막에는 서서히 멈춘다.
- 최종 숫자는 목표값과 정확히 일치해야 한다.
- 천 단위 쉼표와 ‘건’을 표시한다.
- 표시 영역 진입 또는 홈 표시 시 한 번 실행하고 불필요하게 반복하지 않는다.
- 애니메이션 중 숫자 폭 때문에 카드가 흔들리지 않게 한다.
- 카드는 화면 너비에 맞춰 배치되며 잘리거나 겹치지 않아야 한다.

서버 연계 준비:

- 데이터 정의와 화면 렌더링 코드를 분리한다.
- 추후 서버에서 받은 값을 전달할 수 있는 작은 데이터 어댑터 또는 갱신 함수를 제공한다.
- 존재하지 않는 SAP 함수나 API를 임의로 만들고 연계 완료라고 표현하지 않는다.
- 미수신·오류와 실제 0건을 구분한다.
- 실제 연계 시 모듈별 집계 대상과 기준 시점을 정할 수 있게 한다.
- 대용량 데이터를 브라우저에서 가져와 직접 집계하지 않는다.
- 카드 클릭은 기존 연결 근거가 있을 때만 구현한다.

[8. 소스 분석과 구현 순서]

1단계: 원본 보존 및 의존성 분석

- 원본을 별도로 보존하고 파일 목록·크기·해시를 기록한다.
- 전체 파일 중 메인화면에서 사용하는 파일과 호출 관계를 추적한다.
- layout.htm, main.htm, server_util.ssjs, layout3.css와 관련 JS를 우선 조사한다.
- 메뉴·결재현황 소스의 포함 여부를 확인한다.
- 변경 대상, 보존 대상, 추가 필요 자료, 기능 검증표를 작성한다.
- CSS·폰트·공통 로더 변경이 다른 업무 화면에 미치는 영향을 확인한다.
- 운영 브라우저와 IE 모드 요구를 확인한다. 미확정이면 정적 시안은 최신 Edge·Chrome 기준으로 진행하되 운영 호환성이 확정됐다고 하지 않는다.

2단계: 실제 디자인 시안

- 첨부 이미지와 영상의 특징을 반영한 실행 가능한 정적 시안을 제작한다.
- 색상·폰트·아이콘·SVG·타이핑·건수 애니메이션을 포함한다.
- 모의 메뉴와 예시 데이터는 실제 SAP 연계와 구분한다.
- 사용자 수정 의견이 있으면 반영한다.

3단계: 기존 BSP 구조 통합

- 기존 iframe과 업무 호출 구조를 보존하며 새 디자인을 반영한다.
- iframe 문서별 CSS·폰트 적용을 확인한다.
- 상단·검색·결재 영역의 크기를 바꾸면 기존 높이 계산과 리사이즈 코드도 함께 조정한다.
- 고정된 높이 보정값 때문에 메뉴가 잘리지 않게 한다.
- 이벤트 중복 등록, 로딩 전 iframe 함수 호출, 전역 변수 충돌을 점검한다.
- 신규 스타일이 개별 업무 화면에 영향을 주지 않도록 한다.

4단계: 검증

- 1366×768, 1920×1080 및 브라우저 확대 125%, 150%에서 확인한다.
- 잘림·겹침·불필요한 가로 스크롤·버튼 클릭 영역·트리 스크롤을 점검한다.
- 검색, 트리 펼침, 업무 실행, 홈 복귀, 결재, 매뉴얼, 새창, 전체화면, 크기 조절을 검증한다.
- 수정 전부터 있던 오류와 신규 오류를 구분한다.
- 콘솔 오류와 리소스 로딩 실패를 확인한다.
- 키보드 포커스, 버튼 이름, 텍스트 가독성을 확인한다.
- 로컬에서 검증한 항목과 내부 SAP 개발계에서 검증해야 할 항목을 구분한다.

5단계: 서버 반영 패키지와 비교 보고서

- 아래 요구에 따라 최종 웹자산 ZIP과 변경 비교 보고서를 제작한다.
- 마지막 수정 후 패키지·해시·보고서를 다시 대조하여 일치시킨다.

[9. 별도 서버 반영 프로그램과의 연계]

현재 별도 프로젝트에서 다음 기능을 수행하는 프로그램을 개발 중이다.

- 웹자산 ZIP 업로드
- ZIP 소스와 ERP 서버의 기존 자산 비교
- 코드 및 반영 대상 검증
- 검증 결과 확인 후 ERP 서버에 저장·활성화

이 프로젝트에서는 해당 프로그램 자체를 새로 개발하지 않는다. 그 프로그램이 처리할 수 있는 정확한 웹자산 패키지를 만드는 것을 최종 납품 범위에 포함한다.

형식 확인:

- ZIP 입력 규격
- 지원 객체 유형
- BSP 애플리케이션과 경로 매핑 방식
- 문자 인코딩
- 필수 메타데이터
- 신규 자산 생성 지원 여부
- BSP 내보내기 XML·페이지 본문·MIME 바이너리의 처리 방식

규격이 제공되면 이를 최우선으로 준수한다. 규격이 없더라도 분석·수정·시안·변경 명세 작업은 진행한다. 다만 패키지는 잠정본으로 표시하고 최종 확정에 필요한 정보를 명시한다. 확인되지 않은 패키지를 ‘업로드 즉시 반영 가능’하다고 표현하지 않는다.

[10. ERP 서버 반영용 ZIP 구성]

포함 대상:

- 이번 개편으로 신규·수정한 HTML/HTM, JavaScript, CSS, SVG, 이미지, 아이콘, 폰트 등
- 신규 리소스를 참조하도록 수정한 페이지와 스타일
- 반영 프로그램이 요구하는 메타데이터

구성 원칙:

- 기존 파일은 BSP 애플리케이션과 상대 경로를 유지한다.
- ZWEB_COMMON, ZWEB_MENU, ZWEB_WF 등 애플리케이션별 자산을 구분한다.
- 동일 파일명 충돌을 방지한다.
- 로컬 경로, ZIP 내부 경로, 실제 서버 대상 경로의 대응을 명확하게 한다.
- 서버 스크립트를 포함한 BSP 페이지나 SSJS의 변경은 별도로 식별하고 반영 프로그램 지원 여부를 확인한다.
- ABAP 프로그램이나 DDIC 객체 등 지원하지 않는 객체를 웹자산으로 위장하여 포함하지 않는다.
- 변경이 없는 파일은 원칙적으로 제외하되 반영 프로그램이 전체 패키지를 요구하면 해당 규격을 따른다.
- 미리보기, 스크린샷, 임시 파일, 개발 도구, 보고서, 백업은 반영 프로그램에서 요구하지 않는 한 반영 ZIP과 분리한다.

파일별 반영 정보:

- 대상 BSP 애플리케이션
- 객체 또는 자산 유형
- 신규·수정 구분
- ZIP 내부 경로
- 서버 대상 경로 또는 객체 식별자
- 변경 목적
- 텍스트 인코딩 또는 바이너리 여부
- MIME Content-Type
- 파일 크기와 SHA-256
- 원본이 있는 경우 원본 SHA-256
- 함께 반영해야 하는 의존 자산

해시는 실제 파일 바이트로 계산한다. 제공받은 원본 해시가 서버 현행본과 동일하다고 단정하지 않는다.

삭제 처리:

- ZIP에 없는 파일을 서버에서 삭제하도록 지시하지 않는다.
- 물리적 삭제가 필요한 자산은 후보와 참조 관계를 별도로 제시한다.
- 삭제 대상과 프로그램의 삭제 지원이 확인되지 않으면 자동 삭제 지시를 넣지 않는다.

패키지 검증:

- 참조 경로와 대소문자
- 신규 의존 자산 누락
- 중복 경로와 파일명 충돌
- 텍스트 인코딩과 한글
- BSP 서버 구문 보존
- JavaScript·CSS·SVG 구문
- 이미지·폰트 바이너리 손상 여부
- 외부망 의존 여부
- 실제 ZIP 내부 목록과 해시

로컬 구문 검증, 브라우저 검증, SAP 저장·활성화 검증을 구분한다.

[11. 적용·원복 안내]

- 신규 리소스와 참조 페이지의 적용 순서 또는 일괄 반영 필요성을 명시한다.
- 기존 운영 방식에 맞는 CSS·JS·이미지·폰트 캐시 갱신 방안을 제공한다.
- 원복 자료는 반영 ZIP과 분리한다.
- 제공받은 원본 기반 원복 자료와 서버 반영 직전에 확보해야 하는 실제 서버 백업을 구분한다.
- 신규 자산의 원복 시 처리 방법을 명시한다.
- 이 프로젝트에서는 ERP 서버에 직접 업로드하거나 저장·활성화하지 않는다. 서버 반영은 별도 프로그램과 사용자가 정한 절차로 진행한다.
- 실제 서버 반영 결과가 제공되면 오류를 분석하고 수정 패키지 및 보고서를 갱신한다.

[12. 원본 대비 변경 전후 비교 보고서]

최종적으로 ‘웹자산 변경 전후 비교 보고서’를 작성한다. 단순 작업 요약이 아니라 원본과 최종 수정본을 실제로 비교한 명세서여야 한다.

비교 기준:

- 원본 압축파일명, 원본 버전 또는 식별 정보, 최종 패키지 버전, 비교 일시, 해시를 기록한다.
- 제공받은 원본과 비교했음을 명시한다.
- 서버 현행본과 직접 비교하지 않았다면 서버 기준 비교라고 표현하지 않는다.
- 신규·수정·삭제·이동·이름 변경·미변경을 구분한다.
- 이동·이름 변경의 근거가 부족하면 단정하지 않는다.
- ZIP 제외와 서버 삭제를 구분한다.
- 분류별 집계가 중복되지 않도록 기준을 설명한다.

전체 요약:

- 원본과 최종 비교 대상 파일 수
- 상태별 파일 수
- BSP 애플리케이션별 변경 건수
- HTML/HTM·JS·CSS·SVG·이미지·폰트 등 유형별 변경 건수
- 주요 디자인 변경
- 기능에 영향을 주는 변경
- 서버 반영 대상과 별도 확인 대상

파일별 상세 명세:

- 변경 식별번호
- 변경 상태
- BSP 애플리케이션과 객체 유형
- 변경 전 파일명
- 변경 전 전체 상대 경로
- 변경 후 파일명
- 변경 후 전체 상대 경로
- ZIP 내부 경로
- 서버 대상 경로 또는 객체 식별자
- 기존 파일의 역할
- 변경 후 파일의 역할
- 구체적인 변경 내용과 이유
- 유지·제거·추가한 기능
- 참조 대상과 이 파일을 참조하는 파일
- 영향 범위
- 함께 반영해야 하는 파일
- 검증 결과와 미검증 사항
- 원복 방법

경로는 중간을 생략하지 말고 기준 루트부터 전체 상대 경로를 표시한다. 서버 경로가 미확정이면 확인 필요로 표시한다.

[13. 코드·시각 자산의 상세 비교]

텍스트 파일:

## smart-erp-progress-t010-a1

**네. 이 레퍼런스의 구성을 스마트 ERP 메인화면에 적용할 수 있습니다.** 핵심은 **넓은 시스템 조감도를 배경으로 두고, 그 위에 반투명 메뉴와 정보 패널을 배치하는 방식**입니다. 기존의 중앙 일러스트 중심 시안보다 화면 전체가 하나로 연결된 느낌을 줄 수 있습니다.

첨부 원본 소스도 확인했습니다. 현재 상단·왼쪽 메뉴·중앙 업무 화면이 분리되어 있어 이 구성을 적용할 기반은 있습니다. 다만 기존 영역에 흰색 배경과 배경 이미지가 지정되어 있어, 반투명 효과를 내려면 바깥 레이아웃과 메뉴 내부 스타일을 함께 조정해야 합니다.

| 영역 | 스마트 ERP 적용 방향 | 검토 의견 |
| --- | --- | --- |
| **상단** | 얇은 반투명 바에 로고·사용자 정보·기존 기능 배치 | 화면 전체와 자연스럽게 연결 가능 |
| **왼쪽 메뉴** | 반투명 흰색 패널 안에 결재현황·검색·촘촘한 메뉴 트리 배치 | 메뉴 글자는 진하게 유지하고 패널 배경만 투명하게 처리 |
| **중앙** | ERP의 업무와 시스템 연결을 보여주는 넓은 아이소메트릭 조감도 | 이번 디자인의 핵심. 중앙 그림의 구성을 새로 잡는 것이 적절 |
| **하단 업무공지** | 제목·분류·등록일을 보여주는 넓은 패널 | 원본에 공지 조회·상세 열기 코드가 있어 재사용 검토 가능 |
| **하단 알림게시판** | 업무공지 옆에 별도 패널 배치 | 표시할 알림 종류와 실제 데이터 출처 확인 필요 |

**중앙 이미지는 ‘ERP 업무가 연결된 하나의 공간’으로 표현하는 것이 좋겠습니다.** 레퍼런스의 창고 건물을 그대로 가져오기보다, 가운데에 ERP 시스템을 상징하는 허브를 두고 재무회계·구매재고·예산원가·인사·자산 영역을 얇은 선으로 연결하는 구성입니다. 각 영역에는 모니터·문서·데이터 저장소·작업 공간을 배치하고, 앞서 요청하신 코발트 복장의 인물 8명을 자연스럽게 분산할 수 있습니다.

배경 그림은 흰색·옅은 회청색 위주로 낮은 대비를 유지하고, 코발트는 선택 메뉴와 주요 연결 지점에 사용하면 좋겠습니다. 청록이나 옅은 주황은 작은 포인트로만 넣으면 화면이 복잡해지지 않습니다.

실제 적용에서는 다음 사항이 중요합니다.

- **반투명 메뉴의 가독성:** 레퍼런스처럼 모든 요소를 흐리게 만들면 긴 업무 메뉴를 읽기 어렵습니다. 메뉴 뒤쪽 그림은 단순하게 하고, 글자와 선택 상태는 선명하게 유지해야 합니다.
- **iframe 구조:** 현재 메뉴와 결재현황은 별도 문서입니다. 바깥 패널만 반투명하게 바꾸면 내부의 흰 배경이 남을 수 있습니다. 메뉴를 호출하는 코드는 확인했지만, 이번 ZWEB_COMMON.zip에는 ZWEB_MENU 소스가 없어 메뉴 내부 변경 범위는 추가 확인이 필요합니다.
- **브라우저 대응:** 유리처럼 배경이 흐려지는 효과는 CSS로 구현할 수 있습니다. 구형 브라우저에서는 지원 차이가 있어, 흐림 효과가 없어도 반투명 또는 밝은 단색 패널로 읽기 좋게 표시되도록 구성해야 합니다. [MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/backdrop-filter?utm_source=chatgpt.com)
- **업무 화면 전환:** 홈에서는 조감도와 게시판을 보여주고, 메뉴를 선택하면 중앙 영역을 해당 업무 화면에 충분히 내주는 구성이 적절합니다. 배경 그림이 업무 표나 입력 화면을 가리지 않도록 해야 합니다.
- **하단 게시판 공간:** 게시판이 그림 위에 무조건 겹치도록 고정하기보다, 중앙 그림 아래에 공간을 확보하면서 반투명 패널로 연결감을 주는 편이 작은 화면에서도 안정적입니다.

이번 요청을 기준으로 **이전에 제거하기로 했던 공지사항은 ‘업무공지’로 다시 포함하고, ‘알림게시판’을 추가하는 방향**으로 범위를 바꾸면 됩니다. 알림게시판이 운영자가 게시하는 안내인지, 개인별 결재·처리 알림인지에 따라 데이터 연계 범위는 달라집니다.

**디자인 방향은 충분히 적용 가능합니다.** 다음 시안은 **반투명 왼쪽 메뉴 + ERP 시스템 조감도 + 하단 업무공지·알림게시판**을 한 화면으로 구성해 검토하는 것이 적절합니다. 현재는 소스 기반 검토까지 진행했으며, 실제 수정이나 개발계 검증은 하지 않았습니다.

## smart-erp-progress-t024-a1

아래 프롬프트를 **최종 시안 이미지와 추출한 웹 소스 파일을 함께 첨부해서** 사용하면 됩니다. 기존 기능은 그대로 유지하고, 최종 시안의 분위기를 실제 화면에 충실하게 구현하는 데 초점을 맞췄습니다.

글쓰기

ERP 웹 메인화면의 디자인 개편을 진행해줘.

이번 작업의 목표는 기존 ERP의 기능과 업무 흐름을 유지하면서, 첨부한 **최종 시안 이미지에 최대한 가깝게 메인화면을 현대적이고 세련되게 개선하는 것**이다. 새로운 디자인을 자유롭게 제안하는 작업이 아니라, 확정된 시안을 기존 시스템에 적용하는 작업으로 이해해줘.

### 1. 작업 기준과 우선순위

다음 순서로 판단해줘.

1. 기존 기능과 업무 동작 보존
2. 첨부한 최종 시안의 배치와 시각적 분위기 재현
3. 가독성, 조작성, 화면 크기 변화에 대한 안정성
4. 유지보수성과 성능

기존에 논의했던 여러 시안보다 내가 **‘최종 시안’이라고 지정한 서버 인프라 배경의 이미지**를 우선한다.

첨부된 소스를 먼저 분석한 뒤 실제 코드를 수정해줘. 소스를 확인하지 않은 상태에서 파일명이나 시스템 구조, 데이터 연계 방식을 추측해 구현하지 마.

### 2. 기존 소스와 웹 자산 확인

먼저 메인화면을 구성하는 실제 파일과 의존 관계를 확인해줘.

- 메인 레이아웃과 홈 화면
- 좌측 메뉴 트리
- 공통 CSS와 JavaScript
- 게시판과 알림 관련 화면
- 이미지, 아이콘, 로고, 폰트
- 화면 간 iframe 관계와 이벤트 호출
- 메인화면의 데이터 조회와 업무 화면 이동 방식

`ZWEB_COMMON`뿐 아니라 첨부된 메뉴·게시판 등 관련 웹 자산도 함께 확인해줘. 게시판 애플리케이션의 이름은 추정하지 말고 실제 소스의 경로와 호출 관계를 기준으로 판단해줘.

누락된 자산이 있다면 **어느 파일의 어떤 참조 때문에 필요한지** 근거와 함께 정리해줘. 누락 여부와 관계없이 진행할 수 있는 범위는 계속 작업해줘.

### 3. 반드시 보존할 기능

**좌측 메뉴의 트리 구조와 기본 기능은 변경하지 않는다.**

다음 항목은 실제 소스를 기준으로 기존 동작을 보존해줘.

- 메뉴 계층, 순서, 명칭, 업무 연결 경로
- 권한에 따른 메뉴 표시
- 펼치기와 접기
- 선택 상태와 업무 화면 이동
- 검색과 즐겨찾기 등 기존 제공 기능
- 로그인·세션·권한 처리
- 게시판 조회, 상세 화면 이동 및 기존 게시판 기능
- 기존 데이터 조회와 화면 간 연계

트리의 폴더 아이콘, 화살표, 글꼴, 색상, 행 높이, 들여쓰기, 선택·호버 표현은 개선할 수 있다. 다만 디자인을 위해 메뉴를 임의로 삭제하거나 순서를 바꾸거나 정적인 샘플 메뉴로 교체하지 마.

기존 이벤트가 연결된 ID, 함수명, iframe 이름, URL, 전달 인자는 영향을 확인한 뒤 보존해줘.

### 4. 전체 디자인 방향

최종 시안의 핵심은 다음과 같다.

- 화이트와 밝은 회색 중심의 넓고 정돈된 화면
- 서버와 저장장치가 배치된 밝은 아이소메트릭 배경
- 배경이 은은하게 비치는 반투명 화이트 패널
- 얇고 절제된 테두리와 부드러운 그림자
- 작고 정교한 아이콘과 가벼운 인상의 타이포그래피
- 코발트 블루를 중심으로 한 포인트 색상
- 옅은 청록색과 제한적인 보조 색상

불투명한 카드가 가득한 일반적인 관리자 대시보드로 바꾸지 마. 큰 제목, 과도한 둥근 모서리, 짙은 그림자, 강한 그라데이션도 피하고, 시안처럼 배경과 패널이 자연스럽게 어우러지도록 만들어줘.

### 5. 중앙 배경 이미지

중앙은 최종 시안처럼 **물리적인 서버 랙, 스토리지, 원통형 DB 저장소가 낮은 플랫폼 위에 배치된 인프라 공간**으로 표현해줘.

구체적인 기준은 다음과 같다.

- 밝은 화이트·실버 장비와 정교한 전면 디테일
- 자연스러운 원근감, 앞뒤 관계, 그림자
- 서버 간 연결을 나타내는 가는 네트워크 선
- 바닥에 촘촘하게 배치한 옅은 청록색 육각형 벌집 패턴
- 약 10개 정도의 육각형에 은은한 청록색 채움
- 메뉴와 게시판 뒤에서도 시각적으로 복잡하지 않은 밀도

사람 중심 일러스트나 방송 장비, 모뎀처럼 보이는 장비로 바꾸지 마. 단순한 SVG 도형으로 서버를 다시 그려 원본 시안보다 품질이 떨어지는 방식도 사용하지 마.

배경은 고해상도 이미지로 구성해도 된다. 다만 최종 시안 전체를 하나의 이미지로 깔아 메뉴와 글자까지 배경에 포함시키면 안 된다. **배경 이미지와 실제 작동하는 HTML 메뉴·패널·텍스트를 분리해서 구현해줘.**

이미지 준비에 제약이 있다면 임시 자산과 최종 교체가 필요한 부분을 명확하게 밝혀줘.

### 6. 좌측 메뉴 디자인

메뉴는 최종 시안처럼 세로로 긴 반투명 패널로 구성해줘.

- 배경이 은은하게 비치는 화이트 패널
- 충분한 글자 대비와 선명한 메뉴명
- 두께와 크기가 통일된 폴더·업무·펼침 아이콘
- 과도하게 넓지 않은 행 간격으로 많은 메뉴를 확인할 수 있는 밀도
- 계층을 이해하기 쉬운 들여쓰기
- 절제된 코발트 색상의 선택 표시
- 마우스 호버와 키보드 포커스를 구분할 수 있는 표현
- 긴 메뉴명과 스크롤에 대한 안정적인 처리

현재 메뉴 컴포넌트를 최대한 활용하고, 디자인 변경을 이유로 트리 라이브러리나 메뉴 동작을 전면 교체하지 마.

### 7. 상단 영역과 업무 지표

상단은 로고, 기존 내비게이션, 사용자 기능이 정돈된 얇은 반투명 영역으로 구성해줘. 실제 제공된 로고와 시스템 명칭을 사용하고, 참고 이미지의 임의 브랜드나 지역명은 사용하지 마.

주요 업무 지표는 최종 시안처럼 타이틀과 건수가 명확하게 보이도록 배치해줘.

- 재무회계 / 3,465,776건
- 구매재고 / 4,433,476건
- 예산원가 / 1,232,344건
- 인사관리 / 890,888건

위 숫자는 **디자인 예시**다. 실제 데이터가 있으면 기존 조회 방식을 활용하고, 없다면 미리보기용 예시임을 명시해줘. 임의의 숫자를 실제 운영 데이터처럼 표시하지 마.

실제 데이터 근거가 없는 증감률이나 차트도 임의로 추가하지 마.

### 8. 중앙 정보 패널

중앙에는 최종 시안의 ‘처리할 업무’, ‘마감 일정’처럼 의미 있는 업무 정보를 작은 반투명 패널로 배치해줘.

기존 데이터와 기능으로 제공할 수 있는 정보를 우선 사용해줘. 예를 들면 결재 대기, 임시저장 전표, 확인할 요청, 마감 일정 등이다.

연계 가능한 데이터가 없다면 디자인 미리보기에서만 예시로 표현하고, 운영 화면에 적용할 때 필요한 연계 항목을 별도로 정리해줘. 새로운 백엔드 기능을 완성한 것처럼 꾸미지 마.

패널은 서버 배경을 적절하게 드러내면서도 내용이 잘 읽히도록 위치와 투명도를 조절해줘.

### 9. 하단 게시판

하단에는 최종 시안처럼 **업무공지와 알림게시판**을 배치해줘.

- 반투명 화이트 배경
- 정돈된 제목과 날짜
- 얇고 은은한 행 구분선
- 제목 말줄임과 전체 제목 확인 방법
- 자연스러운 호버 및 포커스 표시
- 기존 상세 조회와 더보기 동작 유지

기존 게시판 소스와 호출 방식을 활용해줘. 실제 게시판 대신 정적인 예시 목록만 넣고 구현이 완료됐다고 처리하지 마.

로딩 중, 게시물 없음, 조회 실패 상태도 화면 분위기에 맞춰 정리해줘.

### 10. 서버 불빛 효과

서버 불빛이 은은하게 깜빡이는 효과는 추가할 수 있지만, **정적인 화면의 완성도를 먼저 확보해줘.**

애니메이션을 넣는다면 다음 조건을 지켜줘.

- 서버 LED 일부에만 절제된 효과 적용
- 과한 점멸, 장비 이동, 카메라 이동 금지
- 화면 크기나 배경 크롭이 바뀌어도 불빛 위치 유지
- 실제 서버 상태를 나타내는 것처럼 오해하게 만들지 않기
- 애니메이션 실패 시 정적 배경 표시
- 모션 감소 설정에 대응

고해상도 배경에 좌표를 맞춘 효과나 짧은 무음 반복 영상 등, 실제 구현 환경과 보유 자산에 맞는 방식을 선택하고 이유를 설명해줘. 영상을 사용해도 메뉴와 게시판은 그 위에 별도 HTML 레이어로 배치하여 정상적으로 조작할 수 있어야 한다.

영상 제작이 불가능한 환경이라면 완성했다고 주장하지 말고, 정적 배경을 완성한 뒤 추가로 필요한 자산을 밝혀줘.

### 11. 구현과 화면 대응

기존 기술 구조를 최대한 유지하고, 디자인 개편을 이유로 새로운 프레임워크를 도입하지 마.

- 공통 스타일 변경이 다른 업무 화면에 영향을 주지 않도록 적용 범위 제한
