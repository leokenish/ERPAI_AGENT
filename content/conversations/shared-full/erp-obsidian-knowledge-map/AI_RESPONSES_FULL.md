## obs-m002 · AI 응답

출처: https://chatgpt.com/share/6acf6cf5-03fc-83e8-9921-90f3229f7fd0 / 화면 turn 2 / 2026-10-14 직접 확인

네, 맞아요. **ERP 관련 자료를 Markdown(`.md`) 문서로 정리하고, 문서끼리 연결해서 업무 맥락을 찾아볼 수 있게 만드는 것**이 옵시디언의 핵심 활용 방식입니다.

다만 **옵시디언이 자료를 넣기만 하면 내용을 이해해서 자동으로 분류하고 연결해주는 것은 아니에요.** 옵시디언은 문서를 저장하고 연결을 보여주는 도구이고, 문서 분류·요약·연결은 직접 하거나 AI를 활용해 만드는 방식입니다.

예를 들어 KBS의 **시간외근무 업무**를 정리한다면 이렇게 구성할 수 있어요.

| 문서 | 담을 내용 | 연결할 문서 |
| --- | --- | --- |
| 시간외근무 업무 개요 | 업무 흐름, 담당 부서, 주요 기준 | 규정, 매뉴얼, 관련 프로그램 |
| 시간외 단가 변경 회의록 | 논의 내용, 결정 사항, 적용 시점 | 단가 기준, 변경 요청 |
| 시간외 단가 기준 | 적용 기간별 단가와 적용 조건 | 근거 규정, 결정 회의록 |
| 시간외 신청 매뉴얼 | 신청·승인 절차, 화면 설명 | 업무 개요, 예외 처리 |
| 시간외 계산 프로그램 | 프로그램명, 관련 테이블, 계산 로직 | 단가 기준, 변경 이력 |
| 특정 지급 오류 처리 이력 | 증상, 원인, 조치, 확인 결과 | 해당 프로그램, 관련 업무 기준 |

문서 안에 아래처럼 쓰면 서로 연결됩니다.

```markdown
# 시간외 단가 변경

## 결정 내용
- 적용일: YYYY-MM-DD
- 변경 단가: ○○원

## 근거
- [[시간외 단가 변경 회의록]]
- [[시간외실비 지급 지침]]

## 영향받는 시스템
- [[시간외 계산 프로그램]]
- [[시간외 신청 화면]]

## 확인할 사항
- 적용일 이전 근무분의 정산 기준
- 소급 정산 여부
```

`[[시간외 계산 프로그램]]`을 누르면 그 문서로 이동하고, 해당 프로그램 문서에서는 **어떤 업무 기준이나 회의록에서 자신을 참조했는지**도 확인할 수 있습니다. 이런 역방향 연결을 *백링크*라고 해요.

지금 구상하시는 ERP 업무 정리에서는 **“자료 종류별 보관”과 “업무별 연결”을 함께 하는 것**이 좋습니다.

- **원본 자료:** 규정 PDF, 매뉴얼, 엑셀, 대화 내역 등을 보관합니다.

- **업무 지식 문서:** 원본에서 확인한 기준과 절차를 업무 단위로 정리합니다.

- **논의·결정 기록:** 언제, 누가, 왜 해당 기준을 정했는지 남깁니다.

- **시스템 문서:** 관련 ABAP 프로그램·함수·테이블·트랜잭션을 연결합니다.

특히 **회의에서 나온 의견, 최종 결정, 현재 적용 중인 기준은 구분**해야 합니다. 과거 회의록의 검토안을 현재 규정으로 잘못 이해하지 않도록, 문서에 `출처·작성일·적용일·상태(검토/확정/폐기)`를 남기는 게 중요해요.

이렇게 구성하면 단순히 “매뉴얼이 어디 있지?”를 찾는 수준을 넘어, **“이 로직은 왜 이렇게 만들어졌지?”, “이 규정이 바뀌면 어떤 프로그램을 확인해야 하지?”**까지 근거를 따라가며 파악할 수 있습니다. 원하시는 **ERP 업무와 시스템 사이의 관계 정리**에 잘 맞는 방식이에요.

## obs-m005 · AI 응답

**네. 지금 만든 폴더 구조를 그대로 활용할 수 있어요. 다만 “관계를 분석해서 연결해줘”라는 작업은 코덱스에 맡기고, 옵시디언에서는 그 결과를 탐색하는 방식입니다.** 이미 문서 추출과 스킬화까지 하셨으니 처음부터 다시 정리할 필요는 없습니다.

말씀하신 구조를 기준으로 설명하면 다음과 같습니다. 실제 파일 내용은 아직 확인하지 않은 상태예요.

| 기존 자료 | 활용 방법 |
| --- | --- |
| `SKILL.md` | AI의 업무 처리 지침으로 유지 |
| `knowledge/` | 업무 기준·회의록·매뉴얼을 지식 문서로 활용 |

| `exports/` | ABAP·웹 소스를 유지하고 설명 문서에서 참조 |

**이 폴더들을 포함하는 상위 폴더를 옵시디언의 보관함(Vault)으로 열면 됩니다.** 기존 Markdown 파일을 활용하는 구조라서 별도 데이터베이스로 옮길 필요는 없습니다. 문서 사이의 연결에는 `[[문서명]]`이나 일반 Markdown 링크를 사용할 수 있어요. [Obsidian Help+1](https://obsidian.md/help/data-storage?utm_source=chatgpt.com)

다만 폴더를 열었다고 옵시디언이 자동으로 **“이 회의에서 결정된 사항이 저 ABAP 로직에 반영됐구나”**까지 파악하지는 않습니다. 그 관계를 코덱스가 분석해 문서와 링크로 남겨줘야 합니다.

예를 들어 코덱스가 `시간외 단가 변경.md`라는 연결 문서를 만들고, 그 안에 다음 내용을 묶는 거예요.

- **업무 기준:** `knowledge/`의 단가 적용 기준

- **결정 근거:** 관련 회의록과 대화 기록

- **구현 위치:** `exports/`의 실제 프로그램·함수·계산 구문

- **검증 방법:** `harness/`의 적용일 경계·소급 정산 테스트

- **미확인 사항:** 문서와 소스가 다르거나 근거가 부족한 부분

특히 **소스코드는 별도의 설명용 `.md` 문서를 만들어 연결하는 편이 좋습니다.** `.abap`·`.js` 등을 Markdown 문서처럼 읽고 관계를 분석하는 기능은 옵시디언의 기본 역할이 아닙니다. 프로그램별 설명 문서에 역할·원본 경로·관련 업무·검증 항목을 적으면 탐색하기 쉬워집니다. [Obsidian Help](https://obsidian.md/help/file-formats?utm_source=chatgpt.com)

지금 구조에서는 **기존 폴더와 파일명을 유지하면서 연결 문서를 추가하는 방식**을 권합니다. 파일을 재배치하면 스킬과 검증 스크립트에서 사용하는 경로가 깨질 수 있기 때문이에요.

코덱스에는 아래와 같은 내용으로 지시하면 됩니다.

> 현재 프로젝트를 옵시디언에서 업무 관계를 탐색할 수 있도록 정리해줘. 기존 SKILL.md, knowledge, harness, exports의 파일 경로와 실행 동작은 유지해줘.
> 
> 먼저 전체 파일 목록과 기존 링크를 조사하고, 업무별로 기준·회의록·결정 이력·ABAP 및 웹 소스·검증 항목의 관계를 분석해줘.
> 
> maps 폴더에 업무별 연결 문서와 전체 목차를 만들고, 소스코드는 필요한 프로그램별 설명용 md 문서로 연결해줘.
> 
> 각 관계에는 근거 파일과 해당 절 또는 코드 위치를 남기고, 확인된 관계와 추정 관계를 구분해줘. 과거 검토안과 현재 적용 기준도 구분해줘. 마지막으로 링크 대상의 존재 여부를 검사해줘.

**이미 만들어둔 자료 위에 ‘업무 관계를 보여주는 지도’를 추가한다고 생각하시면 됩니다.** 이후 자료나 코드가 바뀌었을 때 그 지도까지 갱신하는 작업도 코덱스의 작업 지침에 넣으면 됩니다.

## obs-m007 · AI 응답

출처: https://chatgpt.com/share/6acf6cf5-03fc-83e8-9921-90f3229f7fd0 / 화면 turn 6 / 2026-10-14 직접 확인

네, **거의 정확하게 이해하셨어요.** 다만 역할을 더 정확히 나누면 **AI가 업무지도를 만들고 읽으며, 옵시디언은 사람이 그 지도를 편하게 보고 관리하는 도구**입니다.

| 구성 요소 | 역할 |
| --- | --- |
| 원본 자료·소스코드 | 매뉴얼, 회의록, 대화, ABAP 등 실제 근거 |
| Markdown 문서·링크 | 업무의 의미와 자료 사이의 관계를 기록한 지도 |
| 옵시디언 | 문서와 연결 관계를 사람이 탐색하는 화면 |
| AI·코덱스 | 자료를 분석해 지도를 만들고, 지도를 따라 필요한 근거를 찾아 작업 |

**AI가 옵시디언의 그래프 화면을 보는 것은 아니고, 그 밑에 있는 `.md` 문서와 링크를 읽는 방식**이에요. 같은 파일을 사람은 옵시디언으로 보고, AI는 직접 읽는 겁니다.

예를 들어 “시간외 단가 변경에 영향받는 프로그램을 찾아줘”라고 하면 AI는 다음처럼 활용할 수 있어요.

1. 업무 목차에서 **시간외 단가** 문서를 찾습니다.
2. 연결된 **적용 기준·결정 회의록·프로그램 설명**을 읽습니다.
3. 실제 **ABAP 소스와 검증 항목**을 확인합니다.
4. 변경 대상과 확인해야 할 사항을 정리합니다.

여기서 지도의 가치는 단순한 폴더 위치보다 **“이 회의가 이 기준의 근거이고, 이 프로그램이 그 기준을 구현하며, 이 테스트가 이를 검증한다”는 관계**를 남기는 데 있습니다.

그래서 지금 만들어두신 `SKILL.md`, `knowledge`, `harness`, `exports`는 이미 기반이 갖춰진 상태예요. 여기에 **업무별 목차와 근거 있는 연결**을 추가하면, 사람과 AI가 함께 활용하는 ERP 업무지도가 됩니다. 옵시디언 없이도 AI는 그 지도를 읽을 수 있고요.

2. 당시 어떤 환경과 자료를 가지고 있었는가
3. 내가 AI에게 실제로 무엇을 요청했는가

## 2. 추출 범위와 원문 원칙

- 현재 실제로 확인할 수 있는 이 프로젝트의 사용자–AI 대화와 제공 자료를 대상으로 한다.

- 확인 가능한 대화는 순서대로 보존한다. 긴 코드나 파일 내용은 별도 파일로 분리하고 해당 발화와 연결해도 된다.

- 교육용 핵심 구간은 별도로 선정하되, 확인 가능한 나머지 대화를 임의로 버리지 않는다.

- 다른 대화방이나 오래된 메시지를 볼 수 없다면 그 범위를 명확히 적는다. 확인하지 못한 대화까지 모두 추출했다고 표현하지 않는다.

- 실제 발화, 발췌, 요약을 구분한다. 요약 MD에서 추정한 내용을 실제 대화처럼 복원하거나 인용하지 않는다.

- 원문의 오류·오해·잘못된 답변을 당시 메시지에서 몰래 수정하지 않는다. 정정은 별도의 해설과 후속 발화로 연결한다.

- 날짜·버전·파일명·실행 결과가 확인되지 않으면 미확인 또는 null로 남긴다.

- AI의 “수정했다”는 응답, 사용자의 실행 보고, 실제 확인 가능한 테스트 결과를 구분한다.

- 인증값이나 교육에 불필요한 개인 식별정보는 명시적으로 마스킹하고, 마스킹 여부를 기록한다.

- 접근할 수 없는 첨부 파일은 재생성하지 말고 ‘원본 미확보’로 기록한다.

### conversation-data.json — 채팅 UI와 구성도 연결 데이터

UTF-8의 유효한 JSON으로 만들어줘. 주석이나 trailing comma는 넣지 않는다.

최상위 구조는 다음과 같이 맞춰줘.

```text
{
  "schema_version": "1.0",
  "project_id": "영문-프로젝트-id",
  "project_title": "프로젝트명",
  "coverage": {
    "status": "partial",
    "description": "실제로 확인한 대화와 자료 범위",
    "missing": []
  },
  "threads": [],
  "episodes": [],
  "assets": []
}
```

각 배열의 항목은 다음 기준을 따른다.

**threads — 실제 대화**

각 대화방 항목:

- id

- title

- source_description

- messages

각 messages 항목:

- id: 프로젝트 안에서 중복되지 않는 발화 ID

- sequence: 대화방 안의 실제 발화 순서

- role: user 또는 assistant

- timestamp: 확인 가능한 시각, 없으면 null

- content_type: verbatim / excerpt / summary

- content_markdown: 발화 내용

- source_locator: 원래 대화·메시지·문서 위치에 대한 확인 가능한 설명

- redacted: 마스킹 여부

- asset_ids: 연결되는 첨부 ID 배열

실제 플랫폼 메시지 ID가 없으면 자체 ID를 부여해도 된다. 자체 ID를 실제 플랫폼 ID처럼 표현하지 않는다.

**episodes — 교육 화면에 표시할 학습 단계**

각 항목:

- id

- order

- title

- goal

- map_nodes

- prerequisites

- message_refs: 해당 단계의 발화 ID를 읽을 순서대로 나열

- commentary_markdown: 실제 대화와 구분되는 교육 해설

- outcome_markdown: 결과와 확인 상태

- exercise_markdown: 따라 하기와 확인 방법

- asset_ids

map_nodes는 관련된 구성도 요소를 아래 값에서 선택한다. 여러 요소를 연결해도 되며, 이 프로젝트와 무관한 요소를 억지로 넣지 않는다.

- sap: SAP ERP

- export: 소스 추출

- git: GitHub·버전 관리

- knowledge: 업무 지식·MD

- codex: Codex·지침·스킬·업무 에이전트

- diag: DIAG·비교·검증

- maps: Obsidian·관계 문서

- feedback: 담당자 검토·피드백·회귀 사례

- agent: 원격 협업의 주 에이전트

- lookup: ERP 조회 MCP

- hub: 중앙 자문 MCP

- worker: 담당 워커

- expert: 전문 자문 에이전트

- telegram: Telegram 연결

- erp-api: REST·RFC 연계

- portal: 교육 포털 운영

**assets — 첨부와 산출물**

각 항목:

- id

- original_filename

- path: ZIP 내부 상대 경로, 미확보이면 null

- kind: image / code / document / archive / other

- description

- availability: included / unavailable

- version: 확인 가능한 버전, 없으면 null

- related_message_ids

같은 파일의 서로 다른 버전은 별개 항목으로 구분한다. 오류가 발생한 버전과 수정 완료 버전을 섞지 않는다.

### assets/ — 실제 첨부와 산출물

확보 가능한 관련 캡처·코드·MD·ZIP을 포함해줘.

- 가능하면 원본 파일을 보존한다.

- JSON의 path와 실제 파일 경로가 일치하게 한다.

- 긴 코드·로그를 파일로 분리했다면 원래 발화에 분리 사실과 파일 연결을 남긴다.

- 자료가 크면 학습 단계에 필요한 핵심 자료부터 포함하고, 제외한 자료 목록과 이유를 README에 적는다.

## 4. 제출 전 확인

- JSON이 실제로 파싱되는가?

- 발화 ID와 첨부 ID가 중복되지 않는가?

- episodes의 message_refs가 실제 messages 항목을 가리키는가?

- included로 표시한 첨부 파일이 ZIP 안에 존재하는가?

- 발화 순서와 수정 전후 버전이 맞는가?

- 실제 대화와 교육 해설·재작성 프롬프트가 구분되는가?

- 실패·수정·검증 과정이 빠지지 않았는가?

- 보지 못한 대화나 파일을 확보했다고 표시하지 않았는가?

대화량이 많아 파일을 분할해야 한다면 동일한 필드 구조와 중복 없는 ID를 유지하고, README에 결합 순서를 적어줘. 용량 때문에 대화를 조용히 잘라내지 않는다.
