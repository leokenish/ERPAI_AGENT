# 업무 지식을 갱신하는 방법

## 새 자료가 들어올 때

1. 원문을 보존하고 새 출처 ID, 원래 파일명, 버전/발행일, 시행일, SHA-256을 등록한다. 이름이 같은 새 PDF도 기존 원문을 덮어쓰지 않는다.
2. `$zhr5-knowledge-curation`으로 원문 전체를 검토한다. 카톡은 메시지 날짜, 규정은 시행일, 양식은 승인 판본을 구별한다.
3. 해당 주제 문서에 새 사실을 추가한다. 기존 설명을 대체했다면 어떤 대상과 기간부터 대체하는지 근거를 남긴다.
4. `knowledge/INDEX.md`, 관련 `OPEN_QUESTIONS.md`, `decisions/TIMELINE.md`를 갱신한다. 해결되지 않은 질문은 완료로 닫지 않는다.
5. 영향을 받는 업무 질문을 `tests/business-qa.md`에 추가하거나 수정한다. 기대 답변은 업무 담당자의 확인 상태를 기록한다.
6. 지식 변경의 이유·근거·검토자를 Git 변경 설명에 남긴다. 원문 전체를 PR 본문에 붙이지 않는다.

## 코드가 새로 추출될 때

추출일·버전·개발클래스·manifest 상태를 확인하고 실제 변경 파일을 비교한다. 지식의 코드 연결 장부에 경로와 commit을 갱신한다.
함수명이 같아도 로직이 바뀌었을 수 있다. 코드가 바뀌었다는 사실과 업무 정책이 승인되었다는 사실을 별도로 기록한다.
이 프로젝트의 클래스 미지원·외부 패키지 제외·활성 소스 제외 정책을 지식 누락 사유로 남긴다.

## 문서별 책임

| 파일 | 무엇이 바뀔 때 수정하는가 |
|---|---|
| AGENTS.md | 에이전트 역할, 근거 규칙, 작업 범위가 달라질 때 |
| SKILL.md | 질의·정리·영향 검토의 절차가 달라질 때 |
| knowledge/ 문서 | 규정, 매뉴얼, 운영 협의, 사례가 추가/정정될 때 |
| INDEX.md | 자료와 검색 경로가 추가/이동될 때 |
| SOURCE_REGISTER | 원문과 버전이 추가될 때 |
| code-map | 실제 추출 코드 확인과 경로/버전이 바뀔 때 |
| tests/business-qa.md | 새 질문·반례·경계 조건·회귀 오류가 발견될 때 |

업무 대화 한 건을 받을 때마다 SKILL.md에 내용 전체를 붙이지 않는다. 스킬은 작업 절차를 유지하고, 지식 문서를 찾아 읽도록 한다.

## 성능 확인

같은 질문에서 정답/근거/시점 구분이 좋아졌는지, 읽은 파일 수와 불필요한 원문 분량이 줄었는지 비교한다.
파일이 적게 읽혔다는 이유만으로 좋은 결과는 아니다. 후속 정정이나 반례를 빠뜨리면 실패다. 토큰 절감률이나 답변 정확도 향상률은 실제 측정 전에는 수치로 주장하지 않는다.
