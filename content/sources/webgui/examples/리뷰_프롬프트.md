# ERP WebGUI 변경 리뷰 프롬프트 — 교육용 신규 예시

프로젝트: KBS ERP WebGUI·SYSTEMGUI 리팩토링 / 정리 기준일: 2026-10-08

아래는 이번 교육 추출에서 만든 재사용 템플릿이다. 과거 사용 프롬프트 원문이나 운영 명령이 아니다. `<...>`를 검증된 테스트 정보로 교체하고 인증정보를 넣지 않는다.

## 1. 읽기 전용 분석 요청

```text
대상은 <원본/기준본/수정본 경로>의 ERP WebGUI 소스다.
이번에는 읽기 전용으로 분석하고 파일·서버·GitHub를 변경하지 마라.
우선순위는 업무·데이터 정확성, 시스템 호환성, 배치·조작 유지,
디자인·가독성, 근거 있는 성능이다. 브라우저 목표는 <승인된 Chrome 버전>이다.

1. 실제 읽은 파일과 이름만 아는 파일을 구분하라.
2. HTML script 순서, 부모/iframe 컨텍스트, JS 전역·공개 함수,
   CSS/인라인 스타일 연계를 추적하라.
3. 증상 <민감정보를 제거한 오류>의 재현 사실과 원인 가설을 구분하라.
4. 필드명·0/false·한글·인코딩·행 번호·동기 계약·제출 횟수·
   실패 시 폼 복원에 영향을 주는 부분을 우선 검토하라.
5. 타이머 모델 콜백 수를 실제 서버 요청 수로 바꾸어 설명하지 마라.
6. 정적/모의/실제 브라우저/ERP 검증을 분리하고 부족한 자료를 요청하라.
7. 오류를 빈 생성자나 무조건 catch로 숨기는 방안은 제시하지 마라.
```

## 2. 승인 후 변경 요청에 포함할 계약

```text
승인된 변경 범위는 <파일과 결함>이다. 운영 서버에는 적용하지 마라.
기준본은 <버전 및 SHA 목록>이며 현재 배포본과의 일치 여부는 <확인 상태>다.
업무 요청 방식·인코딩·필드/이벤트 이름·부모 함수 인수·레이아웃을 보존하라.
이를 바꿔야 하면 이유와 영향 범위를 먼저 설명하라.
완전한 대상 파일, 변경분, 직전 기준본, diff·검증 결과를 분리해서 제공하라.
실제 환경을 실행하지 못했으면 구현 완료와 운영 검증 완료를 구분하라.
```
