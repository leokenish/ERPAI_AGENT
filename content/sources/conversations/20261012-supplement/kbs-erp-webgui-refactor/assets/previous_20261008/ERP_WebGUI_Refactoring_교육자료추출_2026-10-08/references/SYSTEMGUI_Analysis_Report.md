## 3. JavaScript 수정 상세

| 함수 | 수정 | 보존 사항 |
|---|---|---|
| `dom_getChildNodeByAttrAndValue(element, attribute, value)` | `element.childNodes`를 호출 내부 지역 변수로 보관 | 직계 자식만 순서대로 검사. live NodeList의 길이는 반복 확인. getAttribute 후 반환 슬롯은 다시 조회하며, 기존 전역 `v` 대입과 느슨한 비교 유지 |
| `dom_getChildNodeByNodeName(element, nodeName)` | live NodeList와 현재 자식 노드를 지역 변수로 재사용 | 텍스트·주석 건너뛰기, 노드명 대소문자 비교, 첫 일치 항목 반환, null 반환 유지 |
| `dom_getXPos(obj)` | 조상 처리 후 `clientLeft`를 한 번 읽어 재사용 | offsetParent 재귀 순서, offsetLeft 조회, 덧셈 순서·반환값 유지 |
| `dom_getYPos(obj)` | 조상 처리 후 `clientTop`을 한 번 읽어 재사용 | offsetParent 재귀 순서, offsetTop 조회, 덧셈 순서·반환값 유지 |

캐시는 함수 호출 내부에만 존재한다. DOM 노드나 계산한 좌표를 문서 갱신 이후까지 전역에 저장하지 않는다. 자식 목록의 길이를 최초 값으로 고정하지 않아, 속성 조회를 감싼 코드가 같은 목록을 바꾸는 경우도 기존 탐색 흐름을 유지한다. 기존 암묵적 전역 변수까지 일괄 지역 변수로 바꾸지 않았다.

이 변경은 일반 DOM 속성 읽기가 같은 동기 함수 안에서 안정적으로 동작한다는 전제의 국소 개선이다. 외부 코드가 `childNodes`, `nodeType`, `nodeName`, `clientLeft` 등을 부작용이 있는 getter로 교체한 모든 경우까지 동등성을 보장하지는 않는다. 속성 조회 뒤 목록 변경을 일으키는 getAttribute 래퍼의 대표 사례는 모의 검증했다.

이벤트 등록·해제, 핸들러 순서·this·인수, 폼 제출, 네트워크 요청, 포커스 호출·예약, 세션 정리, IE/표준 브라우저 분기, 원본 프로토타입 및 API 대체 구현은 변경하지 않았다. 최신 문법·strict mode·새 전역 함수·비동기 스케줄링을 추가하지 않았다.

원본의 `border: solid 1px <색상 4개>`, `background-position: center middle`, 구형 filter 등 표준 CSS 유효성이 의심되거나 레거시 엔진에 의존하는 선언은 색상 외 구문을 보존했다. 이번 구조 검사는 원본의 모든 선언이 브라우저에서 유효하다는 판정이 아니다.

## 5. 스크롤 및 초기화 분석

1. `its_utils.js`는 `__gbitsutils` 검사로 같은 문서의 중복 초기화를 이미 제어한다. 전역이 별개인 새 문서·메뉴 프레임까지 초기화가 공유되는 구조는 아니다. 전역 가드를 추가하거나 부모 프레임의 초기화 결과를 무조건 재사용하지 않았다.
2. `PosUtil`은 첫 사용 시 시험용 DOM을 삽입하고 크기·테두리를 측정한 뒤 제거한다. `isValid`로 최초 초기화 여부를 관리한다. 측정 과정 자체가 레이아웃 조건을 확인하는 로직이므로 임의로 삭제하거나 순서를 바꾸지 않았다. 이 코드가 실제 스크롤 화면에서 몇 번 호출되는지는 HTML과 실행 기록 없이 확정할 수 없다.
3. WEBGUI의 표·드롭다운·툴바가 `dom_getChildNodeByNodeName` 등을 호출하고, `gui_scroll.js`가 `dom_getXPos`·`dom_getYPos`를 호출하는 소스 연결을 확인했다. 따라서 해당 SYSTEM 함수 구현이 활성화된 문서에서는 중복 조회 감소가 적용될 수 있다.
4. **같은 함수가 WEBGUI의 `wgu_utils.js`에도 정의돼 있다.** 이번 수정 함수 4개 모두 해당되며, 같은 문서에 어떤 파일이 어떤 순서로 실행되는지에 따라 실제 사용되는 구현이 달라질 수 있다. 모든 화면에 이번 최적화가 반드시 적용된다고 단정하지 않는다. 서로 다른 프레임이면 각 문서의 전역과 로드 순서를 따로 확인해야 한다.
5. 제공된 SYSTEM 소스에는 `jmprow`나 앞서 분석한 350ms·700ms 휠 대기값의 직접 정의가 없다. 기존 WEBGUI의 타이머·휠 이동량·서버 콜백을 이번 작업에서 바꾸지 않았다. 이벤트 시간 슬롯의 SCROLL 상수가 있다는 것과 해당 휠 경로가 실행된다는 것은 다른 주장이다.
6. 이전 대화에서 확인된 스크롤 POST·HTML 재수신과 메뉴 문서 로드는 이번 국소 수정으로 없어지지 않는다. 캐시 정책·문서 갱신 구조도 바뀌지 않는다. 실제 요청 중복이나 350ms·700ms 예약 경로 사용 여부는 여전히 미확인이다.

## 8. 적용·캐시·복원

1. **실제 서버의 현재 파일을 먼저 백업한다.** `SYSTEMGUI_Original.zip`은 제공된 Drive 원본이며 서버의 현재 파일과 자동으로 일치한다고 가정하지 않는다.
2. ZIP의 `SYSTEMGUI/JS`·`CSS`는 Drive의 정리용 폴더명이다. 그대로 서버에 새 폴더를 만드는 것이 아니라 기존 MIME 파일과 대응시킨다. `JS/its_utils.js`는 관찰된 `/mimes/system/sl/script/its_utils.js`에 해당한다. CSS는 현재 문서가 참조하는 SYSTEM `gui.css`의 실제 URL을 대조해 교체한다.
3. 실제 변경 파일은 **its_utils.js와 gui.css 2개**다. 나머지 12개는 전체 구성 유지·비교용으로 제공한다. 파일명이 같아도 `/mimes/webgui/sl`의 파일과 혼동하지 않는다.
4. 검토/테스트 환경에 적용하고 MIME 게시·버전·캐시 정책을 확인한다. 새 세션을 열고 부모·내부 프레임 각각의 Network/Sources에서 수정본의 주석과 함수 본문이 보이는지 확인한다. 캐시 무효화 방식은 현재 서버 운영 절차를 따른다. URL에 임의 파라미터를 영구 추가하지 않는다.
5. 기능 확인 뒤 체감 비교 시에는 DevTools의 **Disable cache를 해제한 동일 조건**에서 비교한다. 최초 진입과 캐시가 준비된 반복 진입을 구분하고 같은 트랜잭션·데이터·휠 조작으로 여러 번 측정한다.
6. 문제가 있으면 변경한 2개 파일을 적용 직전에 백업한 서버 파일로 복원하고 같은 게시·캐시 갱신 절차를 거친다. 서버 백업과 Drive 원본이 일치했던 경우에는 제공된 원본 ZIP을 복원에 사용할 수 있다. 이번 SYSTEM 변경을 되돌리기 위해 기존 WEBGUI 스크롤 패치를 함께 롤백할 필요는 없다.

실제 화면 확인은 초기 진입·재진입, 메뉴/드롭다운/팝업/iframe, 표·트리 스크롤, 포커스·한글 입력·Enter, 비활성/읽기 전용, 확대·창 크기 변경, 저장/제출 및 종료를 대상으로 한다. 데이터를 바꾸는 확인은 테스트 환경·테스트 데이터에서 수행한다. SYSTEM 공통 파일을 사용하는 다른 ITS 화면도 확인 대상이다.

## 9. 다음에 확인할 자료

더 큰 스크롤 개선을 판단하려면 문제가 나는 트랜잭션의 Response HTML과 해당 문서의 실제 스크립트 로드 순서가 필요하다. 이 자료로 생성된 스크롤 콜백, 활성화된 유틸리티 구현, 중복 예약·제출 여부를 연결할 수 있다. 성능 기록에서는 요청 전 대기, POST/HTML 응답, JS 실행, 스타일·레이아웃을 나누어 비교한다. 현재 캡처를 같은 방식으로 반복해서 받을 필요는 없다.

이번 결과의 기대 효과는 **실제로 실행되는 공통 함수의 일부 DOM 접근 감소와 색상 일관성**이다. 문서 전체 재생성 비용이나 서버 왕복을 해소했거나 모든 브라우저 호환 문제를 해결한 것으로 해석하지 않는다.
