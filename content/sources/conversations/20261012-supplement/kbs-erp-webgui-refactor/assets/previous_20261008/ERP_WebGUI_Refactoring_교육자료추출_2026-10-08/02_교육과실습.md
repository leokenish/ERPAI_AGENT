# ERP WebGUI·SYSTEMGUI 리팩토링 — 교육과 실습 초안

프로젝트: KBS ERP WebGUI·SYSTEMGUI HTML·JavaScript·CSS 리팩토링  
정리 기준일: **2026-10-08**  
대상 버전: 2026-09-14 Chrome v3 검토본. 운영 검증 완료본이 아님.

## 1. 교육 대상·사전 지식·학습 결과

### 1.1 교육 대상과 사전 지식

KBS ERP 담당 팀원 중 AI에게 소스 분석·변경을 요청하고, 결과물을 검토하거나 테스트 환경에 반영할 사람을 대상으로 한다. HTML의 script/link/form, CSS 선택자, JavaScript 함수·이벤트, 파일 경로·압축 해제 정도를 알면 좋다. 고급 프레임워크 지식은 필요하지 않다.

오프라인 실습은 Python3와 압축 도구만 있으면 된다. 기존 회귀 스위트 재실행은 별도 Node.js24 환경을 전제로 한다. 실서비스 접속·계정·토큰은 오프라인 실습에 필요하지 않다. 설치 방법 자체는 이 프로젝트에서 다루지 않았다.

### 1.2 학습 후 할 수 있는 일

- 원본·직전 기준본·수정본·실제 배포본을 구분한다.
- 같은 파일명이라도 WEBGUI와 SYSTEMGUI의 경로·역할이 다름을 설명한다.
- 캐시 요청, 문서 재생성, repaint, 서버 왕복을 혼동하지 않는다.
- 오류 문구를 파일 본문·로드 순서·실행 문서와 연결해 증거를 모은다.
- AI에게 데이터·배치·타이밍 계약을 명시하고 작은 검증 가능한 변경을 요청한다.
- 정적 검사·모의 테스트·실제 브라우저·사용자 확인을 구분해 결과를 기록한다.
- 적용 전 백업·버전 확인·캐시 대조·복원 기준을 작성한다.

## 2. 전체 ERP AI 구조에서의 위치

이 모듈은 **AI가 만든 ERP 공통 UI 변경을 사람이 근거로 검토하는 과정**을 교육한다. 입력은 소스·사용자 증상·캡처이고, 출력은 변경 파일·diff·검증 기록·미해결 목록이다. 향후 소스 추출/배포, GitHub 검토, 업무별 회귀 시나리오와 연결할 수 있다.

ERP MCP 서버, Codex Desktop 설치, GitHub 연동 구축, 업무 에이전트/서브에이전트·Obsidian 설정은 이 자료로 가르칠 만큼 확인되지 않았다. 통합 포털의 다른 모듈에서 출처를 제공해야 한다. Node.js는 여기서는 **오프라인 검증 도구**이며 향후 포털 웹서버와 역할이 다르다. [01 문서 §15]

## 3. 왜 필요한가: 실제 업무 문제

사용자는 첫 디자인 개편본을 적용한 뒤 기능 이상은 없어 보인다고 했으나 기존 스크롤 끊김을 보고했다. 단순한 시각 개선만으로 문제가 설명되지 않아 네트워크·공통 소스·HTML로 분석을 확장했다. 이후 휠은 되는데 화살표에서 오류가 발생했다. 이때 “휠 테스트 성공=스크롤 전체 성공”, “생성자 오류=ZIP 파일 누락”이라고 결론 내리면 잘못된 패치를 만들 수 있다. [C02~C09, S04]

교육의 핵심 질문은 “어떻게 빨리 코드를 바꿀까?”보다 **“현재 어떤 바이트가 어떤 문서에서 실행되며, 어떤 업무 계약을 지켜야 하는가?”**다.

## 4. 핵심 용어

| 용어 | 이 프로젝트에서의 의미 | 혼동 금지 |
|---|---|---|
| WEBGUI / SYSTEMGUI | 사용자가 올린 두 소스 묶음. 컨트롤 전용/공통 자원이 연결됨 | 제품 버전 이름이나 서버 실제 폴더명으로 단정하지 않음 |
| MIME 경로 | HTML이 참조하는 기존 자원 주소 | ZIP의 JS/CSS/HTML 분류명과 다름 |
| 주 업무 문서 / 보조 문서 | 서버가 반환한 업무 화면 / menubase 등 프레임용 정적 HTML | 작은 메뉴 문서 Timing을 전체 화면 시간으로 사용하지 않음 |
| 캐시 | 자원을 재사용하는 로드 경로 | 200 표시만 보고 네트워크 전체 다운로드라고 판단하지 않음 |
| repaint / 문서 재구성 | 기존 화면 그리기 / HTML을 받아 파싱·초기화하는 큰 작업 | JS·CSS가 다시 나열되는 원인을 repaint만으로 설명하지 않음 |
| debounce성 대기 | 휠 위치 전달 콜백을 실행하기 전 예약 지연 | 서버 응답 완료를 기다리는 타이머가 아님 |
| iframe 실행 컨텍스트 | 각 문서의 전역과 초기화 환경 | 부모에서 정의된 전역이 자식에 자동 존재한다고 가정하지 않음 |
| baseline / modified | v3 직전 기준본 / v3 수정본 | baseline은 최초 원본이나 운영 백업과 다름 |
| 모의 회귀 | 제한된 모델에서 입력·출력·호출 수를 비교 | 실제 SAP 거래·화면·IME 테스트 아님 |
| 데이터 계약 | 필드명·값·인코딩·행번호·이벤트·요청 순서·반환 의미 | 함수 이름만 같다고 모두 보존된 것은 아님 |

## 6. 실제 사례로 배우기

### 6.1 사례1 — 스크롤마다 JS·CSS가 보인다

| 단계 | 실제 프로젝트 내용 |
|---|---|
| 문제 | 휠 한 번에 여러 JS·CSS·Doc가 나타나고 화면이 끊김 |
| 입력 | 사용자 Network 캡처와 WEBGUI·SYSTEM 소스 |
| 작업 | memory/disk cache,menubase와 업무 Doc,GET/POST,Timing·Initiator 구분 |
| 결과 | 업무 POST가 HTML을 반환하고 보조 문서가 자원을 다시 참조하는 흐름으로 판단 |
| 검증 수준 | 당시 캡처 판독 기록. 현재 원 trace 미확보. 정확한 콜백 연결·실제 중복 POST는 미확인 |

기술 상세: 응답 전체163.19ms는 요청 전 휠 대기와 화면 표시 완료를 모두 포함하지 않는다. “350+700+163.19” 식의 합산은 잘못이다. 모형에서 확인한350/700ms 두 콜백과 화면에서 실제 POST가 몇 번 발생했는지는 별도 증거다. [C04~C05, S01 성능 절]

### 6.2 사례2 — 휠은 되지만 화살표에서 오류

| 단계 | 실제 프로젝트 내용 |
|---|---|
| 문제 | dropdown 미정의·createTextRange 오류·unload 메시지 |
| 입력 | 콘솔 이미지, 제공 ZIP과 원본 소스 |
| 작업 | 생성자 존재 확인,gui_tablecontrol 호출 위치 대조,gui_ts/gui.js 행 위치 비교,UA 모형 재현 |
| 결과 | ZIP 내 생성자 누락 증거는 없음. Chrome의 IE 경로 진입 결함은 재현·수정. 배포 응답 불일치는 남음 |
| 검증 | S04의25건은 커서 국소 모형. 이후 v3의확장 검증과 구분. 실제 오류 화면 완전 해결은 미확인 |

교육 포인트: 에러를 없애려고 빈 `gui_dropdownManager`를 선언하면 업무 기능을 조용히 망가뜨릴 수 있다. 원인 미확정 상태를 인정하고 Response/로드 순서를 확보해야 한다. [S04 §1~5, S01 이전 오류 절]

### 6.3 사례3 — contextmenubase와 부모 업무 폼

| 단계 | 실제 프로젝트 내용 |
|---|---|
| 문제 | 추가 HTML이 누락되어 연결 계약 분석이 불완전했음 |
| 입력 | 재동기화된736바이트 contextmenubase 원본 |
| 작업 | onload→부모 ContextMenu_postUrl의5개 인수,menu.js의 폼 임시 상태/제출 추적 |
| 결과 | helper 폼 GET만 보고 업무 요청을 GET으로 변경하지 않음. 메뉴 제출 실패 시 폼 복원 보완 |
| 검증 | 정상/실패 모형과 부모 위임1회 확인. 실제 서버 메뉴 응답은 미검증 |

### 6.4 사례4 — 빠른 코드보다 정확한 데이터

`framepost.html`은 객체의0/false를 빈 문자열로 바꾸지 않게 수정했고, 모든 파라미터 디코딩이 성공한 다음 hidden field와 제외 목록을 반영한다. `sap_commobj.js`는 속성 문자열을 이스케이프하되 HTML 파서가 읽는 name/value는 원래 값과 같게 유지한다. 삭제 행 뒤의 번호를 당기지 않는다. [S01 통신·데이터 계약, S02-V/S02-M]

여기서 “문자열이 더 예뻐졌다”가 합격 기준이 아니다. **파싱된 필드명·값·행 번호·제출 횟수·실패 후 상태**가 기준이다.

## 7. 따라 하기 실습

### 7.1 공통 안전 수칙

- 이 ZIP을 새 로컬 작업 폴더에 푼다. 운영 MIME 폴더 안에서 실습하지 않는다.
- `attachments`의 기존 ZIP은 수정하지 않는다. 분석용 복사본만 별도 임시 폴더에 푼다.
- 실제 계정·쿠키·토큰·업무 값을 입력하지 않는다.
- HTML 파일을 열었다고 ERP 화면이 정상 재현되는 것은 아니다. 부모 전역·서버 HTML·이미지가 필요할 수 있다.
- 아래 A~D는 ERP에 접속하지 않는다. E는 기존 검증 프로그램 실행이며 F는 별도 테스트 환경이 필요하다.

### 7.2 실습A — 버전과 패키지 무결성 확인

**준비물:** 전체 교육 ZIP,Python3,터미널. **유형:** 이번 교육용으로 새로 작성한 읽기 전용 예제. 과거 프로젝트 스크립트로 오인하지 않는다.

교육자료 최상위 폴더에서 실행한다.

```sh
python3 --version
python3 examples/inspect_package.py
```

프로그램은 Full/Apply/Rollback/Original을 읽고 Evidence의 해당 버전과 비교한다. 네트워크 연결·ERP 제출·파일 수정·압축 해제를 하지 않는다.

예상 결과:

```text
Full: 100 / Apply: 33 / Rollback: 100 / Original: 100
JS: 47 / CSS: 34 / HTML: 19
Changed from baseline: 33 (JS 16 / CSS 3 / HTML 14)
Stored mock cases: 186 (not executed by this script)
PASS: ZIP CRC, member paths, manifest hashes and version contents agree.
```

확인 질문: Rollback을 실제 운영 백업으로 사용할 수 있는가? 답은 **서버 현재 바이트가 그 기준본과 일치한다고 확인한 경우에만**이다. 파일 개수만 같아서는 부족하다.

자주 하는 실수: Apply33개를 전체 배포본으로 사용하기, 서로 다른 ZIP의 동일 파일을 섞기,MD를 읽지 않고 오래된 커서 패치를 v3 위에 다시 덮기. [S01 기준 버전·적용 절]

### 7.3 실습B — HTML에서 의존성 연결 찾기

**준비물:** 압축 도구·텍스트 편집기. **유형:** 실제 v3 소스 읽기 실습,브라우저 실행 아님.

새 임시 폴더에 Evidence를 푼다. 아래 명령은 macOS/Linux 계열의 예시이며 셸 환경에 따라 경로를 조정한다. 원본 파일을 덮어쓰지 않는다.

```sh
LAB_DIR=$(mktemp -d)
unzip -q attachments/ITS_Chrome_v3_Evidence.zip -d "$LAB_DIR"
printf '%s\n' "$LAB_DIR"
```

수행 순서:

1. `$LAB_DIR/modified/SYSTEMGUI/HTML/menubase.html`을 편집기에서 연다.
2. `../script/its_domain.js`, `../script/its_utils.js`와 부모 MIME/테마로 만드는 WEBGUI 메뉴 경로를 적는다.
3. `contextmenubase.html`을 열어 부모 호출5개 인수와 자체 GET 폼을 구분한다.
4. `modified/WEBGUI/JS/menu.js`의 `ContextMenu_postUrl`에서 target/action/event 임시 변경과 복원 구간을 찾는다.
5. `baseline`과 `modified`의 `shmult.html`에서 `SL/sl` 경로와 이벤트 관리자 생성 차이를 찾는다.

예상 결과: “보조 문서→공통 자원”, “보조 문서→부모 업무 함수”, “업무 폼→메뉴 프레임”은 서로 다른 연결임을 설명할 수 있다. **GET form이 보인다는 이유만으로 업무 요청을 GET으로 분류하지 않는다.** [S01 통신 절, S02-D]

### 7.4 실습C — 오류와 소스 일치 여부 판단

**입력:** [안전하게 전사한 콘솔 문구](references/대화와자료_근거목록.md),[화살표 오류 보고서](references/WEBGUI_Arrow_Error_Report.md). 실제 세션 URL은 사용하지 않는다.

1. 원본 `gui_dropdown.js`에서 `function gui_dropdownManager`를 찾는다.
2. 원본 `gui_tablecontrol.js`에서 생성자 호출 위치를 찾는다.
3. 원본 `gui_ts.js`의 줄 수와 `gui.js`의 `webguiSetCursorPosition`을 비교한다.
4. 다음 표를 채운다.

| 주장 | 판단할 증거 | 모범 판단 |
|---|---|---|
| ZIP에서 dropdown 생성자를 누락했다 | Original·baseline·Full 파일/본문 | 제공본에는 존재. 운영 로드 여부는 별도 |
| gui_ts.js를 수정하면 커서 오류가 해결된다 | 실제 Response·함수 위치 | 제공본과 표시 위치 불일치. 파일명을 단정하지 않음 |
| unload를 없애면 나머지도 해결된다 | 오류 사이 호출 인과관계 | 입증되지 않음 |
| v3 shmult 수정이 원래 화면 문제를 해결했다 | 원래 업무 HTML·실제 실행 | 아직 미확인 |

추가 자료 요청 문장도 작성한다: “오류가 난 **문서 컨텍스트의 script 목록과 해당 JS Response 본문**을 민감정보 제거 후 제공해 주세요. 전체 쿠키/HAR는 필요하지 않습니다.”

### 7.5 실습D — 데이터 보존과 실패 복원 리뷰

**유형:** 실제 변경 코드 검토 + 아래 가상 교육 입력. 운영 업무 값이 아니다.

| 가상 입력/상황 | 확인할 계약 | 예상 결과 |
|---|---|---|
| 객체 값 `0`, `false`, 빈 문자열 | truthy/falsy 때문에 값이 사라지지 않음 | `"0"`, `"false"`, `""`로 구분 |
| URL 인코딩된 한글·공백·`+`·`&`·따옴표 | 디코딩과 HTML 직렬화 단계 구분 | 실제 파싱된 값 일치 |
| 두 번째 파라미터에 잘못된 `%` 인코딩 | 부분 반영/제출 금지 | 제출 전 실패, 공유 제외 목록 오염 방지 |
| 중간 행 삭제 | 기존 인덱스 계약 | 삭제 행 생략, 뒤 행 번호 유지 |
| 메뉴 제출 함수가 예외 발생 | 폼 상태 복원 | 기존 target/action/이벤트 값 복원 후 오류 전달 |

읽을 코드: `framepost.html`, `sap_commobj.js`, `menu.js`. 읽을 근거: [validation.json](references/v3_evidence/validation.json)의 `framePOST*`, `serialization*`, `contextMenu*` 그룹 및 [markup_validation.json](references/v3_evidence/markup_validation.json).

모범 결론은 “모형에서 계약을 확인했다”이다. “SAP 서버가 같은 전표/업무 결과를 저장한다”는 결론은 실제 테스트 없이는 쓸 수 없다.

### 7.6 실습E — 기존 모의 회귀 증빙 재실행

**유형:** 과거 제공 스크립트의 재현 절차. **이번 자료 추출에서는 재실행하지 않았다.** 실행 가능한 환경과 결과를 학습자가 별도 기록한다.

선행 조건:

- 실습B의 별도 임시 폴더
- Node.js24·Python3. 기존 `analyze.js`는 Node 내부 Acorn 경로를 이용하므로 런타임이 달라지면 깨질 수 있음
- 검증 스크립트를 먼저 읽고 로컬 모델 작업임을 확인. ERP 서버/실제 계정 필요 없음

```sh
node --version
python3 --version
cd "$LAB_DIR"
node verify.js
python3 verify_markup.py
node integration.js
```

이 명령들은 **임시 폴더 안 검증 결과 JSON을 다시 쓴다**. 첨부 Evidence ZIP이나 원본 폴더에서 직접 실행하지 않는다. 별도 터미널에서는 LAB_DIR 값을 다시 지정해야 한다.

예상 결과는 저장된 기록과 비교한다: JS47,모의186건,HTML19,인라인30/이벤트66,직렬화7건,로드 순서/초기화5개 시나리오. 모형 결과가 같더라도 실제 Chrome 검증이라고 적지 않는다. 숫자가 달라지면 버전·런타임·수정 여부부터 확인한다. 내부 Acorn 경로 오류가 나면 임의 라이브러리 교체로 “같은 검사”라고 주장하지 말고 환경 차이를 기록한다. [S02/README·analyze.js]

### 7.7 실습F — 실제 Chrome·ERP 검증 계획 작성

**유형:** 미실행 운영 연계 과제. 테스트 ERP 접근 권한·테스트 데이터·배포 담당 승인 필요. 이 문서는 운영 반영을 지시하지 않는다.

1. 현재 서버 파일을 백업하고 ZIP/서버 Response의 경로·해시·변경 주석을 대조한다.
2. 대표 화면과 데이터,Chrome 버전·확대율·캐시 조건을 기록한다.
3. 최초 진입/반복 진입을 나누어 휠1회,화살표1회,길게 누르기,경계 이동을 각각 수행한다.
4. Doc와 Fetch/XHR를 모두 확인하고, 큰 업무 Doc와 menubase를 구분한다.
5. dropdown·메뉴·IME·커서·표/트리·팝업·iframe·저장/제출을 테스트 데이터로 확인한다.
6. 동일 조건을 여러 번 반복하여 요청 전 대기,요청/수신,스크립트,레이아웃/표시를 구분해 기록한다. 단일 표본으로 개선율을 발표하지 않는다.
7. 오류 시 실제 서버 백업으로 복원하고 게시·캐시 갱신 후 응답 내용을 다시 확인한다.

성능 비교에서 Disable cache 사용 여부를 동일하게 한다. 캐시 확인용 조작과 평상시 체감 측정을 혼동하지 않는다. 실습 결과 기록에는 **버전·환경·시나리오·예상/실제 값·증거·판정·미검증**을 남긴다. [S01 적용 절,S03 §8]

## 8. AI 협업 프롬프트와 판정 기준

[리뷰 프롬프트](examples/리뷰_프롬프트.md)는 이 교육자료를 위해 새로 작성했다. 역사적 프롬프트의 완전한 복사본이 아니다. 다음 원칙을 담았다.

- 현재 기준본·원본·변경분을 먼저 확인한다.
- 업무 값·동기 호출·이벤트 순서·배치를 우선 보존한다.
- 의도와 증거를 설명하고 요청되지 않은 운영 변경을 하지 않는다.
- 오류가 사라진 것과 기능이 정상인 것을 분리한다.
- 실제/모의/정적/미검증을 각각 보고한다.
- 불확실하면 해당 부분을 보존하고 독립적인 분석은 계속한다.

리뷰 합격 기준: 변경 이유가 구체적이고, 데이터 계약과 실패 복원 경로가 설명되며, 원본/복원본이 대응하고, 미확인 사실을 숨기지 않아야 한다. 코드가 생성되었거나 사용자가 답하지 않았다는 이유로 합격 처리하지 않는다.

## 9. 운영 중 갱신·유지보수 방법

다음은 교육자료 유지보수에 대한 **제안 절차**이며 이 대화에서 GitHub 운영으로 구현된 것은 아니다.

1. 새 원본/서버 버전을 받을 때 경로·취득일·크기·해시·출처를 기록한다. 실제 서버와 Drive 복사본을 구분한다.
2. 원본은 그대로 보관하고 새 변경 묶음에 기준 버전·변경 이유·테스트·복원 대상을 붙인다.
3. 01의 현재 상태·오류표와03의 보완표를 함께 갱신한다. “미확인→확인”에는 증거를 연결한다.
4. 테스트 결과를 이전 결과에 덮어쓰기보다 버전/환경별로 남긴다. 회귀 수치 단순 누적을 피한다.
5. 포털 콘텐츠와 원본 소스·검증 프로그램·이미지를 구분한다. 실제 ERP HTML은 교육 포털에서 자동 실행하지 않고 코드 자료로 취급한다.
6. 팀원의 경험을 추가할 때 재현 조건,증상,원인 확정 여부,조치,검증 환경을 함께 적는다.
7. 통합 저장소의 공개 범위·사내 소스 이용 권한·개인정보 검토를 완료한 뒤 별도 절차로 게시한다.

## 10. 실제 논의 기반 FAQ

### Q1. JS·CSS가 Network에 계속 뜨면 매번 다운로드하는가?

아니다. 당시 대부분 memory/disk cache였다. 상태 코드와 전송 크기·캐시 표시·Initiator를 함께 본다. 캐시여도 새 문서에서 초기화 비용은 남을 수 있다. [C04~C05]

### Q2. Fetch/XHR가 없으면 서버 요청도 없는가?

아니다. 이 사례에서는 Doc에 업무 POST가 있었다. 폼 제출과 프레임 문서 요청을 확인해야 한다. [C05]

### Q3.350/700ms는 호출의 반환값을 기다리는 시간인가?

확인한 코드는 요청 콜백을 실행하기 전 예약 지연이다. 고정 대기로 응답 완료를 보장하지 않는다. v3는 값 자체를 줄이지 않고 중복 예약을 수정했다. [C04,S01 성능 절]

### Q4. SYSTEMGUI도 최적화하면 일반 페이지처럼 부드러워지는가?

공통 함수·초기화의 일부 비용 감소는 기대할 수 있으나,POST와HTML 재구성 구조는 남는다. 실제 체감 개선율은 측정되지 않았다. [S03 §5/9,S01]

### Q5. 생성자가 미정의라면 파일이 빠진 것 아닌가?

가능한 원인 중 하나일 뿐이다. 이번 제공 ZIP에는 생성자가 있었다. 요청 실패·잘못된 본문·경로 대소문자·실행 순서·별도 iframe 컨텍스트를 확인해야 한다. 원래 업무 오류의 운영 원인은 미확정이다. [S04,S02-I]

### Q6. Chrome만 지원하면 레거시 코드를 전부 지워도 되는가?

아니다. 서버 생성 코드·부모 함수·필드명 등 기존 시스템 계약이 남아 있다. 브라우저 분기 변경과 업무 프로토콜 재설계는 별도다. [C08,S01]

### Q7. unload 경고는 모두 pagehide로 바꾸면 되는가?

이 프로젝트는 실패 초기화 객체 해제만 제한 변경했다. 세션·저장·종료 구현이 없는 경로까지 바꾸지 않았다. [S01 이전 오류 절]

### Q8.186건 통과했으면 운영 적용해도 되는가?

해당 모델의 통과 기록이다. 실제Chrome·IME·레이아웃·SAP처리·운영배포 검증을 대체하지 않는다. 승인된 테스트 환경에서 별도 수용 검증이 필요하다. [S02-V/S01]

## 11. 팀원이 혼동하기 쉬운 경계

| 혼동 | 올바른 구분 |
|---|---|
| 사용자 초기 확인=모든 후속 버전 검증 | 피드백이 적용된 버전과 시점에만 한정 |
| original=rollback=서버 백업 | 최초 제공본 / 작업 직전 기준본 / 실제 배포 백업 |
| CSS 바이트 보존=실제 배치 완전 동일 | UA·좌표 분기 변경도 배치에 영향을 줄 수 있어 화면 확인 필요 |
| ES3파싱=IE지원 / Chrome표본UA=운영버전 | 문법 검사와 실제 API·환경은 별개 |
| callback2회=실제POST2회 | 모델 콜백과 네트워크 관측 분리 |
| HTML19개=오류 업무 HTML 확보 | 정적 보조 페이지와 서버 생성 업무 문서 구분 |
| 새 교육 실습=과거 검증 완료 | 실습A는 이번 생성,실습E는 재실행 안내,실습F는 미실행 |
| 설계 제안=구현/운영 | 제안·결정·구현·검증·운영 상태를 따로 표시 |

교육 완료 확인: 학습자가 이 표의 구분을 자기 말로 설명하고, 실제 오류 하나에 대해 **다음에 필요한 최소 증거**를 요청할 수 있으면 이 모듈의 핵심 목표를 달성한 것이다.
