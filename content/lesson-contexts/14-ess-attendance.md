## 1. 이유: 휴가 하루를 바꾸는 일이 복잡한 취소 절차가 되지 않도록

여러 날의 휴가를 신청한 뒤 하루만 바꾸거나 취소하려는데 전체 기간을 다시 처리해야 한다면 신청자에게도 담당자에게도 부담입니다. 실제 요구에는 이런 부분 변경뿐 아니라 좁은 신청 이력창, 첨부 제약, 날짜 선택과 주말 처리, 다른 ESS 화면과의 디자인 통일이 함께 있었습니다. ESS는 직원이 직접 신청하고 확인하는 업무 화면을 뜻합니다.

목표는 **직원이 의도한 날짜와 반차 구분을 이해하기 쉽게 입력하고, 그 내용이 저장과 결재를 거쳐 실제 기록에도 일관되게 남는 것**입니다. 예쁜 달력이나 넓어진 창이 출발점일 수 있지만, 사용자의 휴가와 잔여 일수가 의도와 다르게 바뀌지 않아야 개선이 완성됩니다.

## 2. 실제 근거·시행착오: 화면의 상태와 결재자의 실제 목록이 달랐습니다

초기 AI 설명은 요구를 연차촉진 업무로 잘못 좁혔지만, 실제 자료를 받은 뒤 일반 근태 신청 화면의 개선으로 바로잡았습니다. 이후에도 V2와 R1 안내의 클래스명·페이지 위치가 현재 파일과 달라 사용자가 실제 소스를 다시 확인하게 했습니다. 이름이 비슷한 이전 자료로 다음 수정을 지시하면 다른 경로를 고칠 수 있었습니다.

또 신청자 이력에는 상신 상태가 보이는데 결재자의 목록에는 나타나지 않는 문제가 있었습니다. 날짜가 화면에서 바뀌고 저장 메시지가 나온 것만으로 결재 전달이나 실제 차감까지 성공했다고 볼 수 없었습니다. 이 문제를 통해 **선택한 값 → 저장된 상태 → 결재 전달 → 승인 후 실제 기록**을 따로 대조해야 한다는 점이 더욱 분명해졌습니다.

## 3. 방향 설정: 원래 화면과 이미 승인된 휴가를 비교 기준으로 남기기

사용자는 기존 `guntae_input.kbs`를 직접 바꾸는 대신 새 `guntae_input_r1.kbs`에 기능을 모으도록 요구했습니다. R1은 새 경로를 기존 화면과 나란히 확인하기 위한 구분입니다. 페이지뿐 아니라 실제 호출하는 클래스·달력·관리자 화면도 함께 맞춰야 기존 동작과 새 동작을 비교할 수 있습니다.

이미 승인된 휴가를 바꾸는 요청에서는 원래 승인 데이터와 새 변경 신청을 구분합니다. 저장·상신 단계와 최종 결재 뒤의 반영을 나누고, 날짜·사용량·잔여 일수를 함께 확인합니다. 주말 처리도 모든 근무형태와 휴가에 하나의 규칙을 적용하지 않고 해당 업무 조건을 확인하는 방향입니다.

## 4. 기술적 구현: 날짜 선택부터 잔여 일수까지 연결된 경로를 따라갑니다

BSP는 SAP에서 웹페이지를 구성하는 방식입니다. 화면이 보내는 요청을 ABAP 함수·클래스가 처리하고, 결재 작업과 실제 근태 데이터로 이어집니다. 이 프로젝트에서는 다음 구간을 대조하며 수정했습니다.

1. **신청 화면:** 날짜·반차·기간 분할·첨부·이력에서 사용자가 무엇을 선택했는지 확인합니다.
2. **저장 처리:** 새 R1 경로가 의도한 함수와 클래스를 호출하는지, 임시 저장과 상신 상태가 어떻게 남는지 확인합니다.
3. **결재 연결:** 신청 번호·결재 번호·결재자의 작업 항목이 연결되는지 추적합니다. 상신 표시만 보지 않고 실제 결재자 화면과 비교합니다.
4. **승인 뒤 대조:** 원래 휴가, 변경 신청, 실제 반영 날짜, 사용량과 잔여 일수를 함께 확인합니다.

아래의 기존 사례 1~5는 이 경로에서 실제로 겪은 문제들입니다. 날짜 이동·반차 변경에는 특정 성공 보고가 있고, 마지막 `SUBMIT_PRG01` 수정안 뒤의 재시험은 아직 확인되지 않았습니다. 화면·저장·결재를 나눈 설명을 바탕으로 각 사례의 확인 범위를 읽을 수 있습니다.
