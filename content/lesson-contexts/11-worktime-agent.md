## 1. 이유: 계산식만 알아서는 직원의 질문에 답하기 어렵습니다

근로시간 문의는 “몇 시간인가”에서 끝나지 않습니다. 같은 시간이라도 근무형태·휴가·적용 시점에 따라 설명이 달라지고, “왜 그렇게 처리하기로 했는가”라는 질문에는 담당자끼리 협의한 배경이 필요합니다. 코드에는 현재 계산 방법이, 매뉴얼에는 업무 기준이, 대화에는 예외와 정정 이유가 흩어져 있었습니다.

이 사례는 **담당자가 기억을 더듬어 자료를 찾던 일을, AI와 동료가 같은 근거를 따라 확인하는 일로 바꾸려는 시도**입니다. 처음부터 인사 업무 전체를 다루지 않고 ZHR5의 근로시간·시간외실비·대휴·정산에 범위를 두었습니다. 원하는 결과도 숫자 하나를 단정하는 답보다 적용 조건·이유·근거·남은 확인을 함께 제시하는 답입니다.

## 2. 실제 근거·시행착오: 코드에서 원인을 찾았어도 결론은 틀릴 수 있었습니다

실제 피드백에는 오전 반차를 사용한 시차근무자의 시간외실비가 0원으로 보인 사례가 남아 있습니다. AI는 계산 코드의 조건을 보고 반차 예외가 빠진 결함이라고 판단했습니다. 그러나 담당자는 이 사례의 입력이 실제 출근 시각부터가 아니라 원래 근무 시작 시각부터의 전체 구간이어야 한다고 정정했습니다. **화면에 시간을 어떻게 입력하기로 했는지 확인하기 전에 코드 수정부터 제안한 것**이 문제였습니다.

다른 기록에서는 누적시간 표시를 바꿨다가 되돌린 이유가 빠른 질의응답과 용어집에 충분히 연결되지 않았습니다. 현재 코드만 설명하면 “왜 다시 바꿨는가”를 놓칠 수 있었습니다. 이 경험 때문에 문서를 모으는 데서 멈추지 않고, 후속 정정과 당시 결정 이유를 찾아가는 길을 함께 관리하게 됐습니다. 두 사례는 `FB-20261001-001`, `FB-20261008-001`에 기록되어 있습니다.

## 3. 방향 설정: 업무 내용·일하는 순서·틀린 답의 기록을 나눕니다

업무 지식에는 무엇이 기준인지 적고, 스킬에는 어떤 순서로 근거를 읽고 답할지 적습니다. 업무지도는 질문에서 관련 문서와 코드 설명으로 가는 길을 제공하고, 피드백은 이전 답에서 무엇을 바로잡았는지 남깁니다. 정정한 질문은 다시 물어볼 사례로 연결합니다. 이렇게 나누면 규정 하나가 바뀔 때 AI의 작업 지침 전체를 다시 쓰는 부담을 줄일 수 있습니다.

기준은 “문서가 많으니 맞을 것”이 아니라 **어떤 자료의 어느 시점까지 확인했는지 설명할 수 있는가**입니다. 원문, 담당자의 설명, 완료 보고, 실제 코드 확인을 구분하고 자료가 없는 부분은 남겨 둡니다. 아래 지도는 이 관계를 탐색하기 위한 것이며, 연결선이 실제 SAP 실행이나 업무 승인 순서를 뜻하지는 않습니다.

## 4. 기술적 구현: 질문에서 근거를 찾고, 정정을 다음 질문에 연결합니다

실제 묶음은 다음 역할을 파일로 나누어 연결했습니다. MD는 사람이 읽고 고칠 수 있는 텍스트 문서입니다.

1. **질문을 좁힙니다.** 업무 질의 스킬이 근무형태·기준일·질문의 종류를 확인하고 `knowledge/INDEX.md`에서 읽을 문서를 찾습니다.
2. **설명과 근거를 연결합니다.** 업무 문서, 출처 등록부, 코드 연결 문서와 `maps/`의 링크를 따라가며 실제 확인한 내용과 후보 위치를 나눕니다.
3. **정정을 되돌려 넣습니다.** 피드백 기록을 만들고 해당 지식·색인·지도와 재검증 질문을 함께 갱신합니다. 업무 답변의 정정만으로 SAP 소스를 수정하지는 않습니다.
4. **동료가 탐색할 수 있게 보여줍니다.** 이 포털은 특정 커밋의 783개 MD를 보존하고 문서 관계, 본문 읽기와 원본 다운로드를 제공합니다.

아래에서 기존 문서 지도와 따라 하기 예제로 이 흐름을 확인할 수 있습니다. 확보된 질문 목록·문서 검사와 독립적인 답변 평가·SAP 실행 검증은 서로 다른 확인 단계입니다.
