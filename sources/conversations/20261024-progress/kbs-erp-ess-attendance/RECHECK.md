## 학습 맥락

1. **사용자 화면 요구와 실제 업무 처리 범위를 맞춘다.** 날짜별 선택·제외, 반차, 승인 건의 부분 변경·취소 요구를 미리보기로 구체화하고, BSP 화면뿐 아니라 저장 함수·워크플로·승인 반영 코드를 확인한다. 기존 ESS 01–06 에피소드.
2. **기존 페이지 수정과 R1 개편을 분리한다.** 안내 문구/HWP 변경과 신규 기능 개발이 섞였을 때 사용자가 범위를 바로잡는다. 이후 파일 위치, SE80 이벤트, 적용 순서를 실제 작업자 수준으로 상세화한다. 기존 ESS 07–09 에피소드.
3. **자료 인계 이후 저장 건부터 검증한다.** R1 자료와 실제 SAP 소스를 대조하며 저장 상태 수정·상신·승인 흐름을 확인한다. 원본 INCLUDE를 R1 전용이라고 잘못 가정한 안내는 실제 화면으로 정정한다. 반차의 화면 일수1과 연차 차감0.5를 구분한다. 기존 ESS 10–17 에피소드와 ESS3 105–109번째 턴.
4. **기승인 변경과 원래 데이터를 연결한다.** 저장 메타데이터, 결재 번호, DOCNR·SEQNR, META_ONLY·SYNC_OK를 보며 대기 중 원래 휴가 보존과 승인 이후 실제 변경을 확인한다. 기존 ESS 18–23 에피소드.
5. **사용자 실행 결과를 구체적 시나리오로 남긴다.** 전일→오전반차 변경 후 잔여0.5 표시, 날짜 이동 후 승인 재개 등 사용자가 확인한 범위를 읽는다. 모든 휴가 종류·부분취소·동시처리의 전체 검증으로 확장하지 않는다. 기존 ESS 23–24 에피소드.
6. **상신 성공 이후의 사용자 흐름도 검증한다.** 새로고침·뒤로가기로 POST가 재제출되는 관찰을 TOKEN_STOP·SUBMIT_ONCE01과 대조한다. 마지막 SUBMIT_PRG01은 처리 후 GET 화면 이동과 진단 기록 접기를 제시했으나, 그 뒤 사용자의 적용 후 재시험은 이 공유 대화에 없다. 기존 ESS 25–26 에피소드.

## 보존·변환 파일

- `captures/ess-1.json` … `ess-4.json`: 현재 UI DOM 원본. 임시 signed URL이 있으므로 그대로 게시하지 않는다.
- `ess-normalized/ess-1.json` … `ess-4.json`: 실제 platform turn ID와 구본 순서를 대응시켜 unit 식별자만 0-based 순서로 정규화한 변환 입력.
- `ess-parsed/ess-1.json` … `ess-4.json`, 같은 이름의 MD: 현재 전체 가시 본문. signed query 제거.
- `ess-baseline-normalized`, `ess-baseline-parsed`: 구본 HTML을 같은 변환기로 읽은 비교용 자료.
- `ess-capture-identity.json`: 원본 키↔platform turn ID↔0-based 순서 대응.
- `ess-verification-report.json`: 254턴·245 AI ID·499 본문 일치 검증, 미표시 위치, 이미지 수.

## 기존 이미지 보존 주의

현재 공유 UI는 과거에 인라인으로 보였던 이미지23개를 파일카드만 표시한다. 따라서 현재 captures/ess-parsed로 기존 소스·원문·첨부를 덮어쓰면 안 된다. 기존 이미지와 자산 연결은 그대로 유지하고, 새롭게 확보한 바이트/다운로드 링크만 보강한다. 해당 위치는 `ess-verification-report.json`의 `known_rendering_differences`에 기록했다. 이미지 복구 담당에게 전달했다.

이번 수집의 HTML-to-Markdown 변환은 표204개와 코드블록3개를 확인했다. 구본은 같은 본문에서 코드블록5개이며 차이2개는 코드펜스가 인라인 코드로 표시된 UI 형식 차이다. 코드 내용의 문자 변경은 없다. 기존 교육 원문 파일을 기준으로 유지하면 이 표시 차이를 추가로 도입할 필요가 없다.
