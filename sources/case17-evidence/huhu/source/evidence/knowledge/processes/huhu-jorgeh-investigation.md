# 휴휴 대휴 JORGEH 반복 보정 원인 검토

## 요청과 확인 상태

SRC-25: 2026-10-31 사용자 운영 설명. 인사 담당자가 반기마다 휴휴 대휴의 보정 금액을 전달하고 IT 담당자는 원인이 확인되지 않은 상태에서 ZTHRBS01-JORGEH를 수동 보정한다. 업무 의도는 **휴휴는 입력·저장 때 정산금액을 사전 계산하고, 그 외 일반 대휴는 정산 메뉴에서 ZD_MONEY×2로 계산**하는 것이다. 이는 신규 정책 시행 또는 코드 변경 승인이 아니다.

같은 날 후속 설명: 문제 금액은 반기 정산 확정 **몇 달 전부터 이미 다르다**. 따라서 이번 현상의 우선 조사 범위는 최초 입력·수정 저장과 임시 금액 전달이다. H05 확정/취소 문제는 별도 문제로 유지하되, 이 선행 오차의 원인으로 설명하지 않는다. 최초 저장부터 틀렸는지 이후 변경 저장에서 틀렸는지는 아직 미확인이다. 아래 후보의 성립 조건은 [후속 피드백](../../harness/feedback/FB-20261031-002.md)에 따라 보완했다.

앞선 답변에서 발견한 두 지점(스칼라 덮어쓰기, 대휴 1개에서 시작일 금액만 회수)을 확대 추적했다. 선택근무의 별도 생성 경로가 존재한다는 사실을 이유로 사용자가 설명한 사전 계산·수동 보정 업무를 부정하지 않는다. 이 문서의 주요 오류 후보는 실제 NORM 입력 경로와 공통 반기 정산의 코드다. 선택 생성분 ZSOURFLEX=S와 해당 입력 경로의 개별 연결은 운영 행으로 별도 확인한다.

근거는 SRC-17(2026-10-22 KSP/300)의 현재 로컬 작업본이다. F03의 SRC-18 변경은 근태 검사에 한정되며 이번 JORGEH 분석 구간은 수정하지 않았다. **정적 구문 확인 + 조건부 Python 모형**이며 SAP 구문 검사·실행·운영 재현·지급 대사는 NOT_RUN이다. 원본 ABAP/DDIC와 SAP 데이터는 수정하지 않았다.

## 선택 입력 경로 대조에 따른 적용 범위 정정 — 2026-10-31

**확인한 선택 실적 입력·대휴 생성 경로에는 H02/H03의 8+2 분할 원인을 적용하지 않는다.** 앞선 공통 함수의 조건부 위험 설명을 선택 휴휴의 원인처럼 연결한 부분을 정정한다. 아래 H01–H08의 NORM/SAVE 후보는 통상·교대 시간외 입력 경로의 정적 분석이며, 보정 대상 선택 건과의 연결 확인을 대신하지 않는다. 사용자 운영 설명을 부정하거나 SAP 반영 버전 차이를 확정한 것은 아니다. [피드백 FB-20261031-003](../../harness/feedback/FB-20261031-003.md).

- **ZGUBUN=A는 입력구분 ‘통상근무’.** [입력구분 도메인][GUBUN-DDIC] L70–120: A 통상근무, B 시차근무, C 교대근무, D 당번특근, T 해외출장. 선택근무의 근로유형은 별도 Z52WKTP=0110이다([선택 화면 구조][CW-DDIC] L327–366). ‘선택근무자이므로 ZGUBUN=A’라는 일괄 대응은 성립하지 않는다.
- 선택 화면 구조 ZSHR0141에는 ZGUBUN 필드가 없다. [CW-F02] L385–401은 로컬 일일 계산 구조로 MOVE-CORRESPONDING한 뒤 시차 대상일 때만 ZGUBUN=B를 넣는다. 이 호출 시점의 일반 선택은 초기값, 시차 대상은 B이며 **보정 대상 BS01 저장 행의 ZGUBUN 전수 실측값이라는 뜻은 아니다.**
- [CW-SET-ITEM] L47–51→[CW-F02] L414–424는 DAILY에 I_OPT를 전달하지 않는다(L417은 주석). [CW-F03] L1278–1284의 익일 당번 분리도 동일하다. [CW-CAL] L1075–1079/L1354–1358과 [CW-F04] L639–643/L902–906의 대휴 계산 호출도 I_OPT를 생략한다. DAILY 인터페이스의 I_OPT는 OPTIONAL이며 기본값 X가 없다. DAILY L516의 `CHECK i_opt = 'X'`에서 이후 처리를 종료하므로 L555의 기준시간 조회와 L744–819의 정상/초과 분할까지 도달하지 않는다. 날짜 경계 분리·휴게 계산은 앞 구간에서 수행한다.
- 선택의 휴일 시간은 [CW-F02] L453–458에서 날짜별 실근로시간을 휴일시간에 더한다. 선택기간 소정 미충족분의 충당/제외는 [CW-F04] L647 이후의 별도 처리이며 일일8시간 분할과 혼동하지 않는다.
- **휴일8시간이 평일 정상근무라는 업무 의미는 아니다.** I_OPT=X인 별도 시간외 경로에서도 비C 휴일은 DAILY L840–842에서 두 구간 모두 REGTP=M/TMTYP=H로 재분류한다. ZTHR0101의 ZNORHR/ZTRPHR는 일반/해외출장의 유효기간별 기준시간이며 공통 평일 정상/초과 구분 등에 쓰인다. ‘휴일을 반드시8+2로 나누어야 하는 승인 정책’은 확인하지 못했다. D/T/B 휴일에서 분할이 남는 것은 A/휴일만 제외하는 구현상의 사실이며, 설계 의도·필수성은 별도 확인이다.
- **ZTOMO는 익일여부**([CW-DDIC] L723–766). DAILY L115–160에서 다음 날짜와 자정 구간을 만든다. 평평·평휴·휴평·휴휴 모두 가능하며 휴휴 표시 또는 익휴 ZTOMOH와 구별한다.
- 선택의 BS01 생성 [CW-SAVE] L1197–1301은 ZSOURFLEX=S, ZD_MONEY=대휴시간×단가×0.5를 설정하고 INSERT한다. 해당 FORM에서 ZGUBUN=A/휴휴 JORGEH를 직접 설정하거나 NORM/SAVE를 호출하는 구문은 확인되지 않는다. 인사정보 MOVE-CORRESPONDING과 미추출 구조가 있으므로 ZGUBUN이 모든 운영 행에서 공란이라고 단정하지 않는다. 앞선 ‘웹 저장에서 비휴휴 JORGEH 대입’은 F06/MOBILE의 시간외 웹 경로에 한정하며 선택 실적 웹으로 일반화하지 않는다.

남은 확인은 인사부 보정 대상의 실제 생성·수정 경로 및 ZGUBUN/ZSOURFLEX/원천 실적 연결이다. 현재 추출본의 선택 경로와 사용자 설명의 입력 시 JORGEH 사전 저장 사이의 연결은 미확인이다. 후보를 유지하려고 모든 선택 건이 시간외 NORM 경로를 탄다고 가정하지 않는다.

## 금액 전달 경로

이 절의 F03/F05/F06/SAVE/MOBILE은 **ZHR008_2 시간외 경로**다. 위 선택 경로 대조 결과를 먼저 적용한다.

1. [NORM] L95–100, L123–135, L259–350: 계산 행별 시간·대휴표시를 보고 ZDAEHAMT(입력 당시 실비)와 ZJORGEHAMT(추가 정산분)를 계산한다.
2. [F03] L5754–5781: 계산 행을 구성하고 NORM 호출. 익일 표시 X이면 ZHRDAEHUAMT에 사번·계산날짜별 금액을 MODIFY한다. L5849–5850/L5918은 별도로 마지막 행의 정산액을 출력 구조에 넣는다.
3. [SAVE] L62–83: 입력 구조를 상속하고 재계산 결과를 복사한다. 이 복사 목록에는 JORGEH가 없다. L152–170/174–212에서 대휴 그룹 수에 따라 임시 테이블의 날짜별 금액을 읽는다.
4. [F06] L1026–1063은 웹 저장 전 계산에서 JORGEH를 입력 구조에 복사한다. [ADMIN] L434–480의 명시적 결과 복사에는 JORGEH가 없다. 따라서 모든 호출 경로가 동일한 값을 전달한다고 가정하면 안 된다.
5. [SETTLE] L230–246은 JORGEH가 있으면 그 값, 없으면 일반 대상의 ZD_MONEY×2로 정렬한다. L504–549에서 사용 개수를 반영하고, L1460–1468에서 결과를 JORGEH에 저장한다.
6. [SETTLE] L1658–1664의 확정취소는 JORGEH_TXT만 지우고 금액은 그대로 둔다.

## 우선 조사할 후보

금액 예시의 U는 해당 입력에 적용된 시간외 단가다. 시간은 휴게 반영 후 값이며, 단가 변경·금액 저장 단위·특별한 지급 제외 조건은 모형에 포함하지 않았다. 예시의 금액은 운영 실측값이 아니다.

### H01. 대휴 1개의 발생 방식과 관계없이 RDATE 금액 하나만 회수

- 위치: [SAVE] L152–170. ZDDAY는 발생일로 설정하지만 임시 금액 조회는 `DATUM = RDATE`이다.
- 합산형 3+2시간: NORM 결과는 첫날 3U, 둘째날 2U. 한 대휴에 필요한 금액은 5U인데 시작일 3U만 회수한다. 둘째날 2U는 남는다.
- 익일만 발생하는 2+6시간: 첫날 사전 정산액은 0, 익일은 6U. RDATE로 첫날 0을 읽으면 정산에서 ZD_MONEY×2로 대체한다. 이 예시의 입력 실비는 2×1.5U+6×0.5U=6U이므로 추가 정산이 12U로 과다 계산될 수 있다(기대 6U).
- 반례: 첫날만 발생하는 6+2는 시작일 6U 회수가 맞는다. 같은 휴휴라고 일괄 합산하거나 조회일만 ZDDAY로 바꾸면 합산형 문제가 남는다.
- 수준: 분기·조회 키 확인, M01–M03/M12 조건부 모형. 특정 운영 건 재현 필요.

### H02. 같은 날짜 계산 행을 임시 테이블에서 합산하지 않고 덮어씀

- 적용 범위 정정: 확인한 선택 CW 경로는 I_OPT가 초기값이므로 이 분할 후보에서 제외한다. 아래는 I_OPT=X인 시간외 경로의 조건부 위험이다.
- 입력구분별로 A=통상근무, D=당번특근, T=해외출장, B=시차근무다([GUBUN-DDIC] L70–120). A의 **휴일 행**은 분할을 건너뛰지만 A 평일까지 분할하지 않는다는 뜻은 아니다. D/T/B는 이 휴일 제외 조건에 해당하지 않아 기준시간·누계·I_NGT 등 나머지 조건에 따라 분할될 수 있다. D/B는 ZNORHR, T는 ZTRPHR를 읽으므로 모두 고정8+2라고 일반화하지 않는다. 분할 대상이라는 사실과 JORGEH 오산 확정도 구별한다.
- 위치: [F03] L5775–5781, [TEMP-DDIC] L62–132. 테이블 키는 PERNR/DATUM이며 SEQNR·입력 시작일·요청 식별자가 없다.
- 서로 다른 날짜는 서로 다른 키다. `토8, 일6` 두 행만 있으면 이 MODIFY 때문에 일요일이 토요일을 덮어쓰지 않는다. 같은 날짜의 계산 행이 둘 이상일 때의 문제다.
- [DAILY] L516의 I_OPT=X, 기준시간 조회 성공(L550–561), 분할 대상 유형·시간 조건을 거친 경우 L744–819에서 하루를 필수/초과 구간으로 나누어 추가 행을 APPEND한다. **ZGUBUN=A이고 DAYS=0인 휴일은 L580–581에서 이 분할을 건너뛴다.** NORM 주석 L281–283도 당번특근 10=8+2, 해외출장 11=9+2 및 시차 분할을 설명한다. 일반 휴휴 전체에 동일 날짜 복수 행을 가정하지 않는다.
- 같은 날인데도 나누는 이유는 DAILY가 날짜 분리뿐 아니라 정상근무/초과근로 계산 구간 분리도 담당하기 때문이다. L744–757에서 기존 행을 REGTP=N과 앞 구간 시간으로 수정하고, L762–819에서 같은 DATUM을 유지한 채 뒤 구간을 REGTP=M으로 APPEND한다. 이는 내부 계산 행이며 ZTHRBS01에 같은 날짜 신청이 두 개 저장됐다는 뜻이 아니다. 비C 휴일은 이후 L833–875에서 각 행을 REGTP=M/TMTYP=H로 다시 분류하지만, 두 계산 행을 합치지는 않는다. 따라서 당번특근 등에서 휴일 표시가 같아도 앞 단계의 분할 행은 남을 수 있다. 실제 8시간은 고정값이 아니라 운영 상수 확인이 필요하다.
- 예: 첫날 10시간이 8시간/2시간, 둘째날 6시간이면 첫날 금액을 8U 기록한 뒤 2U로 덮어쓴다. 필요한 첫날 합계는 10U다. 금액 보존식 `일자별 입력 행 합계 = 일자별 임시 저장액`이 깨진다.
- H03 때문에 실제 저장은 2일 분기 자체를 벗어날 수도 있다. **10U→2U는 임시 저장 단계의 결함 후보**이며 모든 최종 BS01이 반드시 2U라는 뜻은 아니다.
- 수준: DDIC/쓰기 구문 확인, M05 모형. 실제 LT_RESULT 행 구성과 순서 확인 필요.

### H03. 날짜별 정렬 없이 인접 그룹 수를 세어 2일이 3건으로 처리될 수 있음

- 적용 범위 정정: H02의 같은 날짜 추가 분할에 따른 이 후보는 확인한 선택 CW 경로에 적용하지 않는다.
- 위치: [DAILY] L578–580, L744–819; [F03] L5754–5764/L5845–5860; [SAVE] L119–174/L284–290.
- DAILY는 H02의 분할 조건을 충족하면 원래 첫날·둘째날 뒤에 첫날의 초과 구간을 APPEND할 수 있다. 예시는 **토10+일6=16시간**을 `토8, 일6, 토2`로 나눈 것이다. 토2는 이미 토10에 포함된 시간이며 새로 발생한 시간이 아니다.
- 사용자의 **토8+일6=14시간** 예시와 구별한다. 일별 기준8시간·I_NGT=Y로 매일 누계 초기화(L588–590) 조건이면 어느 날도 기준을 넘지 않아 이 이유로 세 번째 행이 생기지 않는다. ZGUBUN=A/DAYS=0이면 시간 크기와 관계없이 위 기준시간 분할을 건너뛴다. 기준시간은 ZTHR0101에서 읽으므로 실제 운영 설정을 일괄8시간으로 확정하지 않는다.
- F03은 이 순서대로 상세에 넣고, 대휴표시 X와 LV_NGT=Y 조건이 겹치면 같은 행을 두 번 APPEND한다. 두 번 넣는 것만으로 두 대휴가 생긴다고 단정하지 않는다.
- SAVE는 정렬 없이 `AT END OF DATUM`으로 묶으므로 `토, 토, 일, 일, 토, 토`를 3개 인접 그룹으로 본다. `LINES=2` 분기에 진입하지 못하고 일반 ELSE로 갈 수 있다.
- 결과 후보: 양일 분할/날짜별 JORGEH 회수를 건너뛰고 원래 한 행을 저장. 대휴 개수와 금액이 함께 틀어질 수 있다.

### H05. 확정 때 사전 금액을 0으로 없애고, 취소 후 ×2가 되살아남

[GET-DATA] L22–23/L61–81은 이미 T_ZDAEH(ZSHR0121)와 ES_OVERTIME_DATA를 반환한다. [RESULT-DDIC] L3099의 ZJORGEHAMT는 상세 행의 계산 금액이다. [SAVE] L40–59는 두 결과를 모두 받고 있다. 이번 추출범위에서 T_ZDAEH를 명시적으로 받는 실제 호출부는 SAVE에서 확인했다. 기존 전체 금액과 상세 금액을 함께 사용하면 새 함수·DDIC·함수 매개변수 없이 구성할 수 있다. RFC 외부 소비자까지 조회한 것은 아니다.

T_ZDAEH를 **현재 상태 그대로 전부 합산할 수 없다는 앞선 판단은 유지**한다. F03에서 같은 원행의 중복 APPEND를 없애고, 전체 금액은 필터링 전 LT_RESULT에서 별도로 합산하면 기존 반환값을 사용할 수 있다. 대휴1개에서 상세에 빠진 다른 날짜 기여분은 전체 합계로 보존하고, 대휴2개는 각 발생일에 속한 상세를 날짜별로 합산한다.

### 수정하지 않아도 되는 연결부

- GET_OVERTIME_DATA: 기존 TABLES 전달과 ES 반환을 그대로 사용하므로 본문/인터페이스 변경 불필요한 안이다.

- DAILY, NORM, ZRPTH415F01, 선택 CW, DB 테이블 정의는 변경 대상에서 제외한다. ZHRDAEHUAMT의 기존 행을 일괄 삭제하지 않아도 이 전달 경로에서 읽지 않으면 신규 계산에 혼입되지 않는다. 다른 패키지 소비자 여부는 별도 확인 사항이다.

실제 구현 논리 단위는 **F03와 SAVE 두 곳**이다. 로컬 추출에는 SAVE 본문과 LZHR008_2U39가 바이트 동일한 중복으로 존재함을 확인했다. 향후 로컬 반영 시 두 사본을 동일 패치로 관리한다면 ABAP 파일은 F03+SAVE 본문+U39의3개다. 새 독립 로직3개가 아니다. 변경 전 사본/패치/전후 해시를 exports 밖에 남기고 manifest·로그·baseline은 유지한다. 함수 인터페이스 변경은 없으므로 Tables.xml 수정도 필요하지 않은 안이다.

## 앞선 두 의심 지점의 해석 보완

F03 L5850의 스칼라 덮어쓰기는 존재하지만, 그것을 `합계 +=`로만 고치면 해결된다는 제안은 하지 않는다. M12처럼 스칼라가 마지막 0이어도 날짜별 임시 조회가 정상 금액을 공급하는 경우가 있다. 반대로 임시 저장 자체가 H02로 훼손되면 스칼라 합계 수정으로 해결되지 않는다. **신청 전체, 역일, 발생 대휴별 금액의 귀속을 각각 보존**해야 한다.

X/Y만으로 오류를 단정하지 않았다. [MOBILE] L49–58에서 상신 시 Y→X 정규화, [ADMIN] L1287 등에서도 정규화가 확인된다. 저장의 Y와 계산의 X가 다르다는 이유만으로 현재 오류의 원인으로 채택하지 않는다. 단가 시작일 적용, 기존 ×100/÷100도 그 자체를 오류로 분류하지 않았다(SRC-23 후속 금액 단위 정정 주의).
