- 정리 기준일: **2026-10-08**

- 교육 상태: 확인된 자료로 만든 초안. **최신 SAP 실행·현재 Codex 설치 화면·전체 운영 절차는 추가 검증 필요**.

## 1. 교육 대상·사전 지식·학습 목표

### 1.1 대상과 준비 수준

KBS ERP 업무 담당자, ABAP 개발자, 업무 지식을 관리하는 팀원, 패키지 에이전트 구축 담당자가 대상이다. SAP 패키지/프로그램의 기본 개념, 폴더·ZIP·텍스트 파일, Git 저장소의 기초를 알면 진행할 수 있다. 심화 실습의 SAP 조회·프로그램 설치에는 별도 개발 권한이 필요하다.

교육은 다음 순서로 구성한다. 대화 발생 순서와 다르게, 먼저 역할과 한계를 이해한 뒤 파일·비교·진단·업무 지식으로 들어간다.

| 학습 단위 | 할 수 있게 되는 일 | 실습 조건 |
|---|---|---|
| 1. 전체 역할 | Export·CHECK·DIAG·에이전트의 역할을 구분 | MD만 있으면 가능 |
| 2. 추출물 읽기 | 함수·BSP·DDIC·MIME·원본 경로를 해석 | 실제 패키지 ZIP은 별도 준비 |
| 3. 세 자료 비교 | 신규/누락/수정/변경없음을 방향대로 해석 | 제공 JSON 예시로 가능 |
| 4. 실제 결과 해석 | XML/함수/미수행 사례를 근거로 판단 | 제공 Excel로 가능 |
| 5. SAP DIAG 사용 | 입력·필터·상세·JSON을 점검 | 승인된 개발 SAP, 최신 도구 검증 필요 |
| 6. 업무 지식·스킬 | 코드와 정책·협의를 분리하고 연결 | 제공 가이드·스킬로 설계 가능 |
| 7. 피드백 회귀 | 오답을 검증 가능한 사례로 남김 | 업무 담당자 근거·승인 필요 |

### 1.2 학습 후 기대 결과

학습자는 “무엇을 추출하지 못했는가”, “어느 쪽이 바뀌었는가”, “자료를 읽은 것인가 활성 근거를 확인한 것인가”, “어떤 문서가 현재 정책 근거인가”를 구분하여 설명할 수 있어야 한다. 자동 SAP 반영을 수행하는 능력은 이 교육의 목표가 아니다.

## 2. 왜 이 구조가 필요한가

### 2.1 실제 업무 문제

ZHR5 담당자가 시간외·근로시간 질문을 받았다고 가정하면, ABAP은 현재 구현을 보여주지만 정책 시행일과 담당자 합의까지 모두 담고 있지 않을 수 있다. 반대로 카카오톡 한 문장은 당시의 문의나 제안일 수 있어 현행 규정으로 적용하기 어렵다. 이 프로젝트는 코드와 업무 지식의 근거를 연결하려고 시작했다. 이 문장은 구조 설명용 상황이며 특정 정책 답변을 새로 확정하는 예시가 아니다.

추출물 검토에서도 문제가 있었다. 함수 속성 XML을 보고 변경이 많다고 느꼈지만 실제로는 공통 프로그램 메타데이터 변경이 반복될 수 있었다. 함수 소스의 세 비교가 같아도 API와 활성 Include의 확인은 별도로 실패할 수 있었다. 상태를 하나로 줄이면 담당자는 무엇을 믿어야 하는지 알 수 없었다. [실제 결과 분석 §10](01_프로젝트_맥락과설계.md), [결과 Excel](attachments/results/ZHR5_result_uploaded_20261007.xlsx)

### 2.2 전체 ERP AI 구조에서 맡는 역할

이 프로젝트는 **자료 공급·검증 의미·업무 지식 운영 기준**을 제공한다. ERP MCP, 전사 오케스트레이터, 웹 포털·서버·Obsidian은 여기서 구축된 것으로 설명하지 않는다. 연결 구조는 [설계 문서 §4·15](01_프로젝트_맥락과설계.md)를 사용한다.

## 4. 학습 1 — 추출물의 구조와 제한 읽기

### 4.1 핵심 설명

파일명은 SE80에서 찾는 탭·객체와 대응하도록 바뀌었다. 함수마다 `Source code`를 두고, BSP는 Properties/Layout/Event Handler/Page Attributes/Type Definitions를 구분한다. DDIC 구조와 DB 테이블을 분리하고 독립 MIME은 유형별로 묶었다.

아래는 경로 읽기 예이며, 이번 교육 ZIP 안에 해당 업무 패키지의 실제 본문이 모두 있는 것은 아니다.

| 교육용 경로 예 | 확인할 내용 |
|---|---|
| `packages/ZHR5/function-groups/FUGR/<그룹>/Function Module/<함수>/Source code/<함수>.abap` | 함수 본문과 해당 함수의 탭 XML 연결 |
| `packages/ZHR5/Dictionary Object/Structures/<구조>/definition.xml` | 필드·타입 정의, 업무 테이블 데이터 아님 |
| `packages/ZMM6/BSP Application/WAPA/ZPCM0001/pages/<페이지>/Properties.xml` | 페이지 속성, 실제 Layout과 구별 |
| `.../Event Handler/OnInitialization.abap` | 식별된 이벤트 소스. 없는 이벤트를 임의 생성하지 않음 |
| `packages/ZWEB/MIME/image/png/<파일>.png` | 바이너리 본문, metadata에서 식별자·URL 확인 |
| `.devhub/baseline/packages/...` | 추출 시점 원문 사본 |

### 4.2 따라 하기: 실제 추출물 구조 점검

**준비물:** 별도로 준비한 승인된 패키지 추출 ZIP, Export 버전 정보. 이번 교육 자료 ZIP은 대신 사용할 수 없다.

1. 별도 작업 폴더에 압축을 푼다. `manifest.xml` 위치와 대응 `packages`, `catalog`, `.devhub/baseline`을 확인한다.
2. macOS Finder에서 숨긴 폴더가 보이지 않더라도 `.devhub/baseline`이 없는 것으로 단정하지 않는다.
3. [CHECK HTML](attachments/tools/DEVHUB_CHECK_0_3_3.html)을 로컬에서 연다. 입력 폴더는 `manifest.xml`이 바로 아래 있는 폴더를 고른다.
4. 동일·변경·파일 실패·SAP 실패·생략·참고 로그·웹 구성요소를 각각 기록한다.
5. 함수 한 개와 BSP 페이지 한 개의 폴더가 SAP 객체와 어떻게 대응하는지 적는다.
6. 실제 업무 파일을 고치더라도 baseline은 보존한다. 원본 변경 시험은 복사된 실습 자료에서만 한다.

**예상 결과:** 파일 무결성 점검과 범위/생략 해석을 분리한 점검 메모가 나온다. “파일 실패 0”만으로 모든 SAP 객체가 포함됐다고 결론 내리지 않는다.

**자주 하는 실수:** 폴더 한 단계 위를 선택함, 숨긴 baseline을 재압축에서 빠뜨림, 버전 간 파일 수 차이를 손실로 단정함, 클래스명이 보인다는 이유로 클래스 본문도 포함됐다고 생각함.

**검증 상태:** 과거 CHECK 사용 결과는 존재하지만 이번 자료 추출에서는 실제 패키지 ZIP으로 브라우저를 재실행하지 않았다. [ZWEB 과거 검토](references/DEVHUB_ZWEB_0_3_17_REVIEW.md)

## 5. 학습 2 — 비교 방향을 정확히 판단하기

### 5.1 핵심 설명

각 비교는 “기준 → 대상”이다. 세 번째 열은 **SAP → 추출본**이므로 다른 두 열과 기준이 다르다.

| 원본 | 추출본 | SAP | 추출본/원본 | SAP/원본 | 추출본/SAP |
|---|---|---|---|---|---|
| A | A | A | 변경없음 | 변경없음 | 변경없음 |
| A | B | A | 수정 | 변경없음 | 수정 |
| A | A | B | 변경없음 | 수정 | 수정 |
| A | B | B | 수정 | 수정 | 변경없음 |
| A | B | C | 수정 | 수정 | 수정 |
| 없음 확인 | 없음 확인 | A | 판정 없음 | 신규 | 누락 |
| A | 없음 확인 | A | 누락 | 변경없음 | 누락 |
| A | A | 읽기 실패 | 변경없음 | 미확인 | 미확인 |

이는 **합성 교육 예시**다. A/B/C는 값의 기호이며 과거 프로그램의 ABC 모드 명칭이 아니다. 마지막 두 행을 모두 삭제/누락으로 처리하지 않는 이유를 설명할 수 있어야 한다.

### 5.2 따라 하기: 로컬 비교 사례 실행

**준비물:** Python 3가 설치된 로컬 환경. 미설치 환경이면 표만 읽어도 된다. 설치 작업은 이 실습 범위가 아니다.

교육 ZIP 최상위 폴더에서 다음을 실행한다.

```bash
python3 examples/compare_cases.py
```

[스크립트](examples/compare_cases.py)는 [합성 입력](examples/three_way_cases.json)의 바이트와 존재 상태만 비교한다. SAP에 연결하거나 원본 파일을 수정하지 않는다. 전체 DIAG 구현을 대체하는 코드가 아니다.

**예상 결과:** 모든 합성 사례에 `PASS`, 마지막에 통과 수가 출력된다. 0바이트 본문과 부재, 읽기 실패와 부재를 다르게 처리하는지 확인한다. 이 PASS는 합성 비교 실습의 통과이며 SAP 호환 검사 통과가 아니다.

### 5.3 기술 상세

같은 크기는 같은 내용이 아니다. `AA`와 `BB`는 둘 다 UTF-8 2 bytes지만 값은 다르다. XML에서 값·들여쓰기·BOM·개행 등이 바뀌면 바이트 차이가 생길 수 있다. 상세 구조 비교에서 어떤 차이인지 분류한 뒤 업무 영향까지 판단한다.

## 6. 학습 3 — 실제 ZHR5 Excel로 진단을 해석하기

### 6.1 준비와 기본 작업

**준비물:** [실제 결과 Excel](attachments/results/ZHR5_result_uploaded_20261007.xlsx). 원본을 수정하지 않고 읽는다.

1. `RawData` 시트를 선택한다. 헤더 포함 2,542행, 데이터 2,541행인지 확인한다.
2. E/F/G는 세 비교, H/I는 SAP 조회 결과·설명, J/K는 활성 확인·설명, L은 문법형식이다.
3. `Format`, `Header` 같은 표시용 시트를 중복 합산하지 않는다.
4. 설명이 잘린 경우 원래 문장을 지어내지 말고 최신 JSON·상세 화면을 요청한다.
5. 다음 세 사례를 확인한다. 현재 DIAG 최신 버전의 결과로 표시하지 않는다.

### 6.2 실제 사례 A — 크기는 같은데 XML이 수정

- **문제:** `Attributes.xml`의 bytes는 같아 보이는데 수정이라고 나온다.
- **입력:** `RawData` 1440행, 함수 `ZHR_52TM_GET_SHIFT_OT_DATA`.
- **작업:** E/F/G, P/Q/R을 함께 읽는다.
- **관찰 결과:** 추출본/원본은 변경없음, SAP/원본과 추출본/SAP는 수정. 세 크기는 모두 **3,210 bytes**.
- **검증:** 용량 비교만 했다면 구별하지 못할 사례다. 다만 어떤 XML 필드가 바뀌었는지는 Excel만으로 확정할 수 없다. 원본·추출본·SAP XML 또는 최신 상세를 확보한다.
- **추가 학습:** 함수 속성 변경과 공통 프로그램/그룹 메타데이터 변경을 구분한다. 공통 필드라고 없애면 추적 근거를 잃을 수 있다.

### 6.3 실제 사례 B — 세 비교는 같은데 활성 확인 실패

- **문제:** 내용은 변경없음인데 오류처럼 보이는 확인 실패가 있다.
- **입력:** 828행, `VIEWFRAME_ZTHRBS01V`, 함수 API 소스.
- **작업:** 세 비교와 K열의 별도 근거 대조 설명을 읽는다.
- **관찰 결과:** 세 비교는 같지만 API 소스와 활성 Include의 전체 바이트 대조는 불일치로 기록됐다.
- **검증:** 같은 API 읽기 경로로 구성한 원본/추출본/SAP가 같다는 것과 API 소스가 활성 Include와 같다는 것은 다른 질문이다. 비활성 함수라고 결론 내리지 않는다.
- **후속:** 최신 DIAG의 함수/Include 연결·활성 소스 대조 상세로 실제 줄 차이를 확인한다. 최신 SAP 결과는 추가 확보 대상이다.

### 6.4 실제 사례 C — 71건 실패와 10건 미수행

- **문제:** 71건을 모두 함수 오류로 보거나, 검사 미수행을 검사 기능 고장으로 해석하기 쉽다.
- **입력:** J열의 확인 시도 실패와 C열 구성요소, 2532–2542행.
- **작업:** 구성요소별로 집계한다.
- **관찰 결과:** 실패 71 = 함수 API 70 + DDIC 진단 1. 검사 미수행 10은 SAP 신규 파일이며 원본/추출본에는 없다.
- **검증:** 2542행 DDIC `diagnostic-dd02l.xml`을 함수에 포함하지 않는다. 검사할 추출본이 없는 경우와 실제 검사 오류를 구분한다. 10파일은 DB 테이블 1객체와 프로그램 3객체에서 나온 것이다.
- **후속:** 최신 JSON에서 대상 부재 설명이 의도대로 바뀌었는지 확인한다.

집계 기준과 숫자는 [설계 문서 §10](01_프로젝트_맥락과설계.md), [파생 JSON](examples/ZHR5_result_facts_derived.json)을 참조한다. 파생 JSON은 이번 분석 결과이며 SAP가 출력한 진단 JSON과 다른 형식이다.

## 7. 학습 4 — SAP에서 최신 DIAG를 검증하는 절차

### 7.1 선행 조건과 변경 경계

이 절은 **실행 검증이 남은 절차 초안**이다. 승인된 개발/검증 SAP, 해당 개발클래스 조회 권한, 정합한 패키지 ZIP, 복구 가능한 개발 절차가 필요하다. 제공 소스는 최신 접근 가능 0.4.5이지만 실제 SAP 활성화 성공은 확인되지 않았다.

**도구 Z프로그램을 설치·교체·활성화하는 행위는 ERP 저장소 변경**이다. 읽기 전용 DIAG를 실행하는 것과 구분하여 담당자가 승인된 개발 절차로 수행해야 한다. 교육 참가자가 운영 서버에 임의로 설치·활성화하는 단계는 포함하지 않는다.

### 7.2 수행 순서

1. SAP 담당자가 [DIAG 소스](attachments/programs/Z_PACKAGE_DIAG_0_4_5.abap) 헤더 `0.4.5`, 보고서명 `Z_PACKAGE_DIAG`를 확인한다.
2. 개발 환경에서 문법 검사·활성화 결과를 남긴다. 이전 9128줄 오류가 재현되지 않는지 확인한다.
3. 입력은 단일 개발클래스 예시 `ZHR5`, 대응 추출 ZIP, 기본 **소스코드**, 기본 **신규/누락/수정만 조회**로 둔다.
4. 진행 표시와 완료 시간을 기록한다. 표시 필터 전에 필요한 전체 진단을 하므로 필터가 실행시간을 그대로 줄일 것이라고 기대하지 않는다.
5. 메인 A/B 헤더의 모집단 차이를 확인한다. A는 선택 범위, B는 전체 진단 결과라는 현행 구현을 기준으로 비교한다.
6. 변경만 보기를 해제한 실행과 결과유형 XML을 선택한 실행을 비교한다. 원래 상태를 변경해 맞추지 않는다.
7. 함수 소스·Attributes XML·SAP 신규 사례의 상세를 연다. 원본/추출본/SAP, 세 상태, 실제 변경 필드, 함수/Include 연결을 확인한다.
8. F3가 기존 목록으로 돌아오는지, 가로 스크롤에서 고정 열이 남는지 확인한다.
9. JSON 다운로드를 실행해 전체 건수·선택 여부·버전·날짜·시간을 확인한다.
10. SAP 저장소 쓰기·객체 활성화·CTS 실행이 발생하지 않는 진단 목적을 유지한다. UI에 없는 반영 기능을 추가로 실행하지 않는다.

### 7.3 예상 결과와 합격 기준

| 확인 항목 | 기대 | 아직 확보할 증거 |
|---|---|---|
| 타입 호환 | D/T 인수를 STRING으로 변환하여 문법 오류 해소 | 실제 SAP 활성화 결과 |
| 상태 해석 | 부재/읽기 실패/미구현을 구별 | 최신 사례 JSON·상세 |
| 함수 연결 | 실제 소유·유일성 근거로 Include 연결 | 함수/API 대조 화면 |
| XML 상세 | 직접 값 중심, 함수/공통 속성 구분 | 실제 세 XML 또는 차이 상세 |
| JSON | UTF-8 파싱, 전체 결과·선택 여부, 0.4.5 | 실제 다운로드 파일 |
| UI | F3 복귀, A/B 헤더, 적절한 폭·높이 | 최신 입력/목록/상세 캡처 |

JSON 파일이 생기면 로컬에서 다음 **확인용 예시**를 사용할 수 있다. 실제 경로는 대체한다.

```bash
python3 -m json.tool "<다운로드한_DIAG_JSON_경로>" > /dev/null
```

형식이 맞으면 종료 코드가 0이지만, 업무 내용·SAP 활성 상태까지 검증한 것은 아니다. `schema_version`, `metadata.tool_version`, `total_count`, `selected_count`, `results`와 각 행의 `selected_by_input_filters`를 현재 소스와 대조한다. ALV 필터로 숨긴 행까지 포함할 수 있다. JSON 시각에는 SAP 시스템 기준이라는 설명이 있으며 UTC라고 임의 변환하지 않는다. [DIAG `im_json_build`, `im_json_row`](attachments/programs/Z_PACKAGE_DIAG_0_4_5.abap)

PACKAGE_AGENT_BUILD_GUIDE.md를 읽고 현재 저장소의 실제 경로를 조사하라.

### 8.3 원문·MD·스킬의 권장 역할

원문은 보존하고 읽기 쉬운 MD를 만든다. 표·수치·조건·시행일을 임의 요약하지 않는다. MD에는 원문 위치·근거 수준·유효 기간·검토 이력을 두고 INDEX에서 연결한다. SKILL에는 작업 절차와 필요한 참고 경로를 두며 자료 전문을 반복하지 않는다. `.devhub/baseline`은 소스 검색의 중복 대상에서 제외하되 진단 ZIP에서는 보존한다.

카카오톡 대화를 그대로 AGENTS에 넣으면 토큰 사용과 근거 혼동이 커질 수 있다. 개인정보가 포함된 원문을 공개 저장소에 자동 push하지 않는다. 제공 가이드의 원문 접근·민감정보 처리 지침을 적용한다. [구축 가이드](references/PACKAGE_AGENT_BUILD_GUIDE.md), [ZHR5 설치 안내](references/ZHR5_KNOWLEDGE_SETUP.md)

## 9. 학습 6 — 업무 오답을 하네스 피드백으로 만들기

### 9.1 실패는 SAP 오류 코드만 뜻하지 않는다

업무 답변에서 다음은 검증 가능한 실패가 될 수 있다: 근거 문서 누락, 시행일 혼동, 제안을 확정 정책으로 단정, 코드 동작을 규정으로 단정, 숫자 오독, 다른 패키지의 미확인 내용을 사실처럼 답변. SAP 프로그램을 실행하지 않아도 질문·근거·판정 기준으로 회귀 사례를 만들 수 있다.

코드 검증 하네스와 업무 검증 하네스를 분리한다. 이 프로젝트는 업무 피드백 지침을 먼저 마련했고, 전체 자동 실행기 운영 완료는 확인하지 못했다.

### 9.2 따라 하기: 피드백 1건 작성

**준비물:** 실제 업무 질문·이전 답변·수정 근거, 업무 담당자의 검토. 아래는 **가상 형식 예시**이며 특정 KBS 규정값이 아니다.

```text
[업무 답변 피드백]
질문: <질문 원문>
문제 답변: <수정이 필요한 문장>
오류 유형: <시점/근거/수치/해석/검색 누락>
확인 근거: <규정 파일명, 절, 시행일 또는 협의 날짜>
정정 방향: <확인된 내용만>
미확인 항목: <담당자에게 확인할 점>

BUSINESS_FEEDBACK_POLICY.md에 따라 관련 업무 MD 수정안과 회귀 사례를 작성하라.
원문과 baseline, ABAP·DDIC·BSP 소스는 수정하지 말라.
실제로 재검증하지 않았다면 NOT_RUN으로 표시하라.
정답을 맞추려고 평가 기준을 완화하지 말고, 근거가 충돌하면 REVIEW_REQUIRED로 남겨라.
```

**수행 순서:** 근거 확인 → 오류 분류 → 허용된 MD 수정 → 사례/기대 근거/금지 단정 등록 → 새 답변 검증 → 결과와 변경 이유 기록.

**예상 결과:** 동일 질문뿐 아니라 근접 질문에서도 시점·근거·범위를 지키는지 판단할 자료. 숫자 한 개를 답변에 암기시키는 것과 다르다.

**확인 방법:** 질문 정답만 보지 말고 출처 정확성·미확인 처리·회귀 사례 유출 여부를 함께 본다. [피드백 정책](references/BUSINESS_FEEDBACK_POLICY.md)의 중단·반복 제한을 따른다. 키트의 질문 34개는 초안 목록이며 34개 자동 테스트 통과 실적이 아니다.

## 11. 실제 논의에서 나온 FAQ

### Q1. baseline은 중복인데 지워도 되는가?

현재 DIAG의 변경 전 원문이다. AI 검색의 중복에서는 제외할 수 있지만 진단 ZIP에서 없애면 원본 대비 상세를 재현할 수 없다. Git commit으로 대체하는 기능은 구현되지 않았다.

### Q2. 같은 bytes면 같은 파일 아닌가?

아니다. 실제 Excel 1440행은 세 크기 3,210이지만 SAP와 내용이 다르다고 판정됐다. 크기, 전체 바이트, XML 구조·값, 업무 의미를 순서대로 구분한다.

### Q3. 확인 실패면 SAP에서 비활성인가?

아니다. 어떤 확인을 시도했고 왜 근거가 성립하지 않았는지 읽는다. 함수 API와 활성 Include의 불일치가 세 비교의 차이와 별개일 수 있다.

### Q4. 문법 검사를 기본 켰는데 왜 생략/미수행인가?

내용 동일, 검사할 추출본 없음, 대상 아님, 문맥 부족 등의 이유가 있다. 기본 사용은 모든 행을 동일하게 검사한다는 뜻이 아니다. 사유를 설명하고 성공으로 바꾸지 않는다.

### Q5. HTML·JS·CSS도 줄 차이가 보이는가?

텍스트 차이 표시 대상이다. 브라우저 실행·화면 렌더링·웹 문법 검사까지 완료한 것은 아니다. PNG는 바이너리 변화 확인이며 시각 요소의 의미 해석 기능은 별도다.

### Q6. XML을 고치면 테이블 구조를 자동 반영할 수 있는가?

현재 도구는 비교·형식·지원된 메타데이터 조회에 집중한다. DDIC 생성·변경·활성화는 현재 범위 밖이다. 자동 반영을 위한 안전성·의존성·업무 영향 검증도 완료되지 않았다.

### Q7. 카톡·매뉴얼을 모두 스킬에 넣으면 되는가?

원문과 지식 MD, 작업 지침을 분리한다. 카톡은 당시 협의 근거이지 모든 문장이 현재 확정 정책인 것은 아니다. 스킬은 관련 자료를 필요한 만큼 찾도록 한다.

### Q8. GitHub에서 에이전트끼리 자동 협업하는가?

자료와 코드를 공유하는 기반이다. 업무 분담·질문 전달·결과 형식·검토 책임·실행 주체를 별도로 구성해야 한다. 이 프로젝트에서는 자동 협업 운영 완료를 확인하지 못했다.

### Q9. Actions는 AI인가? 로컬 Codex로 실패가 자동 전달되는가?

논의한 Actions는 정해진 작업의 자동 실행 도구다. AI를 호출하도록 따로 구성하지 않으면 그 자체가 AI가 아니다. 실패 결과를 로컬 Codex에 가져오는 연동도 별도이며 현재 구현 증거가 없다. 실제 workflow/러너 교육은 통합할 다른 프로젝트 자료로 보완한다.

### Q10. 왜 SAP에서 바로 GitHub를 읽지 않는가?

시험에서 RECEIVE 단계 SSL 오류가 발생해 보류했다. SAP 오류 코드 407을 HTTP 프록시 상태로 단정하지 않는다. 현재는 ZIP으로 전달한다.

### Q11. 패키지를 받아 에이전트를 만들었으니 모델 학습이 끝난 것인가?

이 프로젝트가 확인한 것은 코드·문서를 참조하는 업무 에이전트 구성이다. 모델 가중치를 재학습한 실적이나 모든 업무 질문의 정확도 검증을 뜻하지 않는다.

### Q12. 실제 제품 화면을 설명 그림으로 대신해도 되는가?

실제 조작 실습에는 실제 현재 화면을 캡처한다. 생성 이미지나 개념도는 구조 설명으로 명시한다. 포함된 SAP 표준 비교 화면도 최신 DIAG 화면으로 바꿔 표기하면 안 된다.

## 12. 교육 공개 전 확인

- 실습의 파일 버전·대상 시스템·권한·입력 ZIP을 명시한다.
- 최신 DIAG 0.4.5 실제 활성화/실행과 JSON을 확인하고 미확인 표시를 갱신한다.
- 실제 화면은 [캡처 요청 목록](03_자료목록과보완사항.md)의 필수 요소를 담는다.
- 기존 스킬의 업무 지식 의존 파일을 확보하고 정책 효력·민감정보 범위를 담당자가 검토한다.
- 본문 합성 예시를 실적·실제 KBS 정책으로 바꾸어 소개하지 않는다.
- 다른 프로젝트의 제품 설정·서버·MCP·Obsidian 구현은 해당 원본으로 확인한다.
